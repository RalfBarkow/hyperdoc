Warum findet ASDF eine .asd im Nix Store nicht mehr?

Ein laufendes Image merkt sich Store-Pfade; verschwindet einer, scheitert erst das nächste Laden.

Antwort und Geltungsbereich

In der gepinnten HyperDoc-Dev-Shell startet sbcl über einen Nix-Wrapper. Er setzt CL_SOURCE_REGISTRY auf die Store-Pfade aller mitgelieferten Lisp-Pakete, je als Baum mit //, etwa /nix/store/…-sbcl-zip-20150608-git//. Beim ersten Suchen durchläuft ASDF diese Bäume einmal und merkt sich für jedes System den Pfad seiner .asd. Geladen wird ein System erst, wenn es gebraucht wird.

Wird der Store-Pfad danach entfernt, etwa durch nix-collect-garbage oder die automatische Garbage Collection, bleibt der gemerkte Eintrag im Image stehen. Die Store-Pfade einer Dev-Shell sind keine GC-Wurzeln. Braucht ein asdf:load-system das System später als Abhängigkeit, meldet ASDF LOAD-SYSTEM-DEFINITION-ERROR mit Couldn't load …/zip.asd: file does not exist. Ein direktes asdf:find-system auf dasselbe System meldet stattdessen MISSING-COMPONENT.

Abhilfe: Den fehlenden Pfad wiederherstellen und im Debugger RETRY wählen. Derselbe Store-Pfad entsteht wieder, wenn dieselbe Dev-Shell erneut ausgewertet wird. Im selben Prozess lädt ASDF danach ohne Neustart. Ergibt der Checkout eine andere Dev-Shell als die, aus der das Image stammt, entstehen andere Pfade; dann das Image aus dem aktuellen Checkout neu starten. Eine GC-Wurzel auf die Dev-Shell verhindert, dass die Pfade wieder verschwinden.

nix develop --no-update-lock-file -c true
nix develop --no-update-lock-file --profile ~/.cache/hyperdoc-devshell -c true

Belege

Beobachtet beim Operator am 2026-11-20 im lokalen SLY-Image auf dem Mac, beim Laden von dreyeck/fedwiki-hyperdoc (über dreyeck/fedwiki-story, das zip braucht): LOAD-SYSTEM-DEFINITION-ERROR für /nix/store/m65hc7qy2z2pxsrbqil48gilvfwfl624-sbcl-zip-20150608-git/zip.asd, file does not exist, aus LOAD-ASD innerhalb von FIND-SYSTEM. Ob der Pfad durch eine Garbage Collection verschwand und ob die Wiederherstellung dort gelang, ist noch nicht berichtet.

Das verlinkte Prüfprotokoll stellt den Ablauf mit einem echten, eigens angelegten Store-Pfad nach. Es nennt den geprüften HyperDoc-Commit, die Lock-Prüfsumme, die nixpkgs-Revision, die Plattform, den Benutzer und den Abschlusszeitpunkt. Der archivierte Lauf erfolgte auf x86_64-linux mit SBCL 2.4.10 und ASDF 3.3.1, als root in einem Container mit Nix 2.34.6.

  • Registriert. Ein kleines Verzeichnis mit faq-gc-probe.asd wird mit nix store add-path in den Store gelegt und wie vom Wrapper als Baum eingetragen. Vor jedem Laden zeigt die Quellregistrierung von ASDF auf die .asd im Store.
  • Verschwunden. nix-store --delete entfernt genau diesen Pfad. Ein System ausserhalb des Store, das davon abhängt, scheitert bei asdf:load-system mit LOAD-SYSTEM-DEFINITION-ERROR und file does not exist für den gemerkten Pfad. Ein direktes find-system meldet MISSING-COMPONENT.
  • Diagnose. Die Form unten findet den Eintrag als verschwunden.
  • Wiederhergestellt. Dasselbe Verzeichnis ergibt beim erneuten Hinzufügen denselben Store-Pfad. Im selben Prozess gelingt das Laden danach ohne Neustart; die geladene Funktion liefert 42.
  • Mit GC-Wurzel. Solange nix-store --add-root auf den Pfad zeigt, verweigert nix-store --delete das Löschen (still alive).

Die Garbage Collection selbst wurde nicht ausgelöst; der Lauf löscht nur seinen eigenen Pfad. Ob eine GC unter macOS Pfade schont, die ein laufendes Image nur über seine Umgebung kennt, ist nicht geprüft.

Prüfung im laufenden Image

Im SLY-Debugger zuerst *ABORT wählen, um zum mREPL-Prompt zurückzukehren. Die Form listet Einträge der Quellregistrierung und registrierte Systeme, deren .asd nicht mehr existiert. Sie lädt nichts und ändert nichts.

(append
 (loop for name being the hash-keys of asdf/source-registry::*source-registry* using (hash-value asd)
       unless (probe-file asd) collect (list :registry name asd))
 (loop for name in (asdf:registered-systems)
       for asd = (asdf:system-source-file (asdf:registered-system name))
       when (and asd (not (probe-file asd))) collect (list :registered name asd)))

Eine leere Liste heisst: Jede gemerkte Systemdefinition liegt noch vor. Jeder Eintrag nennt einen Pfad, der vor dem nächsten Laden wiederhergestellt werden muss.

Prüflauf wiederholen

Im HyperDoc-Checkout legt dieser Befehl ein eigenes kleines Verzeichnis in den Store, löscht genau diesen Pfad, legt ihn wieder an und prüft die GC-Wurzel. Andere Store-Pfade fasst er nicht an. Für nix-store --delete braucht der Benutzer das Recht, Store-Pfade zu löschen.

nix develop --no-update-lock-file -c bash scripts/check-asdf-registry-store-gc.sh
