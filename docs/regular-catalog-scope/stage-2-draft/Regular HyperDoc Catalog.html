Regular HyperDoc Catalog

The Work item topic-maps-regular-hyperdoc, Regular HyperDoc Catalog with a Navigable Project Topic Map, is declared on the Work Breakdown. This page states its Work Breakdown Structure and its plan. The WBS Dictionary that defines each work package is Regular HyperDoc Catalog WBS Dictionary.

The scope is distinct from two others and repeats no deliverable of either. The separate staging Catalog of the proposal tmd-deployment serves Topic Maps for review on loopback and is already installed on dreyeck.ch (Zettel 11353); this scope concerns the regular HyperDoc Catalog of the production service. The exchangeable project CTM of project-work-ctm-exchange is read by this scope and not changed by it.

Every status on this page is open. A status states the state of the work, not an acceptance: no work package here is accepted, no plan step is verified, and an implementation assignment that reports a result on Implementation Assignments changes none of them.

Completeness and overlap

Completeness: the six packages together are the whole defined scope. A Topic Maps revision whose identity can be checked (1), a Project Workspace that reads the unchanged project CTM with it (2), project work a reader can navigate and inspect in that Workspace (3), a public Inspector that is safe to expose (4), the regular Catalog package built reproducibly (5) and its verified deployment (6). What the scope needs and does not deliver appears below as plan preconditions: the user's admission of the Project Workspace to a served runtime, an independent security review, the decision to publish the archive and the approval of the production activation.

Overlap: 1 and 5 meet at the snapshot: 1 makes the revision and its manifest verifiable, 5 builds the package that serves it. 2 and 3 both concern the Project Workspace: 2 that it reads the unchanged project CTM with the revision and refuses what it cannot identify, 3 what the project work shows and how it is navigated. 4 and 6 meet at exposure: 4 makes the views safe, 6 activates them. No relation contract relates a Work item to a Deliverable, so none is declared between topic-maps-regular-hyperdoc and tm-regular-catalog; the project CTM names that gap.

Plan

Plan steps, each for one work package, and the preconditions the steps wait on. A plan step is work to do, not a deliverable; a precondition is something the scope needs and does not deliver. No plan step or precondition grants authority.

  • P1 Integrate and verify Topic Maps 6162ed68 — fast-forward the Topic Maps line, pin the snapshot, verify it without .git and run the Topic Maps suite.
  • P2 Verify the unchanged project CTM — read it with the revision, within the operational limit, and compare the signature and the CXTM.
  • P3 Integrate Project Workspace and Inspector navigation — the project work navigable from the Work Item to its evidence, and the reading of the integration.
  • P4 Verify and enforce public Inspector security — read-only public views, gated run buttons, an independent review.
  • P5 Build and test the regular Linux and Nix Catalog package — on an independent builder, with the derivation compared.
  • P6 Stage, verify, obtain production approval and deploy — activate the generation, verify identity and boundaries, show the rollback.
  • Admission of the Project Workspace to a served runtime — the user's decision; the Catalog's startup guard refuses the Workspace until it is made.
  • Independent security review of the public Inspector — a report by a reviewer who is not the executor.
  • Decision to publish or transfer the archive — the user's; a builder must be able to obtain the Topic Maps snapshot.
  • Approval of the production activation — the user's, for the generation on dreyeck.ch, with the operator's record of the server's state.
