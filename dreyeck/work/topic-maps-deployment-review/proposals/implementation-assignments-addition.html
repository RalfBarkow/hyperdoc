Proposed Work: Deploying Topic Maps with HyperDoc on dreyeck.ch

The Work Item, the Deliverable, the work packages and the plan of the assignments below. None of them is declared, and none has a work status. The work packages are described by the draft Topic Maps Deployment WBS Dictionary, which declares nothing either.

Completeness: the five elements together are the whole defined scope. A source that can be verified (1), a package that serves it under a startup policy (2), a reading in which the package can be reviewed (3), a candidate validated where it will run (4), and the deployment activated and verified (5). What the scope needs and does not deliver are preconditions of the plan below: the user's authorizations and approvals, the decisions D2 to D5, an independent builder, and evidence of the server's state. Project management is not an element: the design and these proposals are assignments that deliver no package.

Overlap: 1 and 2.1 meet in flake.nix and dreyeck.asd, which declare parts of both. 2.2 and 3 both make Topic Maps inspectable in HyperDoc: 2.2 in the package as it is served, 3 only locally, for the review. 2 and 4 meet at the reviewed revision: 4 changes no code, and a Linux fix is a new revision of 2. 4 ends with a staged, unactivated candidate; 5 begins with the activation. Verifying the deployment is the acceptance of 5, not an element of its own.

  • Deploying Topic Maps with HyperDoc on dreyeck.ch — run the independent ANSI Common Lisp Topic Maps implementation, at b2eecffa, as a reproducible ASDF dependency of a separate Nix package on the NixOS server dreyeck.ch, inspectable in HyperDoc.
  • Topic Maps operating with HyperDoc on dreyeck.ch — the defined scope: the verified source, the integrated Catalog package, its review reading, a validated Linux candidate, and the activated and verified deployment.
  • 1 Verified Topic Maps Source Distribution — the runtime snapshot of b2eecffa without reports/, verifiable without .git and obtainable by a builder.
  • 2 Integrated HyperDoc Catalog Package — the separate package hyperdoc-catalog-topic-maps; a summary element of 2.1 to 2.3.
  • 2.1 Catalog package definition — the Nix declarations and checks that build hyperdoc-catalog-topic-maps beside an unchanged hyperdoc-catalog.
  • 2.2 Provenance dispatch of the Topic Maps readings — the 22U reading and the CTM review, reading Topic Maps from the verified snapshot or a Git checkout and saying which.
  • 2.3 Catalog startup policy — loopback only, verified ASDF origins, the Project Workspace refused, ASDF's own methods preserved.

  • 5 Operational HyperDoc Deployment — an activated NixOS generation with the package, verified in operation, with a rollback.

Proposed plan

Plan steps, each for one work package, and the preconditions the steps wait on. A precondition is something the scope needs and does not deliver: an approval, a decision, a builder, evidence from the server. No plan step or precondition grants authority.

  • Export, pin and verify the snapshot — git archive without reports/, the manifest of Git objects, the NAR hash in Nix, the verifiers.
  • Define the Catalog package — the derivation, its registry, wrapper and flake check, and the comparison with hyperdoc-catalog.
  • Dispatch the Topic Maps readings by provenance — the 22U reading and the CTM review read the snapshot or a checkout and say which.
  • Enforce the startup policy — loopback only, the origin check, the Project Workspace guard.
  • Correct the guard's method identities — methods with specializers ASDF does not use, with fresh-process checks that ASDF's own methods stay ASDF's; the tested files and their evidence are made anew.
  • Build the HyperDoc review reading — Text Pages, Code Pages and a Workspace over the candidate's objects and evidence, and its operator start.
  • Keep the snapshot alive for a reading session — a garbage-collector root for the store path while the reading runs, removed when it stops.
  • Build, check and stage on x86_64-linux — on an independent builder from the pushed revision, then a loopback staging run on the NixOS host.
  • Activate and verify the deployment — activate the generation, verify identity, reachability and boundaries, show the rollback.
  • Authorization to change tested files — the user's, for the files of the candidate: the guard correction changes dreyeck/src/catalog-topic-maps.lisp and its tests.
  • Candidate committed on approval — the reviewed candidate committed locally, on the user's approval after the review of its diff.
  • Approval to push dreyeck.ch — the user's; decision D4 keeps the branch unpushed.
  • Archive obtainable by the builder — decision D2: published at a release URL, or transferred into the builder's store.
  • Independent x86_64-linux builder — decision D3: its configuration and capacity checked; not the production server.
  • Server state from the operator — disk, current generation and service state of dreyeck.ch, gathered by the operator; Claude Code does not connect to the server.
  • Exposure decision — decision D5: whether and how the Catalog is reachable beyond loopback, given its plain v:thunk buttons.
  • Approval to activate — the user's, for the generation on dreyeck.ch.
