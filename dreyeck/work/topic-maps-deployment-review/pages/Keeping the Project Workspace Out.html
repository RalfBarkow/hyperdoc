Keeping the Project Workspace Out

The older HyperDoc Project Workspace, dreyeck/work/project, is bound to another Topic Maps revision: its pin as this candidate was reviewed (5a4a668; the Topic Maps 6162ed68 integration has since bound it to 6162ed68, see docs/topic-maps-6162ed68-integration), Topic Maps 5a4a668. Git says that 5a4a668 is not an ancestor of b2eecffa: they are separate lineages (claim). An image holds only one topic-maps, so the workspace loaded beside the snapshot would silently run against b2eecffa. Its own identity check reports a mismatch and does not refuse. The candidate leaves the workspace and its binding unchanged and keeps it out of the variant's image.

The guard

The variant's main calls verify-startup before it serves. That verifies the Topic Maps origins and then calls refuse-project-workspace: it reads the definition of the one system the Catalog is asked to load, HYPERDOC_CATALOG_SYSTEM, and of its dependencies, and refuses, before anything is loaded, if one is dreyeck/work/project or one of its subsystems: the check. It adds no method to ASDF. The executable refused it before listening: recorded. Ask it in this image: the button asks the check about the Project Workspace and reports the refusal and that nothing was loaded. The claim.

The page-attached system loader

After startup, one application path can load a system named by a wiki page: dreyeck/page-attached-hyperdoc, reached through dreyeck/fedwiki-hyperdoc by the Activate page-attached HyperDoc button of a local FedWiki page. That button is a plain thunk, which the authority policy does not gate (Execution Authority), and the system a page names could depend on the Project Workspace. The default Catalog does not depend on it and the optional runtime does not contain it, and loader-system-p makes the startup check refuse a catalog system that does: the claim.

What the guard does not protect

The check is made once, at startup. A load made later by other means, such as asdf:load-system at a Lisp prompt in the running image, is not refused; the executable has no such prompt. The written account is docs/topic-maps-deployment/staging.md.

A defect of the first version of the guard, corrected

The first version defined two methods with the same qualifiers and specializers as two of ASDF's own, operate :before on (t t) and perform :before on (operation component), so defining them replaced ASDF's methods. Which methods ASDF runs now: its own. The claim. The history, with the records of the defect as they were found, is in The ASDF Method Collision.
