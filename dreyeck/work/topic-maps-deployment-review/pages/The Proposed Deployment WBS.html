The Proposed Deployment WBS

The goal stays the deployment: Topic Maps b2eecffa running with HyperDoc on dreyeck.ch, as a reproducible ASDF dependency of the separate package hyperdoc-catalog-topic-maps, inspectable in HyperDoc. This page reads the deployment's work breakdown, dictionary and plan. They are proposals: nothing here is declared, no package has a work status, and none is accepted.

They exist in two files of this reading, in forms the project already has: an addition to Implementation Assignments, not appended to that page, and a draft WBS Dictionary. This reading states nothing about the project work of its own; its Lisp only reads those files. Everything at once, and the proposal Workspace: WBS on top, the plan under it, preconditions under the steps that wait on them, assignments at the bottom. At Point it answers four questions apart: decomposition, plan, reported evidence, acceptance.

Where the deployment stands

Reported by the executor, not a status. Steps 1 to 4 and 6 were carried out locally on 2026-10-26 and 2026-10-27, by the assignments for the local packaging and for this review. Step 5, correcting the guard, waits on your authorization to change tested files. Steps 7 to 9 have not started. The Linux build waits on five preconditions, among them your approvals to commit and to push; the activation on two more.

1. The breakdown: deliverables and work packages

The Work Item; the Level 1 deliverable, the whole defined scope, which decomposes into:

  1. Verified Topic Maps Source Distribution, a work package;
  2. Integrated HyperDoc Catalog Package, a summary element of three work packages: 2.1 package definition, 2.2 provenance dispatch, 2.3 startup policy;
  3. Inspectable Project Documentation, this reading;
  4. Validated Linux Deployment Candidate;
  5. Operational HyperDoc Deployment.

In PMI's terms a work package is the lowest level of the breakdown, so element 2 is a summary element and its three packages are where work is defined and accepted; under NASA's usage the same elements are products. Completeness and overlap are argued in the proposal itself, beside the breakdown, as the CTM plan page argues its own: the addition. What the scope needs and does not deliver is a precondition of the plan, not an element. That decomposition, verification and project management are treated this way is decision 3.

2. The dictionary: scope, exclusions, criterion, implementation objects

Each work package has one draft entry, read by the CTM plan page's own read-wbs-dictionary. Its scope ends with what it excludes (decision 5). Its effect field names the repository files it adds or changes, and these are its implementation objects: entry-effect-paths reads them from the entry's code elements, and each leads to the candidate file as the working tree holds it now. Every program and test file of the candidate is named by exactly one package, except flake.nix and dreyeck.asd, which declare parts of two.

For example, the entry of 2.3, the startup policy: its criterion says that after the guard is loaded every method ASDF defines is still ASDF's own, and its control for that is planned, with no test yet. That is where the ASDF method collision belongs (the finding).

3. The plan: steps, dependencies, preconditions

Nine plan steps, each producing one work package; two of them, correcting the guard and keeping the snapshot alive for a session, produce a package a first step already produced, because what was found requires them. A step depends on earlier steps or on preconditions, never on a test result. The preconditions are your authorizations and approvals, the Phase A decisions D2 to D5 that are still to be met, an independent builder, and evidence of the server's state, for example the approval to push, which names decision D4. Decomposition, production and dependency are three relation types with three contracts: the CTM plan page declares them.

4. Evidence: what the assignments report

An assignment records that it was given, what it asks for, and what its executor reports. Its evidence entries are either execution reports, with the facts of one run (test, repository, revision 53ee9993, tree modified, a content reference to the tested SHA-256 list, observation, time), or notes. Where a record states no run time, the entry is a note: the model refuses an execution report without one. For example, the package contract's run and the collision probe, each leading to its record. An entry belongs to its assignment; the assignment names the one package it delivers, if any. Which other reports bear on a package is derived, and says so where it is shown: by the test file of the package's controls (reported-runs), or by the file a report's content reference names (content-naming-runs). That is how the probe, evidence of the review, reaches 2.3.

The local packaging produced the content of four packages, but an assignment's delivers names one package (the emitter), so that assignment names none and says why in its goal. The design and these proposals are assignments that deliver no package.

5. Acceptance

None. No Acceptance Records page is a source here, and a proposed package cannot be accepted at all until it is declared (D5 of the acceptance model). A passed test, a completed assignment or an executor's report is evidence, not an acceptance; every package's view says so under Acceptance.

6. How the proposals were checked, and in which image

The project CTM emitter cannot run in this image: its system, dreyeck/work/project, is bound to Topic Maps 5a4a668, and this image runs b2eecffa (Keeping the Project Workspace Out). So it ran in a process of its own, with the clean 5a4a668 clone, on the page followed by the addition, read in memory as its own tests read an addition: its recorded reading. It refused nothing, derived the gaps it derives for any proposal, and changed no file. The same view compares that reading with what this image's readers read now (reader-agreement). The ordinary Work reader reads no declaration from the addition.

The readers here are this reading's read-addition, which follows the emitter's reader of the assignments page, and the CTM plan page's read-wbs-dictionary, which is already loaded in this image. Nothing of the Project Workspace is loaded.
