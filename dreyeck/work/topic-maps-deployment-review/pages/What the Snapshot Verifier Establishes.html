What the Snapshot Verifier Establishes

A Nix source snapshot has no .git, so no Git check can run against it. verify-snapshot-tree instead hashes the snapshot's files the way Git hashes them and checks a chain that ends in the pinned commit id.

The chain

  1. The manifest's raw commit object hashes to b2eecffa…, the id the 22U reading and the CTM review already pin.
  2. That commit object names the root tree 2b2ad058….
  3. The manifest's root listing hashes to that tree.
  4. The snapshot's root entries are exactly the listing's entries without reports/: nothing more, nothing less, no .git.
  5. Every shipped file, mode and subtree hashes to the listing. Names come from readdir and kinds from lstat, so a symbolic link is refused, never followed.

reports/ is named by its tree id and is neither shipped nor verified.

Where a tree is accepted as the loaded source

The tree check does not care where the tree lies. Whether a tree is accepted as the source ASDF loaded is a separate policy, source-kind. A directory with .git is a Git checkout, and Git's own checks apply unchanged. A read-only /nix/store path without .git is verified by verify-store-snapshot. Anything else is refused. Only two readings dispatch on this, the 22U reading's checked-source-evidence and the CTM review; tmdm-reading's checked-repository still requires a checkout (derived).

What it does not establish

Git's object ids are SHA-1. The SHA-256 NAR hash pins the same bytes independently, but the chain itself is as strong as SHA-1. The commit is SSH-signed, and the signature is not verified. The verifier says nothing about the archive's own bytes, only about the unpacked tree. The claim.
