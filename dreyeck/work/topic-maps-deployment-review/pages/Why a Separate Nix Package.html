Why a Separate Nix Package

Because the reviewer decided so on the Phase A design: D1. The production executable, hyperdoc-catalog, stays exactly as it is, and Topic Maps enters a second executable that the public service does not run.

What the two declarations are

The production package is this attribute of flake.nix, built by nix/catalog.nix. Neither is changed: nix/catalog.nix is not a candidate file at all. The variant is a new attribute built by nix/catalog-topic-maps.nix: the same runtime, the verified snapshot added to the ASDF registry, HyperDoc's revision as the flake states it, and its own startup script.

How "unchanged" was shown

A derivation names everything that goes into a build. compare-catalog-derivation.py evaluated hyperdoc-catalog at the base and at the candidate and compared the two derivations field by field. They are equal except HyperDoc's own source path, which changes with any repository change, and the output path that follows from it; every input derivation is the same. Recorded for x86_64-linux and x86_64-darwin. That the comparison can fail is shown by a positive control: one flag added to the wrapper is reported as different.

The production Catalog's own startup check also ran on the candidate tree: checks.x86_64-darwin.catalog.

What this does not show

For Linux the comparison is an evaluation. The claim says so, and the Linux build and its contract, run separately, is a subject of its own in the Topicmap.
