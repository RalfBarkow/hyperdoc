topic-maps-deployment-review

From Git Commit to Verified Snapshot

The source is Topic Maps b2eecffa in the local repository, which is the authority. Its tracked tree is about 2.47 GB, nearly all of it reports/, as the Phase A design measured. So the package does not take the repository: it takes a snapshot, decided as D2.

Export

create runs git archive of every root entry of the commit except reports/, gzips it without a time stamp, and writes HyperDoc's manifest: the raw commit object, the root tree listing, the excluded entry and the NAR hash. Git is asked hermetically: only the commit's own .gitattributes count, not system or user files. The result is the runtime snapshot, 2,328 files.

Two pins

Nix pins the unpacked snapshot by its NAR hash in nix/topic-maps-source.nix, a fetchzip, so flake.lock is untouched. Git's identity is pinned by the manifest, a candidate file that holds Git objects and no implementation file.

Checked against the commit

verify uses Git and Nix, not the Lisp verifier, to check that the archive is exactly the commit's tree without reports/: the same paths, modes and blob ids, no links, no submodules, no attribute that rewrites bytes, and the manifest's NAR hash. Its recorded run lists both .gitattributes files of the commit. The nested one, vendor/cxtm/.gitattributes, sets text eol=lf and binary. The Phase A design missed it; neither attribute rewrites an LF blob, and every archived file hashes to its blob. That the verifier can fail: nine altered archives and manifests, all refused.

The claim and its limit: the check is against the local repository, and nothing is published (open).
