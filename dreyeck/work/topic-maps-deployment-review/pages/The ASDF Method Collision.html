The ASDF Method Collision

A defect of the first version of the candidate's guard, found while this reading was built and corrected on 2026-10-27. The records of the defect are kept as they were found. The page is read as a history in five steps, each to the object itself; the last step is the correction.

1. What the guard is for

The Project Workspace is bound to another Topic Maps lineage, so the packaged variant must never load it beside the snapshot (Keeping the Project Workspace Out). The variant's main calls verify-startup before it serves, and that calls refuse-project-workspace. The first version did this differently: it refused an ASDF operation on dreyeck/work/project, on its subsystems or on anything depending on them, before ASDF planned, with a backstop at every action. Which systems it refuses: refused-system-p. In the Workspace: the guard's subject.

2. The first version's two methods

Their text, kept verbatim as the candidate's file held it on 2026-10-26: the first guard's two methods. The candidate's file no longer holds them. In this image the methods with those identities are ASDF's own: operate :before on (t t) and perform :before on (operation component). Each method's Generic view shows its qualifiers and specializers; its source is in ASDF's own file, at the path SBCL was built in, which a machine other than the builder does not have, so the text is below, from the installation.

3. ASDF's own methods with the same identities

A method is identified by its generic function, qualifiers and specializers. ASDF defines methods with exactly these two identities, and defining one with the same three replaces it. While the first guard was loaded they were not in the image; in the corrected candidate they are, and here is ASDF's own text of each, asking the image whose method has its identity now: perform :before ((o operation) (c component)), which creates an action's output directories, and operate :before (operation-class system &rest args), which refuses ASDF-BINARY-LOCATIONS and whose unspecialized parameters are (t t). The generic functions' methods: asdf:operate, asdf:perform.

4. The evidence of the replacement

Observed, of the first version. The probe's record: two fresh processes, ASDF alone and after loading the first version of dreyeck/catalog-topic-maps. Both identities move from ASDF's file to the candidate's, and asdf:operate keeps its count of 7 methods, so one was replaced and none added. The guarded run loaded the very bytes the candidate's first tests ran on. The record is unchanged by the correction. The live check asks the same of this image whenever it is shown, and now says that both are ASDF's own. The claim.

In the Workspace, the subjects: go to Project Workspace guard or ASDF 3.3.1. The relation once replaced two methods of has the probe as its evidence. Two more relations, replaced, lead to ASDF's two originals, Method collision probe records the replacement by the guard, and adds no method to says what holds now.

5. The violated invariant, its consequences, the correction

Derived: the invariant. Code that adds a refusal to ASDF must add methods, never take an identity ASDF's own methods have. Where it held: every image that loaded the first version of dreyeck/catalog-topic-maps.

Observed consequences, on the probe's own action, with the first guard loaded: ASDF no longer creates an action's output directories. Why the recorded runs could not notice: compiling creates its own directories.

Inferred, never tested: which real actions were affected, and the lost ASDF-BINARY-LOCATIONS check. The corrected test now exercises both behaviours.

Corrected: the correction: the guard is an explicit check of the Catalog's startup and defines no method on ASDF. The claim, observed in a fresh-process test. Open: whether the package contract passes in a completed Nix build.
