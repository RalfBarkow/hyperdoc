Remaining Requirements

What the re-pin does not establish, in the words of the Task 1E commit and review, plus what this step did not run.

  • Linux. Everything here ran on one x86_64-darwin Intel Mac with SBCL 2.4.10. No x86_64-linux build or check was made.
  • Memory. The peak resident set size observed was 460 to 505 MB per process, which includes compilation, but it is not a measurement on the constrained NixOS host. The review measured about 14 to 15 percent more cumulative allocation for the index, which is churn, not peak memory. Suitability for a 2 GiB host is unmeasured.
  • High-arity performance. Performance with many Roles or Scopes per Association was not benchmarked; the fast path still has quadratic work inside one Association.
  • Stage 2. The Stage 2 CTM is neither declared nor measured.
  • The Unicode/NFC checker. check-nfc.py fails at its Unicode version assertion with Python 3.14 (Unicode 16) on the baseline and on the candidate alike; a successful NFC verification is unavailable in these interpreters. It is a pre-existing mismatch, not caused by Task 1E.
  • The Catalog test suite. dreyeck/catalog-topic-maps/tests demands that HyperDoc itself load from a /nix/store source, so it only runs inside the Nix build check. Trying it from a development tree stops at HYPERDOC-FROM-A-STORE-SOURCE; that is the test's own precondition, not a failure of the re-pin. The packaged check (checks.<system>.catalog-topic-maps) was not run on this candidate. The Catalog's guard and its refusal of the Project Workspace are textually unchanged: only the pinned commit in dreyeck/src/catalog-topic-maps.lisp differs.
  • The browser walks. scripts/test-project-workspace.mjs and the Zettel 11359 scope walk were not re-run in this step.
  • The earlier readings. Integrating Topic Maps 6162ed68 is bound to 6162ed68 by design, and its check pins:catalog-and-22u-reading-and-workspace-and-reading-name-one-commit now fails; the suite stops there, so its later checks were not seen. The earlier deployment review's main suite passed (343 assertions, where the 6162ed68 record says 344; the difference was not explained because the baseline run for it was stopped before it finished) and its second procedure fails at EVIDENCE-NAMES-ITS-RECORD, as it did before. No check was weakened. The older reading is intentionally left unchanged. Open design decision: how a historical, revision-bound reading (true of 6162ed68 for good) is told apart from the currently selected integration revision (88994c1b), so that its pin check states its own commit instead of failing or being edited when the pin moves.
  • Deployment. The snapshot archive is not published at the URL in nix/topic-maps-source.nix; no Linux build, staging or change to the running service at dreyeck.ch happened or is proposed here. The staging procedure in docs/topic-maps-6162ed68-integration still applies with the new commit and hash, and still needs the owner's approval and an operator.
  • Commit. This candidate is uncommitted. Whether it is ready for a local commit is a recommendation in the final report, not a decision made here.
