The Project Workspace in a Browser

The Lisp-level checks of the Project Workspace pass; this page is about the browser. The claim, the log and the result.

What ran

scripts/test-project-workspace.mjs (the file), in a fresh process with headless Chrome, over the original project CTM (SHA-256 f4f04bb4…b540d3) and Topic Maps 6162ed68 as a clean Git checkout. It takes its expectation from the Workspace's own pin, read from its source, and checks the checkout without the Lisp that serves the Catalog: Git's HEAD, a clean tree, and a committed manifest naming the commit. Earlier it asserted 5a4a668; that expectation changed only where the new identity was verified independently.

  1. Catalog → HyperBook HyperDoc Project Workspace → its page → the Project Workspace reading (Work Areas, Work Items, assignments, proposals, gaps).
  2. Roundtrip: the reader is the pinned checkout; the export equals the observed octets; the CXTM equals the sources'; every Topic and statement traces to its declaration.
  3. A declared Work Item, along Associations of the native Workspace: Working on HyperDoc → Work Breakdown → Author the CTM Plan Page through HyperDoc → its carrier page → the Item edited through HyperDoc → a Deliverable → a work package (WBS) → its plan step → a precondition.
  4. Its source page, and the declaration in the page source (a work-topic-source-occurrence).
  5. An Implementation Assignment and its evidence file dreyeck/tests/project-ctm.lisp.
  6. Absent evidence is named: the work package ctm-wp-2 shows acceptance criterion without an acceptance record; the reading says that no acceptance is recorded; the assignment says that no acceptance by the user is recorded.
  7. Object identity retained: the Work Breakdown page is the same Lisp object (the same printed address under each pane's Print tab) whether reached from its Topic in the Workspace or from the reading's Sources table; another page is another object (the control).
  8. The CTM document and its download: 161,228 octets, equal to the file and its sidecar digest.
  9. Nothing written: the four source pages and the CTM keep their digests; the site root stays empty; Git shows the Work pages and the CTM unchanged.

A trusted review runtime, not the guarded Catalog

The walk ran in scripts/serve-project-workspace.lisp (the file): a fresh Catalog on loopback over an empty test-copy site root that loads the Project Workspace by choice. The packaged executable is a different thing: its startup guard refuse-project-workspace reads the system the Catalog is asked to load and refuses dreyeck/work/project and anything that depends on it, before listening. That is unchanged: only its message now says that admission is a separate decision, because the Workspace is no longer bound to another lineage. Neither the guard nor the executable was bypassed or weakened to run the browser test; the Nix contract that includes the executable's refusal passes (record).

What remains

The browser walk was not run with the Git-free snapshot as the Topic Maps root; the Lisp-level runs were (Project Workspace Compatibility). Serving the Workspace from the packaged staging service is not possible without the admission decision (Remaining Work and Acceptance).
