topic-maps-integration-review

The Reviewed Change

Topic Maps merges Topics that share an identifier. After nearly every statement it asks: which two Topics merge next? Until now it answered by comparing every pair; for pairs without a shared identifier, each comparison enumerated every information item to see whether the Topics reify the same one. On the project CTM that cost grew with the square of the Topics times the items.

The commit

6162ed68 is one commit on b2eecffa: its subjects; the revision and the branches holding it. How it became the primary branch.

The two functions

next-topic-merge returns the pair; scan-next-topic-merge is the old search, moved unchanged, kept as the fallback and as the test oracle. normalize-topic-map now calls only the first. Read the docstrings: they state the argument.

  • Candidate selection. Two live Topics are equal exactly when they share an item or subject identifier (one namespace) or a subject locator, the rule of equal-topics-p. The index maps each identifier to its Topics in map order and picks, in order, the first Topic with a later partner and its first partner.
  • The nonconflicting-reifier preference. A staged import can hold equal reifier Topics whose reified Names are not yet equal. Merging them first would signal a reifier conflict that disappears once their owners merge. So the search prefers a pair whose members do not reify different items, and only if none exists returns the plain first pair, whose merge then signals the real conflict. The claim: the index returns exactly the pair of the old search.
  • Index lifetime and invalidation. The reification table and the identifier index are local to one call. After each merge the loop asks again, from the map. Nothing outlives a merge or a change of reifier, so there is no invalidation rule to get wrong.
  • Fallback. If a Topic reifies two items, or a listed Topic is not its own representative, the old search runs, so the condition and the moment it is signalled stay as they were.

What it does not touch

The Association pair search, the CTM reader, the public API and the retained-handle forwarding are unchanged. The experimental association index is not part of the commit. Claim and sources.
