Project Workspace Compatibility

The Project Workspace reads the HyperDoc project CTM, traces it to the Work pages, compares revisions by octets and CXTM and projects it into a Topicmap Workspace. It was bound to the sibling lineage 5a4a668; b2eecffa read the CTM correctly but not in practical time. The integration reuses the existing Workspace, Work pages and CTM emitter and changes only what binds it to a revision.

What changed in the Workspace

  • The pin: +topic-maps-revision+ is now 6162ed68.
  • topic-maps-source-identity knows three kinds of root: a Git checkout (as before), a verified /nix/store snapshot (through verify-store-snapshot), and anything else. A directory Git cannot identify used to look clean with an empty commit; it now has no commit, is not clean and is not pinned. pinned-state-p states the pin: the commit, no change, one root for topic-maps, /tmdm, /ctm and /cxtm.
  • The Roundtrip view says which kind of root it has; an obsolete assertion (b2eecffa accepts the template that 5a4a668 refused) became one that checks the new behaviour, and malformed input is still refused with its code.

The pin can fail

Three negatives: the 5a4a668 checkout (not pinned), the b2eecffa snapshot (does not verify as 6162ed68) and a directory without .git outside the store (unverifiable).

The Catalog guard stays

The packaged Catalog refuses dreyeck/work/project and everything depending on it, before it loads or serves anything. Its old reason (another Topic Maps lineage) no longer holds, so its message now says that admission to the served runtime is a separate decision; its behaviour is unchanged and its tests still require the refusal.
