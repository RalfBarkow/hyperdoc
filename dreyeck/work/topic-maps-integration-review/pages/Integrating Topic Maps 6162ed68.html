Integrating Topic Maps 6162ed68

HyperDoc's Project Workspace, its Catalog packaging and its Topic Maps readings depend on one independent Topic Maps implementation. This reading follows the step that moves all of them to 6162ed68: the independently reviewed change that lets that implementation read the HyperDoc project CTM in practical time. It is a local, uncommitted candidate in HyperDoc; nothing is pushed, published or deployed, and no server was touched.

The short answer

  • The change is bounded: one production file, its tests and 25 recorded fixtures; the experimental association index is not in it.
  • On the unchanged project CTM the result is byte-identical to the earlier reference in both the semantic signature and the CXTM, and it reads within the 90-second limit (about 30 s; it did not finish in 120 s before).
  • The 20-second aspiration is not met. The corpus never merges two Topics, so the merge-choice logic is shown by tests and controls, not by the corpus.
  • The Project Workspace suite passes and works from a Git checkout and from the verified Git-free snapshot; its pin can fail; the Catalog guard still refuses the Workspace.
  • This reading was served and navigated in a browser. The Project Workspace itself passed a fresh-process browser walk in a trusted review runtime, not the guarded Catalog.
  • The earlier review's path contract is now version-bound and the four commit boundaries were rehearsed. The Zettel's navigation is proposed, not declared.
  • The packaged Nix contract passes on x86_64-darwin; Linux, a browser walk from the snapshot and staging are open.
