FedWiki Component Order and Source Relations

dreyeck/fedwiki-source-relations

1. Question and historical source

The ASDF system hyperbook/fedwiki places hyperbook-fedwiki/fedwiki.lisp immediately before hyperbook-fedwiki/story-items.lisp . At the same time, source relations run in both directions between these files.

The question is not whether every source reference determines file order, nor whether arbitrary reordering can be proved safe. The narrower question is: which observed source relations actually constrain the ASDF component order?

The observation is bound to merge commit 56325b3e08581198649f9f47d7b23dc059ea671a . It reads hyperbook.asd , hyperbook-fedwiki/fedwiki.lisp , and hyperbook-fedwiki/story-items.lisp as historical Git objects without evaluating those files.

2. ASDF order is an observation, not yet an explanation

Parsing the historical ASDF definition gives this serial component order: 

package
utilities
pages
fedwiki
story-items
wiki-links
plugins
views

This establishes an observed system-definition relation:

Inspect fedwiki.lisp — :LOADS-BEFORE → story-items.lisp

Its phase is (:SYSTEM-DEFINITION), its ordering constraint is :OBSERVED-COMPONENT-ORDER, and its ordering basis is (:ASDF-DEPENDENCY).

This tells us what order ASDF specifies. It does not, by itself, tell us which Lisp source relation makes that order necessary.

3. A forward function call does not establish the component order

The source in fedwiki.lisp contains a call from FETCH-SITE-OWNER to PROCESS-TEXT-AND-LINKS, whose definition is in story-items.lisp.

Inspect the relation itself:

Inspect FETCH-SITE-OWNER — :CALLS → PROCESS-TEXT-AND-LINKS

The observation classifies this relation as: 

Phases               (:RUN-TIME)
Ordering constraint  :NONE-OBSERVED
Ordering basis       NIL

The reference occurs in a function body. Compiling the definition of FETCH-SITE-OWNER therefore does not require PROCESS-TEXT-AND-LINKS to have been loaded first. After the complete system has loaded, the target function is available before the call can occur at run time.

The derived file-level relation fedwiki.lisp — :USES-DEFINITION-FROM → story-items.lisp therefore records source use, but it does not provide a reason to reverse the observed ASDF order.

4. A relation in the opposite direction does constrain compilation

The reverse direction is different. FIND-EXAMPLES-FOR-STORY-ITEM-TYPES, defined in story-items.lisp, refers to *NEIGHBORHOOD*, whose top-level DEFVAR is in fedwiki.lisp.

Inspect this relation:

Inspect FIND-EXAMPLES-FOR-STORY-ITEM-TYPES — :READS-SPECIAL → *NEIGHBORHOOD*

The observation classifies it as: 

Phases               (:COMPILE-TIME :RUN-TIME)
Ordering constraint  :REQUIRED-COMPONENT-ORDER
Ordering basis       (:SPECIAL-PROCLAMATION)

The distinction between the two phases matters. The value of *NEIGHBORHOOD* is read when FIND-EXAMPLES-FOR-STORY-ITEM-TYPES runs. But the top-level DEFVAR also establishes that the variable is special, and that proclamation must already be available when the reference in story-items.lisp is compiled.

Under the observed source structure, this gives a concrete compile-time reason for fedwiki.lisp to precede story-items.lisp.

5. The same relation type can have different phase semantics

The remaining special-variable relations are internal to story-items.lisp. They demonstrate why a relation type such as :READS-SPECIAL is not sufficient on its own to characterize ordering.

Function-body use of *LINK-REGEX*

Inspect PROCESS-TEXT-AND-LINKS — :READS-SPECIAL → *LINK-REGEX* 

Phases               (:COMPILE-TIME :RUN-TIME)
Ordering constraint  :REQUIRED-WITHIN-FILE
Ordering basis       (:SPECIAL-PROCLAMATION)

Here the special proclamation matters while the function body is compiled, while the variable's value is read when the function runs.

Load-time construction of *LINK-REGEX*

Inspect *LINK-REGEX* — :READS-SPECIAL → *URL-REGEX*

Inspect *LINK-REGEX* — :READS-SPECIAL → *ANY-EXCEPT-CLOSING-BRACKET-REGEX* 

Phases               (:COMPILE-TIME :LOAD-TIME)
Ordering constraint  :REQUIRED-WITHIN-FILE
Ordering basis       (:SPECIAL-PROCLAMATION :LOAD-TIME-VALUE)

These references occur in the top-level initializer of *LINK-REGEX*. The earlier variables therefore contribute both compile-time special proclamations and values required when that initializer is evaluated while the file is loaded.

6. Phase-sensitive source relations

The observation therefore distinguishes source use from ordering semantics:

Relation Phase Ordering consequence
ordinary function call :RUN-TIME :NONE-OBSERVED
cross-file special-variable reference :COMPILE-TIME and :RUN-TIME :REQUIRED-COMPONENT-ORDER
function-body special-variable reference within one file :COMPILE-TIME and :RUN-TIME :REQUIRED-WITHIN-FILE
top-level initializer dependency within one file :COMPILE-TIME and :LOAD-TIME :REQUIRED-WITHIN-FILE
ASDF serial relation :SYSTEM-DEFINITION :OBSERVED-COMPONENT-ORDER

In particular, :OBSERVED-COMPONENT-ORDER and :REQUIRED-COMPONENT-ORDER are intentionally different claims. The first records what the system definition says. The second records a source relation whose phase semantics require that order under the current source structure.

File-level :USES-DEFINITION-FROM relations are explicit derivations from the corresponding definition-level relations. They inherit their phase and ordering annotations; they do not constitute an independent ordering argument.

8. What the current evidence establishes

The forward call from FETCH-SITE-OWNER to PROCESS-TEXT-AND-LINKS does not establish a component-order requirement.

The reverse reference from FIND-EXAMPLES-FOR-STORY-ITEM-TYPES to *NEIGHBORHOOD* does establish such a requirement under the current source structure: the top-level DEFVAR in fedwiki.lisp establishes the special proclamation needed when the corresponding reference in story-items.lisp is compiled.

The observed serial order is therefore semantically relevant, but this does not imply that the present organization is the only possible organization. Moving definitions, separating development helpers, or extracting a coherent earlier parser component would change the dependency structure and must be evaluated as separate refactoring hypotheses.

9. Current analysis boundary

The historical files, definitions, and exact source fragments in this observation are backed by the fixed Git blobs. The phase and ordering annotations shown on this page are, however, currently explicit classifications in the observation builder.

In particular, the current implementation does not yet derive all phase and ordering classifications automatically from arbitrary Common Lisp source.

This is intentional for the present slice. The explicit classifications define inspectable reference cases for a later source analyzer. Such an analyzer could derive facts such as:

  • a reference occurs in a function body;
  • a reference occurs in a top-level initializer;
  • a top-level DEFVAR or DEFPARAMETER establishes a special proclamation;
  • a value is required at load time;
  • an ASDF component relation is supplied by the system definition.

Project-specific interpretations such as :PRODUCTION versus :DEVELOPMENT-HELPER may remain curated even when more of the Common Lisp phase analysis becomes derived.

12. Refactoring remains a separate question

The observation still carries two unexecuted refactoring hypotheses: separating FIND-EXAMPLES-FOR-STORY-ITEM-TYPES as development support, and extracting the Wiki-text parser as a coherent earlier component. Neither proposal follows automatically from the phase analysis.

Inspect the unexecuted refactoring hypotheses

A declaration could change what the compiler knows at a phase boundary without necessarily changing source ownership. Conversely, moving a definition can change the dependency graph itself. These are distinct refactoring operations and should remain separately inspectable.
