Reconstructing Workflow

A running definition is not proof that its source can recreate it. Workflow distinguishes loaded image state, registered change history, current persistence risk, source authority and fresh-process verification. Process and deployment boundaries limit what that evidence establishes.

QuestionEvidence / API
Explicitly registered?REGISTER-CHANGE records a known operation/function pair.
Recorded definition still current?OBSERVE-CHANGE reports :RECORDED-DEFINITION-CURRENT-P.
Reconstruction verified?CHANGE-RECONSTRUCTION-PROOF retains accepted evidence; reconstruction status is :VERIFIED or :UNVERIFIED.
Persisted source authority?OBSERVE-OPERATION locates possible source; PERSISTENCE-PLAN names an explicitly owned source form and expectation.

These are distinct relations. A loaded definition need not be registered, a registered definition need not remain current, and locating source does not prove reconstruction. This book loads through ordinary dreyeck/catalog. The ► buttons transclude real persisted DEFEXAMPLE definitions.

Registered changes: history, current risk, and closure

What in the image is not yet persistent? The bounded answer is: explicitly registered changes that are still current and reconstruction-unverified. OUTSTANDING-CHANGES and CURRENT-OUTSTANDING-CHANGES are two projections over registered records: open reconstruction history and current persistence risk. Both preserve registration order.

A record retains its operation, captured function identity, registration observation and optional reconstruction proof. Re-registering the same operation and EQ-identical function returns the same record. A later definition cannot close the older superseded record.

reading-change-verification

In ordinary runtime the closure example returns an authoring requirement. In the pinned authoring shell it runs the durable A/B experiment through the real PERSIST-IN and VERIFY-CHANGE operations against temporary authorities. It returns records, before/after observations and accepted proof. Temporary source is removed afterward; the proof describes that completed experiment.

Failed verification leaves the record open. Source discovery, in-image RECONSTRUCT, and PERSIST-IN without an associated change do not close a record. Only explicitly registered ordinary-function mutations are covered: unregistered mutations remain invisible, with no whole-image scanning, automatic hooks or generic-function method tracking.

Copy these SLY/mREPL forms and inspect their ordinary Lisp results:

(dreyeck/workflow:outstanding-changes)
(dreyeck/workflow:current-outstanding-changes)
(let ((change (first (dreyeck/workflow:outstanding-changes))))
  (when change (dreyeck/workflow:observe-change change)))

What is the smallest source authority?

After identifying a current outstanding change, the next question is: what persisted source owns the definition? The current workflow requires explicit ASDF ownership; it does not automatically assign an unowned image-only definition to a source file or insert a new top-level definition.

persistence-plan records an ASDF system, its owned source pathname, a unique top-level DEFUN or DEFSYSTEM key, the observed source and form, proposed Lisp data, and an expectation for a fresh process. The source owns the capability; the plan is a disposable observation/proposal. No persistent registry, fragment codec or construction-history chain is needed to recover this model.

reading-plan

Open “Persistence boundary” to inspect the source, before/after forms, status and expectation. The example proposes a documentation change to the real PLAN-STATUS definition; it does not execute it.

reading-live-operation

SBCL introspection supplies source-location evidence for the named operation. Compiled closures may have no recoverable source; the returned pathname does not establish ownership or reconstructive equivalence.

Ownership does not imply dependency

reading-dependency

The dependency example observes the real workflow DEFSYSTEM. UIOP is already present, so its plan is unchanged. ASDF owns component membership, system dependencies and reconstruction order. Workflow changes that existing declaration structurally; it does not maintain a parallel dependency graph. Definition calls, ASDF load prerequisites, source provenance and verification expectations remain different relations.

The falsification test writes a perfectly owned fixture DEFSYSTEM whose dependency does not exist. Ownership succeeds; fresh reconstruction fails. This is the concrete observation requiring dependency knowledge beyond ownership. It does not require fragment authorities or an extension chain.

PERSIST-IN crosses an explicit authoring boundary

reading-authoring-boundary

Ordinary runtime constructs plans and defines the PERSIST-IN and VERIFY-CHANGE protocols, but has no authoring method. Loading the Catalog grants no writing capability. In an authoring-capable process, load dreyeck/workflow/authoring and create its explicit authoring environment. That environment verifies the selected writer source and commit.

The nix develop path:.#workflow-authoring shell pins html-inspector-views 38afb02d79838d4098589c2e203ba39799a44853. Ordinary HyperDoc keeps 386df8937a21457b3d91e1b61e070f836550ff71. Neither path depends on a local editor checkout.

Use (dreyeck/workflow:persist-in plan environment :change change) to persist and verify a particular record. Use (dreyeck/workflow:verify-change change plan environment) to verify already-persisted source without rewriting it. The plan must own the operation, the proposed form and surrounding forms must match persisted source, and the captured function must remain current before and after verification.

The executor rejects stale source and ambiguous form identity, uses the CST writer, and reparses the result. It then starts a fresh ordinary-runtime SBCL process to load the owning ASDF system and evaluate the expectation. For registered-change closure, the explicit behavioral expectation must hold in both the authoring image and the fresh process. Use observational expectations that do not mutate the operation. This proves the stated expectation, not general equivalence. A write followed by failed reconstruction remains on disk for inspection rather than being silently rolled back.

reading-persistence-roundtrip

In ordinary runtime this button returns the required environment and an inspectable request. In the pinned authoring shell it exercises the same PERSIST-IN seam against temporary authorities, including wrong results, stale requests and missing dependencies. No production source or Git state is modified by the example.

Countermodels and design history

Medley File Package

The Interlisp primary project timeline describes file ownership, change tracking and cleanup in 1971, and contrasts that system with dependency-aware make. The surviving implementation provides a more precise comparison than an analogy alone.

reading-medley

Evidence is fixed to Medley commit 3a14c9aa040d6cd897e3d6c3c3fa664a3e2d1442, sources/FILEPKG, blob 46d6906bdb1f92c49e19b128459ca223289717ed. Each evidence object retains its definition, line, observation, immutable source link and MIT license attribution. Medley is neither copied into this repository nor required at runtime.

FILECOMS resolves the command-variable name for a file. The command list describes what belongs there. MARKASCHANGED records names by type and invokes change hooks; MAKEFILE consults pending changes and file properties. CLEANUP coordinates dumping, listing and optional compilation; FILES? exposes pending work.

The analogy has limits. This workflow detects divergence between a scoped proposal and an observed authority; it does not implement Medley's change hooks. FILECREATED is source metadata, not a fresh-process behavioral test. FILECOMS is not an operation assembly registry. Further, modern CHECKIMPORTS checks imported versions. The claim that all present-day Medley lacks dependency-related behavior is therefore rejected. ASDF remains the relevant dependency mechanism for this Common Lisp system.

Historical HyperDoc workflow

reading-historical

Historical PERSIST-IN mixed a Catalog-specific append operation, a tests-specific append operation, and overlapping ASDF dependency guards. Newest-first closures preserved the history of those implementations. They did not establish distinct semantic authorities. Direct structural plans replace this dispatch history and reject duplicate target forms instead of appending competing definitions.

How this explanation reconstructs itself

reading-bootstrap

The seed is Common Lisp and ASDF, the pinned runtime libraries, HyperDoc/HyperBook, DEFEXAMPLE/source transclusion, Inspector, Topicmap and Workspace. Persisted workflow source creates the plan protocol. Persisted reading definitions create observations and projections. The HTML page transcludes those definitions. Ordinary Catalog membership loads the reading system; it does not execute source writing. Fresh tests repeat this chain without a pre-populated workflow registry. This is an explainable bootstrap, not a claim of complete self-hosting.

Run ordinary tests with nix develop path:. -c sbcl --no-userinit --non-interactive --eval '(require :asdf)' --eval '(asdf:test-system "dreyeck/workflow/reading/tests")'. Run persistence falsification in nix develop path:.#workflow-authoring with (asdf:test-system "dreyeck/workflow/authoring/tests"). The optional TALA shell exercises the layout comparison. No routine Catalog startup runs these authoring tests or CLEANUP-like behavior.

Operational boundaries

Process boundary

Change records and change logs are currently image-local. The log survives ordinary source reload through DEFVAR, but is not persisted across process restarts. The authoring tests create and close their records within an authoring-capable Lisp process. A separate fresh ordinary-runtime process supplies reconstruction evidence; it does not receive or close the original RECORDED-CHANGE object.

The current workflow has no demonstrated transport protocol for transferring a RECORDED-CHANGE from one Lisp process to another and later closing it there. This is a scope boundary, not a claim that such a mechanism is impossible. The tests do not prove cross-process record transfer.

Deployment authority

Local source reconstruction is executable repository evidence; it does not prove remote deployment state. The bootstrap example retains operator-supplied evidence that dreyeck.ch:/etc/nixos/hyperdoc-service.nix starts nix develop .#tala -c ./scripts/serve-catalog.sh 8080, and that the TALA reading page is available. This is the operator's observed command, quoted without changing its spelling.

Remote evidence is supplied explicitly by the operator. Tests, examples, Inspector views and reconstruction require no SSH, SCP, rsync or server access; deployment mutations remain operator-controlled. If a service-equivalent D2/TALA witness is needed, the operator runs it manually and returns the output. Local test results cannot substitute for that evidence.

Local instructions on this page use path:. to select this checkout explicitly, as in the fresh tests. Existing executable-example metadata may retain the shorter .#workflow-authoring spelling for the same local shell; the observed deployment command above remains historical evidence.

Development note: reloading the change model

In the reported development session, the running image initially held the older RECORDED-CHANGE class with operation, function and observation state, while persisted source already contained the reconstruction-proof model. Reloading dreyeck/workflow redefined the class. The pre-existing record remained the same object of that class and acquired a bound RECONSTRUCTION-PROOF slot initialized to NIL, so its status remained :UNVERIFIED.

This was a development-session observation, not itself a fresh-process reconstruction proof. The durable distinction between historical obligations and current definitions is exercised by READING-OUTSTANDING-CHANGES earlier on this page; it is transcluded there once, without depending on object addresses or the previous image.
