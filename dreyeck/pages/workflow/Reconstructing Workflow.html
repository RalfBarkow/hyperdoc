Reconstructing Workflow

A running definition is not proof that its source can recreate it. Workflow connects one owned source form, a proposed change, and an explicit reconstruction expectation. It neither replaces ASDF nor serializes the entire Lisp image.

This book loads through ordinary dreyeck/catalog. Loading and inspecting it writes no source and changes no Git state. The ► buttons transclude real persisted DEFEXAMPLE definitions. Each example constructs its own observation.

What is the smallest authority?

persistence-plan records an ASDF system, its owned source pathname, a unique top-level DEFUN or DEFSYSTEM key, the observed source and form, proposed Lisp data, and an expectation for a fresh process. The source owns the capability; the plan is a disposable observation/proposal. No persistent registry, fragment codec or construction-history chain is needed to recover this model.

reading-plan

Open “Persistence boundary” to inspect the source, before/after forms, status and expectation. The example proposes a documentation change to the real PLAN-STATUS definition; it does not execute it.

reading-live-operation

A source pathname found through SBCL introspection is evidence of location, not proof of equivalence. Observation covers only the supplied operation. Compiled closures may have no recoverable source. There is no claim to detect every unpersisted capability in the image, and no global scanner or hidden cleanup pass.

Ownership does not imply dependency

reading-dependency

The dependency example observes the real workflow DEFSYSTEM. UIOP is already present, so its plan is unchanged. ASDF owns component membership, system dependencies and reconstruction order. Workflow changes that existing declaration structurally; it does not maintain a parallel dependency graph. Definition calls, ASDF load prerequisites, source provenance and verification expectations remain different relations.

The falsification test writes a perfectly owned fixture DEFSYSTEM whose dependency does not exist. Ownership succeeds; fresh reconstruction fails. This is the concrete observation requiring dependency knowledge beyond ownership. It does not require fragment authorities or an extension chain.

PERSIST-IN crosses an explicit authoring boundary

reading-authoring-boundary

Ordinary runtime creates plans and exposes the PERSIST-IN protocol. It has no authoring method. In nix develop .#workflow-authoring, load dreyeck/workflow/authoring and create its explicit authoring environment. That environment verifies the selected writer source and commit. Then (dreyeck/workflow:persist-in plan environment) is the actual operation.

The separate shell pins html-inspector-views 4b0607d93b193e21bd2ca5dc0d7e47c062ac8112. Ordinary HyperDoc keeps 386df8937a21457b3d91e1b61e070f836550ff71. Neither path depends on a local editor checkout.

The executor rejects stale source and ambiguous form identity, uses the existing CST writer, reparses the file, compares the intended form and unrelated forms, then starts a fresh ordinary-runtime SBCL process. That process loads the owning ASDF system and evaluates the expectation. Only success yields :verified. A failed reconstruction leaves a written, unaccepted edit for inspection; it is not silently rolled back or reported as persisted success. Expectations are explicit behavioral tests, not a general proof of equivalence.

reading-persistence-roundtrip

In ordinary runtime this button returns the required environment and an inspectable request. In the pinned authoring shell it runs the real PERSIST-IN seam against temporary authorities: 42 becomes 43 and is reconstructed in a fresh process. It also disproves acceptance of stale requests, wrong results and missing dependencies. Temporary test files are removed afterward. No production source or Git state is modified by this example.

Read the File Package as a countermodel

The Interlisp primary project timeline describes file ownership, change tracking and cleanup in 1971, and contrasts that system with dependency-aware make. The surviving implementation provides a more precise comparison than an analogy alone.

reading-medley

Evidence is fixed to Medley commit 3a14c9aa040d6cd897e3d6c3c3fa664a3e2d1442, sources/FILEPKG, blob 46d6906bdb1f92c49e19b128459ca223289717ed. Each evidence object retains its definition, line, observation, immutable source link and MIT license attribution. Medley is neither copied into this repository nor required at runtime.

FILECOMS resolves the command-variable name for a file. The command list describes what belongs there. MARKASCHANGED records names by type and invokes change hooks; MAKEFILE consults pending changes and file properties. CLEANUP coordinates dumping, listing and optional compilation; FILES? exposes pending work.

The analogy has limits. This workflow detects divergence between a scoped proposal and an observed authority; it does not implement Medley's change hooks. FILECREATED is source metadata, not a fresh-process behavioral test. FILECOMS is not an operation assembly registry. Further, modern CHECKIMPORTS checks imported versions. The claim that all present-day Medley lacks dependency-related behavior is therefore rejected. ASDF remains the relevant dependency mechanism for this Common Lisp system.

What survived the historical workflow?

reading-historical

Historical PERSIST-IN mixed a Catalog-specific append operation, a tests-specific append operation, and overlapping ASDF dependency guards. Newest-first closures preserved the history of those implementations. They did not establish distinct semantic authorities. Direct structural plans replace this dispatch history and reject duplicate target forms instead of appending competing definitions.

The map is not the territory

reading-workspace

The existing Workspace exposes plans, ASDF ownership, historical evidence, Medley evidence and the authoring boundary. Every relation stores a warrant and epistemic status: source-observed fact, mechanically derived fact, design inference or working hypothesis. The comparison edge to Medley is explicitly a hypothesis; layout cannot promote it to a fact.

reading-layout-comparison

Native placement emphasizes a readable comparison row. Optional TALA derives orthogonal placement from the same Workspace. The existing comparison retains the same Projection, Topic IDs, Association IDs/endpoints, point and history. Native signs keep their existing navigation thunks; the TALA image is a noninteractive rendering proof. Without D2 the button returns an explicit capability requirement and a usable native Workspace. Proximity, routing and left-to-right placement have no workflow authority.

How this explanation reconstructs itself

reading-bootstrap

The seed is Common Lisp and ASDF, the pinned runtime libraries, HyperDoc/HyperBook, DEFEXAMPLE/source transclusion, Inspector, Topicmap and Workspace. Persisted workflow source creates the plan protocol. Persisted reading definitions create observations and projections. The HTML page transcludes those definitions. Ordinary Catalog membership loads the reading system; it does not execute source writing. Fresh tests repeat this chain without a pre-populated workflow registry. This is an explainable bootstrap, not a claim of complete self-hosting.

Run ordinary tests with nix develop -c sbcl --no-userinit --non-interactive --eval '(require :asdf)' --eval '(asdf:test-system "dreyeck/workflow/reading/tests")'. Run persistence falsification in nix develop .#workflow-authoring with (asdf:test-system "dreyeck/workflow/authoring/tests"). The optional TALA shell exercises the layout comparison. No routine Catalog startup runs these authoring tests or CLEANUP-like behavior.

Deployment is a distinct authority

Local source reconstruction is executable repository evidence. It does not prove the state of a remote deployment. The bootstrap example retains explicitly operator-supplied evidence: dreyeck.ch:/etc/nixos/hyperdoc-service.nix starts nix develop .#tala -c ./scripts/serve-catalog.sh 8080, and the operator reports the TALA reading page available there. The workflow does not acquire remote evidence implicitly. Tests, examples, Inspector views and reconstruction require no SSH, SCP, rsync or server access. Deployment mutations remain operator-controlled.

A server-side dependency witness, if needed, is run manually by the operator in /home/rgb/workspace/hyperdoc: nix develop .#tala -c sbcl --noinform --no-userinit --non-interactive --eval '(require :asdf)' --eval '(asdf:load-system "dreyeck/topicmap/tala")' --eval '(format t "SERVICE-TALA-STATUS=~S~%" (dreyeck/topicmap/tala:tala-dependency-status))'. It tests executable availability, expects supported D2 v0.9.0 with TALA, and does not restart the service. A returned witness must be attributed to the operator; local tests cannot substitute for it.

Was im Image ist noch nicht persistent?

For this slice, the operational question is: show registered live-image changes whose reconstruction has not yet been verified. Recording a mutation, observing an operation, locating source, planning persistence and verifying fresh reconstruction remain separate responsibilities.

reading-outstanding-changes

The example compiles a live-only increment function under a fresh symbol, explicitly registers it in an isolated change log and returns outstanding records and their observations. No production source or Git state is modified. The function has no source pathname and remains unverified. Registering the same symbol and identical function object twice returns the same record; a redefinition is a distinct change. A later unregistered redefinition is visible when observing an existing record, but is not automatically registered.

In SLY/mREPL, evaluate (dreyeck/workflow:outstanding-changes) and inspect the returned list. After a deliberate mutation, explicitly call (dreyeck/workflow:register-change 'your-package:your-function). Each record exposes its operation, captured function, registration-time observation and reconstruction status; (dreyeck/workflow:observe-change record) adds the current observation. Source location alone is never a verification claim.

This layer is motivated narrowly by Medley's MARKASCHANGED (record change) and FILES? (expose pending work). It does not reproduce FILEPKG or scan the image. Unregistered changes remain invisible. The log is image-local, uses sequential explicit registration and survives ordinary source reload through DEFVAR; it is not persisted across process restarts. This slice has no transition that clears a record: every registered change stays unverified. Neither RECONSTRUCT nor merely writing a source file clears it. A future verified transition must connect the recorded function/change identity to successful fresh-process evidence through the existing persistence boundary.
