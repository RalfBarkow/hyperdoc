The Fischer Critic as an Environment

dreyeck/lisp-critic/reading

Fischer's LISP-CRITIC is documented here, not observed and not executed. What has changed since the first version of this page is the quality of the documentation: the claims below now come from the primary papers, one sentence at a time, each with a locator you can re-check.

Not a pipeline

It is tempting to read the system as a sequence — rules produce a critique, then an explanation, then eventually a user model. That ordering is wrong and it misrepresents what was interesting about the work. The 1987 paper describes an integrated environment in which these parts were present together: 

Fischer 1987: integrated critic environment
  rules
  rule interpreter
  user model
  explanation / knowledge browser / visualization
  learning on demand

The user model is not a later addition to a linter. It is part of what the system was for: supporting incremental learning while someone works, rather than checking a program once.

What came after

The later work is where the versioning, the empirical grounding and the generalisation happen: 

later work
  more systematic user-model framework
  empirical validation
  versioned Common-Lisp / Genera development
  richer conceptual / domain model
  editor interaction: Accept / Reject / Explain
  generalization toward the Critiquing Paradigm

Who built what

Boecker is documented as the developer of the original ideas, the rule set and the rule interpreter. That is a contribution credited in the acknowledgements — not co-authorship of the 1987 paper, and the reading keeps those apart. Morel implemented the explanation capabilities and Burns the statistical analysis. The 1991 paper additionally credits Morel, Burns and Cormack for Version 1, and Rieman, Johl and Lynn for Version 2.

Why evidence has no single ranking

It would be convenient to say that source code beats a paper. It does not, because the two answer different questions. Riesbeck's repository history can settle mechanically that two macros were merged in 2003; it is silent on whether a 1987 system had a user model. The 1987 paper is the opposite. Strength is therefore a relation between a piece of evidence and a particular claim, and this reading writes that relation down rather than implying a hierarchy.
