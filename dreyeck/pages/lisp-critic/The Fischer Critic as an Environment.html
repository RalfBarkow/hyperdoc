The Fischer Critic as an Environment

dreyeck/lisp-critic/reading

Fischer's LISP-CRITIC is documented here, not observed and not executed. What has changed since the first version of this page is the quality of the documentation: the claims below now come from the primary papers, one sentence at a time, each with a locator you can re-check.

Not a pipeline

It is tempting to read the system as a sequence — rules produce a critique, then an explanation, then eventually a user model. That ordering is wrong, and it misrepresents what was interesting about the work. In the 1987 abstract the advice is already based on the model of the user; the user model is not something the explanation eventually feeds. The paper then places the explanatory tools around that critic, as "additional tools" and "additional system components": 

Fischer 1987, as the paper lays it out
  the critic
    rules
    rule interpreter
    user model            <- the advice already rests on this
  additional components, to explain and illustrate the advice
    knowledge browser
    KAESTLE (visualization)
  purpose: incremental learning, learning on demand

"Environment" is this reading's word for that arrangement, and the page title keeps it. The paper itself does not use it: it says "additional", which puts those tools beside the critic rather than inside one integrated whole. The distinction is small but it is the kind this reading is for, so it is recorded rather than smoothed over. The abstract is here to be checked against.

The user model is not a later addition to a linter. It is part of what the system was for: supporting incremental learning while someone works, rather than checking a program once.

What came after

The later work is where the versioning, the empirical grounding and the generalisation happen:

  empirical validation

Who built what

Boecker is documented as the developer of the original ideas, the rule set and the rule interpreter. That is a contribution credited in the acknowledgements — not co-authorship of the 1987 paper, and the reading keeps those apart. The 1987 acknowledgements give each person a specific job: Morel implemented the explanation capabilities, Burns the statistical analysis package, and Cormack analysed user programs with that package. The 1991 acknowledgments do not repeat those jobs; they group the same three as contributors to version 1, and name Rieman, Johl and Lynn for version 2. Both wordings are kept, because the difference between them is itself something a later reader may want.

Why evidence has no single ranking

It would be convenient to say that source code beats a paper. It does not, because the two answer different questions. Riesbeck's repository history can settle mechanically that two macros were merged in 2003; it is silent on whether a 1987 system had a user model. The 1987 paper is the opposite. Strength is therefore a relation between a piece of evidence and a particular claim, and this reading writes that relation down rather than implying a hierarchy.
