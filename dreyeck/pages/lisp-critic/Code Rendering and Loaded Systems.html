Code Rendering and Loaded Systems

dreyeck/lisp-critic/reading

Decision 1: may loading the Verified Example system change how ordinary Code items look? No decision has been taken. A Claude Code review wrote this page to prepare it; the answer is the project owner's.

Today it does: in an image that loads the Verified Example system, every ordinary Code item loses its code label, its grey background and its Inspector link. In an image that does not load it, nothing changes. This was observed, not only read from the code: before, after, evidence commit e91349f6.

Answer: No, loading must not change ordinary Code

In practice: ordinary Code looks the same in every image. The Verified Example code would handle only items marked as Verified Examples and hand every other Code item back to the general way of showing Code. The probe shows that this general way is still there, unchanged, after loading, so handing back would restore exactly the earlier look; the marked items would keep their own separate path. Any later change to how ordinary Code looks would then have to be made in that general place, for all images alike.

For:

  • A reader, or a reviewer, cannot tell from a page which optional systems an image has loaded. If the look depends on it, the same page looks different in two places for no visible reason. (a consequence, read from the observation)
  • The Verified Example code's own comment says ordinary Code "remains" a passive source view, and its report says it stays one. Both promise that nothing changes. (observed in the text)
  • Elsewhere in this code base, optional extensions add to an existing rendering instead of replacing it. (inferred from two examples)

Against:

  • The difference only appears in images that load the Verified Example system, and the public Catalog does not load it. (observed)
  • An optional system may be allowed to take over how a whole item type is shown; the general way of showing items is a fallback, not a promise. (an assumption about what counts as a contract)
  • Every future change to ordinary Code then affects every image at once, which makes such changes weightier. (a consequence)

Answer: Yes, loading may change ordinary Code

In practice: today's behaviour stays. The comment and the report that say the look "remains" would have to be corrected, so that they describe what actually happens. Whether a page shows the Inspector link would depend on the image, so the second decision could have a different answer in different images.

For:

  • A trust-sensitive optional part may want to show all Code in one plain way while it is loaded. (an assumption about the intended design)
  • No change to the code is needed. (observed: it is today's behaviour)

Against:

  • Nothing written so far says the change was intended: no test and no document asks for it, while comment and report say the opposite. (observed)
  • What a reader sees then depends on something the reader cannot see. (a consequence)

The earlier question

This decision is the general form of the review's earlier question. Answering "No" here is what Position A asks for. Answering "Yes" leaves room for Position B. Both answer the question. That this decision maps onto those positions so is the review's reading, not something the pages establish.
