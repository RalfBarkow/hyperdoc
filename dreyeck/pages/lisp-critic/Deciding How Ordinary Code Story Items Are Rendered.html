Deciding How Ordinary Code Story Items Are Rendered

dreyeck/lisp-critic/reading

No decision has been taken. This page prepares two decisions for the owner of the HyperDoc project and says where an answer goes. A Claude Code review wrote it. Nothing here is your answer, and nothing here releases a change to the code.

What this is about

A Federated Wiki page can hold a Code item: a block of source text. HyperDoc shows such an item as text in a grey box, with a small label code above it. Clicking the label opens the item itself in the Inspector, where its data can be read, for example the programming language the author gave it.

An ordinary Code item is one that is not marked as a Verified Example. Verified Examples are a newer, optional part of HyperDoc that shows stored, checked results of code, and only after a person has approved them. Loading that optional part also changes how every Code item is shown, the ordinary ones included. That side effect is what the two decisions are about.

What was observed

A probe rendered one ordinary Code item, the text (defun square (x) (* x x)) with the language lisp, twice in one fresh process: once before and once after loading the Verified Example system. The code examined is commit 9b57bd4b. The probe ran to the end, and a second run gave the same result.

Before loading, HyperDoc produced:

<div><i><small><span class='inspector-inspect'><span id='inspect-309'>code</span></span></small></i></div><pre style='background-color: #eee;'>(defun square (x) (* x x))</pre>

After loading, it produced:

<pre>(defun square (x) (* x x))</pre>
  • The text stays the same and stays safely escaped in both cases.
  • After loading, the code label, the grey background and the Inspector link to the item are gone.
  • The item itself is unchanged: its language is still stored with it. Only the way to reach it from the page is gone.
  • It is the loading alone that makes the difference: the general way of showing Code is still there afterwards, but the Verified Example part now answers first for every Code item.

The evidence is kept in the repository at commit e91349f6171839a12eea7ee2f24da393b4dd870c: the report, the HTML before, the HTML after and the run's log. Every file there matches its recorded SHA-256 checksum. The probe was run outside this review; the review read and checked its files.

The two decisions

  1. May loading the Verified Example system change how ordinary Code items look?
  2. Should an ordinary Code item keep its Inspector link to the item itself?

Each page shows the possible answers, what each would mean in practice, and the arguments for and against. The two decisions are separate, but they meet: see the table below.

Keep the linkRemove the link
Loading must not change ordinary Code The Verified Example part hands ordinary items back to the general way of showing Code. Ordinary Code then looks as it did before. The link goes everywhere, in the general way of showing Code, for every image, whether or not Verified Examples are loaded.
Loading may change ordinary Code Unusual: the link stays, but other parts of the look may differ by image. Today's behaviour. Its comments and report, which say the look "remains", would have to be corrected.

The earlier question and its two positions

The review first asked a narrower question, about one piece of code, and offered two positions on it. They are Wiki pages written by the review:

  • The question: should the Verified Example code keep the earlier look of ordinary Code items, link included? Its note that the probe had not run was written before the probe ran.
  • Position A: yes, keep the earlier look.
  • Position B: not necessarily, plain passive text may be what was intended.

The two decisions above are what that question rests on. Answering them answers it: keeping the earlier look regardless of what is loaded is Position A; removing the link only when Verified Examples are loaded is today's behaviour, which Position B defends as possibly intended.

Not part of these decisions: whether Code should ever be coloured by language (syntax highlighting), and what to do when the language is missing or unknown. HyperDoc colours nothing today, the probe found no difference by language, and other systems choose differently: Federated Wiki guesses the language, D2 shows plain text. That is a question of its own.

How to give your answer

Your answer is yours, on a Federated Wiki site you own. The review's pages are not on any public site. Their site name, trusted-examples-review.invalid, is deliberately not an address; do not link to it.

  1. On your own site, create a new page, for example by writing its title as a link in a paragraph and clicking it. Any title will do, for example My Decision on Rendering Ordinary Code Items.
  2. Give it four fold items, named exactly as in the Claim Template: question, claim, support and oppose.
  3. Under question, one paragraph per decision, naming this page and the commit you read it at (the links below).
  4. Under claim, your answer to each decision, one paragraph each.
  5. Under support and oppose, your reasons, one per paragraph. You may cite the evidence links or the review's arguments, or contest them.

Paragraphs you can copy and complete:

Asked in HyperDoc, "Deciding How Ordinary Code Story Items Are Rendered", repository RalfBarkow/hyperdoc. Evidence: [https://github.com/RalfBarkow/hyperdoc/commit/e91349f6171839a12eea7ee2f24da393b4dd870c P1 evidence e91349f6].

Nothing links back to your page by itself. If you want the review's pages to point to your answer, say so: that is a separate change, made only on your explicit request, and it would quote your page, not speak for you.

Three different things

  • The review's text: this page, the two decision pages, the question and its positions. Written by a Claude Code review, and marked as such.
  • Your position: your page on your own site. Only you write it.
  • A binding project decision: an explicit instruction from you to change, or not to change, the code. Neither the review nor your Wiki page is one by itself. The project's Acceptance Records page, which records binding decisions on declared work packages, records none today, and none of its work packages concerns this question.
