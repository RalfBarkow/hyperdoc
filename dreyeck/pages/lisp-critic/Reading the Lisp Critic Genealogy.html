1. Two histories to keep apart

2. What Fischer's Critic was

Not a linter. There are rules and a rule interpreter, but the 1987 abstract has the advice resting on a model of the user, and puts a knowledge browser and visualization alongside as additional tools that explain and illustrate it. Its purpose was to improve a program locally according to an encoded style, not to check a whole program for correctness.

Later work adds numbered versions, an empirical footing, a Genera environment, and finally a generalisation away from Lisp altogether, into a framework for critic systems.

3. What Riesbeck preserves

A working rule-matching critic core, in Common Lisp, present here as source. Rules are patterns with response templates; applying one to a form yields findings. The engine reached this workspace through Zach Beane's 2004 ASDF adaptation and a page-attached wrapper this repository binds to rather than depends on.

The engine's own definitions, transcluded from the source

4. What HyperDoc adds

Riesbeck's engine prints findings. This repository turns one rule application into a record that exists whether or not anything was found, and turns a finding into a Critique object with its own relations. Execution evidence and critique are separate things, and both can be inspected.

Where the source lives

The pages above read the Critic as a subject. Its source is a separate question with a different shape: four systems in this repository, one that lives beside a wiki page, and a vendored copy of the historical engine. No single ASDF system contains it, which is why this book's Code pages tab is empty and correctly so.
