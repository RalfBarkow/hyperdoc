FedWiki story-item transfer as an inspectable operation

dreyeck/fedwiki-story-item-transfer

We first materialize the transfer operation. Browser gestures can be added later as ways to invoke it. This is the operation-first boundary: the Lisp contract exists before any drag, Shift-click, or other gesture is assigned to it. 

Source story item
  -> Transfer action
  -> Transfer representation
  -> Inspectable outcome

Reference preparation

PREPARE-STORY-ITEM-TRANSFER currently accepts only the non-destructive action :REFERENCE. The source page must already be loaded and must contain the supplied story item by object identity. The resulting STORY-ITEM-TRANSFER retains the source page, its actual origin, the identical story item, an optional diagnostic target, and the action's outcome. No page is loaded or changed by this operation.

For :REFERENCE, the outcome is the same story-item object by EQ. The resource remains at its source origin; no story-item data or image bytes are copied.

Production operations

Source provenance is obtained through ORIGIN-OF. Image resource addresses continue to use RESOLVE-STORY-ITEM-URL. The new preparation boundary is PREPARE-STORY-ITEM-TRANSFER.

Executable image example

This deterministic example constructs an in-memory FedWiki page and the observed image story item through the existing page/story constructors. It returns a STORY-ITEM-TRANSFER with action :REFERENCE. Inspecting it permits navigation from the transfer to its source page, source origin, and story item. The image section derives the stored resource reference and resolved resource URL without adding duplicate URL, width, height, or size slots to the transfer object.

Local-first interpretation

The following is an interpretation and an open architecture question, not an implemented storage policy: 

REFERENCE
  keeps ownership and resource bytes at the source origin

future IMPORT
  would fetch bytes, store a local asset, retain provenance,
  and create a local resource reference

This slice implements REFERENCE, not IMPORT. COPY is also deferred: without a target page or persistence contract, choosing a new local item identity and copy depth would claim semantics the current object model does not yet provide. MOVE remains outside the boundary because it would require a successful import followed by deletion at the source.

Future gestures

A future drag could invoke an existing transfer action. A modified drag could later select another action, but no modifier mapping is decided or encoded here. There are no HTML5 drag handlers, JavaScript events, page writes, uploads, downloads, or persistence in this slice.
