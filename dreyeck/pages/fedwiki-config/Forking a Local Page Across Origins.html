Forking a Local Page Across Origins

The destination-origin browser and a local-origin browser have different authority. A remote Wiki client asking for localhost:3000 addresses the user's workstation through the browser. A server-side fallback asking for localhost addresses the server's own loopback. Starting a normal fork in a local Wiki normally writes to that local Wiki origin; it does not select a remote destination merely because another page is in the lineup.

Here public-origin is the client's hostname classification: remote.fixture.test is not a loopback hostname, although fixture DNS maps it to loopback. The captured rejection is not evidence of a real public-IP browser network boundary.

In the retained positive fixture, the destination browser acquires source data, constructs a remote PageObject, and uses the normal fork action. pageHandler.put supplies a forkPage snapshot to origin.put. The wire request is an authenticated same-origin PUT with form-encoded action JSON. The server authorizes, stores the snapshot and appends its fork journal. That snapshot avoids requiring the server to fetch the user's localhost.

The source localhost:3000 was fulfilled by a disposable browser route. The fixtures used a real packaged client/server, a fixture security provider, and a real distinct-origin CORS-negative listener. They did not access the user's local Wiki or production pages. Production HTTPS, Local Network Access, cookie/authentication and actual public-to-local network behavior remain unverified.
