Reading the HyperDoc Authority Surface

The composition problem concerns several different relations. We can name them before choosing an implementation.

From a method to an invocation

Method applicability concerns dispatch: a method specialized on Page can participate when its generic function receives a Page. Our marker method is such a definition. Inspector discovery has its own selection rules, including superclass traversal and a one-argument filter; inspect the actual discovery functions rather than treating the list as a complete account of CLOS dispatch.

Inspectability means seeing a method and examining its definition. Invocation affordance means being offered a way to run it. The upstream Operations source supplies both a method reference and an Evaluate button. These are distinct offers.

Invocation authority asks whether this visitor may request that execution in this context. The current dreyeck evidence objects expose the marker's absent contract and the Page reader's observational contract. The dreyeck containment definitions withhold an unpermitted Evaluate offer and check again at typed thunk invocation. This is downstream containment, not an upstream library contract.

Capability, effect and verification

Runtime capability asks whether the runtime has the means to perform an operation; permission asks whether it may. Having a writer available, for example, would not establish permission to change a particular document.

For a changing operation, effect authority identifies what it may act on. Effect extent bounds which changes are permitted. Post-effect verification asks what observation would establish that the intended change, within those bounds, actually occurred.

Consider a hypothetical edit of one field in one document. Its authority might be that particular document in the state we inspected; its extent might be only that field; verification might reread the document and compare it with the expected result, including the unchanged remainder. This explains the concepts; it is not an operation implemented or executed by this reading.

The existing Page reader contract is the simpler observational case: it describes returning the Page ID with no change and requires no additional capability (:none). The behavioral witness checks its returned ID and that the Page ID remains unchanged. That check is not a general verification of all Page state.

Two other authority questions

Disclosure asks what an inspection may reveal. The pathname Items and Content definitions expose directory entries or file contents without changing those files. The same source group shows dreyeck's current root predicate. Describing permitted changes alone would not answer who may read those resources.

Authored evaluation asks why code supplied by a Page may run. The HTML generator and expression-link serialization source call PARSE-AND-EVAL during rendering, before an invocation button is clicked. This source-exposing example does not exercise or contain that route. Render-time evaluation remains unresolved and under investigation.

A later concrete example of the effect concepts

The existing dreyeck Work status contract applies these concepts to a status field in an HTML document. “Topic” here means the item described by a declaration in that document. The record identifies the observed declaration, bounds the intended change to its status character range, and calls for rereading the installed source and the item reconstructed from it. Its “authoring environment” names the runtime's supported source-writing means; owner permission is a separate requirement. These are contract statements, not evidence of a write performed here. The decision source checks capability separately from permission and presently grants only anonymous permission, so it does not implement owner authorization.
