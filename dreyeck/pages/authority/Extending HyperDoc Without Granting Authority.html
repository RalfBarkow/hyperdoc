Extending HyperDoc Without Granting Authority

The witnesses motivate an acceptance criterion for using HyperDoc as a library:

adding an applicable downstream method must not by itself grant remote invocation authority

This is a desired composition contract, offered for upstream discussion. The following purposes explain what we would need; they do not prescribe a particular set of APIs.

Keep discovery open; decide invocation separately

Automatically discovering downstream methods is useful. We want 👀operations to keep exposing real behavior and its source. Discovery should establish that a method is a candidate for this object. Whether a browser visitor may execute it is a separate decision. The upstream definition currently constructs Evaluate along with discovery; the dreyeck replacement is one experiment in separating them.

Make the description and decision inspectable

A reader should be able to inspect the operation, its target, possible effects, required authority, expected result and unresolved questions. For example, the adopted LOAD-PAGE definitions read source and update Page state; the Code Page method also evaluates SEE arguments. The current LOAD-PAGE record marks invocation authority unresolved. A useful Inspector can show that uncertainty alongside the definition.

The decision should explain why an operation is offered or refused here. The present decision objects demonstrate one representation. Could upstream expose a way for a downstream library user to supply and inspect such a decision? A decision protocol is a possible implementation; the requirement is an understandable, separate decision.

Enforce the decision when invoking

Hiding a button does not enforce authority. At server-side invocation the operation must still be permitted, its required capability present, and its target and authority current. The present method-thunk gate rechecks its limited contract decision, and the effect-free witness challenges that gate. It does not verify every target snapshot, effective method combination or evaluation path. Could the library provide an invocation boundary at which a downstream policy can enforce its decision?

Control disclosure independently

The pathname source illustrates why a non-writing view may still need authority. A library user needs to describe which resources a view may disclose and to whom. A view policy or source-root protocol might implement that purpose; neither a write-effect contract nor a hidden Evaluate button settles it.

Give authored evaluation its own account

The render-time source requires further questions: which source authority supplied this expression, why should rendering evaluate it, and what may it do? An evaluation context might be an extension seam, but we have not established its required contract. This class remains open.

The dreyeck containment replaces upstream methods and relies on internal seams, recorded by its adapter inventory. It is evidence for discussion, not a completed HyperDoc security architecture.
