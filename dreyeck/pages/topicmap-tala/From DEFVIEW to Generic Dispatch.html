From DEFVIEW to Generic Dispatch

DEFVIEW looks like a definition form. What did it actually install? Start at the existing 👀tala-input view. Its source says (views:defview 👀tala-input (input tala:tala-input) ...). These examples observe the loaded SBCL image, without scratch globals and without running the TALA renderer.

What is bound to the name?

reading-view-generic-function

A STANDARD-GENERIC-FUNCTION, not the view. The view returned when that function is called is a different object. On first registration DEFVIEW creates the generic function with a primary method specialized on T returning nil and an :around method specialized on T that attaches object and method metadata to returned views. It registers the view function, then defines the primary method specialized on TALA:TALA-INPUT.

Where do its methods live?

reading-view-workspace reading-view-projection

Open the Workspace's native Topicmap. Its point denotes the same generic function. Follow :has-method to a method, :defined-by to its definition source, and :source-file to the file. The existing Lisp-image projection owns these relations; missing source metadata is not replaced by an invented location.

The method Topics keep the live STANDARD-METHOD as their object, so METHOD-QUALIFIERS and METHOD-SPECIALIZERS read the same objects from there. The specializer reached through the projection is EQ to (find-class 'tala:tala-input). This page once carried a separate example that returned methods with their specializers; it was removed when that EQ identity was measured, because the projection had never lost what the example claimed to preserve. The page's own reading test still makes that measurement, so the sentence stays falsifiable.

What is not asserted

One method is specialized on TALA:TALA-INPUT, and that is observable. It does not follow that a SPECIALIZED-ON association should be created in order to teach the fact. Inspect the specializer as the class of the argument the method is defined for; the method belongs to the generic function, not to the class. No new Topic type, association type or Workspace kind is introduced by this reading.

Which view operations are generic?

reading-view-operations

In this image OBJECT-REF and ALL-VIEWS are ordinary functions; VIEW-REFERENCES and VIEW-HTML are generic accessors. Do not infer generic dispatch from an operation's name. These four have no projection on this page, so the example carries their methods itself. An accessor's generic-function source record can have no pathname even when its accessor and :before methods have file-backed sources; that absence is preserved rather than filled in.

Read alongside the observations

Peter Seibel, Practical Common Lisp (Apress, 2005), chapter 16, “Object Reorientation: Generic Functions”, explains how methods implement an operation and specialize its behavior for arguments. Use the three methods above as a concrete example of primary and qualified methods belonging to one operation. Chapter 17, “Object Reorientation: Classes”, explains class definitions, inheritance, and slots.

These chapter connections are authored reading suggestions. The observed program graph does not assert that a method requires a chapter or that one chapter precedes another. A warranted learning relation would need its own explicit authorship and evidence contract; this page leaves that relation in prose rather than introducing a new Topicmap ontology.
