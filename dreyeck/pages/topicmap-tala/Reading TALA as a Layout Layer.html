Reading TALA as a Layout Layer

TALA is an experimental Layout-layer rendering backend. One existing HyperDoc Git repository/HEAD projection supplies both views: the same Topics, Associations and endpoints, Workspace point, and native Inspector navigation thunks. Only derived layout differs. The native renderer remains the default.

Load dreyeck/topicmap/tala/reading in nix develop .#tala. Press the existing ► source buttons below to evaluate examples. Each starts from the real current repository, with no manually initialized globals. Separate clicks create separate observations; the comparison holds one shared Projection for both renderings.

Cross the adapter boundary

The TALA open-source announcement introduces the engine bundled in D2 0.9.0. The source links on this page are fixed to D2 commit d5a51743b6d5c00f1ec6f8340003f5d5a6ba4eda.

Read the README for the layout entry point and explicit seeds, then ARCHITECTURE.md for translation, candidate placement, routing and selection. Why a separate representation? The optimizer needs mutable geometric state. HyperDoc's semantic objects remain outside that state.

HyperDoc's corresponding boundary is projection-tala-input. It sorts copies, uses seed 44, encodes Topic IDs reversibly, and keeps Association IDs and endpoints in an explicit map. Labels are presentation; they never become identity. Manual positions and Workspace point are excluded from D2 input.

reading-layout-input reading-id-mapping

In upstream adapter.go, translation maps connect D2 entities to the layout graph. HyperDoc similarly retains an explicit mapping, but sends only derived D2 text to a subprocess. No TALA mutation reaches its Projection.

Observe derived geometry

Check availability first. Missing D2, an unsupported version, or invalid output is an explicit error; no hidden renderer fallback occurs. The optional Nix shell supplies checksum-pinned D2 0.9.0 with bundled TALA.

reading-dependency reading-layout-result reading-geometry

The CLI returns SVG. This slice is a static SVG rendering proof: inspect rectangles, viewboxes, route paths and their matched Topic/Association IDs. It does not claim a normalized numeric Topicmap layout API. Exact SVG group coverage is checked against encoded IDs, never inferred from label text or spatial proximity. A later machine-geometry adapter can feed native signs without changing this semantic boundary.

Read candidate_movement.go for candidate movement and restoration, edge_length.go for geometric cost, and route.go for ports and path segments. These change placement or routes; none defines a new HyperDoc relation.

Check preservation, then compare

Upstream result.go validates and scores completed candidates before selection. HyperDoc checks its own boundary: unchanged Projection state, exact Topic/Association coverage and endpoints, and unchanged point/history during layout. Its report is preservation evidence, not TALA's quality score.
