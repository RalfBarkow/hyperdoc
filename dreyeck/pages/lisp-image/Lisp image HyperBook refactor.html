Lisp image HyperBook refactor

dreyeck/lisp-image

This page is the executable reading path for moving the Lisp-image browsing functionality from the historical hauptsache branch into dreyeck.ch-owned subsystems.

The immediate problem is that the Lisp functions and Lisp classes HyperBooks describe themselves as containing one page for each corresponding symbol in the Lisp image, while the current implementations do not expose all of those definitions as a browseable page collection.

0. Which HyperDoc owns this page?

An ASDF static-file component does not by itself make an HTML file a page of an arbitrary HyperDoc. A HyperDoc discovers text pages in its own configured directory.

Before restoring any historical implementation, observe what the currently loaded Lisp functions and Lisp classes HyperBooks can already do.

First distinguish direct lookup from enumeration. A HyperBook may be able to construct a page for a package-qualified symbol whose name is already known without offering a way to browse all such pages in the running Lisp image.

5. Model the running Lisp image

The current Lisp functions and Lisp classes HyperBooks can be addressed directly, but their current inspector views do not include Loaded functions or Loaded classes.

Before adding such views, model enumeration independently of HyperBook page construction. The dreyeck.ch-owned inventory records which home-package symbols in the running Lisp image satisfy the relevant predicates and assigns each one a package-qualified page identifier.

5.1 Construct a fresh inventory

lisp-image-inventory-example

Inspect the returned Lisp-image inventory. It contains separate collections for function-bound symbols and symbols with class definitions. Each entry records the symbol, its home package, whether it is internal or external, and the package-qualified page identifier that could later be used to address a HyperBook page.

Function enumeration deliberately uses FBOUNDP without yet assuming that every such name can be turned into a page by the current Lisp functions HyperBook. Enumeration and page construction remain separate concerns at this stage.

6. Observe transfer from inventory to HyperBook pages

Membership in the function inventory is established with FBOUNDP. That does not yet establish that the current Lisp functions HyperBook can construct a page for every inventory entry.

Compare representative function-bound names with different language roles: CAR as an ordinary function, WHEN and SETF as macros, and IF as a special operator.

lisp-function-inventory-transfer-example

For each name, the observation records its inventory entry, FBOUNDP, MACRO-FUNCTION, SPECIAL-OPERATOR-P, and the result of asking the current Lisp functions HyperBook for the corresponding page. Lookup failures are retained as inspectable conditions instead of aborting the observation.

This distinguishes two contracts that the historical implementation combined: deciding which names belong to the running Lisp-image inventory, and deciding which of those names can be represented by the existing HyperBook page model.

In the current SBCL image, all four representative names transfer successfully from inventory membership to existing Lisp-function HyperBook pages. This includes an ordinary function, macros, and a special operator.

The representative observation therefore does not justify changing the current Lisp-function lookup implementation. Before adding browseable Loaded views, audit the same transfer over the complete function and class inventories.

7. Audit the complete inventory transfer

The representative function names all transfer successfully to pages of the existing Lisp functions HyperBook. That is not yet evidence that every inventory entry does.

Audit the complete function and class inventories without changing either HyperBook. The observation counts successful and unsuccessful page lookups and retains a small sample of page identifiers for any failures.

lisp-image-inventory-transfer-audit-example

If the failure counts are zero, the existing HyperBooks already provide the page-construction contract needed by the inventory; dreyeck.ch can then add browseability by projecting inventory entries through the existing FIND-PAGE methods rather than duplicating the HyperBook page implementations.

If failures remain, inspect those failures before changing page lookup behavior.

8. Inspect function page identifier failures

The earlier complete transfer audit exposed a small set of function inventory entries whose raw package-qualified identifiers did not survive Lisp reader round-trip.

After introducing reader-safe package-qualified identifiers, the current failure count should be zero. The earlier failures motivated the identifier work in the following section; they were not missing function definitions.

9. Make package-qualified page identifiers reader-safe

A Lisp-image page identifier must read back as the identical symbol. Familiar identifiers are retained when they already satisfy that contract; otherwise package and symbol tokens are escaped.

lisp-image-inventory-transfer-audit-example

The current running image now transfers every function and class inventory entry through the existing HyperBooks. The earlier function-page failures were identifier serialization failures, not lookup failures.

10. Project inventory entries through the existing HyperBooks

The complete transfer audit establishes that every current inventory entry can be resolved by the existing Lisp functions or Lisp classes HyperBook. Make that relation explicit without introducing another page model.

lisp-image-page-projection-example

Inspect the representative projections. Each starts with a dreyeck.ch-owned inventory entry, selects the HyperBook responsible for that entry kind, and delegates page construction to that HyperBook's existing FIND-PAGE method.

The inventory therefore remains responsible for enumeration and reader-safe identifiers, while the existing HyperBooks remain responsible for their page objects.

11. Project complete inventories to page collections

Representative inventory entries can already be projected through the existing Lisp functions and Lisp classes HyperBooks. Apply the same projection to the complete inventories and retain the resulting pages as explicit collections.

lisp-image-page-collections-example

Each collection retains its inventory entries, the HyperBook responsible for resolving them, and the resulting page objects. The entry and page counts should agree for both collections.

This collection layer does not introduce another page implementation. Enumeration remains dreyeck.ch-owned, while page construction remains delegated to the existing HyperBooks.

12. Expose the page collections as Loaded views

The complete function and class inventories project without loss to page collections owned by the existing HyperBooks. The remaining step is presentation: expose those collections as inspector views on the Lisp functions and Lisp classes HyperBooks.

lisp-image-loaded-views-example

The view methods are Dreyeck-owned extensions. They specialize on the existing HyperBook objects, construct fresh Lisp-image inventories, project those inventories to the existing page model, and render the resulting pages with LIST-VIEW.

Neither Lisp HyperBook acquires a second enumeration implementation, and page ownership remains unchanged.
