Lisp image HyperBook refactor

dreyeck/lisp-image

This page is the executable reading path for moving the Lisp-image browsing functionality from the historical hauptsache branch into Dreyeck-owned subsystems.

The immediate problem is that the Lisp functions and Lisp classes HyperBooks describe themselves as containing one page for each corresponding symbol in the Lisp image, while the current implementations do not expose all of those definitions as a browseable page collection.

0. Which HyperDoc owns this page?

An ASDF static-file component does not by itself make an HTML file a page of an arbitrary HyperDoc. A HyperDoc discovers text pages in its own configured directory.

lisp-image-page-ownership-example

1. Observe the current Lisp HyperBooks

Before restoring any historical implementation, observe what the currently loaded Lisp functions and Lisp classes HyperBooks can already do.

First distinguish direct lookup from enumeration. A HyperBook may be able to construct a page for a package-qualified symbol whose name is already known without offering a way to browse all such pages in the running Lisp image.

1.2 Views of the two HyperBooks

If direct lookup succeeds while the two Loaded views are absent, the missing capability is narrower than page lookup: the current HyperBooks are addressable but do not expose the running Lisp image as a browseable collection.

4. Separate the behavior we want from adjacent changes

The historical diff contains more than one concern. The following example separates inventory and browsing signals from lookup hardening signals.

lisp-image-hauptsache-contract-example

The inventory side contains package-qualified symbol names, collection of function and class pages, and the Loaded functions and Loaded classes views. The same historical diff also contains changes to lookup behavior and lookup-issue construction.

Our current refactoring hypothesis is therefore narrower than copying the hauptsache files: first recover Lisp-image enumeration and browseability as Dreyeck-owned functionality. Lookup hardening remains a separate question until its necessity has been observed independently.

Next observation

If the current HyperBooks support direct lookup while Loaded functions and Loaded classes are absent, the next step is to model Lisp-image enumeration as dreyeck.ch-owned functionality.

That next observation should enumerate function and class definitions in the running Lisp image without yet adding inspector views or changing the existing HyperBook implementations. The resulting inventory can then be inspected independently before it is connected to browseable Loaded views.
