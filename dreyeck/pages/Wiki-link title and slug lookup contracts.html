Wiki-link title and slug lookup contracts

dreyeck/wiki-link-contract-demo

This page provides an executable arrangement for observing and retracing title and slug lookup behavior for FedWiki links. It does not assume that the behavior is a bug, and it does not propose a correction. Its purpose is to make the relevant operations and their observable consequences retraceable in one running HyperDoc image.

A WIKI-LINK stores target title and target slug separately. Its HB:KEY-OF method uses the stored target slug. The examples below compare observable behavior without deciding in advance which lookup contract is intended.

How to retrace the observation

Run the four examples in order by selecting their ► actions:

  1. Compare title lookup and slug lookup for an existing target.
  2. Execute the expression found in the investigated upstream revision.
  3. Execute direct slug lookup on the same missing-target fixture.
  4. Execute the real stored thunk of the currently loaded implementation.

Each example returns an inspectable observation object. Expected lookup failures are caught and represented as data; they do not enter the debugger. This makes it possible to compare the supplied values, the selected operation, and the resulting failure evidence directly.

What can be observed?

1. Existing target: equal local effects

The first example creates an in-memory wiki at example.test and installs one target page. It then looks up that page once by its human-readable title and once by its canonical slug.

In this case both operations determine the same page because normalizing the already canonical slug leaves it unchanged. The example therefore demonstrates a local equality of effects: 

title lookup ─┐
              ├─ determines the same target page
slug lookup  ─┘

This result does not establish that the two operations accept the same kind of input, preserve the same evidence, or have the same contract.

wiki-link-successful-lookup-equivalence-example

2. Expression observed in the upstream revision

At upstream commit 0d5bd1b, the stored link thunk contained the following expression: 

(find-target-by-title target-slug source-page)

The value supplied to FIND-TARGET-BY-TITLE is therefore the already stored target slug. For an existing target, applying slug normalization again can still lead to the expected page. For a missing target, however, the resulting condition makes the selected operation observable.

With the fixture used here, the condition records "missing-human-title" both as slug evidence and as title evidence: 

condition slug:  "missing-human-title"
title bound:     T
condition title: "missing-human-title"

The example currently reports RED under the explicitly stated strict slug-contract hypothesis. This is a conditional classification, not a general judgment that the upstream behavior is erroneous.

wiki-link-upstream-title-path-example

3. Comparison expression: direct slug lookup

The next example executes a different operation on the same stored slug and the same missing-target fixture: 

(find-target-by-slug target-slug source-page)

In this trace, the missing slug is recorded as slug evidence, while no title evidence is bound: 

condition slug:  "missing-human-title"
title bound:     NIL
condition title: NIL

The example currently reports GREEN under the same strict slug-contract hypothesis. The direct slug expression is included as a comparison operation. On this page it is not yet presented as a proposed correction.

wiki-link-strict-slug-path-example

4. Stored thunk of the currently loaded implementation

The final example does not reproduce either expression manually. It creates a real link with MAKE-WIKI-LINK, obtains its stored thunk through HB:THUNK-OF, and evaluates that thunk through VIEWS:EVAL-THUNK.

It then compares the resulting missing-target evidence with the two traces shown above and reports one of:

  • MATCHES-TITLE-PATH
  • MATCHES-SLUG-PATH
  • OTHER

This classification describes the behavior installed in the currently running Lisp image. It does not by itself determine which behavior is intended.

What follows from the examples?

The four executions support the following limited observations:

  • WIKI-LINK preserves target title and target slug as distinct values.
  • HB:KEY-OF uses the stored target slug.
  • Title lookup and direct slug lookup can determine the same existing page.
  • Their missing-target traces can nevertheless preserve different evidence.
  • The investigated upstream expression passes the stored slug to FIND-TARGET-BY-TITLE.
  • The behavior of the currently running implementation can be observed independently through its real stored thunk.

These observations do not establish the intended lookup contract or the intended meaning of the condition slots.

Which contracts are compatible with the observation?

Hypothesis A: distinct title and slug contracts

Under this hypothesis, FIND-TARGET-BY-TITLE accepts a human title, derives its canonical slug, and preserves both the supplied title and the derived slug as failure evidence.

FIND-TARGET-BY-SLUG accepts an already canonical lookup key and preserves only slug evidence. Because the stored thunk already has TARGET-SLUG, passing that value to the title operation would cross the two input contracts.

Under this hypothesis, the two example classifications RED and GREEN distinguish non-conforming and conforming traces.

Hypothesis B: normalization-tolerant locator resolution

Under this hypothesis, FIND-TARGET-BY-TITLE is not restricted to human-readable titles. It acts as a normalizing resolver that may accept either a title or an already canonical slug.

Re-normalizing a canonical slug would then be intentional defensive behavior. The observed successful lookup would be an instance of the intended representation tolerance.

This interpretation raises a different set of questions about names and failure evidence: the operation called FIND-TARGET-BY-TITLE would have a broader locator contract, and the condition slot called TITLE might contain a value that was supplied as a slug.

Hypothesis C: the TITLE slot records the supplied locator

A further possibility is that the condition slot named TITLE is intended to preserve the originally supplied lookup expression rather than specifically a human-readable page title.

Under this interpretation, binding the slug in that slot would not necessarily be incorrect, but the names TITLE and FIND-TARGET-BY-TITLE would require a broader reading than their ordinary wording suggests.

Questions left open

  • Is FIND-TARGET-BY-TITLE intended to accept only human titles, or is it a generic normalizing locator resolver?
  • What distinct role is intended for FIND-TARGET-BY-SLUG?
  • Does the condition slot TITLE mean a human page title, the original lookup input, or something else?
  • Is the distinction between TARGET-TITLE and TARGET-SLUG intended only for presentation and keying, or also for selecting the lookup operation?
  • Should missing-target evidence preserve the representation in which the lookup value was supplied?

Scope of the demonstration

This page is an observation and discussion aid. It does not decide whether the upstream expression is a bug, a compatibility feature, or an instance of a more general locator contract. It also does not recommend a patch.

All four examples use private in-memory fixtures under example.test. During missing-target lookup they suppress the plugin-page fallback locally and restore the original function afterward. They do not read ~/.wiki, contact a wiki, or write durable data.
