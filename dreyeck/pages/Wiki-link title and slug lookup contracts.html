Wiki-link title and slug lookup contracts

dreyeck/wiki-link-contract-demo

This page provides four executable examples of FedWiki title and slug lookup. It separates what the running code did from how that evidence can be read and from the contract questions that remain open. It does not change or prescribe production lookup behavior.

A WIKI-LINK stores target title and target slug separately. Its HB:KEY-OF method uses the stored target slug.

1. Observed execution evidence

Each executable example returns a fact-preserving record of one lookup execution: a WIKI-LINK-LOOKUP-OBSERVATION containing only three facts:

  • ROUTE: TITLE, SLUG, or INSTALLED;
  • LOOKUP-VALUE: the exact string supplied to the lookup, or the target slug captured by the installed thunk;
  • OUTCOME: the actual FedWiki page returned or the actual WIKI-LOOKUP-FAILURE condition observed.

The execution-and-recording helper catches only WIKI-LOOKUP-FAILURE. A normal NIL or non-page return is rejected, and unrelated conditions escape unchanged. The successful-page check intentionally uses the internal FEDWIKI-PAGE class: this is a small, explicit white-box dependency of the demonstration.

Example 1: existing target

A fresh in-memory wiki receives one target page. The example invokes FIND-TARGET-BY-TITLE with "Existing Human Title" and FIND-TARGET-BY-SLUG with "existing-human-title". It returns two observations, each retaining the page object returned by its lookup. Applying SAME-RESOLVED-TARGET-P to them demonstrates the fixture's object-identity claim with EQ. 

title lookup ─┐
              ├─ same returned page object
slug lookup  ─┘

Equal local effects do not establish that the operations accept the same representation or preserve the same failure evidence.

Example 2: historic title operation supplied with a slug

At upstream commit 0d5bd1b, the investigated stored link thunk contained this expression: 

(find-target-by-title target-slug source-page)

The example invokes that real title operation with the missing target slug "missing-human-title". The retained condition has the same string as slug evidence and as bound title evidence. The observation itself does not store a classification of those facts.

Example 3: direct slug operation

A separate fresh fixture invokes the real slug operation with the same missing slug: 

(find-target-by-slug target-slug source-page)

Its retained condition contains matching slug evidence and leaves the title slot unbound. Again, the observation records the condition rather than a prepared report about it.

Example 4: currently installed Wiki-link thunk

The final example creates a real link with MAKE-WIKI-LINK, obtains its stored wrapper through HB:THUNK-OF, and invokes it through VIEWS:EVAL-THUNK. That invocation protocol is retained because the stored value is an inspector thunk wrapper, not a function that can be passed directly to FUNCALL.

Its route is INSTALLED, its lookup value is the target slug captured by the link, and its outcome is whatever the real installed thunk produces. Extraction or invocation errors are not converted into evidence.

wiki-link-installed-thunk-example

The missing-target examples temporarily replace GET-PLUGIN-PAGE and restore its original symbol function with UNWIND-PROTECT. That replacement is global, serial-only, and not safe for concurrent execution. Every example constructs its own in-memory wiki and source page; there is no shared or memoized fixture.

2. Derived reading

The raw observation can be queried without changing it. WIKI-LINK-LOOKUP-RESOLVED-P distinguishes a returned page from a lookup failure. WIKI-LINK-LOOKUP-EVIDENCE-SHAPE reads only the outcome, lookup value, condition slug, and condition title boundness and value. It returns one of:

  • TITLE-AND-SLUG-EVIDENCE
  • SLUG-ONLY-EVIDENCE
  • OTHER
  • NOT-APPLICABLE

OTHER has a narrow meaning: the expected lookup-failure type occurred, but its values or slot boundness match neither familiar form. It never represents an arbitrary runtime error, failed thunk extraction, or invalid normal return. NOT-APPLICABLE means that lookup resolved.

The route is deliberately absent from evidence-shape derivation. WIKI-LINK-ROUTE-EVIDENCE-RELATION compares the declared route with that independently derived shape and returns CONSISTENT, INCONSISTENT, NOT-DECLARED, or NOT-APPLICABLE. Thus a future change in observed evidence appears as a mismatch rather than being classified according to the route that was expected.

Declared route Derived evidence Relation
TITLE TITLE-AND-SLUG-EVIDENCE CONSISTENT
SLUG SLUG-ONLY-EVIDENCE CONSISTENT
TITLE SLUG-ONLY-EVIDENCE INCONSISTENT
SLUG TITLE-AND-SLUG-EVIDENCE INCONSISTENT
INSTALLED any failure evidence NOT-DECLARED

INSTALLED-LOOKUP-PATTERN maps only the actual retained outcome to MATCHES-TITLE-PATH, MATCHES-SLUG-PATH, OTHER, or RESOLVED. It does not absorb unexpected conditions.

Red and green remain useful as a visual and conversational diff metaphor: they identify the two compared execution paths. They are not stored runtime classifications, they do not by themselves mean wrong and right, and they are not the runtime vocabulary. The runtime vocabulary is TITLE-AND-SLUG-EVIDENCE, SLUG-ONLY-EVIDENCE, OTHER, and NOT-APPLICABLE.

3. Open contract hypotheses

Hypothesis A: distinct title and slug contracts

Under this hypothesis, FIND-TARGET-BY-TITLE accepts a human title, derives its canonical slug, and preserves both supplied title and derived slug as failure evidence. FIND-TARGET-BY-SLUG accepts an already canonical key and preserves only slug evidence. Supplying a stored slug to the title operation would cross those input contracts.

Hypothesis B: normalization-tolerant locator resolution

Under this hypothesis, FIND-TARGET-BY-TITLE is a normalizing resolver that intentionally accepts either a title or an already canonical slug. Re-normalizing a slug is representation tolerance rather than a contract crossing. This raises a naming question because a slot called TITLE can then retain a value supplied as a slug.

Hypothesis C: TITLE records the supplied locator

A further possibility is that the condition's TITLE slot is meant to retain the original lookup expression rather than specifically a human-readable page title. Binding a slug there would not necessarily be incorrect, but the ordinary reading of the operation and slot names would be broader than their wording suggests.

Questions left open

  • Is FIND-TARGET-BY-TITLE restricted to human titles or is it a generic normalizing locator resolver?
  • What distinct role is intended for FIND-TARGET-BY-SLUG?
  • Does the condition slot TITLE mean a human page title, the original lookup input, or something else?
  • Is the title/slug distinction intended only for presentation and keying, or also for selecting the lookup operation?
  • Should failure evidence preserve the representation in which the lookup value was supplied?

These observations do not decide whether the historic expression is a bug, a compatibility feature, or an instance of a broader locator contract.
