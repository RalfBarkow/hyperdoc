How SHOP3 Reads the Architecture Task

SHOP3 ist ein hierarchischer Aufgabenplaner. Man gibt ihm eine Aufgabe, Wissen über die angenommene Situation und Regeln, wie Aufgaben zerlegt werden dürfen. Er arbeitet die Aufgabe in der Reihenfolge ihrer Zerlegung ab. Eine passende Zerlegung liefert einen Plan aus primitiven Schritten; fehlt eine notwendige Bedingung, ist dieser Weg nicht anwendbar.

Die vier Begriffe an einem Beispiel

Die Aufgabe sagt, was erreicht werden soll, ohne den Zugangsweg festzulegen:

(enable-mobile-control zettelkasten macbook-a android)

Eine Methode erklärt, wie diese abstrakte Aufgabe in kleinere Aufgaben zerlegt wird. Hier gibt es zwei getrennte Methodendefinitionen für dieselbe Aufgabe. Die Agentenmethode benötigt eine Agentensitzung; die direkte Methode benötigt einen direkten Transport. Beide verlangen Application API, hypothetische Autorisierung und lokale Zuständigkeit.

Ein Operator ist ein primitiver Schritt, der nicht weiter zerlegt wird. In diesem Experiment fügt er ausschließlich dem simulierten Zustand Fakten hinzu. Der Operator !model-agent-route hält beispielsweise fest, dass der Agentenweg modelliert gewählt wurde. Er richtet keine Sitzung ein.

Der Zustand ist die Menge der Fakten, mit denen SHOP3 rechnet. Eine Aussage wie (authorized android zettelkasten) ist hier ein hypothetisches Faktum. Sie ist kein Zugriffstoken und keine Zustimmung einer Person. Der Planer kann nur mit den Bedingungen rechnen, die die Domain überhaupt beschreibt.

Zwei Methoden, keine erfundene dritte Lösung

Das frühere Dokumentationsexperiment zerlegte eine Aufgabe in eine einzige feste Schrittfolge. Es erhielt deshalb Bewertung B. Die jetzige Domain enthält zwei vorgegebene Alternativen. SHOP3 erfindet sie nicht: Sein zusätzlicher Beitrag ist, ihre Anwendbarkeit für verschiedene Eingaben zu prüfen und beide gültigen Zerlegungen aufzuzählen.

Der Runner verwendet :which :all und :plan-tree t. Er behält Pläne, Rechenzeit, Planbäume und Endzustände im vorhandenen HyperDoc-Planresultat. Eine leere Menge von Lösungen bedeutet hier „kein Plan“. Das wäre etwas anderes als ein gültiger Plan ohne weitere Schritte.

Der SHOP3-Aufgabenfall, die tatsächlichen Methoden und das berechnete Resultat erlauben den Übergang von dieser Erklärung zur Implementierung. Diese Objekte bleiben die Autorität für die berechneten Pläne.

Offene Frage. Ob diese beiden Zugangswege für eine reale Anwendung tragfähig sind, ist damit noch nicht entschieden. Der Planer prüft das Modell, nicht dessen Vollständigkeit gegenüber einer realen Installation.
