How SHOP3 Reads the Architecture Task

SHOP3 is a hierarchical task planner. Its inputs are a task, facts about the assumed situation, and rules for decomposing tasks. It works through a task in the order specified by its decomposition. An applicable decomposition yields a plan of primitive steps; if a necessary condition is missing, that approach is inapplicable.

Four concepts in one example

The task states what should be achieved without selecting an access route:

(enable-mobile-control zettelkasten macbook-a android)

A method explains how to decompose this abstract task into smaller tasks. Here, two separate method definitions address the same task. The agent method requires an agent session; the direct method requires a direct transport. Both require an Application API, hypothetical authorization, and local authority.

An operator is a primitive step that is not decomposed further. In this experiment, it adds facts only to the simulated state. For example, !model-agent-route records the modeled selection of the agent route. It does not establish a session.

The state is the set of facts with which SHOP3 reasons. A statement such as (authorized android zettelkasten) is a hypothetical fact here. It is neither an access token nor a person's consent. The planner can reason only about conditions that the domain describes.

Two methods, without inventing a third solution

The earlier documentation experiment decomposed a task into a single fixed sequence. It therefore received verdict B. The present domain contains two predefined alternatives. SHOP3 does not invent them: its additional contribution is to check their applicability for different inputs and enumerate both valid decompositions.

The runner uses :which :all and :plan-tree t. It retains plans, CPU time, plan trees, and final states in the existing HyperDoc plan result. An empty set of solutions means “no plan” here. That differs from a valid plan requiring no further steps.

The SHOP3 problem instance, the actual methods, and the computed result connect this explanation to the implementation. These objects remain the authority for the computed plans.

Open question. This does not yet establish whether either access route is viable for a real application. The planner checks the model; it does not establish that the model completely describes a real installation.
