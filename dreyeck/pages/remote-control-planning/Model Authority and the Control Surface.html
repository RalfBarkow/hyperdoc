2 of 6 · The boundary between model and control surface

Model Authority and the Control Surface

A user action and its effect on the domain model are distinct. The phone can display the selected note and formulate a request to change it. The local runtime decides whether that request becomes a valid change and how to persist it. Both planning alternatives share this assignment of authority.

What should remain local

Execution authority means that the MacBook application performs domain operations. Model authority means that its local Zettelkasten model is the authoritative instance for those operations. The mobile control surface presents commands and results. This separation does not by itself make remote access secure; it identifies where permission checks and consistency guarantees would have to be enforced.

Why existing ports are not yet a remote API

In the inspected ZettelkastenFX revision, zk-core excludes UI and storage implementations from its core. Repository ports describe domain access; SQLite implements the storage adapters. The ZKN3 source adapter reads interchange data into an import batch. These boundaries suggest an architectural direction. They define neither a remote command nor an agent session.

The core boundary test and the ZKN3 reader port are sources for this account. The documented boundaries are not evidence of implemented mobile control.

Modeled assumption. The planning state contains (execution-authority zettelkasten macbook-a) and (model-authority zettelkasten macbook-a). Both methods require these facts; no operator removes them or transfers authority to Android.

The initial facts of Case C make this decision explicit. A future implementation would have to enforce the boundary in practice. Here, the planner checks only that its symbolic description preserves it.
