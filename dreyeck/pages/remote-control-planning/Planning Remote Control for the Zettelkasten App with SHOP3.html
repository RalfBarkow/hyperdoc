Planning Remote Control for the Zettelkasten App with SHOP3

Zettelkasten runs on the MacBook. Someone using an Android device wants to select a note or request a change. What must connect these two places so that control becomes mobile while responsibility for data and execution stays with the local application? This question from Zettel 11551 guides the reading.

A network connection alone does not answer the architecture question. An interface can send a request; the local application must understand it, determine whether it is permitted, and execute it against its domain model. A second copy of the model on the phone would introduce further questions about synchronization and conflicting changes. This experiment specifically examines the separation of local execution from mobile control.

Modeled assumption. Two approaches could support this separation: a remote agent session with local access to an Application API, or a direct HTTP/WebSocket adapter for a browser/PWA interface. Their availability is an input to the experiment, not an observation about installed services.

One question, two possible approaches

On the agent route, a session connects Android to a local agent or MCP client. On the direct route, the mobile interface communicates with an application adapter. In both cases, the Application API remains a local domain boundary. The methods differ in how they provide access, while preserving model ownership.

SHOP3 acts as the planner: it checks assumed prerequisites and decomposes a shared task into possible steps. It starts no agent and opens no connection. We first explain why both approaches must respect the same boundary, then examine why the planner sometimes produces two answers and sometimes none.

Observed evidence. The first slice's Cloud tests produced two plans for Case C. The assignment for this reading also reports that Case C is accessible in the local CLOG Inspector and shows :plan-only. This does not establish successful mobile control.
