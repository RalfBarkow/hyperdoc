Planning Remote Control for the Zettelkasten App with SHOP3

Auf dem MacBook läuft der Zettelkasten. Auf dem Android-Gerät möchte jemand einen Zettel auswählen oder eine Änderung anstoßen. Was muss zwischen diesen beiden Orten liegen, damit die Bedienung mobil wird, die Verantwortung für Daten und Ausführung aber bei der lokalen Anwendung bleibt? Diese Frage aus Zettel 11551 führt durch dieses Buch.

Die naheliegende Verbindung über ein Netz löst die Architekturfrage noch nicht. Eine Oberfläche kann einen Wunsch senden; die lokale Anwendung muss ihn verstehen, seine Zulässigkeit beurteilen und ihn gegen ihr fachliches Modell ausführen. Eine zweite Modellkopie auf dem Telefon würde dagegen zusätzliche Fragen nach Synchronisation und widersprüchlichen Änderungen eröffnen. Dieses Experiment untersucht bewusst die Trennung von lokaler Ausführung und mobiler Bedienung.

Modellierte Annahme. Zwei Wege könnten diese Trennung tragen: eine entfernte Agentensitzung mit lokalem Zugriff auf eine Application API oder ein direkter HTTP-/WebSocket-Adapter für eine Browser-/PWA-Oberfläche. Ihre Verfügbarkeit ist eine Eingabe des Experiments, kein Befund über installierte Dienste.

Eine Frage, zwei mögliche Wege

Beim Agentenweg vermittelt eine Sitzung zwischen Android und einem lokalen Agenten beziehungsweise MCP-Client. Beim direkten Weg spricht die mobile Oberfläche mit einem Adapter der Anwendung. In beiden Fällen bleibt die Application API eine lokale fachliche Grenze. Die Methoden unterscheiden den Zugang, nicht den Besitzer des Modells.

SHOP3 wird hier als Planer eingesetzt: Es prüft angenommene Voraussetzungen und zerlegt eine gemeinsame Aufgabe in mögliche Schritte. Es startet keinen Agenten und öffnet keine Verbindung. Erst wird erklärt, warum beide Wege dieselbe Grenze respektieren müssen; dann lässt sich verstehen, warum der Planer manchmal zwei Antworten und manchmal keine liefert.

Beobachtete Evidenz. Die Cloud-Tests des ersten Slices lieferten für Fall C zwei Pläne. Der Auftrag zu dieser Lektüre berichtet zusätzlich, dass Fall C lokal im CLOG Inspector erreichbar ist und :plan-only zeigt. Daraus folgt keine erfolgreiche mobile Bedienung.

Der Lesepfad

  1. Diese Architekturfrage stellt das Ziel.
  2. Modell und Control Surface klärt die Zuständigkeit.
  3. Die Sprache von SHOP3 erklärt das Planen.
  4. Fall C verfolgt die beiden Zerlegungen.
  5. Fälle D und E erklären ausbleibende Pläne.
  6. Evidenz und offene Abnahme begrenzt die Aussage.

Wer schon jetzt das Untersuchungsobjekt sehen möchte, kann den tatsächlichen Fall C öffnen. Für das Verständnis der beiden Alternativen ist dieser Schritt noch nicht nötig. Der Bezug auf Zettel 11551 übernimmt Titel und Architekturziel aus dem Auftrag; die produktive ZKN3-Datenquelle wurde nicht geöffnet.
