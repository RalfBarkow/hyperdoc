Locate the task before declaring a problem

The problem-bestimmen workflow uses the distinction from Zettel 6129 (Simon 48.2): a problem is a task that existing routines of behavior, action or interaction cannot solve. Task Location (Zettel 8992) first asks where the task belongs in the existing learned task space. A failed first lookup is not evidence that no routine exists.

  1. State the task as an observable outcome, not as a preferred implementation.
  2. Locate existing routines, their inputs, ownership, effects and applicable constraints.
  3. Check whether an existing routine covers the whole task or only part of it.
  4. When relevant, let SHOP3 expose alternative existing decompositions, retaining native plans and :PLAN-ONLY provenance.
  5. Only if the task remains unsolvable with the available routines, specify the gap as a problem and search for another method.

This page records the inquiry; it does not claim that the complete task space has been searched or that HyperDoc provides an automatic task-location planner. The interactive development-shell orientation is in docs/task-location-before-problem.md, also available as hyperdoc-dev task-location on this branch.

Concrete task: local presence of a linked page

The real S1 capture from ward.asia.wiki.org acquired Safe and Familiar Welcome as HTTP response bytes and hydrated an offline native FedWiki page. Its Story has 17 Items and its Journal 28 actions. Item 12 links to making-the-welcome-page. Wards recorded sitemap contains that slug. Those facts describe the source, not our local destination.

Task: Determine whether the destination wiki contains making-the-welcome-page, preserving the identity of the source relation and distinguishing observed presence, confirmed local absence and read failure. The destination wiki is not yet selected.

Problem assessment and next observation

Not yet established as a new problem. There is an unanswered choice of local destination and a possible SQLite persistence adaptation; neither proves that existing routines cannot answer the task. A deliberately empty SQLite test database could only establish absence in that database, not in an already existing wiki. Do not infer local absence from Wards sitemap or from the S1 capture.

Next, name the actual destination wiki and observe its local lookup contract. If SQLite is adopted, first consider a storage implementation behind existing hyperbook:find-page and observe-link rather than a second link-resolution workflow. Any new method must preserve provenance, the observed/derived/hypothesized distinction, and the no-write boundary of S2 planning.

No operation is authorized by this reading: no remote fetch, database creation, fork, merge, automatic TMDM mapping, service restart or deployment.
