Deriving HyperDoc Authoring Constraints

dreyeck/work/authoring-architecture

This page uses Fielding's constraint/property method. It does not claim that HyperDoc Authoring currently conforms to REST.

HyperDoc Authoring is the path by which a signed request may change one Item on one local FedWiki page. This page reads its development as a derivation: each step adds one constraint for a stated requirement, and each constraint is judged by the properties it induces and what it costs. Where a property has been shown by a test, the page says so and names the commit; where it is only intended or inferred, the page says that instead.

1. Why constraints rather than "a REST API"

Using HTTP, JSON or signed requests does not make an architecture RESTful, and having no login session does not make it stateless. HyperDoc Authoring keeps server-held state on purpose: one-time challenges, a principal registry and page locks. Calling it a REST API would be a claim that is not established; naming its constraints and their effects can be checked against evidence.

2. Fielding's architectural method

Reference: FIELDING, Roy Thomas, 2000. Architectural Styles and the Design of Network-based Software Architectures. Doctoral dissertation, University of California, Irvine. The ideas used here, each with where it is stated:

  • Run-time abstraction. A software architecture abstracts the run-time elements and behavior of a system; the structure of its source code is a different thing (§1.1). So the run-time view below shows no source files, although source files implement it.
  • Elements. An architecture is a configuration of components, connectors and data (§1.2, §1.2.1–1.2.3). The run-time view uses those three kinds.
  • Constraints induce properties. Properties are induced by the constraints of an architecture, and a style is a coordinated set of constraints (§1.4, §1.5); a style is evaluated by the properties it induces, and improving one property can cost another (§3.1.2).
  • Incremental derivation. Fielding starts from the null style and adds one constraint at a time, examining the effect of each (§5.1, §5.1.1–5.1.8). The derivation below borrows that method, not REST's constraints.
  • Anarchic scalability. At Internet scale, elements must keep working under unanticipated load and when given malformed or maliciously constructed data, and information from outside a trust boundary is untrusted unless authenticated (§4.1.4.1).
  • Intermediaries at boundaries. Layers let security policies be enforced on data crossing an organizational boundary (§5.1.6); a gateway is an intermediary component imposed by the network or the origin server (§5.2.3). Visibility is the ability of a component to monitor or mediate an interaction between two others (§2.3.5).

Fielding does not describe HyperDoc or its protocol. Nothing here says that he would endorse these constraints.

The starting requirement, and seven constraints added in order. For each: the problem it answers, the constraint itself, and what it costs. Its properties and evidence are Associations further down, not prose here.

  • Public network authoring — requirement: authoring requests arrive over the public Internet, from clients and through networks the server does not control. Planned; not deployed.
  • Signed intent. Requirement: a request's authority cannot rest on the channel or on a login session, because whatever relays it may be untrusted. Constraint: every authoring request carries one signed envelope naming service, principal, operation, site, page, nonce, validity window and the Keccak-256 digest of the exact body, and the server verifies its secp256k1 signature before acting on any of it. Trade-off: clients must hold and use a private key; one fixed envelope format and signature scheme; how a browser keeps the key is unresolved.
  • Authenticated principal. Requirement: a valid signature says only that some key signed; the server must know who may act. Constraint: the envelope's principal must be in a server-held registry, and the signature must verify under one of that principal's registered public keys. Trade-off: enrollment, rotation and recovery of keys become the server's obligations; the registry is not yet durable.
  • Single-use freshness. Requirement: a captured signed request must not be replayable. Constraint: each request names a server-issued challenge bound to its principal, and the challenge is consumed atomically, exactly once, before any effect. Trade-off: server-held challenge state and an extra round trip; the interaction is not stateless, and a restart invalidates outstanding challenges.
  • Bounded freshness state. Requirement: challenge issuance is reachable by anyone, so allocation that grows with requests lets any requester exhaust server memory. Constraint: challenges are allocated only for registered principals, with a fixed limit on outstanding challenges per principal checked under one lock, expired challenges pruned and consumed ones kept only up to a second limit. Trade-off: a principal holds only finitely many simultaneous challenges; anyone who knows a principal's id can occupy them until they expire; old replay diagnostics disappear.
  • Explicit authoring rule. Requirement: knowing who signed does not decide what they may change. Constraint: an explicit rule names principal, operation, site and page; a request no rule permits is refused before its challenge is consumed. Trade-off: rules are enumerated and static; there is no delegation and no policy language.
  • Scoped capability. Requirement: even a permitted request must not reach beyond the page it names. Constraint: from the matched rule the server derives a capability for one configured site root, one validated page slug and the edit action, and the effect layer accepts nothing outside it. Trade-off: only the edit of one Item on an existing page; other FedWiki actions and page creation are outside.
  • Serialized verified effect. Requirement: FedWiki's own server can lose concurrent updates, and an effect must not silently overwrite another. Constraint: edits of one page are serialized under a page lock, conditioned on the Item the client observed, written through an exclusive temporary file, journalled only when the Item changed and verified by reading the page back. Trade-off: one writer per page at a time within one process; another process or a direct file write is not serialized; nothing is synced to disk, so crash durability is not established.

Status production means committed production source with in-process tests. It says nothing about deployment.

Properties. A property's status is the strength of the claim made for it: demonstrated means a committed test shows it in-process; intended means it is the architectural aim or an inference and has not been measured.

  • Integrity of intent — demonstrated: an altered envelope or body is refused.
  • Interaction visibility — intended: the whole intent is in the request, so an intermediary could see what is asked; no intermediary inspects it yet.
  • Only registered principals act — demonstrated: unknown principals and unregistered keys are refused.
  • Replay resistance — demonstrated: replay and concurrent duplicates are refused; exactly one effect.
  • Bounded resource consumption — demonstrated for challenge state.
  • Anarchic scalability — intended, not directly measured.
  • Bounded authorization — demonstrated: requests outside every rule are refused.
  • Least authority, confined effect — demonstrated: other pages, actions and slugs outside pages/ are refused.
  • Consistency: no lost update — demonstrated within one process.
  • Reliability of the effect — intended; crash durability is not established.

6. Bounded challenges as a worked derivation

This step, commit 9a041fdd, followed Fielding's order: a requirement, one added constraint, and its induced properties weighed against its cost.

  • Observed failure. In the scratch HTTP experiment, 2000 anonymous requests for unregistered principal ids grew the challenge store by exactly 2000 entries; nothing removed used or expired challenges. That was unbounded allocation, observed in scratch, not in repository history.
  • Requirement. Public authoring must remain operable under untrusted, potentially adversarial request load (§4.1.4.1).
  • Constraint. Allocate challenge state only for registered principals, and bound its lifecycle through issuance, expiry and consumption.
  • Mechanism. An outstanding limit per principal (default 4); a consumed limit (default 8), kept only to name a replay; expired challenges pruned; the limit check and the insertion made atomically under the store's one lock.
  • Demonstrated in the committed tests. 5000 issuance requests for unknown principals caused zero store growth. With 16 concurrent issuers, exactly the configured 4 challenges were issued in each round. Capacity returned after consumption and after expiry. These are in-process results.
  • Intended, not measured. Better scalability and reliability under adversarial interaction. No load test and no public deployment support this yet.
  • Trade-off. Finitely many simultaneous challenges per principal; old replay diagnostics disappear, so a pruned replay is refused as unknown rather than as used; issuance is not authenticated, so anyone knowing a principal's id can occupy its challenges until they expire.

7. What has NOT been established

  • The production HTTP adapter (8a019b2f, corrected in afb8f064) has been exercised only on a loopback socket in tests. It is not deployed: no nginx route, no TLS and no public listener exist for authoring.
  • Nothing is deployed, and no nginx or TLS configuration for authoring has been checked.
  • Scalability and reliability under adversarial load are intended properties; neither has been measured.
  • The principal registry and the challenges live in memory: no durability, no key enrollment, rotation or recovery.
  • No fsync: crash durability of an effect is not established. Another process writing the same page is not serialized.
  • Challenge issuance is not authenticated; there is no rate limiting. Because issuance answers only registered principals, a caller can tell a registered principal id from an unknown one.
  • HyperDoc Authoring is not shown to be RESTful, and it is not stateless: challenges, the registry and page locks are server-held state.

8. Next architectural boundary

After 9a041fdd, the next boundary this derivation justified was a production HTTP adapter: the connector that carries the exact envelope and body to the authority, with bounded request bodies and no session. Since 8a019b2f it exists, tested on a loopback socket. What reaches it from outside, and under which operator policy, is the next question; this page does not decide it.

Browser key storage, nginx deployment and Lisp source or image authoring remain separate questions.

Remote evaluation is not the model. Fielding's Remote Evaluation style sends code from client to server for execution; its main limitation is lost visibility, since the server receives code instead of standardized requests, which is a deployment problem when the server cannot trust its clients (§3.5.2). Prospective Lisp authoring is therefore not represented as a client sending Lisp for the server to EVAL. A signed request carries semantic data and server-known identifiers; the server constructs a bounded operation from them, derives a scoped capability, and only then causes an effect. This avoids a Remote Evaluation interaction style for public authoring.
