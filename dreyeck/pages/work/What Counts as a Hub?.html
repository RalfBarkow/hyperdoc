Neighborhood, incoming references and hits

walks(count, way, neighborhood, ...) treats its supplied neighborhood array as the universe. This is distinct from the original Wiki browser's session neighborhood and from a global Lisp sitemap cache. HyperDoc's existing browser host supplies only its declared page/context subset and loading states. A ranking in one subset need not match a ranking in another.

hubs considers source pages having links and at most 15 outgoing link keys. Each key contributes one hit if find(link) locates a target in neighborhood. Link values are not weights; a 16-link source contributes no hits. Missing targets contribute nothing. hits[slug] aggregates all matching references without target-site qualification. find(slug) returns the first matching record, so site order can change the target selected for expansion.

The implementation sorts entries by descending hit count, takes count (default 12), and makes an aspect named hub N slug for each selected entry. Equal counts retain their insertion order in the tested JavaScript runtime; that order is not a separate site-resolution policy. A Hub is this ranked target; an aspect is the named graph wrapper; a graph node is a local object in an expanded graph. These are different objects and their identifiers must not be equated.

Blanket expansion is a separate operation

blanket(info) adds the Hub node, parents, children, and parents of children. Explicit patterns.up resolves supplied slugs; even an empty array suppresses fallback. Otherwise parents come from back(slug): only source pages with fewer than 10 outgoing links qualify. newr sorts these by date descending, deduplicates by slug and takes the newest three. Thus an exactly-15-link source can contribute a hit without becoming a fallback parent.

patterns.down overrides children; otherwise link keys are used. Children must be findable, again by the first matching slug. Explicit up references are not filtered to remove missing targets: a bad supplied parent can fail expansion. The graph's node deduplication uses type and name, not site/slug. Relation types produced here are empty; they are not extracted typed Discourse relations or Trail memberships. Duplicate relations can remain.

Inspect a falsifiable example

Inspecting a Hub Selection exposes seven synthetic runs of the unchanged Mech module. Open selection and expansion: four hits produce a graph root with one incoming relation. Reverse two records with slug hub on different sites and the ranking stays equal while the root changes from Hub A to Hub B. This is controlled evidence, not a reconstruction of Wards chosen Hubs.
