dreyeck.ch deployment

Which applications serve dreyeck.ch and its Wiki subdomains?

The latest supported routing observation separates two applications. The exact hostname dreyeck.ch reaches the Lisp-based HyperDoc application through hyperdoc.service. The recorded wildcard Wiki routing reaches a separate Node Federated Wiki farm through wiki.service. The explicit MCP route is a further exception to the wildcard. Sharing a machine does not make these the same service.

Latest supported observation: 8 October 2026

The operator's read-only host output was captured at 03:29:16 UTC on 8 October. It records the HyperDoc service and SBCL process, immutable package source, routes and mutable site assets separately. This is the latest evidence in this reading, not a live monitor.

How the startup changed

The observations below answer different questions. They are kept separate rather than merged into one timeless deployment record.

  1. 28 September — checkout and service snapshot. The reported startup used nix develop and a relative script. Its WorkingDirectory named the checkout; startup from the checkout revision was inferred from directory and times. Capture time for the whole snapshot was not supplied. Inspect the earlier basis and inference.
  2. 1 October — built startup confirmation. The operator confirmed hyperdoc-catalog as the startup program. This did not supply exact arguments, package path or current WorkingDirectory. Inspect what that confirmation establishes.
  3. 3 October — source update and activation. The operator supplied command output: first the HyperDoc flake input changed, then NixOS activation built the application and stopped/started the service. Successful activation alone does not establish post-restart health or proxy state. Inspect the two operations and their result.
  4. 8 October — source and process observation. The later capture records the store-based startup and loopback listener. It refines the later deployment without rewriting September's checkout witness. Return to the latest supported observation.

Its publication does not prove that the Node farm selected either package, and a hostname alone does not select independent plugin assets inside a shared farm.
