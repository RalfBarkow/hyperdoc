Shift-click Is Pane Policy

dreyeck/work/shift-click

What does Shift-click mean in HyperDoc? In this image and its pinned dependencies, it decides whether the Inspector keeps the panes to the right of the one that was clicked. It does not select an operation. The Topicmap of this reading starts at Shift-click. Its associations show what reads it and what merely carries it. The reader, the Inspector's click handler, is in turn compared with Mech's CLICK, and only compared. Each association records a warrant and a status in its properties: source-observed, directly observed, or design inference.

One handler reads Shift

Clicks on references reach the Inspector's click handler, in clog-moldable-inspector as pinned for this repository. Its inspect- and eval- branches guard one call with (unless (getf event :shift-key) (close-panes-after inspector pane)). Everything else they do is the same with or without Shift:

ClickPanes to the rightThen
ordinaryclosedthe reference; its pane follows the clicked one
Shiftkeptthe same reference; its pane goes last

CLOSE-PANES-AFTER is the whole difference. An action- reference opens no pane, and the handler reads Shift there only together with Alt. Alt is not pane policy. On an eval- or action- reference it opens the reference's own thunk instead of running it, so it yields a different result.

Same operation, different pane policy

A followable federated-context Topic sign is an eval- reference. Its PRIMARY activation is one method: Workspace Point moves to the Topic, the local Point presentation is updated, and the existing operation/follow runs on that Topic's sign occurrence. Its result opens in the next pane. Run it on a fresh context:

topic-primary-activation

Point moves from Jan / John Dewey to Thompson / How We Think, and history records Jan / John Dewey. The Point presentation is updated with Point already at How We Think. The result is the Topic's represented page itself. The handler reads Shift before this thunk runs, and nothing reaches the thunk from the click event. Shift-PRIMARY therefore makes the same Point, the same Follow and the same result. Only the panes to the right differ.

The Shift regression in dreyeck/work/reading/tests checks the table. It captures the click handlers that the pinned code installs on this context's own references and calls them with CLOG's parse of a plain and of a shifted click, without a browser. Without Shift the real CLOSE-PANES-AFTER removes the trailing pane; with Shift it is not called. Point, history, the Follow identity and the opened object agree in both cases. With Alt, the handler opens the sign's own reference instead, and Point stays where it was. That control shows the harness can see a modifier that does change the result.

Operation is not invocation

Follow is a semantic operation identity, a SEMANTIC-OPERATION-IDENTITY. What reaches it differs:

  • PRIMARY, through the Inspector's eval transport and the composition above;
  • SECONDARY, through two GESTURE-BINDINGs, the radial-menu and the learned-mark Binding at 90°.

Neither modifier becomes part of the Follow invocation. Shift is consumed by the Inspector as pane policy while the underlying PRIMARY activation still reaches Follow; Alt is consumed as meta-inspection and does not run that eval path.

follow-identity

Both Bindings reference the identity EQ. The composition names it in its source, and the federated-context Topic-operations test records the same EQ identity for PRIMARY, radial and learned-mark Follow. That identity is the claim; the result cannot carry it, because for a page Topic, Inspect represented object returns the same page. There is no common invocation protocol either. The Point panel's Follow button calls FOLLOW-CONTEXT-OBJECT directly, without the identity.

PRIMARY and SECONDARY

PRIMARY on a Topic
Point := Topic, then default Follow where applicable.
SECONDARY on a Topic
An explicit operation on the transient gesture target. Point is unchanged.

CONTEXT-TOPIC-PRIMARY-REFERENCE gives a followable context sign an eval- reference. Other context signs get an action- reference that only moves Point, and temporal signs keep selecting an event. A completed gesture reaches %SHOW-TOPIC-SELECTION, which runs the selected Operation on the exact occurrence and opens the result with %OPEN-BESIDE.

Shift differs between the two. PRIMARY gets pane policy from the Inspector without any Topic code. SECONDARY carries Shift but never interprets it:

secondary-modifier-transport

The transport puts :SHIFT into the GESTURE-INPUT-SAMPLE of every event. A GESTURE-BINDING has no modifier slot, and the reducer selects the same Binding and Operation either way. %OPEN-BESIDE then closes the panes to the right, Shift or not. This is an observation of the current code. Nothing in this reading changes it.

Mech's Shift-click is another mechanism

Ward Cunningham reports a Mech Shift-click that reports the properties used in each block. His screenshot shows aspect ⇒ above a line SOLO ⇒ 1 sources, 3 aspects, and status ⇒ above REPORT status. His current, unpublished implementation was not inspected. What can be inspected is the Mech revision that the Trails Rendered reading already pins:

(mech-excerpt-view :click) (mech-excerpt-view :inspect)

A CLICK sets state.debug from event.shiftKey and then runs the same blocks. While state.debug is set, inspect writes a key ⇒ label for each key it is called with. So Shift turns on reporting over an unchanged execution. The screenshot is consistent with this pinned output form: SOLO inspects aspect and writes ⇒ N sources, M aspects, and REPORT inspects the key it reports. Where Ward's status comes from was not established. These are excerpts with provenance, not HyperDoc runtime objects.

Interpretation, not observation: both are modifiers read when an invocation starts, and both leave what runs unchanged. That is the whole analogy. HyperDoc's Shift keeps panes and Mech's turns on reports, and the two share no implementation. Mech's Shift-click is neither Inspect represented object nor Inspect Topicmap sign. Both of those are explicit SECONDARY operations that return a different object, with no run and no report.

Boundary: properties used

Ward's example reports block properties such as aspect and status. In the pinned Mech, those keys are not inferred: the SOLO and REPORT blocks shown above name them in explicit inspect calls. HyperDoc has no runtime representation of the properties that a View or an Operation actually reads, and this reading does not add one.
