Item Edit Path in HyperDoc

dreyeck/work/ctm-page-authoring

How one Story Item of a Federated Wiki page is proposed, previewed, completed, authorized, executed and verified in HyperDoc, as the code on branch dreyeck.ch has it on 2026-10-18. This is the technical documentation of the work packages 2 to 4 of Authoring the CTM Plan Page; what each has reached is in its implementation state, and the terms are those of Work Breakdown. The links below open the real Lisp objects in the Inspector: a class, a function with its Source code view, an ASDF system, a file. E3 (ed37e9bac2fcd548) is only the example Item; no content decision about it is made here. Links into the execution, topic-maps and TMDM systems open only in the local review Catalog (see Operation).

The path and its objects

Each step is a separate object, and no step implies the next. Open the Item in the Page source view of /view/ctm-and-tmdm-in-hyperdoc, then follow its Edit tab.

Three statements about an execution

execute-completed-edit reads the page file again and decides by what the file shows, not by what was signalled. It keeps three statements apart, and none stands for another:

  • File against preview (expectation): :as-previewed or :differs with its deviations. Only the file enters it.
  • The run's condition (condition): the condition signalled during the run, if any, kept as an object. It says nothing about the file.
  • Attribution (observed :attribution): the write is ascribed to this call only where the writer returned its record or signalled its own post-write :verification refusal. With an unused challenge it is excluded (consuming comes before the writer); otherwise it is undetermined, because another process may have written the same Action.

"No page byte was written" is claimed only for a refusal that is provably made before the page can be replaced. An unchanged file does not show that nothing was written, and a used challenge does not show that an Action was persisted. Verified states the file, not that the run was clean or that this call wrote it.

Operation

Local review Catalog. The note and the start script give the command: it needs TOPIC_MAPS_ROOT (a clean checkout of topic-maps at the commit above) and HYPERDOC_FEDWIKI_SITE_ROOT, and listens on 127.0.0.1:18773. It reads the site root and writes nothing: without an attached signed request nothing can be executed.

Served Catalog. A service that sets HYPERDOC_CATALOG_SYSTEM=dreyeck/ctm-page-authoring and is restarted shows Edit, proposal, preview and Action context. It has no writer and no execution, and no Completed Action or Execution view. The variable can name only systems of the packaged registry, and topic-maps is not in it: it has no remote and is not packaged (the open question E1), so the TMDM readings are not reproducible on a server yet. The Catalog operations note has the startup flow and the limits of the packaged runtime. Observed on 2026-10-18 on a Mac: the built hyperdoc-catalog with that variable served the page and reached the proposal for E3 on a copy. The Linux server was not observed.

Tests and evidence

All tests write on temporary copies of the retained page (retained copy); the real wiki page is never written. Each refusal is paired with the same fixture succeeding, so that a refusal is a difference.

  • Preview: dreyeck/tests/fedwiki-item-edit-preview.lisp; browser: scripts/test-item-edit-preview-outcomes.mjs, scripts/test-item-edit-preview-activation.mjs.
  • Proposal anatomy: dreyeck/tests/work-item-edit-proposal.lisp; browser: scripts/test-item-edit-proposal.mjs.
  • Execution: dreyeck/tests/fedwiki-item-edit-execution.lisp, with test keys made in memory; browser: scripts/test-item-edit-execution.mjs. They cover the three statements, refusals, a concurrent request in the same process and the fresh-process verification.
  • Diagnosis of the missing Edit view: dreyeck/tests/work-item-edit-view-diagnosis.lisp; TMDM: dreyeck/tests/topic-maps-reading.lisp, dreyeck/tests/tmdm-model-reading.lisp.

The tests need a Git checkout with a local branch dreyeck.ch (the Catalog and Work readings), and the topic-maps checkout for the two TMDM tests. A test on a copy is evidence of function on that copy. It is not an observation of a real page, not a deployment and not an acceptance. A file observed after the fact shows what the file holds; it does not show who wrote it.

Known limits

The writer's page lock holds within one process. Another operating-system process, such as the Node wiki server, can write between the revision check and the writer's own read (the writer then applies the edit to the newer page, or refuses if E3 changed, with the challenge already used up), or between the writer's read and the rename (that write is lost and the read afterwards cannot tell). There is no sync, so a crash may lose the write. The signature covers the expected Item and the Action, not the page revision; the revision is checked outside it. Interruptions are not caught. None of this is changed here.
