Completeness and overlap

Completeness: the five packages together are the whole defined scope. Observing the source (1), proposing the change without effect (2), performing exactly that effect under its authority (3), observing the persisted result independently (4) and recording it in HyperDoc (5). Three things the scope needs are not deliverables of this Work item and appear below as plan preconditions instead: the operator's transfer of the page, the human decision on the Item's content, and the edit authority for the site and page.

Overlap: 2 and 3 meet at the proposal. Package 2 ends with an unexecuted proposal; package 3 executes exactly that proposal and nothing else. 3 and 4 both read the page after the effect. The reread inside the writer's own transaction belongs to 3; the independent reread in a fresh process, compared with the proposal, belongs to 4. Package 5 records status and evidence links in HyperDoc and produces no verification of its own.

Relation contracts

  • decomposes into — WBS: the target deliverable is part of the source deliverable's scope, and the targets together are all of it. It asserts scope membership only: no order, dependency, status or authority.
  • depends on — Plan: the source step cannot be completed before the target step or precondition is satisfied. It asserts an ordering condition only: no scope, status or authority.
  • produces — Plan: the source step yields the target work package, accepted by the criterion in the WBS Dictionary. It asserts what a step is for, not that it may be performed.

Its repository revision and its other systems are not reported. No reading here inspects a long-lived image.

Proposal and preview, implemented and tested: dreyeck/fedwiki-item-edit-preview selects one Item through the Page source view, forms the expected Item, the replacement and the edit Action as one unexecuted proposal, reads the page again and refuses a changed revision, and plans the edit with the writer's own page checks (plan-fedwiki-page-edit). Those checks live in dreyeck/fedwiki-page-edit-plan, which the writer dreyeck/fedwiki-page-authoring imports and the preview loads without the writer. It holds no capability and writes nothing.

Activation, the operator's: a served Catalog shows the Edit tab when its service sets HYPERDOC_CATALOG_SYSTEM=dreyeck/ctm-page-authoring and is restarted. The variable adds systems to the default Catalog and can name only systems of the packaged registry. This system loads neither the writer nor a capability and leaves the served-mode policy in force. scripts/test-item-edit-preview-activation.mjs starts a Catalog that way and follows /view → Page source → E3 → Edit → Edit proposal → Preview on a copy of the retained page, which stays unchanged.

Execution, implemented, local only: dreyeck/fedwiki-item-edit-execution takes a previewed proposal to the existing authorized path. complete-item-edit copies the Action and adds the date; trusted code attaches a request signed by a registered principal (attach-signed-request); execute-completed-edit lets authenticate-authorize-fedwiki-page-edit derive the capability and calls the writer. It reads the page file again and keeps three statements apart: how the file compares with the preview, the condition the run signalled, and whom the write is ascribed to. verify-persisted-edit reads the file again in a fresh process. No Inspector control signs or authorizes anything, and loading the system grants nothing. The system loads the writer and is therefore not in the served-sized system; it is part of dreyeck/ctm-page-authoring/local.

Not done: the productive activation; any edit of a real wiki page; the user's content decision and edit authority for a productive edit. Nothing was written to a real wiki page by any test or by this documentation.
