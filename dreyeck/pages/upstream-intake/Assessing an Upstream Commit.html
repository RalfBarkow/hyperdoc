Assessing an Upstream Commit

dreyeck/upstream-intake

Observing an upstream commit reveals its current status. To assess it, we consider its implications for dreyeck.ch, asking questions such as: what has changed; where that definition stands in the fork; which ASDF system owns it and which should own it; what it affects; and how to proceed. The assessment reads Git objects and source text, but does not load any library code, fetch anything, or record any decisions. A decision is a proposal until a person accepts it, and accepting it is not carrying it out.

Five words that are not the same thing

A question about an upstream commit mixes five relations. The assessment keeps them apart, and says for each what it can find out and from where.

Git fork

A relation of history. dreyeck.ch is a fork of Konrad Hinsen's repository if its Git history contains upstream's commits. Whether a commit is an ancestor of the fork's HEAD says nothing about whether its definitions stand in the fork's source, and the reverse. The run reports both, as Git ancestry and source adoption.

Library dependency

A relation of loading. dreyeck.ch uses Konrad's systems, for example hyperbook/fedwiki, as a library: ASDF loads them because a dreyeck system lists them in :depends-on. The assessment reads the ASDF definitions as text; it loads nothing.

Local definition

A relation of text. A definition is local if its text in the fork differs from upstream's, or if upstream has no definition with that key. This is found by comparing digests of syntax trees. It says nothing about why the text differs.

Dreyeck extension

A relation of intent. A local definition is an extension if dreyeck keeps it in order to extend or adapt the library. Source text cannot show that. Where this checkout says it, a document says it (docs/hyperdoc-upstream-boundary.md), in general terms and for groups of definitions, not for each one.

Code ownership

A relation of maintenance: who changes the text, and which ASDF system carries it. The assessment shows three things next to each other and decides none: the ASDF system that lists the file now (derived from the ASDF definitions), the default by path (a file under a library path of the upstream contract is upstream's), and what is stated or proposed for this definition, each with its source. A per-definition ownership inventory is proposed in RalfBarkow/hyperdoc#21, a draft that is not integrated into dreyeck.ch; the assessment lists what that draft proposes as a proposal that is not in force, and does not presuppose it.

The relation of a definition to the fork is therefore worded as a finding about text. Where the text that upstream changed no longer stands in the upstream definition but does stand in another definition of the fork, the finding is the changed text stands in other definitions of the fork. It is not called a replacement: that would claim that the two definitions do the same, which the text does not show.

The case, in five steps

Open the link above, then follow the references in the result. Each is an underlined name; a click opens it in a new pane.

  1. The commit. Its page shows the commit, its evidence (recorded: its objects are not in this checkout) and the changed definition, function:make-fedwiki. Open What 58a2b2c changed for the change itself: upstream changed the type list of the second handler of make-fedwiki, the one that protects fetch-sitemap and fetch-plugin-data; the first handler, around the HTTPS connection attempt, is the same before and after.
  2. The definition in the fork. make-fedwiki exists in the fork, but the old type list stands in initialize-fedwiki, which make-fedwiki now calls on a thread. Open function:initialize-fedwiki for its source. That the text of the two lists matches is a finding. That initialize-fedwiki is the dreyeck counterpart of upstream's second handler is a working hypothesis from reading the two definitions; it is not equated by any rule.
  3. The owner. Open Ownership. It shows the ASDF system that lists hyperbook-fedwiki/fedwiki.lisp now (hyperbook/fedwiki), the path default (upstream-owned), what docs/hyperdoc-upstream-boundary.md says (reusable library fixes, candidates for contribution), and what #21 proposes (not in force). The intended owner of this definition is not decided; the page says so.
  4. What may be affected. The change view lists the systems and tests that own or depend on it and the definitions that mention the name. A mention is a lead, not proof of a call.
  5. The decision. Two proposals are recorded, defer (do not adopt the line and do not choose between usocket:ns-error and the explicit condition classes here) and prepare-upstream-contribution. Each shows its rationale, its evidence by epistemic status, the migration it would need and how it would be verified. Under Open the change view lists what is still undecided. A proposal is not accepted until a person accepts it, and accepting it changes no source.

Why the source above says ▷ and “Not run here”

The example is shown with its source, and before the source stands a marker, ▷. In a served Catalog its tooltip says Not run here: no operation contract. That is not an error and not a missing permission for reading. Two different things are being told apart:

  • Navigation is the link above. The page author wrote the expression (upstream-assessment-commit-example) into the page, so it is part of the repository, not of what a visitor types. It is evaluated when the page is rendered, and its result is an object that the Inspector opens. Reading needs no contract: a visitor chooses which pane to open, never what is evaluated.
  • Execution is the run button that upstream puts before an example's source. A click would evaluate the example in the served image on the visitor's request. The authority policy offers that only for an example with a reviewed operation contract. These examples have none, on purpose, because nothing here needs to be run: the link already shows the result. The marker says exactly that, and a run obtained in another way is refused before the example is called.

Should a run ever be needed, the proposal would be a contract of its own for each example, not a general permission: observational only; it reads docs/upstream-intake/ (state, ledger, recorded evidence) and the checkout's own source files and allocates its result in memory; it opens no Git repository of an upstream and none of the fork, runs no process, fetches nothing and writes no file; reviewed against the source of upstream-assessment-run, with the tests that show no repository changed. No such contract is registered here.
