Specialization Without Integration

dreyeck/upstream-intake

Dreyeck uses Konrad's protocol. None of the four commits that created it is an ancestor of dreyeck.ch. Both statements are true at once, and the only way to hold them together is to stop using one word for several different relations.

Four relations, four answers

The temptation is to ask whether the work is "integrated". That word hides at least four separate questions, and in this case they do not agree with each other. Each gets its own observed value.

Ask all four questions about the same pair of forms

page-loading-four-relations-example 
Git ancestry          is the upstream commit an ancestor?        NIL
source adoption       does the local tree carry the form?        T
semantic equivalence  do the spellings read to the same form?    T
text similarity       are the spellings the same text?           NIL

Two true, two false, about one pair of forms. Semantic equivalence is answered by the project's own structural reader rather than by comparing strings: in package hyperdoc, hdoc and hyperdoc::hdoc designate the same symbol. That is why text similarity can be false while semantic equivalence is true.

The existing Upstream Intake observation reached the same Git conclusion earlier and recorded it as :AVAILABLE-NOT-INTEGRATED. Source adoption has since changed; the ancestry has not.

What Dreyeck actually added

The specialization is small, and it is all ordinary CLOS resting on the published protocol: a book subclass, a page subclass, one PAGE-CLASS method, one LOAD-PAGE :AFTER method.

Read the LOAD-PAGE methods in the result. Upstream's primary methods on HYPERDOC:HTML-PAGE and HYPERDOC:MARKDOWN-PAGE are still there, untouched, and Dreyeck's method is an :AFTER on its own DREYECK/HYPERDOC:HTML-PAGE. Nothing was replaced. That is capability E from the previous page, visible in the metaobject protocol rather than asserted.

CL-USER and CL: the direction of the history

It is tempting to describe the local change in the ordinary renderer as returning to an older CL default. The history does not support that, and the phrase inverts the direction of events.

Sample the reader package at three points in upstream history

page-loading-reader-package-history-example

CL-USER is upstream's own long-standing default. It is there in February 2025, and it is still there in August 2026 after the renderer is restructured. Konrad changed the general default to CL in b3e7322, in the same commit that exported *CURRENT-PACKAGE*. There was no earlier CL default to return to, so the observation records :EARLIER-CL-DEFAULT-P NIL.

The correct description is therefore: Dreyeck adopted a new upstream default, and re-established CL-USER only for Dreyeck pages, through its own LOAD-PAGE specialization. The effect the boundary documentation describes is right; the direction in time was not.

One further nuance the history makes visible: upstream published two seams for reader context, and Dreyeck uses the other one. Upstream rebinds *CURRENT-PACKAGE* at serialization time; Dreyeck prepends reader context to the parse tree at load time. Both are supported, but they are not the same seam.
