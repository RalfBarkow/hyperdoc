Follow the complete commit-observation reading path

Observing an upstream change is a routine

receive upstream hint
  -> retain reference
  -> locate local object or component
  -> compare local and upstream evidence
  -> inspect the current live Lisp image
  -> identify possible consequences
  -> retain the observation
  -> inspect
  -> only later: decide

OBSERVE-UPSTREAM-CHANGE is the recognizable read-only operation behind this routine. Re-running an example produces a new observation of the present checkout and present image. Integration is a separate operation.

Follow the complete component-hypothesis reading path

Compare the two kinds of reference

  • A :GIT-COMMIT reference observes commit identity, current ancestry, patch evidence, and live overlap for definitions evidenced by that patch.
  • A :COMPONENT reference retains a local subject, candidate, proposed relation, verification status, contract questions, and current local live-image facts. Missing candidate runtime evidence stays unknown.

Commit identity, patch equivalence, and integration decision remain distinct: 

Git commit identity
  != patch equivalence
  != integration decision

Component intake preserves an analogous distinction: 

observed upstream capability
  != verified contract equivalence
  != supersession decision

What intake deliberately does not do

OBSERVE != APPLY, COMPARE != LOAD, and VERIFY != INSTALL. Intake does not fetch, merge, cherry-pick, install the candidate, load it, redefine live definitions, or confirm a contract from similarity alone.

An intake object is not a RECORDED-CHANGE. A recorded change requires explicit registration of an ordinary-function mutation in the current image. Intake neither registers that mutation nor invokes PERSIST-IN. Image-local records, cross-process authoring and deployment evidence remain separate boundaries.
