page-loading-repository-context-example Observe the repository context

Before: one concrete loader

Early HyperDoc loaded one kind of page. LOAD-PAGE was an ordinary function that parsed Scriba into a document, and MAKE-PAGE always built the same class: 

(defun load-page (page)
  (with-slots (document) page
    (let ((*current-page* page))
      (setf document (parse-and-expand (file page)))))
  page)

(defun make-page (hdoc file)
  (make-instance 'page :hyperdoc hdoc :file file))

There is nothing to specialize here. A second filetype cannot be added without editing this function.

The mechanism appears

a8683fb "Prepare for HTML pages" replaces both concrete definitions with generic operations and makes construction select a class by filetype. Run the example and read its warrants.

Observe the commit that introduces the two generics

page-loading-mechanism-example

What to conclude, and what not to

A mechanism now exists: PAGE-CLASS dispatches on a filetype and LOAD-PAGE is a generic operation, so methods can be added. A public downstream contract does not exist. Neither name is exported, the dispatch cannot see which HyperDoc is asking, and the concrete page classes cannot be subclassed from another package. The observation records that directly as :PUBLIC-CONTRACT-YET-P NIL.

Eighteen months of relocation

Between February 2025 and August 2026 the code moves repeatedly: out of hyperdoc/hyperdoc.lisp, into the explorer, between the HyperDoc and HyperBook layers. Reading every relocation patch would not help. The question that matters is whether the protocol changed shape, and that can be answered by comparing the two ends of the range.

The contract arrives in four commits

On 17 and 18 August 2026 four consecutive commits turn the mechanism into a protocol. The first two are twenty-five seconds apart: this is one design session, not accretion.

Verify the four-commit chain against the object database

page-loading-contract-sequence-example

b3e7322: a general default, and a public knob

The ordinary renderer stops binding the reader package to CL-USER and binds CL instead, and *CURRENT-PACKAGE* is exported in the same commit. That pairing is the principle the rest of the transition follows: make the default unspecific, then publish the knob that lets someone else be specific. 

- (let ((*current-package* (find-package "CL-USER")))
+ (let ((*current-package* (find-package "CL")))
+ (export '(*current-package*))

a15bb54: publish the dynamic context

*CURRENT-PAGE* and *CURRENT-HYPERBOOK* join the export list, so a downstream method can tell which page and which book it is running inside.

beb1689 is the structural centre

This is the only commit in the transition that changes behavior. Everything else moves names onto an export list. 

- (defgeneric page-class (filetype))
+ (defgeneric page-class (hdoc filetype))

- (page-class type-as-kw)
+ (page-class hdoc type-as-kw)

- (defmethod page-class ((filetype (eql :html)))
+ (defmethod page-class ((hd hyperdoc) (filetype (eql :html)))
+   (declare (ignore hd))

Three things had to land together. The dispatch must admit the book; PAGE-CLASS must be exported; and HTML-PAGE and MARKDOWN-PAGE must be exported, because otherwise a downstream book could select a class but would have nothing it was allowed to subclass.

Inspect the five warrants of the central commit

page-loading-structural-center-example

Notice the shape of the upstream method: it specializes on the base class hyperdoc and then ignores the argument. The default is deliberately as unspecific as it can be, so any subclass method wins by ordinary method specificity. No registry, no precedence rule, no override.

8a1149 publishes; it does not implement

The target commit adds two lines to one file: 

+           ;; Load a page
+           #:load-page

Nothing else changes. The generic and its primary methods are byte-identical to the parent, which the example checks by comparing the implementation file at both commits.
