Plain Text After CCNx

dreyeck/ccnx-federated-wiki

Two things are asked of the CCNx prototypes here. Can what they held be read without them? And if a page were taken over by today's Federated Wiki, or shown in HyperDoc, what would come with it? Then the answers are held against the old wiki page about the Power Of Plain Text. Everything below rests on the source as read, not on a run.

Can it be read without the historical runtime?

  • The repositories' own data files: yes. default-data/pages/welcome-visitors and how-to-wiki are plain Smallest Federated Wiki JSON files, byte-identical in both repositories. welcome-visitors has 7 story items and 30 journal actions, and any JSON parser reads it. These files carry none of the CCNx fields.
  • The CCNx forms: in principle. The content of an NDN object is JSON text, but it sits in a binary ccnb element beside name, signed info and signature, so a decoder for that encoding is needed. The IndexedDB records are objects inside a browser profile, not files. Neither client can export a page to a file: the .coffee sources contain no Blob, download or save call. Taking pages out of a stored browser profile was not tried.
  • The server of the repository stores pages as flat JSON files (server/express/lib/page.coffee), but the CCNx client does not use it.

The Power Of Plain Text, assessed

The c2 page states the assertion: “storing resources as plain text makes them easier to view, maintain, increases their longevity, and/or makes it easier to share information with multiple languages and systems.” Its list of benefits includes that no special editor is required, that the format is readable by common tools, that it is relatively robust against corruption, that it works with version control, and that “Every person, pipe, and computer sees the same stream of bytes.” Among the disadvantages it names parsing overhead, hard random access, and security: it has to sit on the file, not on the editor. Among its examples are “Some wiki-like systems”. (Read on 2026-11-04 from the JSON file c2.com/wiki/remodel/pages/PowerOfPlainText, dated November 26, 2014, and from the kidneybone copy.)

The page saysThe CCNx prototypes
Readable with common tools, “parsed … by eye”Partly. The record and the content are JSON text and the journal reads as a history. At rest it is inside a browser store; on the wire it is a signed binary envelope.
Longevity, survives the applicationNot shown by these sources. The only files that outlive the runtime are the Smallest Federated Wiki data files, and there is no export.
Fits version controlThe journal, yes; a file, no. The journal is a complete plain-text history, but there is no file to commit.
Different systems can read itThe vocabulary, yes; the container, no. Today's reader opens the record.
Security belongs on the file, not the editorThis is where the CCNx design is tested. Signing exists, but its verdict is not decisive, the key is shared and signatures are not kept. The protection of the plain text is not in the plain text.
A format that tries to do too much degradesNot observed. The four added fields are small and derivable.

Assessment. The content model is plain text in the sense of the c2 page, and it survives intact. What the CCNx prototypes added around it — name, identity, signature — does not survive as plain text: it is constant, derivable, binary, or not stored.

Where is Ward's pointer to local JSON files?

Open. A statement by Ward Cunningham about local JSON files was not found in any of the four sources. The kidneybone text does not contain the words “Ward”, “Cunningham”, “JSON”, “federated” or “CCN”. What can be observed in the c2 sources: the c2 application loads every page as a JSON file, {date, text}, from c2.com/wiki/remodel/pages/<Title>, and has an “export to fedwiki” function that turns each page into Federated Wiki JSON, paragraph items with hashed ids and one create action, and downloads it. The files read do not say who wrote that application. The text of Zettel 11483 that holds the pointer was not available to this review.

Open questions

  1. Where exactly is Ward's pointer to local JSON files: Zettel 11483, a page, a message? It is not in the four sources.
  2. Runtime behaviour was not observed. Does the unconditional “verified” in NDN.js behave as read? Is a tampered object accepted by a browser?
  3. The store for the favicon is declared with lowercase option names (keypath, autoincrement) where the other stores use keyPath and autoIncrement (repository.coffee L33–L40). Whether the bundled idbstore.js honours them, and so what key the favicon record has, was not tested.
  4. How do two nodes that forked different lines settle excludes and version? The account above is a reading, not a run.
  5. How would a fork action whose site is an image be mapped to a host in today's Federated Wiki? Is the favicon a usable fingerprint at all?
  6. The test deployment named in the Prototype's ReadMe was not examined. Was a key other than the shipped one ever used?
  7. Is there any export of an IndexedDB page to a JSON file in the history of either repository? Only one commit of each was read.
  8. When and by whom was the c2 remodel data and application made?
