Identity, Versions and Signatures

dreyeck/ccnx-federated-wiki

A page that moves between browsers without DNS has to answer four questions that a server answers by its name: what is this page called, which version is it, who made this copy, and can I trust it. This page reads what the two repositories do about each. As before, nothing was run; every claim names the lines it rests on. “Main” is 8426dc5, “Prototype” is c5b1b93.

The name

NameThe version in it
Main/wiki/page/<slug>.json/<version>the date of the page's last journal action, in milliseconds
Prototype/sfw/<slug>/<timestamp>the time of publication, from the signed info; not a journal date

The host is not in the Main name. registerFace first computes a name prefix from the host name, and then assigns the constant "wiki" (interfaces.coffee L55–L69, the assignment at L62). Every site registers the same prefix. A name says which page and which version; it never said whose.

Versions

  • Main. The version is the date of the last journal action (repository.coffee L141–L176). Pages with the same slug and different versions live side by side in the store. The viewer lists them as newer, same and older twins, each shown by its favicon (refresh.coffee L112–L141).
  • A past state can be rebuilt from the journal alone; revision.coffee does it by replaying create, add, edit, move and remove (revision.coffee).
  • Prototype. One record per slug, overwritten by each publication; other lines of a page are kept as twins in a second store (SDB.js L284–L312).

version is not a content identity

version is the date of the last journal action. That is a claimed time, not an identity of the content. Nothing in the code derives it from the content or checks it against the content.

  • Implemented. The date is the editing browser's own clock, taken when the action is made (pageHandler.coffee L143). It is unauthenticated and need not be unique or increasing.
  • Implemented. version is the key of the store page/<slug>.json (repository.coffee L152–L157), so a record with the same slug and the same version replaces the stored one.
  • Derived, not run. Two different pages with the same slug whose last action carries the same date have the same version and the same NDN name, and the later write replaces the earlier. Two copies with identical content can carry different versions. The number orders copies by their claimed time; it does not say whether two copies are equal.
  • Implemented. The only check against content on this path is an optional digest component of a name. It is compared only when present, only logged, and after the page has been handed on (ndn-closures.js L133–L149); the names these clients make carry none.
  • Implemented. A signature does cover the content, but under one shared key and without a decisive check (below). It does not turn the version into a content identity either.

In the Prototype the version is the publication timestamp, equally a clock reading and equally no content identity.

Forks

In Main a fork is detected when the page's favicon is not this browser's. It is recorded as a journal action {type: "fork", site: …, date}, and site is the favicon data URL of the page being forked, not a host name (pageHandler.coffee L112–L163).

The field excludes is built by walking the journal from the newest action backwards, collecting each action's date until the first fork action (pageHandler.coffee L86–L93). When a page arrives from a peer, the stored records whose key is in its excludes are removed (repository.coffee L94–L124). Derived, not run: a peer's earlier versions of its own line since its last fork are replaced; versions from before that fork stay, as separate twins.

Site identity

In both repositories the “site” is an image. A plugin draws a 32×32 gradient on a canvas with random colours and keeps it in the browser's database. In Main it is copied into every page as favicon, decides whether a page is “mine” (repository.coffee L191–L239), and marks forks. In the Prototype it is part of a local identity record {id: 1, name: "anonymous", favicon}, which becomes page.publisher (favicon.coffee L52–L57).

The express server of Main still has an owner and a Persona login (server/express/lib/server.coffee). The CCNx client path does not consult it.

Publisher identity

Every NDN object carries a publisher: the SHA-256 digest of a public key, and a key locator that is that key (ContentObject.js L281–L335). The key is one RSA key pair written into the source of the library (KeyManager.js L31–L34). The digest of its public half is b5506b1aba3da7761b0f8d61a4aa7e3b6d15b426feb5bda82389aca765a3b81c, the same in both repositories. Beside it stands an X.509 certificate with the subject axelcdv, valid from 2012-04-28 to 2012-05-28; no call site in the client sources uses it. Nothing in the source read maps this key to a person, a site or a name.

Signatures: made

Every object these clients make is signed by ContentObject.sign(): RSA with SHA-256 over the encoded name, signed info and content, with that key (ContentObject.js L36–L80). It happens when an Interest is answered (interfaces.coffee L19–L24). A function that also signs a page, pageToContentObject, is defined but has no caller.

What follows (derived from 1–3, not run). On this path the result of the signature check does not decide whether a page is accepted. And a correct check would show only that the object agrees with the key it carries. With one shared key there is no trust anchor, and a signature cannot say who published a page.

Not kept. What reaches IndexedDB is the plain JSON record. Signatures are not stored.
