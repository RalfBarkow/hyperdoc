Reading the CCNx Federated Wiki

dreyeck/ccnx-federated-wiki

In 2013 two repositories by rynomad ported the browser editor of Ward Cunningham's Smallest Federated Wiki to Content Centric Networking: pages were kept in the browser's IndexedDB and moved between browsers as NDN Content Objects, with no DNS name in between. This reading follows one wiki page along that path and asks what, of that page, is still plain text.

It belongs to Zettel 11483, Federated Wiki without DNS: Identity, Reachability, and Local Continuity. The path it reconstructs is:

wiki page → JSON → IndexedDB → NDN Content Object → NDN retrieval → wiki page

What this reading is, and is not

It is a source review. Two historical repositories were fetched at fixed revisions and read. No code of either repository was run, no CCNx or NDN runtime was installed, and nothing here connects to a network or writes a Wiki page. A statement that begins “the source does” is a statement about the lines cited, not about something observed running.

It says nothing about why either repository stopped changing, or whether it did. Each was read as a single commit; no history, issue or deployment was read.

Three kinds of statement

  • Implemented. The cited source does this. Every such statement carries a link to the lines, pinned to a commit.
  • Documented. A README or comment says it. The source may or may not agree; where it was checked, the page says so.
  • Open. Not established by what was read. These are collected on Plain Text After CCNx.

The seven questions, answered briefly

  1. What is stored as JSON? The ordinary Federated Wiki page (title, story, journal) plus four fields: page, excludes, favicon, version. The same record, as JSON text, is the content of the NDN object. (Implemented in Main; see One Page From Browser to NDN and Back.)
  2. How does the NDN name arise? Main: /wiki/page/<slug>.json/<version>. The code computes a prefix from the host name and then overwrites it with the constant wiki, so no site is in the name. Prototype: /sfw/<slug>/<timestamp>. (Implemented; see Identity, Versions and Signatures.)
  3. How are versions and forks represented? The version is the date of the last journal action: a claimed time, not a content identity, and it is the store key, so equal slug and version replace each other. A fork is a journal action whose site is a favicon image, not a host name. excludes lists the journal dates since the last fork. (Implemented.)
  4. Where are site and publisher identity? The site is a random favicon, drawn in the browser. The publisher in every NDN object is the digest of one RSA key written into the source of the library, the same in both repositories. (Implemented.)
  5. Which signatures are made, and which are checked? Every object is signed with that one key. The verification code does run, but for a key carried in the object it raises “verified” whatever the result. Signatures are not stored. (Implemented, by the source; not run.)
  6. Can the content be read as a JSON file without the historical runtime? The repositories' own data files, yes. The CCNx forms, only with a browser profile or a ccnb decoder; neither client can export a page to a file. (Implemented; extraction not tried.)
  7. What would survive adoption today? Three different things, kept apart on Plain Text After CCNx. JSON and Story Item structure: kept completely, including item ids. Semantic compatibility: partly; the page content means the same, but version, excludes, the site of a fork and the favicon do not. Provenance: mostly lost; the name, the publisher, the signature and the origin of a fork do not survive in a usable form.

Look at the example page

The reading follows one illustrative page, Plain Text Example: two items and five journal actions. It is built for this reading, not taken from either repository. Its two forms that are Wiki pages open as ordinary Inspector objects, with the existing Story view:

  • the page as a Federated Wiki server stores it
  • the same page as the Main code leaves it in IndexedDB

The Story view shows the same two paragraphs for both: the four added fields are not part of the story. Open the page object and look at its data to see them. The example holds no link to another page, so showing it triggers no page lookup. The small icon beside the title is the favicon of the page's origin; the example's logical site is the reserved, never resolvable name ccnx-example.invalid, so the icon stays broken.

Reading order

  1. One Page From Browser to NDN and Back: the path, step by step, with the example.
  2. Identity, Versions and Signatures: names, versions, forks, keys, and what is checked.
  3. Plain Text After CCNx: readability, what survives, the Power Of Plain Text assessed, and the open questions.
