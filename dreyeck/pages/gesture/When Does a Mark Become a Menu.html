When Does a Mark Become a Menu?

A marking menu can end in two ways. The pointer goes down, and then either it moves straight away and leaves a mark, or it stays put long enough for a menu to appear and the selection is made from that menu. The question this page asks is narrow: what, exactly, decides which of the two happened — and where in this repository can that decision be looked at?

What the paper says, and what it does not

Kurtenbach and Buxton (CHI '94) report four things this page relies on. A press-and-wait threshold of approximately one third of a second. That immediate movement produces a mark without the menu being displayed first. That menuing and marking are “not mutually exclusive modes”. And that a user may move between the two within one interaction protocol, rather than choosing between them beforehand.

Everything else on this page is ours. The paper does not contain the state names used here, does not describe a reveal-deadline event, knows nothing of browser sequence numbers, of an ordered transport, of CLOG, of Binding objects or of an Operation identity. Those are this repository's representation of the distinction the paper draws, and they are named as such below.

The threshold is worth stating twice, because the two numbers are not the same and neither should be quietly rewritten into the other:

paper parameter            approximately 1/3 second
this HyperDoc's witness    500 ms

The 500 ms is a parameter of the browser bridge, chosen here and documented where it lives. It is not a reading of the paper.

Represented here as

The interaction the paper describes has one beginning and two continuations. Represented here, the beginning is the state :PRESSED; a qualifying move arriving first is represented as :MARKING; and the browser's report that the wait elapsed, arriving first, is represented as :MENU-VISIBLE.

POINTER-DOWN                     -> PRESSED

  qualifying MOVE first          -> MARKING
  REVEAL-DEADLINE first          -> MENU-VISIBLE

both continue                    -> SECTOR-SELECTED

Nothing in that mapping is a historical claim. It says what this implementation does with the distinction, not what anyone in 1994 wrote.

What is read back from a run

race-reading

Three orders are kept apart because they are three different facts. The browser assigns a sequence number to each event it forwards. The host then delivers each event on its own thread, so the order the callbacks arrive in is not the order the browser sent. The queue releases only the next contiguous number, and that third order — consumer delivery — is the only one the reducer ever sees.

Movement wins

movement-wins-reading

Run it. The browser numbered the press 1, the move 2 and the deadline 3; the callback threads arrived 1, 3, 2; the queue delivered 1, 2, 3. The move is therefore reduced before the deadline, the session is in :SECTOR-SELECTED when the deadline arrives, and the deadline is recorded as :OBSOLETE-REVEAL-DEADLINE — consumed, kept, and without effect. The selected Binding is binding/mark-insert-defexample.

The wait wins

deadline-wins-reading

Identical geometry: the same press at the origin, the same move to the same point. The only difference is where the deadline sits in the browser's own order. This time it is delivered second, the menu becomes visible, and the same move then selects a sector from a visible menu. The Binding is binding/radial-insert-defexample.

Two runs, one geometry, two Bindings. What separated them was an order, and nothing else.

Two Bindings, one Operation

Both readings report the Operation identity beside the Binding, and both report that it is the same object — :OPERATION-IS-THE-SHARED-IDENTITY is T in each, tested with EQ and not with a string comparison of the id. The Binding is how the operation was reached; the Operation identity is what was reached. Collapsing them would make the two continuations look like two different intentions, which is exactly the distinction the paper says users do not make in advance.

binding/mark-insert-defexample    \
                                    ->  operation/insert-executable-defexample
binding/radial-insert-defexample  /

Browser sequence is not global time

A sequence number means something only inside the page that assigned it. It is local evidence from one sequencing authority — one browsing context holding one counter — and it says nothing whatever about how two such sources relate. The scope that survives is therefore small and strict:

one browser sequencing authority
    ↔ one ORDERED-TRANSPORT
    ↔ one GESTURE-INPUT-SESSION

This is not a stylistic preference. It was found by breaking it. Two pages were open on the probe at once, each counting from one, both feeding a single transport, and the result was not a tidy failure.

two-authorities-session two-authorities-reading

Run it. Source A presses and moves; source B is a different browsing context and, counting for itself, also numbers its press 1 and its deadline 2. Before 2b72697b the second envelope with a given number could replace the first in the pending table, or fill the slot the first was still waiting for — so that a press from one page and a deadline from another were reduced as one interaction, and the reducer reported a gesture that had happened on neither page. The reading above shows what happens now: each repeated number is refused, the refusal carries what already stood in its place, and what is left is source A's own order, unmixed.

The point is epistemic rather than defensive. The queue reconstructs an order observed by one source; it does not establish an order between sources. That is the same discipline the Topicmap projections follow — keep the order that was observed, and do not supply the order that was not.

No identifier was added to the envelope to make the merged case work. Two authorities are not to be reconciled; they are to be kept apart.

Where the evidence comes from

The two cases above are reduced in Lisp from constructed envelopes, which is why they can be run on this page. Both were also demonstrated end to end through a real browser: mouse input injected at the browser's input layer, the browser's own timeout callback, the host's per-event callbacks, the ordered queue, the reducer, and a completed gesture with its Binding.

CDP mouse input -> pointer events -> timeout callback -> host callback
                -> ordered transport -> Gesture -> COMPLETED

In that run the pointer events carried isTrusted true and the generated deadline carried isTrusted false. That is the honest line between what a user did and what the bridge concluded from it, and it is visible in the browser rather than asserted here.

No claim is made about a physical device. The input was injected, not performed, and the page does not pretend otherwise.

Where this stops

The threshold is a parameter, not a finding: 500 ms is what this witness uses, and no measurement here bears on whether it is the right number for anybody. The Operation identity is still opaque and still not FUNCALLable, so nothing on this page can run the operation the two Bindings agree on. And the ownership rule stated above is a contract the transport now enforces at its own boundary; the binder that has to honour it lives outside this system, which has no browser dependency at all.
