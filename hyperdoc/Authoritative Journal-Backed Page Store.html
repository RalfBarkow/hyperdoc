Authoritative Journal-Backed Page Store

This page specifies the conditions under which a page rename, and more generally page evolution, is authored in a journal rather than inferred later from a file, a heading, or a path rename. The goal is to make the journal the primary source of truth for writable pages instead of a downstream mirror of changes decided elsewhere.

1. Problem

A system is not journal-backed in the authoritative sense if page identity is established outside the journal and the journal merely records a reflected copy of that state. In that arrangement, a rename originates in some upstream surface such as a file edit, a heading change, or a path migration. The journal can then describe the resulting state, but it cannot serve as the causal record of the rename.

The desired model is stronger: the rename itself is a journal event. Every materialized representation of the page, including rendered views, stored files, mirrors, and exported twins, is derived from replaying the journal over a stable page identity.

2. Scope

This specification covers writable page-like objects that have durable identity, mutable metadata, and replayable history. It does not require every surface to be stored only in one physical format. It does require that all authoritative state transitions be representable as journal actions.

3. Core requirements

3.1 Stable page identity

Each page must have an immutable key that does not change when the visible title, slug alias set, storage filename, or neighborhood placement changes. This key is the canonical identity used for lookup, linking, journaling, and conflict resolution.

  • The stable key must be created exactly once.
  • The stable key must survive rename, retitle, and relocation operations.
  • The stable key must be the target of internal links and references.

3.2 Journaled page state

All mutable page state that matters for behavior must be reconstructable by replay. This includes at least:

  • title
  • story or visible content structure
  • aliases or redirects, if supported
  • ordering- or neighborhood-relevant metadata, if supported
  • publication or mirror metadata, if supported

No externally edited field may outrank the replayed page state. If a materialized file exists, that file is a projection or cache, not the primary authority.

3.3 Explicit journal action vocabulary

The journal must contain first-class operations for page lifecycle and metadata changes. At minimum the model must distinguish between creating a page and changing its visible name.

Required action families:

  • create-page
  • set-title or rename-page
  • story-editing actions such as add, edit, move, and remove
  • alias or redirect updates, if aliases exist
  • materialization actions only if they themselves are part of desired history

A rename action must not be encoded implicitly as delete-old plus create-new. It must preserve stable identity and express that only selected metadata changed.

3.4 Replay semantics

Replay must compute current page state from the stable page key plus the ordered action stream. Replaying a journal must produce the same title, content, alias set, and current revision metadata that the live page exposes.

A conforming replay engine must therefore support:

  • deterministic ordering rules
  • clear handling of repeated renames
  • clear handling of no-op metadata writes
  • validation that rename targets do not accidentally fork page identity

3.5 Journal checking

The checker must validate not only chronology and structural well-formedness but also identity invariants. It must be able to state whether a page history is replayable and whether page identity remained stable across title changes.

A conforming checker should report at least:

  • missing creation
  • malformed actions
  • chronology violations
  • identity splits caused by invalid rename modeling
  • alias conflicts, if aliases exist
  • materialized state mismatch after replay

3.6 Link resolution

Internal links must resolve by stable page identity, not by mutable title text. User-visible text may show the current title, but the durable target must remain the immutable key.

If human-authored links still use titles or slugs in source text, the system must define how those are normalized into stable identities and how old labels continue to resolve after rename. That resolution strategy may use aliases, redirect tables, or a link migration workflow, but the stable identity must remain primary.

3.7 Materialization boundary

Any derived representation such as HTML files, Markdown files, exported FedWiki twins, static site pages, or cached indexes must be explicitly treated as materializations. Materializations may lag, be rebuilt, or be discarded without changing the canonical journaled history.

Boundary rule. If deleting a materialized artifact destroys the only surviving record of a rename, then the system is not yet authoritative and journal-backed.

4. Required behaviors

4.1 Rename

A rename operation must satisfy all of the following:

  • the stable page key remains unchanged
  • the visible title changes
  • the action is appended to the journal
  • replay yields the new title
  • existing links by stable identity continue to resolve without change
  • legacy title- or alias-based references resolve through declared compatibility rules

4.2 Export or mirror rebuild

A mirror or export must be reproducible from the journaled state. Rebuilding a mirror after a rename must not require hand-authoring a separate rename in the mirror as an independent source of truth.

4.3 Recovery

If all materialized files are deleted but the journal remains, the page must be reconstructable with the same identity and current title. If the journal cannot do that, it is still acting as a mirror description rather than an authoritative store.

5. Non-goals

  • forcing every consumer to display immutable keys to users
  • banning static exports or file-based caches
  • requiring alias retention forever
  • encoding every operational rebuild step as a page-history event

6. Minimal data model sketch

(page
  :page-key "7f7a6c1d-..."
  :current-title "Immutable Slug, Mutable Title"
  :aliases '("immutable-slug-mutable-title")
  :journal
  '((:op :create-page :page-key "7f7a6c1d-..." :title "Journal Rename Spec")
    (:op :set-title   :page-key "7f7a6c1d-..." :title "Immutable Slug, Mutable Title")
    (:op :add-item    :page-key "7f7a6c1d-..." ...)
    (:op :edit-item   :page-key "7f7a6c1d-..." ...)))

The point of this sketch is not the concrete syntax. The point is that a rename is represented as a journal action over a stable page key rather than a new page identity inferred from a new heading or a new filename.

7. Acceptance criteria

  • A page can be renamed any number of times without changing its stable identity.
  • Deleting all materialized files does not erase the rename history.
  • Replay yields the current title and content.
  • Journal checking can detect invalid rename modeling.
  • Mirrors and exports can be regenerated from journaled state.
  • Stable-identity links never break merely because the title changed.

8. Summary

A journal is authoritative only when page identity, mutable title state, replay, and link resolution all live inside the journaled object model. Until then, the journal describes a projection of changes decided elsewhere.
