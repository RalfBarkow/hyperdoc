Capability-scoped Extensions for FedWiki

A capability-scoped extension is the local design answer to the question, "how should HyperDoc or FedWiki grow programmable behavior without defaulting to arbitrary page JavaScript?" The durable pattern is an extension host: the host defines the boundary, the extension declares intent up front, and execution only proceeds through a bounded API surface.

  • Declarative extension manifest

Why extension host beats arbitrary page JavaScript

"Run whatever script the page happens to contain" is the wrong default architecture for a browser-isolation cluster. It gives the document too much ambient authority and makes it difficult to inspect, mediate, or explain what the code is trying to do.

An extension host is stronger because the host remains in charge of policy, data access, and visible effects. The extension asks through a boundary the host already understands. Comparative systems such as Figma plugins, browser WebExtensions, and Jamovi differ in mechanics, but they share that durable shape: host-defined verbs first, extension code second.

Declarative manifest and capability profile

A declarative extension manifest states intent before execution. It can describe the extension's entry point, requested powers, message surface, and expected artifacts without first granting those powers.

That manifest becomes a capability profile the host can inspect, compare, log, and present to the user before anything runs. The important move is not only metadata. It is that the host can now evaluate the request at a stable boundary instead of inferring it from arbitrary text after the fact.

Permission partition by effect

Capability partitioning should stay effect-oriented:

  • content mutation
  • user-interface mutation
  • data read
  • data transformation

Those are different powers with different risk surfaces. Treating them as one generic "execute code" permission erases the distinction that the host needs in order to explain and govern extension behavior.

Consent before execution

A consent-gated execution boundary means the user sees the requested powers before the extension runs. Execution should be an explicit grant, not an accidental consequence of visiting a page or clicking an unrelated link.

Relation to browser isolation layer

Universal Thing and Browser Isolation in FedWiki already shows the local direction: browser-facing behavior is more useful when it is pulled behind an explicit seam. Capability-scoped extensions take the same move further by making the browser- or app-facing power surface a host-defined contract rather than an implicit page privilege.

Relation to Mech CODE experiments

Mech CODE Block analysis is still valuable because it identifies a real executable seam. The safe maturation path is to place declarative manifests, consent checks, and inspectable capability profiles at that seam rather than using the seam as a reason to normalize silent arbitrary-code execution.

Why this matters for end-user-programmable systems

This is not only an enterprise plugin story. End-user-programmable systems need the same clarity because they mix authoring, execution, and explanation in one place. Capability-scoped extension design keeps that power available without making the page itself the default authority surface.
