Journaled Association Changes and Undo Redo

This specification defines the journal and history model for association topics whose player1 and player2 bindings may change over time. It is intended for the DMX-style case in which immutable subject identity coexists with mutable titles, names, aliases, or other representations. It also defines a bounded undo/redo mechanism in the style of an explicit change history rather than implicit editor state.

1. Goal

A change to player1, player2, or association metadata must be:

  • recorded as a durable event
  • replayable into current association state
  • inspectable as history
  • reversible through explicit undo/redo operations
  • safe with respect to stable subject identity

2. Journal ownership

The journal belongs to the association topic, not only to the rendered page that happens to show it. A page may be one occurrence or one editable surface, but the history must attach to the first-class association subject itself.

3. Event model

The journal is an ordered log of association events. Each event has a durable id, timestamp, author or agent, target association id, and event payload.

3.1 Required event types

  • create-association
  • set-player1
  • set-player2
  • set-role1-type
  • set-role2-type
  • set-status
  • supersede-association
  • undo-event
  • redo-event

Additional metadata events may exist, but a minimal viable system needs at least the ability to create an association, change either player binding, and record undo/redo.

3.2 Event payload requirements

JournalEvent
  - event_id
  - association_id
  - event_type
  - timestamp
  - author
  - previous_revision
  - payload
  - inverse_of           ; optional, used for undo/redo linkage
  - supersedes           ; optional
  - note                 ; optional rationale

4. State reconstruction

Current association state is obtained by replaying journal events in order, starting from create-association. Replay must be deterministic.

  • If an event is undone, replay must ignore its forward effect and apply the undo event semantics.
  • If a later redo exists for that event, replay must reapply the intended forward effect.
  • At any point, the active state must be derivable without consulting hidden mutable fields.

5. Versioning policy

Changes to player1 or player2 are not silent field mutation. They create a new association revision. The system may materialize revisions as a revision number, as snapshots derived from the journal, or both.

The important invariant is that the historical sequence of role bindings remains inspectable.

5.1 Change classes

  • Binding change: player1 or player2 points to a different topic.
  • Role-meaning change: the role type labels attached to player1 or player2 change.
  • Status change: active, superseded, historical, draft, deprecated.
  • Supersession: a successor association replaces the current active one.

6. Undo / redo semantics

Undo and redo are explicit journal events, not hidden UI stack tricks. That means they are themselves inspectable, serializable, and replayable.

6.1 Undo

An undo-event names the target event being undone. The system computes or stores the inverse effect of that target event.

  • Undoing set-player2 restores the previous player2 binding.
  • Undoing set-player1 restores the previous player1 binding.
  • Undoing set-status restores the previous status.
  • Undoing supersede-association reactivates the superseded association only if no conflicting later state prevents it.

6.2 Redo

A redo-event reapplies a previously undone event. It must point to the specific undo-event or original event that it reactivates.

6.3 Branch policy

The system should choose one of two policies and make it explicit:

  1. Linear history policy: after undo, a new forward edit invalidates the redo chain beyond the current point.
  2. Branching history policy: after undo, a new forward edit creates a new branch while preserving the old redo lineage for inspection.

Recommended policy for topic/association systems: branching history. It is more honest about graph-shaped editorial evolution and aligns better with a first-class history object model.

7. Safety constraints

  • The stable subject topic key must never be altered by undo/redo of title-side relations.
  • An undo that would orphan the association or violate required role cardinality must be rejected or require explicit repair.
  • Replay must detect contradictory event order or missing predecessor state.
  • Role semantics must remain consistent for the association type across revisions.

8. Recommended rename workflow

For the common rename case, where the stable subject remains the same and the title changes:

  1. Keep the stable subject topic unchanged.
  2. Create a new title topic or identify an existing title topic.
  3. Record set-player2 or create a successor association revision.
  4. Mark the old title relation historical or superseded.
  5. Update presentation layers to resolve current display title from the active association.
  6. Keep journal history available for inspection and possible undo.

9. Minimum inspection surfaces

Any inspector or editor for this model should expose at least the following:

  • current association state
  • journal event list
  • revision lineage
  • active player1 and player2 bindings
  • undoable events from the current head
  • redoable events from the current head or branch

10. Example

Association A42
  type: subject-has-title
  player1: Topic S10   ; stable subject key = hyperdoc-runtime-model
  player2: Topic T17   ; "HyperDoc runtime model"

Event 1: create-association A42
Event 2: set-player2 A42 -> T18   ; "HyperDoc runtime vocabulary model"
Event 3: undo-event Event 2
Event 4: redo-event Event 2

The enduring subject is still S10. Only the title-side association state changes. Undo and redo do not delete the subject; they only traverse explicit history of the representation relation.

11. Resulting architectural rule

Stable identity is held by the subject topic. Mutable representation is held by one or more first-class association topics. Change history belongs to those associations and is captured in a replayable journal with explicit undo/redo events.
