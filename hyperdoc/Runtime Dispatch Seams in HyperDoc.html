Runtime Dispatch Seams in HyperDoc

A runtime dispatch seam is a compact execution boundary where authored syntax has already been normalized enough for work to be done, but is still close enough to the authored source that explanation, provenance, and diagnostics can attach to the same event.

In the broader boundary vocabulary, a dispatch seam is one especially consequential execution boundary, not the generic boundary abstraction as a whole.

What makes a dispatch seam architecturally important

A seam matters when it joins three things in one place:

  • the authored source form that a human can still recognize
  • the normalized operational form that a machine can execute
  • the live runtime situation where effects and failures become visible

When those three are co-present, inspectable explanation stops being an after-the-fact reconstruction problem. It becomes a normal byproduct of execution.

Retrospective pass versus same-protocol explanation

A retrospective explanation pass tries to reconstruct what happened after execution has already collapsed into output. It infers source relevance, context, branches, outputs, and failures later, which makes it vulnerable to semantic drift and provenance loss.

A dispatch-seam explanation is stronger because it records evidence at the same semantic boundary that performed the work. In that model, generation and explanation become twin outputs: the same event can produce the artifact and an execution evidence object, runtime provenance, a boundary report, and other inspectable traces without a second explanatory layer.

Smalltalk stepping seam

In the Smalltalk line of work around Expanding the Role of Tools in a Literate Programming Environment, executable explanation emerged from the triangulation of class browser, object inspector, and single-step debugger. The key primitive was CompiledMethod interpretNextInstructionFor: aContext. That seam sits near the language/runtime semantics and supports reading behavior off execution rather than inferring it from static source alone.

Mech emit seam

Mech is narrower and more domain-specific. It is not a VM-level stepper. It normalizes a block command into operation and arguments, assembles execution context, then dispatches through blocks[op].emit. That makes Mech a current analogue at the block-DSL level: not the same as the Smalltalk mechanism, but a practical block-level interpreter seam that is easier to operationalize in HyperDoc-style inspectable workflows.

Why seams matter for HyperDoc

HyperDoc already values inspectable runtime objects, graph-rooted publishing, and explanatory navigation across heterogeneous systems. A runtime dispatch seam is where those values can attach to execution itself.

  • Diagnostic publication can emit visible findings instead of burying them in logs.
  • Runtime provenance can tie generated artifacts back to source command and execution step.
  • First-class run records can preserve chronology, boundaries, and state changes as inspectable objects.
  • Published explanation can stay close to the same seam that performed the work.

Boundary of the analogy

The analogy should stay bounded. Smalltalk's stepping seam is deeper and more universal. Mech's seam is narrower and block-specific. HyperDoc should use that difference productively: Mech does not replace a debugger, but it does offer a concrete execution seam where explanation can become first-class.

Literate tracing as an adjacent trace-centered model

Literate Tracing is a useful adjacent reference point. It frames explanation around annotated, concrete execution traces rather than around a dispatch protocol directly. That makes it neither the same as the Smalltalk stepping primitive nor the same as Mech's emit seam, but it asks a closely related question: how can an execution-grounded account stay faithful enough to the run to explain real behavior rather than static intent alone?

For HyperDoc, the comparison is productive because it separates two layers. A runtime dispatch seam explains where evidence can be minted. Literate tracing suggests what a richer published form of that evidence might look like once it is preserved, annotated, and linked back into an explanatory surface.
