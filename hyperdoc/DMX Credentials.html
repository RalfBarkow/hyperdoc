DMX Credentials

hyperdoc

DMX Credentials names the DMX-core-native structure that carries username, password, and methodName after DMX reads an Authorization header or receives username/password input through a JSON login body. HyperDoc does not invent a competing credential object here. It only makes the DMX-side shape inspectable so operators can learn what the three repair-console input modes eventually mean at the backend boundary. The concrete learning object is a dmx-auth-path-example.

Backend shape

In dmx-platform, systems.dmx.core.service.accesscontrol.Credentials has three important public fields:

  • username
  • password
  • methodName

The constructor Credentials(String authHeader) splits the incoming Authorization header into method plus token, Base64-decodes Basic payloads, and then populates those fields. That means a repair-console example such as Basic YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA== can be shown safely as the same learning content as username alice plus password example-password.

What HyperDoc derives

HyperDoc's three input modes are not three different DMX-native credential formats. They are three operator entry paths that normalize to one of these backend outcomes:

  • username/password: HyperDoc derives an equivalent Basic Authorization header, which DMX can parse into a Credentials-like structure
  • authorization header: HyperDoc preserves the header as entered, and a Basic header can be decoded into the same Credentials-like display
  • bearer token: HyperDoc derives Authorization: Bearer ..., but no false DMX-core-native Credentials summary is claimed unless the installation proves a matching non-Basic auth method

What this page does not claim

  • It does not claim that JSESSIONID is a primary credential input mode.
  • It does not claim that bearer tokens are universally native to DMX core.
  • It does not claim that hyperdoc-mcp.service already has live auth configured.
