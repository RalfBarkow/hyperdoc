Hauptsache Entry Model

The hauptsache project should be understood as a public entry model, not as a company website clone and not as a raw wiki endpoint.

The relevant public surfaces are:

  • https://hauptsache.dreyeck.ch/assets/home/index.html
  • the FedWiki at hauptsache.dreyeck.ch

By contrast, www.hauptsache.ch is the company website and should not be treated as the project's working surface.

Idea 1: this is also a kiosk project

The key use case is not an abstract visitor on the open web. It is a visitor standing inside the hauptsache hairdressing salon while a wall screen displays the landing page.

That means the project includes a hardware/system slice as well. The Swiss German working title for that slice is Kioskberrli: a Raspberry Pi 4 Model B running a NixOS-based SD-card system that boots into the salon landing page.

Idea 2: separate entry from workspace

The landing page and the wiki do different jobs.

  • The landing page is the public entry surface.
  • The FedWiki is the working surface.
  • The kiosk target is ARM64 (aarch64-linux).

This separation keeps the first impression deliberate while still preserving the wiki as the editable, journaled, exploratory medium.

Idea 3: the landing page should orient, not replace

The landing page should explain what hauptsache is, who it is for, and where the visitor can go next. It should not try to duplicate the wiki's role as the place where ongoing work, notes, and page-to-page linking live.

In that sense the landing page is a threshold, not the whole building.

Idea 4: the wiki is the project memory

The FedWiki should be treated as the durable working memory of the project. That is where evolving topics, notes, examples, and linked pages belong.

This matches the pattern discussed in Story Neighborhood Workflow: the wiki is not just background content, it is the medium in which the project's neighborhood can grow and be maintained.

Idea 5: navigation should be explicit

A visitor arriving on the landing page should be given a clear path into the wiki. The most useful form is an explicit link such as:

  • enter the project wiki
  • read the current story
  • open the working notes

The landing page should not assume that the visitor already understands what a FedWiki is.

Idea 6: this is a Home Away From Home pattern

The model is close to the pattern described on the FedWiki page Home Away From Home.

The point of that pattern is not merely to redirect traffic. The point is to define a non-wiki front door while keeping the wiki as the real working system behind it.

Idea 7: the next implementation questions

Once this entry model is accepted, the next concrete questions are: 

What exact link or links should /assets/home/index.html offer into
hauptsache.dreyeck.ch?

What NixOS SD-card system should turn a Raspberry Pi 4 Model B into the
first Kioskberrli in the salon?

The first question defines the public handoff. The second defines the device that makes the landing page physically present in the salon.

That second question now has an initial concrete answer in the dedicated hauptsache repo: 

.#nixosConfigurations.kioskberrli.config.system.build.sdImage

This is a declared build target, not yet a proven kiosk artifact. So the project has only moved partway from “what should the kiosk system be?” to “how should that kiosk image be hardened and maintained in the salon?”.

A credible maintenance story still needs evidence for build, flash, boot, network bring-up, kiosk startup, and landing-page display on the target device.

For that next phase, see Salon Pi 4 Kiosk Hardening Checklist.

Pragmatic conclusion

The hauptsache project should be modeled as: 

public landing page
  ->
project wiki

not as: 

company website
  ->
project

and not as: 

raw wiki only
