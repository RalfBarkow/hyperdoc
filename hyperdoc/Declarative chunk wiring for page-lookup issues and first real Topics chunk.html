Declarative chunk wiring for page-lookup issues and first real Topics chunk

hyperdoc

This page records the current stable lookup-issue layering after the bounded lookup-issue extraction. The shared issue protocol now lives in hyperbook-explorer/lookup-failures.lisp, while HyperDoc keeps the topic-specific page repair semantics in hyperdoc-explorer/lookup-repairs.lisp and the chunk truth in hyperdoc/page-lookup-chunks.lisp.

Current layering

  • Shared issue model: lookup-issue, bounded-lookup-issue, page-lookup-issue, and function-lookup-issue live in hyperbook-explorer/lookup-failures.lisp.
  • Shared bounded hook API: current status, suggested repair, repair description, repair thunk, and details are derived through the bounded-issue hook surface exported from hyperbook-explorer.
  • Generic presentation: the shared Overview, Details, Repair, and Condition views render whatever the bounded issue reports at runtime. The explorer presents that state; it does not own repair policy.
  • HyperDoc page/topic semantics: hyperdoc-explorer/lookup-repairs.lisp specializes only the page/topic path that HyperDoc actually owns.
  • Chunk truth: hyperdoc/page-lookup-chunks.lisp determines whether the missing Topics target needs a new authored factory, a fresh materialization, or no repair at all.

Current page/topic diagnosis model

For a page-lookup-issue targeting HyperBook topics, HyperDoc computes a topic-page-availability-chunk from the expected topic title and derives the current issue state from that chunk on demand.

  • No authored factory in hyperdoc/topics.lisp: :needs-topic-creation
  • Authored factory exists but the Topics page is unresolved or the materialized signature is stale: :needs-local-materialization
  • Topics page resolves from the current running image: :fixed

That diagnosis stays chunk-first. The issue does not invent a separate page repair policy of its own. It asks the current chunk state, status reason, repair hint, and freshness evidence whenever the issue is rendered.

Current issue-to-chunk flow

  1. A page lookup failure first becomes a shared page-lookup-issue.
  2. HyperDoc enrichment routes only the topics target into the topic-page repair path.
  3. issue-target-chunk returns the matching topic-page-availability-chunk.
  4. The shared bounded hook API asks that chunk for current status, suggested repair, repair description, and runtime details.
  5. The issue-level Overview and Repair tabs therefore stay generic while still showing current topic-specific truth.
  6. The issue-level repair action remains inspect-first: it hands back the target chunk object.
  7. The bounded mutation helper is repair-lookup-issue-via-chunks, which ensures the target chunk in code and in the smoke tests.

What repair means for Topics

Ensuring the target chunk keeps the current topic diagnosis logic unchanged:

  1. If no authored topic factory exists, HyperDoc materializes a placeholder factory safely enough for this bounded repair path.
  2. If the authored factory already exists, HyperDoc keeps that authored source and refreshes only the running Topics materialization.
  3. If the Topics page already resolves, the issue is already fixed and no extra authoring plan is needed.

This is why a Topics repair is not modeled as writing a separate topic HTML file. Topics pages are derived from authored factories plus runtime materialization state.

Presentation boundary

The shared explorer views remain presentation-only. They render:

  • preserved authored evidence from issue creation,
  • current bounded status from runtime hooks,
  • current repair description and details,
  • and the current repair object or thunk result.

Manual title-bar status buttons still exist as editorial overrides, but the runtime-owned topic diagnosis now comes from chunk state rather than from a hand-maintained repair string.

Most important corrections

  • Do not treat a missing Topics page as a missing standalone HTML file.
  • Do not route non-Topics page failures through HyperDoc topic repair semantics.
  • Do not collapse function lookup into the page/topic chunk model. Both issue classes share the bounded protocol, but each keeps its own runtime truth.
