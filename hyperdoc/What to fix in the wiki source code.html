What to fix in the wiki source code

Mostly wiki-client, not wiki-server.

The server proxy already does the right basic transport fallback: it builds remote candidates as https://... then http://..., and /proxy/* uses that fallback before returning 502.

What is broken is the client’s handling of failure.

1) Fix stale neighbor state in wiki-client/lib/neighborhood.js

Right now, when sitemap refresh fails, the code marks the neighbor as failed and logs Unable to fetch sitemap for ${site}, but it does not invalidate any previously cached sitemap or siteIndex.

Then neighborhood.search still searches any neighbor that has a siteIndex. If sitemap is missing or invalid, it logs +++ sitemap not valid for ..., sets neighborInfo.sitemap = [], but it still searches the stale index and then tries to resolve matches back through neighborInfo.sitemap.find(...). That is how you get misleading search and UI behavior after a fetch failure.

What to change:

  • In the sitemap fetch error path, clear the cached search state too.
  • Set neighborInfo.sitemap = null.
  • Set neighborInfo.siteIndex = null.
  • Set neighborInfo.lastModified = 0.
  • Optionally set neighborInfo.error = err.
  • In neighborhood.search, only search a neighbor when there is a valid sitemap.
  • If a search hit cannot be mapped back to a sitemap entry, drop it.

Minimal logic rule: sitemap is authoritative, siteIndex is derivative. Never trust an index after sitemap fetch has failed.

2) Fix route discovery in wiki-client/lib/siteAdapter.js

The current adapter logic determines reachability and prefix by probing /favicon.png with AJAX, and on failure it stores an empty prefix, which later makes the whole site look unreachable.

That is too tightly coupled to favicon availability and browser security behavior.

What to change:

  • Stop using /favicon.png as the authoritative probe for remote site reachability.
  • Probe system/sitemap.json instead.
  • For remote sites viewed from an HTTPS wiki, do not start with a direct cross-origin browser AJAX probe.
  • Go straight to the server proxy path: /proxy/${site}/system/sitemap.json.
  • Treat favicon as decoration only.

This is the core design defect behind the observed logs: the client currently answers “can I talk to this wiki?” by asking “can I AJAX-fetch its favicon?”

3) Keep neighbors.js honest about failure

formatNeighborTitle currently catches bad sitemap state and only logs +++ sitemap not valid for .... That hides a real invalid-state condition behind a title-generation path.

What to change:

  • If a neighbor is in failed state, show that explicitly in the title text.
  • Do not treat missing or invalid sitemap as a normal variant of a loaded neighbor.
  • Consider a distinct state flag such as neighborInfo.failed = true.

4) Add tests for the actual broken state transitions

The current neighborhood tests cover an unpopulated neighbor, but they do not cover the more dangerous case where a neighbor had a valid sitemap and site index, a later refresh fails, the stale index survives, and search still runs.

Add tests for:

  • failed sitemap refresh clears siteIndex
  • search skips neighbors with invalid or missing sitemap even if siteIndex exists
  • retry after failure repopulates cleanly
  • siteAdapter on HTTPS uses proxy-first for remote sitemap probing
  • favicon failure does not by itself mark a site unreachable

5) wiki-server changes are optional, not primary

I would not make the server the first patch target here. Its proxy behavior is already aligned with the intended fallback model.

Useful server-side improvements, but secondary:

  • better 502 diagnostics in logs
  • include which candidate URL failed
  • optionally include a debug header in non-production for the attempted upstream URL

Smallest high-value patch

If you want the narrowest fix set:

  1. In wiki-client/lib/neighborhood.js, invalidate cached sitemap and index on fetch failure and require a valid sitemap before search.
  2. In wiki-client/lib/siteAdapter.js, change remote prefix discovery from favicon probe to sitemap probe, preferably proxy-first on HTTPS pages.

That removes the misleading sitemap not valid secondary symptom and makes the client fail for the right reason instead of poisoning its own cache.
