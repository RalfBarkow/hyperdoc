Repairing duplicate DMX admin username ambiguity

hyperdoc

Repairing duplicate DMX admin username ambiguity is the concrete workflow page for the failure shape in which two Neo4j topics match dmx.accesscontrol.username = admin and DMX login/bootstrap becomes ambiguous. The workflow is inspection first, plan second, guarded repair third, verification fourth.

The supported repair for this first slice is intentionally narrow: rename the stale standalone duplicate off admin while preserving the canonical account-backed identity. Rename is preferred over delete because it preserves evidence and reduces blast radius on an already damaged store.

Inspection report

The read-only report object gathers the exact duplicate-username evidence needed for this case: matching username topics, owning dmx.accesscontrol.user_account topics, workspace assignment evidence, and password-topic presence. Classification is decided in Lisp from that structured report data. The view layer only displays the result.

The supported shape is:

  • exactly two matching username topics,
  • exactly one account-backed canonical identity,
  • exactly one standalone stale duplicate,
  • no unresolved ambiguity left after report classification.

Reviewed repair plan

A neo4j-duplicate-username-repair-plan exists before execution. It already contains the deterministic stale node id, canonical node id, rename target, backup path, and verification operation. Execution does not fill in missing operational details later.

  • No implicit backup-path generation during execution.
  • No implicit offline assumption.
  • No inferred stale/canonical ids at mutation time.
  • No implicit approval.

Offline-only preconditions

The guarded repair verb refuses unless all offline-only preconditions are already satisfied in Lisp:

  • the local DMX/Neo4j instance is explicitly confirmed stopped,
  • a backup path is present and recorded on the plan,
  • the inspection report still proves the supported duplicate-admin shape,
  • the deterministic rename target remains the reviewed one.

This refusal-first behavior matters because the surrounding store may already be damaged. The duplicate-admin workflow stays available, but broader Lucene or Neo4j recovery remains a separate later boundary.

Refusal behavior

Unsupported cases remain inspectable refusals rather than auto-falling into a broader maintenance shell. Refusal is the correct outcome when:

  • approval is missing,
  • offline confirmation is missing,
  • backup evidence is missing,
  • the report is ambiguous or unsupported,
  • the live store no longer matches the reviewed plan.

Verification after repair

Verification remains separate from mutation. First the store is reinspected for the username value. Later, after restart, the live HTTP username probe checks that authentication bootstrap moved past the old ambiguity blocker. That post-repair probe is read-only.
