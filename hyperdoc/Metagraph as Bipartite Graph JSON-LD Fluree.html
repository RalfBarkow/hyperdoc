Metagraph as Bipartite Graph: JSON-LD + Fluree

hyperdoc

This HyperDoc page turns the attached article into a topic-oriented, inspectable implementation note. The central move is to model a metagraph as a layered graph in which relationships are first-class nodes, then persist the result as JSON-LD in Fluree's temporal ledger.

The page is deliberately not a linear reproduction of the article. It is a HyperDoc working surface: concepts become topics, implementation fragments become code snippets, and operational checks become clickable examples.

Core claim

Ordinary triples are adequate for simple facts, but they become awkward when the system must ask questions about relationships: who verified an attendance, when it became true, whether it caused another event, or how a decision changed over time. The metagraph solution is to promote relationships to addressable entities.

In this page's terminology, a relationship that matters operationally should be a Relationship node, not only an edge property. That lets the relationship participate in further causality, context, provenance, and temporal queries.

Layer model

The article's implementation pattern uses three semantic layers:

LayerNode roleExamples
NEntity nodespeople, projects, features, milestones, concepts
ERelationship nodesmeetings, decisions, consequences, causal links
SSubgraph nodesepisodes, contexts, narratives, named graphs, schemas

The useful invariant is not merely “there are three labels”. It is that every edge crosses a declared boundary: N→E, E→N, E→S, S→E, or S→S. Direct N→N and E→E shortcuts are modeling errors.

Vocabulary starter

The vocabulary gives each layer and predicate a portable URI. This is the smallest useful shape of the model, condensed for documentation. 

{
  "@context": {
    "@vocab": "https://metagraph.ai/vocab#",
    "mg": "https://metagraph.ai/vocab#",
    "xsd": "http://www.w3.org/2001/XMLSchema#",
    "rdfs": "http://www.w3.org/2000/01/rdf-schema#",
    "owl": "http://www.w3.org/2002/07/owl#",
    "prov": "http://www.w3.org/ns/prov#"
  },
  "@graph": [
    { "@id": "mg:EntityNode", "@type": "owl:Class" },
    { "@id": "mg:RelationshipNode", "@type": "owl:Class" },
    { "@id": "mg:SubgraphNode", "@type": "owl:Class" },
    { "@id": "mg:MEMBER_OF", "@type": "owl:ObjectProperty" },
    { "@id": "mg:PART_OF", "@type": "owl:ObjectProperty" },
    { "@id": "mg:REFERENCES", "@type": "owl:ObjectProperty" },
    { "@id": "mg:CONTAINS", "@type": "owl:ObjectProperty" },
    { "@id": "mg:RELATES_TO", "@type": "owl:ObjectProperty" }
  ]
}

SHACL guard for the model

The write-time guard belongs in SHACL: it turns the layer contract into a database constraint rather than a style convention. 

{
  "@context": {
    "mg": "https://metagraph.ai/vocab#",
    "sh": "http://www.w3.org/ns/shacl#",
    "xsd": "http://www.w3.org/2001/XMLSchema#"
  },
  "@graph": [
    {
      "@id": "mg:EntityNodeShape",
      "@type": "sh:NodeShape",
      "sh:targetClass": { "@id": "mg:EntityNode" },
      "sh:property": [
        { "sh:path": { "@id": "rdfs:label" }, "sh:minCount": 1 },
        { "sh:path": { "@id": "mg:kind" }, "sh:minCount": 1 }
      ]
    },
    {
      "@id": "mg:RelationshipNodeShape",
      "@type": "sh:NodeShape",
      "sh:targetClass": { "@id": "mg:RelationshipNode" },
      "sh:property": [
        { "sh:path": { "@id": "mg:relationKind" }, "sh:minCount": 1 },
        { "sh:path": { "@id": "mg:arity" }, "sh:minCount": 1 }
      ]
    }
  ]
}

Participation as role-bearing data

Participation nodes keep role and position metadata without collapsing the metagraph back into flat edge annotations. 

{
  "@id": "mg:participation/carol-decision",
  "@type": "mg:Participation",
  "mg:participant": { "@id": "mg:person/carol" },
  "mg:inRelationship": { "@id": "mg:decision/accelerate-q2" },
  "mg:role": "authority",
  "mg:position": 1
}

Queries: participants and causal chain

SPARQL: participants in the planning meeting

PREFIX mg: <https://metagraph.ai/vocab#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?personLabel ?role ?position
WHERE {
  ?p mg:inRelationship mg:event/planning-meeting-2026-03-24 .
  ?p mg:participant ?person .
  ?p mg:role ?role .
  ?p mg:position ?position .
  ?person rdfs:label ?personLabel .
}
ORDER BY ?position

SPARQL: causal links as first-class relationship nodes

PREFIX mg: <https://metagraph.ai/vocab#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?causeName ?effectName ?strength
WHERE {
  ?causal a mg:RelationshipNode ;
          mg:relationKind "Causality" ;
          mg:strength ?strength .
  ?cause_p mg:inRelationship ?causal ;
           mg:role "cause" ;
           mg:participant ?causeNode .
  ?effect_p mg:inRelationship ?causal ;
            mg:role "effect" ;
            mg:participant ?effectNode .
  ?causeNode rdfs:label ?causeName .
  ?effectNode rdfs:label ?effectName .
}
ORDER BY DESC(?strength)

Temporal layer

Fluree's ledger model adds transaction time: the graph can be queried as it existed at a prior block or timestamp. The vocabulary also carries valid-time predicates, which describe when a statement was true in the modeled domain. 

{
  "ledger": "metagraph/planning",
  "query": {
    "select": { "?event": ["*"] },
    "where": [
      ["?event", "@type", "mg:RelationshipNode"],
      ["?event", "mg:relationKind", "?kind"]
    ]
  },
  "opts": {
    "as-of": "2026-03-24T17:00:00Z"
  }
}

That query should return the meeting and decision but exclude the scope-cut consequence, because the consequence enters the ledger later.

Named-graph provenance

Named graphs let the model preserve multiple perspectives on the same event. An observer's notes, confidence score, timestamp, and claims can be attached to the graph that contains the claims. 

{
  "@id": "mg:named-graph/bob-meeting-notes",
  "@type": "mg:SubgraphNode",
  "mg:subgraphKind": "provenance-graph",
  "prov:wasAttributedTo": { "@id": "mg:person/bob" },
  "mg:confidence": 0.85,
  "@graph": [
    {
      "@id": "mg:event/planning-meeting-2026-03-24",
      "mg:mood": "tense"
    }
  ]
}

When this stack fits

  • Use it when relationships are events you must query, annotate, and relate.
  • Use it when history is part of the knowledge rather than an audit afterthought.
  • Use it when provenance and multi-agent perspectives must be preserved.
  • Use it when causal reasoning should be a graph query instead of an application procedure.
  • Avoid it for high-throughput write paths or simple transitive graphs that do not need meta-level reasoning.
