Code path graphs in HyperDoc

hyperdoc

Code path graphs in HyperDoc defines a reusable inspectable graph object family for two closely related jobs: curated architectural call graphs and traced runtime code paths. HyperDoc renders from graph objects with multiple inspector views rather than treating one static diagram as the source of truth.

Why HyperDoc Starts Here

  • Start from inspectable objects, not from an exhaustive static Lisp call-graph extractor.
  • Keep nodes and edges typed and inspectable so one graph can support several views.
  • Allow curated graphs and traced graphs to share the same rendering and export path.
  • Keep Graphviz DOT export derived from the graph object rather than making DOT the only representation.

Shared Object Shape

The reusable base object is code-path-graph. It carries stable graph identity and editorial framing through id, title, and summary, plus the graph payload in entrypoints, nodes, edges, optional trace-events, and optional focus-paths.

Nodes carry meaningful path steps such as read entrypoints, diff engines, explicit write helpers, runtime step events, or terminal states. Each node can also point back to a concrete source anchor through source-file/source-function and, when useful, to a runtime object anchor, HyperDoc topic id, or literal expr handle.

Edges carry from, to, kind, status, and summary, plus optional flags such as write-capable-p. That is enough to show safe read paths, suppressed write edges, or traced runtime transitions without inventing a generic persistence layer.

Default Inspector Views

  • Overview: graph counts, entrypoints, focus-path list, and graph-specific summary extras
  • Nodes: source-backed node catalog with optional object/topic anchors
  • Edges: typed transitions with status and write-capable flags
  • Focused paths: curated or traced subpaths through the graph
  • Source references: concrete source anchors for the live graph nodes
  • DOT export: Graphviz DOT text derived from the current graph object

Two Concrete Uses

  • Curated architectural graph: DMX workspace journal reconcile call graph models the reconcile-on-read boundary around companion journal note 924694 in topicmap 919822. It keeps the active read path, focused paths, and the suppressed write edge inspectable.
  • Traced runtime graph: the live Playground stepper now derives a playground-stepper-code-path-graph object from the current stepped source selection. That turns runtime step state into the same reusable graph surface instead of requiring a separate one-off picture object.

Relation To The Diagramming Debugger Surface

Diagramming Debugger Surface already established the practical design direction: meaningful runtime steps, explicit trace events, inspector views, and Graphviz export. The reusable code-path-graph abstraction generalizes that successful pattern so the same rendering vocabulary also works for curated architectural diagrams like the DMX reconcile boundary.

Boundary

This slice does not introduce a generic raw graph persistence layer, and it does not promise an exhaustive static Lisp call graph. The graph object is an inspectable runtime/documentation surface first. If a future slice adds tracing or static extraction, it should still materialize its results into this graph object family rather than bypassing it.
