Boundary

hyperdoc

A Boundary is a bounded transition or contract edge where one mode of access, representation, authority, or execution gives way to another. In HyperDoc, a boundary is not mere policy prose: it should exist as an inspectable runtime object whose sides, crossing condition, evidence, and failure classifications can be inspected directly.

Boundary as object, not only prose

HyperDoc already distinguishes durable pages, inspectable topic handles, runtime objects, and parallel documentation surfaces. A boundary belongs in that same operational model. The page explains the concept, but the runtime object carries the sides, crossing condition, evidence, and blocked or successful crossing state.

Static and dynamic boundaries

Some boundaries are static contracts. They define what counts as a valid representation, read path, mutation target, or authority edge. Others are dynamic stage crossings inside one run, such as the moment a guarded preflight must succeed before later mutation stages may proceed.

  • Contract boundary: stable access or representation rule.
  • Transition boundary: concrete stage crossing during one run.
  • Authentication boundary: explicit authority crossing before guarded mutation.
  • Read-write boundary: contract boundary that distinguishes stable read and write targets.

Boundary is not seam, report, or surface

A boundary is broader than the existing runtime dispatch seam vocabulary. A seam is one especially important execution boundary, but not every boundary is a seam.

A boundary is also not the same as a boundary report. A report summarizes unresolved or blocked crossings. The boundary itself is the contract or stage edge being crossed or blocked.

Nor is a boundary identical with a documentation or diagnostic surface. The existing documentation surfaces and HyperDoc surface boundaries vocabulary describes where explanation or action appears. A boundary describes the crossing or contract edge that those surfaces expose.
