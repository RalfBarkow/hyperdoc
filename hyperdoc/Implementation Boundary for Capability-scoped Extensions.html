Implementation Boundary for Capability-scoped Extensions

This page marks the current implementation boundary between written design and eventual runtime surfaces for the capability/WebXDC cluster. It explains what remains in the planning phase, sketches the inspectable objects that must exist later, and links back to the continuity shells that precede the runtime work.

What remains documentation and planning

  • Capability-scoped extension – the HyperDoc/FedWiki host API contract must still be scripted, documented, and paired with a FedWiki twin that reports manifest intent.
  • Declarative extension manifest – the manifest schema and review surface are notes at this point; the FedWiki twin will describe how to inspect requested powers before granting them.
  • Consent-gated execution – the user-visible consent template is a planning artifact, not yet wired to a running command.
  • Shared-state app story item – the shared state object is being recorded as a continuity shell rather than actual host storage.
  • WebXDC-style story item – the packaged-app parent/app contract is documented here, but no runtime boundary has been enforced yet.

Eventual runtime surfaces

Once the documentation settles, the stack will need:

  • a host-managed service that enforces declared capabilities
  • a manifest inspector that publishes requested powers and highlights UI/data effects
  • a consent UI that records the user’s decision before any extension runs
  • a host/app message contract with signature, origin, and replay rules
  • an item-local shared-state object that survives story-item restarts

Inspectable objects to expect later

  • Capability profile – the manifest’s ability list plus risk metadata.
  • Consent decision – a logged, inspectable approval or denial record.
  • Host/app message contract – the traceable `postMessage`/WebXDC channel signature.
  • Item-local shared state object – the persisted state container attached to each story item.

None of these objects exist in this slice. They are called out here so future runtime work knows where to attach findings, instrumentation, and FedWiki twins.

Continuity shells

The five topics above now have HyperDoc continuity shells that describe the pending FedWiki twins and host surfaces. Each one will eventually branch toward a FedWiki page (slug matching the topic slugs) that mirrors this page’s planning notes and links back to a running implementation.

This is also the place to record interim FedWiki links so that collaborative writers can anchor future narrative drafts without waiting for the runtime plumbing.

Why nothing is implemented yet

The documentation deliberately stops short of wiring new sandboxed execution surfaces. The job is to describe the boundaries, not to invent host APIs or message protocols that might later change. When the API/manifest/consent story stabilizes, the inspectable objects listed above will be created, and the FedWiki twins referenced here will become what we publish.
