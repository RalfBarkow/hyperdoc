Universal Thing and Browser Isolation in FedWiki

Ward's Matrix post adds a compact legend for a browser-centered execution diagram and, more importantly, highlights a test seam: a custom isolation layer can be exercised with Universal Thing standing in for the browser.

Diagram legend

  • Gold = blocks
  • Pink = arguments provided with commands
  • Tan = user action to proceed
  • Blue = data passed as interpreter state
  • White = styled features, input, and output

These colors are diagram notation for reading the execution story. They are not separate HyperDoc topic pages and should not be promoted into their own durable topic cluster.

What is new here

The new material is not just the legend. The operational addition is the custom browser-isolation layer: browser-facing behavior is pulled behind a test seam and exercised with Universal Thing as the collaborator that stands in for the browser.

That makes the browser protocol testable. Command arguments, the user action that advances execution, interpreter state, and the styled input/output surface can all be described without requiring the live browser itself to be the only runtime host.

Why Universal Thing matters

Universal Thing matters because it acts as a browser stand-in: a test double, surrogate runtime collaborator, and harness component for browser-facing behavior. It makes it possible to isolate the protocol that the interpreter expects from the browser and to test that protocol outside the browser.

In HyperDoc terms, this fits the existing split between documentary pages and runtime objects. The page can explain the seam durably, while any live DMX proxy layer remains a separate runtime surface that should only be bound once stable DMX identifiers are known.

Host-defined extension boundary

The browser-isolation move should not be read as a license to run arbitrary page JavaScript. It points in the opposite direction: browser-facing powers should be pulled behind a host-defined API boundary that HyperDoc or FedWiki controls explicitly.

That is the durable pattern worth keeping. Comparative systems such as Figma plugins, browser WebExtensions, and Jamovi differ in detail, but they share the same architectural move: the host defines the verbs, mediation, and policy surface instead of letting every document inherit ambient browser privilege.

In this cluster, Universal Thing and the browser isolation layer are the in-tree evidence that this boundary already wants to exist. The browser role is becoming an explicit collaborator, not an unbounded execution environment.

Explicit consent and capability partitioning

Once the host owns the extension boundary, consent can be made explicit rather than accidental. A click on a link or a page load should not silently authorize execution with broad powers.

The permission split should stay effect-oriented: an extension may ask to change content, change user interface, access data, or transform data. Those are meaningfully different powers and should not collapse into one generic "run script" permission.

The local follow-on pages for that idea are Capability-scoped Extensions for FedWiki and WebXDC-style Story Items for FedWiki and HyperDoc. They extend this browser-isolation note without promoting every comparative example into its own durable topic page.
