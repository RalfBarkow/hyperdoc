ASDF Systems, Examples, and Tests in HyperDoc

hyperdoc

HyperDoc should organize runnable exploration around ASDF systems. In real ASDF terms, a system is a named top-level component defined in a .asd file and used as the boundary for operations such as loading and testing. The root HyperDoc object should express what HyperDoc is; one hop away, an ASDF system expresses what belongs together, which examples explain it, and which test surfaces verify it.

For the detailed ASDF grounding behind this page, see Understanding ASDF Systems in HyperDoc. This page focuses on the architectural consequence for examples and tests after that ASDF model is understood.

ASDF terms that matter here

  • System: the named top-level ASDF component that asdf:find-system resolves and that operations such as load-op and test-op target.
  • Component: any node in the ASDF graph. Systems, modules, and source files are all components.
  • Module: a parent component that groups child components, often mirroring a directory or an ordered cluster of files.
  • Source file: a leaf component that names a concrete source file to compile or load.
  • Operation: an action planned over the component graph. load-op loads a system into the image; test-op runs the system's test entry point, often through a separate test system.
  • Source registry: the configuration that tells ASDF where to look for system definitions. A system is only discoverable when it is visible there.

Why ASDF systems are the right scope

ASDF systems already define the boundary HyperDoc needs. A system names a loadable and testable unit, gathers related components, and exposes the dependency structure that makes that unit meaningful. That makes it a better scope object than the HyperDoc root object or a loose package list.

Edmund Weitz's Common Lisp Recipes provides a practical external justification for the same choice. His ASDF recipes treat the system definition as the place where project layout, components, dependencies, and publication metadata come together. That is exactly why HyperDoc should attach examples and tests to ASDF systems rather than to a root-level package list or a free-floating checks console.

GT often uses the package as an example scope. HyperDoc should translate that idea explicitly rather than copy it literally: Common Lisp packages are name spaces, but ASDF systems are the top-level build/load/test boundaries. HyperDoc should therefore use the ASDF system as the scope object and keep packages as a secondary low-level surface for code archaeology.

This repository already uses that style of boundary in hyperdoc.asd and hyperbook.asd: explicit defsystem forms define systems such as hyperdoc, hyperdoc/explorer, hyperdoc/server, hyperbook, and hyperbook/explorer. These slash-named systems are real ASDF systems, not pseudo-folders. They matter because they let HyperDoc distinguish main systems from narrower explorer or test subsystems without inventing a parallel scope model.

Package-inferred systems matter in ASDF because they can derive component structure from package and file naming conventions. HyperDoc should know that model exists, but this repository is not organized that way. The current repo uses explicit system definitions, so the explorer should present the explicit system boundaries that ASDF already knows.

Quicklisp and Quickproject fit around that architecture rather than replacing it. Quicklisp is the practical library distribution layer that helps obtain systems ASDF can then find and load, and Quickproject can generate a project skeleton with system definitions and dependency declarations already in the right place. In this repository, that remains ecosystem context rather than a local prerequisite: the flake sets up SBCL and ASDF registry visibility directly.

The source registry matters for this scope model as well. HyperDoc can only present meaningful system objects if asdf:find-system can resolve them in the running image. In practice that means the Nix development shell and dev.sh are part of the documentation story: they establish the source-registry context in which the local systems are visible.

Existing inspection seam

HyperDoc already has the right seam for this architecture. The system html-inspector-views/standard ships views for ASDF systems and components, including source, children, dependencies, and plans. The systems component of that system is the source file that defines those views.

HyperBook Explorer already exposes real asdf:system objects through its ASDF Systems hyperbook. HyperDoc should extend those existing ASDF object views with Examples, Tests, and secondary Packages surfaces rather than wrapping systems in a HyperDoc-local pseudo-scope.

Examples belong to a system

Examples explain a system. In ASDF terms, an example becomes available because the source-file component that defines its defexample form is part of that system's load plan. A system-scoped examples surface therefore answers which runnable slices belong to this unit, what they are trying to show, and which inspectable results they produce.

That system-scoped picture also applies to portable examples. In this repository, base examples belong to :hyperdoc, portable examples belong to :hyperdoc/examples, and narrower operational examples belong to :hyperdoc/examples/ops. The resulting example system boundary keeps the Examples surface aligned with the ASDF system that actually loaded the defining files instead of flattening all example layers into one root-global list. See Portable examples in HyperDoc for the repo-local boundary in more detail.

That placement keeps the HyperDoc root honest. Root views should express what HyperDoc is: pages, topics, and system scopes. They should not pretend that all examples in the image belong to one undifferentiated root console.

Run as an example action

Run should be an action on each scoped example. HyperDoc already has the per-example ► affordance on top-level defexample forms; the architectural move is to present that action under the owning ASDF system rather than as a free-floating mechanism.

This keeps the GT lesson intact in HyperDoc terms: pick a scope object, list its examples, and let each example run into an inspectable result object.

Tests are separate from identity

Tests verify a system; they do not define the stable identity of the HyperDoc root object. Test surfaces should sit one hop away from root identity, attached to the relevant system or test subsystem.

This follows ASDF practice as well. Testing is often attached to a separate slash-named test system, and test-op is an operation over a system boundary rather than a property of the documentation root object.

Examples and tests are related because both are runnable. They are distinct because examples are exploratory and pedagogical, while tests are operational and verification-oriented. Internally they currently share the check-* runtime model.

Relation to HyperDoc Test Runner

The HyperDoc Test Runner remains the runtime model for check-spec, check-result, and check-run. What changes is placement: the runner should be entered through system-scoped test surfaces, not taught as a primary facet of the HyperDoc root object.

This keeps the runner useful without confusing test tooling with the root identity surface.
