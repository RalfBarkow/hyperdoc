Why a commit hash can stay outside the target branch even when its content is integrated

hyperdoc

Commit equivalence vs ancestry names a recurring merge-intent confusion: an original commit hash can remain outside the target branch even though the target branch already contains the same content under a replayed hash.

This happens after cherry-pick or replay-style integration. The graph keeps the original commit on the preserved source branch, while the target branch receives a new commit object with different identity but equivalent patch content.

Operational rule

  • Do not confuse original commit identity with content integration.
  • Use ancestry to answer whether the original object is reachable.
  • Use git cherry, left/right history, and git range-diff with an explicit shared base to answer whether the content was replayed equivalently.
  • Do not use a floating remote ref as the primary range-diff base once the target branch has moved.
