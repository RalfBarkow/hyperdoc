Journal Gate Script and Lisp Implementation

hyperdoc

This page documents the commit gate script used for localhost FedWiki page edits and exposes the Lisp implementation source as inspectable functions.

The gate is not a general linter. It is a semantic gate for localhost FedWiki page journal integrity: replayability, creation ordering, action chronology, and revision reconstruction.

Inspectable objects

  • Journal checker commit gate
  • Journal gate script and Lisp implementation
  • Journal date origin and fork chronology
  • Journal monotonic normalization

Gate rule

A page is commit-blocked when checker findings include any of: CREATION, CHRONOLOGY, REVISION, or MALFORMED.

The blocking findings set is held in +journalmatic-commit-gate-findings+. A page passes only when journalmatic-commit-gate-findings returns NIL.

Syntax and semantics

python3 -m json.tool is necessary but not sufficient. It validates JSON syntax and basic structure. It does not prove that a FedWiki page journal replays cleanly, that action dates are monotonic, or that revision reconstruction matches the current story.

The journal gate is the semantic check that follows syntax validation. Use both steps in that order.

Lisp source

The reusable helpers live in hyperdoc/journal-gate.lisp. These functions define the gate findings set, derive page-level gate findings, and return a pass/fail gate decision.

Runnable script

The runnable gate script lives at tools/journal-gate.lisp. It is a thin wrapper around the Lisp helpers:

  • load :hyperdoc
  • read one or more localhost FedWiki page JSON files
  • normalize the raw page JSON into the plist shape expected by the gate helpers
  • print one result per page
  • exit nonzero if any page is commit-blocked

Adapter rule: if raw page JSON contains string values in journal action type fields, the script normalizes those strings to keywords before calling the Lisp gate helpers. 

nix develop --command sbcl --no-userinit --script tools/journal-gate.lisp \
  tools/testdata/journal-gate/good-page.json \
  tools/testdata/journal-gate/bad-chronology-page.json

Worked example

The fixture pair under tools/testdata/journal-gate/ shows one page that passes and one page that is commit-blocked on chronology. The exact pass/fail shape is: 

JOURNAL_GATE tools/testdata/journal-gate/good-page.json
(:FINDINGS NIL :PASS? T)

JOURNAL_GATE tools/testdata/journal-gate/bad-chronology-page.json
(:FINDINGS (:CHRONOLOGY) :PASS? NIL)

The inspectable Lisp example journalmatic-commit-gate-script-example returns the same model in a richer form: 

(:GATE-FINDINGS (:CREATION :CHRONOLOGY :REVISION :MALFORMED)
 :BAD-PAGE (:TITLE "Chronology Example"
            :FINDINGS (:CHRONOLOGY)
            :PASS? NIL)
 :GOOD-PAGE (:TITLE "Example Journal Page"
             :FINDINGS NIL
             :PASS? T))

Timestamp policy

Earlier manual page generation used hardcoded date values. Some values were ahead of real fork time, so a later fork action got a smaller timestamp and created chronology/revision errors.

Use wiki-client style date generation instead:

  • base date source: runtime epoch milliseconds (Date.now() equivalent)
  • per-action write rule: max(now, last-date + 1)
  • never hardcode fixed date constants in generated journals

Rule (canonical wording): action dates use runtime epoch millis with monotonic rule: max(now, last-date + 1).

Monotonic normalization

For imported/forked journals with out-of-order dates, normalize dates in the current action order so chronology is monotonic while story replay semantics stay aligned with action sequence.

Monotonic normalization is a repair tool, not a license to ignore the gate. After repair, run the semantic gate again and commit only when the blocking findings are gone.

Operational sequence

  1. Run python3 -m json.tool for JSON syntax and structure.
  2. Run journal checker and compute commit-gate findings.
  3. If any gate findings remain, repair journal before commit.
  4. Commit journal repairs separately from docs/topic updates.
