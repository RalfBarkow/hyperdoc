Integrate Ward's story-neighborhood update into HyperDoc

This note proposes a narrow HyperDoc slice that integrates Ward's newer story-neighborhood and book-assembly thread into the existing Mech/ Story-Neighborhood cluster.

Recommended scope

Do not create a parallel cluster. Fold the new material into the existing pages Story Neighborhood Workflow, Story Neighborhood Workflow Entry Point, and Inspectable Mech Runs, and add one new page for the saved/timestamped report history.

Why this shape fits the current repo

  • Story Neighborhood Workflow already covers story as seed set, WALK by clicks, gateway/neighborhood/book scope, and PRINT draft.
  • Story Neighborhood Workflow Entry Point still treats PRINT/REVIEW as partly missing concrete surfaces.
  • Mech Plugin Progress March 2026 and Inspectable Mech Runs already frame findings, reports, and run records as inspectable publication surfaces.

Ward's newer thread adds four things that deserve explicit capture:

  1. SOLO as overlap browser across multiple WALK result sets.
  2. The editorial staircase 1 click -> 2 clicks -> 3 clicks.
  3. PRINT draft plus PREVIEW synopsis items as report publication, not only artifact generation.
  4. Saving timestamped report pages and walked aspects as comparable editorial history.

  • Update: hyperdoc/Inspectable Mech Runs.html

New topic handles

  • gateway-page-topic — first-hop page that must reset reader context when leaving the authored story.
  • story-neighborhood-report-topic — saved report page describing one bounded WALK/PRINT run.
  • walked-aspect-set-topic — the set of aspects handed from WALK to SOLO or PRINT.

I would not add separate topics for every detail such as gold overlaps, review variations, or click count. Those can stay page-local prose.

  • PRINT plus PREVIEW as report publication — explain PRINT draft and PREVIEW synopsis items as publication of decisions.

Add one short section connecting the proposed run-object model to Ward's saved report pages:

  • a timestamped synopsis page is a publication surface for one run

4. New page: Timestamped Story-Neighborhood Reports

This should be the durable page for Ward's 05:02–05:10 material. It should explain:

  • PRINT emits draft plus decision statistics
  • PREVIEW synopsis items can materialize those decisions as wiki items
  • authors can save timestamped report pages during iteration
  • each report should also link back to the walked aspects used for that draft
  • the result is a side-by-side comparable editorial history of variants

Draft text for the new page

<h1>Timestamped Story-Neighborhood Reports</h1>

<p>
A story-neighborhood run should not disappear after one draft download. When
<tt>PRINT</tt> assembles a draft, it also makes editorial decisions about scope,
missing pages, unresolved references, item-type wishes, and other boundaries.
Those decisions are useful review material in their own right.
</p>

<p>
Ward's newer workflow makes that review material publishable. A stack such as:
</p>

<pre>
WALK 3 clicks
PRINT draft
PREVIEW synopsis items
</pre>

<p>
can materialize a draft and also publish synopsis items describing how the
assembly proceeded. Those synopsis items can then be saved as ordinary wiki
pages.
</p>

<h2>Why save reports</h2>

<p>
While reviewing a draft, one often wants to compare variants: one click versus
two clicks, one neighborhood source set versus another, or one editorial repair
before and after a reference fix. Saved report pages make those variants durable
and comparable.
</p>

<p>
In this workflow, the report page is not merely commentary. It is a compact
publication of one bounded run and its findings.
</p>

<h2>Timestamp and walked aspects</h2>

<p>
Ward's suggestion is to label report pages with a timestamp and the walked
aspects used for the draft. The timestamp distinguishes successive attempts.
The walked aspects preserve the structural neighborhood that was handed from
<tt>WALK</tt> to <tt>PRINT</tt>.
</p>

<p>
That pairing matters because a draft alone is not enough. The saved aspects show
what graph was actually explored, and the report page shows how that graph was
interpreted for publication.
</p>

<h2>Relation to inspectable runs</h2>

<p>
A timestamped report page is already a useful publication surface, but it is not
quite a full inspectable run object. It is better understood as one durable
externalization of a run. A future Mech execution model could preserve the same
information as a first-class run record with chronology, provenance, findings,
and artifact links.
</p>
