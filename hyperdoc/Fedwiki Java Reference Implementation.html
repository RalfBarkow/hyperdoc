Fedwiki Java Reference Implementation

The repository ~/workspace/fedwiki-java is a small Java interpreter for Federated Wiki navigation. In practice it is useful as an executable reference for collaborative link resolution, context handling, lineup behavior, and neighborhood discovery.

It is not a full wiki server or browser UI. Its value is that the navigation semantics are compact enough to inspect directly in code.

What it implements

  • read page JSON over HTTP
  • maintain a lineup of visited panels
  • follow the first collaborative link in the current item
  • derive page context from journal site entries
  • accumulate a neighborhood via /system/sitemap.json

The command-line interface described in README.md includes commands such as find, link, back, and next.

Why it matters

For HyperDoc and HyperBook work, this code is valuable because it exposes a minimal, explicit version of collaborative link semantics. It shows what is primary in resolution and what is secondary.

Collaborative link extraction

In Main.java, the Item.links() method parses the first [[...]] occurrence from item text and converts the visible text into a slug by:

  • replacing whitespace with -
  • removing non-alphanumeric characters except -
  • lowercasing the result

This means the reference implementation resolves collaborative links by slug, not by page title.

Context derivation

A page's context is derived from its journal. The Page.context() method walks journal entries backward and collects distinct site values. This makes context provenance-based rather than purely local-page based.

That matches the idea that context is about the page's federation history, not simply the current server or owner.

Resolution order

The core collaborative-link resolution lives in Panel.load(Panel from, String slug).

Resolution proceeds as follows:

  1. Start with the page context derived from the current page journal.
  2. If the current item has its own site, move that site to the front of the context list.
  3. Try the origin site first.
  4. If not found, try each context site in order.
  5. Fetch http://site/slug.json at each step.
  6. The first successful fetch wins.

If no site resolves the slug, the program stops with can't find page in current context.

Neighborhood is related but separate

The code also accumulates a neighborhood by fetching /system/sitemap.json for encountered sites. That supports broader site awareness, but it is not the primary clicked-link resolution path. Direct page fetch by slug across origin and context sites remains primary.

Implication for HyperDoc design

Any HyperDoc feature that wants to link to concrete FedWiki pages should be grounded in this resolution model. The important fields are:

  • target slug
  • origin site
  • context site list
  • optional item-level site override

A purely title-based HyperDoc link model would not match the reference implementation closely enough.
