Merge Intent Relations Between Git Commits

hyperdoc

A merge-intent relation is a first-class object that says more than "these two commits are related." It records an intended merge direction, the explicit review anchors, the planning prompt, and the conflict policy that should guide the work if the merge turns out to be non-trivial.

In this first slice, the relation is typed as merge-intent and links two existing inspectable git-commit-target objects. The relation also carries source and target branch objects so the history surface can render the same fact in both a lane-oriented view and an actionable worklist view.

Why keep this as an object

HyperDoc already has a pattern of turning bounded workflow state into small inspectable objects instead of terminal-only output. A merge-intent relation follows the same rule: the durable fact is the relation object, not only a narrative paragraph on a page.

Fields stored on the relation

  • a stable id and title,
  • relation type merge-intent,
  • status planned,
  • source branch and source commit anchor,
  • target branch and target commit anchor,
  • the full prompt text to guide the merge,
  • the conflict policy that prefers a dreyeck subsystem fallback over dirty overwrite,
  • the success criteria that must remain true after the merge.

Views

  • 👀merge-intent renders the prompt, conflict policy, and success criteria directly on the relation object.
  • 👀git-history on the surrounding history surface shows the same relation in lane context.
  • 👀merge-worklist on the history surface filters the relation set by target branch and expands the checklist for execution.
