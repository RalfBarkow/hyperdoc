Bibliography subcollections in HyperDoc

hyperdoc

HyperDoc can now treat a named bibliography subcollection as a first-class HyperBook collection surface rather than as pasted source text. The current concrete source is a read-only Zotero subcollection, exposed through a dedicated bibliography HyperBook and turned into inspectable bibliography entries, candidate topics, topic-comparison reports, authoring decisions, and a separate materialization preview.

Three distinct layers

  1. Live runtime/import objects: Zotero-backed subcollections, entries, candidate signals, comparison reports, and plans.
  2. Stable topic objects: reusable concept handles such as Candidate topic or Topic comparison report in hyperdoc/topics.lisp.
  3. Authored HyperDoc pages: durable prose pages that explain the capability and later absorb approved materialized outputs.

The import layer does not silently mutate authored pages or hyperdoc/topics.lisp. It produces an inspectable authoring plan first, then a separate explicit materialization bundle only after review.

Provenance versus editorial inference

Zotero collection identity and editorial topic inference are deliberately kept separate.

  • Source provenance: the subcollection object preserves source system, collection id, collection key, collection name, and full collection path.
  • Editorial inference: candidate topics aggregate signals from the collection name and from bibliography-entry fields such as title, tags, notes, and venue.
  • Boundary rule: a Zotero collection name can influence candidate extraction, but it does not automatically become a HyperDoc topic.

This matters for Coachmark bibliography authoring plan: the collection cue coachmark is preserved as provenance, but the plan still asks whether Coach marks, Onboarding, or adjacent UX pattern concepts deserve new topics, page updates, or only arrangement-level mention.

Comparison rule

Candidate-topic comparison follows the same doctrine already documented for manual topic merging:

  1. check the exact topic title first
  2. then check aliases and near-duplicate normalization
  3. then check broader-topic absorption
  4. only then mark a candidate as genuinely new

That comparison is visible as typed report objects, not hidden inside a write script.

Materialization boundary

The authoring plan exposes a materialization preview and a write action, but the write action generates a separate review bundle. It does not patch hyperdoc/topics.lisp or overwrite authored pages in place.

Each Authoring decision now keeps its own compact rationale, grouped evidence surface, and materialization consequence. The plan-level preview also distinguishes the bundle file that would be written now from the proposed later repo touch, such as a topic-factory function in hyperdoc/topics.lisp or a page fragment/update against a specific hyperdoc/<Title>.html page.

(let ((plan (coachmark-bibliography-authoring-plan))) (materialize-bibliography-authoring-plan plan))

Use that step only after inspecting the plan. The generated bundle is the review surface for proposed topic-factory snippets, page fragments, and page update notes.

Stand-in seam before browser rendering

HyperDoc also exposes a stand-in inspection layer for bibliography plans. That seam classifies entry-page selection, runtime-surface inventory, workspace-versus-flake mismatch, plan readiness, artifact-bundle readiness, and failure classification before browser rendering. It is the local bibliography version of the browser stand-in pattern and keeps Playwright focused on the later pane-open and rendering boundary.
