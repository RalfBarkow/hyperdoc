Boundary

The repair target is not "restart the Lisp image". Restarting may produce a cleaner image, but it also throws away the good chunks that should remain inspectable. The runtime coherence report preserves the object chunk and records which support chunk blocks browser inspection.

The first split is between an ASDF code root and a static asset root. ASDF answers where Lisp systems such as :clog resolve from. Static assets answer where files such as boot.html, js/boot.js, and js/jquery.min.js are served from. Those can be different roots.

CLOG_SRC is currently overloaded. In the observed image it pointed at a patched CLOG source/static overlay, not at a directory containing clog.asd. The coherence model therefore classifies CLOG_SRC by evidence: whether the path contains an ASDF definition, whether it is a static root, or whether CLOG_SRC/static-files/ is the patched asset root.

Running-image coherence gate

The CLOG moldable inspector startup path now has an explicit running image coherence gate. The canonical startup sequence is repair first, guarded load second: 

(hyperdoc:repair-running-image-coherence
 :profile :clog-moldable-inspector)

(hyperdoc:load-coherent-system :clog-moldable-inspector
                               :profile :clog-moldable-inspector)

The gate first derives a chunk map for the :clog-moldable-inspector profile. It checks the expected repo/Nix source universe, the current image's CL_SOURCE_REGISTRY, foreign source-registry contaminants, ASDF visibility for :s-graphviz, :clog-ace, :html-inspector-views/standard, and :clog-moldable-inspector, plus CLOG static assets, live html-inspector-views/standard method-table coherence, and dependency-precompute safety.

This is McDermott's chunk/basis/derive model applied to a dirty Common Lisp image. The basis is not just source text; it includes ASDF's current source registry, process environment variables, loaded packages, live generic functions, and selected system source files. The deriver is ensure-running-image-coherent for diagnosis, repair-running-image-coherence for explicit derivation or repair planning, and load-coherent-system for the guarded load boundary.

If :s-graphviz is invisible, or :clog-ace resolves from ~/common-lisp while the repo/Nix universe should be authoritative, the gate returns a runtime-coherence-report with a refused load-coherent-system-gate chunk. It does not silently load from the foreign root, and it does not invoke Quicklisp, a Downloads helper script, or a restart as the primary fix.

Derivable repair chunks

Refusal is no longer the only shape for stale running-image chunks. The repair entry point derives the expected dev-shell source registry, current image source registry, source-registry equivalence, foreign ASDF contaminants, ASDF visibility for :s-graphviz and :clog-ace, and :clog-moldable-inspector readiness. 

(multiple-value-bind (repaired-p report repair-plan)
    (hyperdoc:repair-running-image-coherence
     :profile :clog-moldable-inspector)
  (declare (ignore repaired-p report))
  repair-plan)

(hyperdoc:load-coherent-system :clog-moldable-inspector
                               :profile :clog-moldable-inspector)

The repair actions are explicit: import the dev-shell source registry, clear ASDF's source-registry cache, quarantine foreign ASDF source contaminants, reload selected .asd definitions, and rederive ASDF visibility for selected systems. None of those actions call asdf:load-system. If a repair is unsafe or incomplete, the result is an inspectable running image coherence repair plan with action chunks and evidence, not a bare debugger failure.

Source-registry contaminants

ASDF source-registry contaminant names the case where ASDF can find a system, but the source file comes from a non-authoritative root. The observed shape is: 

:S-GRAPHVIZ -> NIL
:CLOG-ACE   -> /Users/rgb/common-lisp/clog-ace/clog-ace.asd

That is worse than a simple missing dependency. It proves that the running image has a foreign source-registry basis mixed into the inspector load path. The contaminant chunk records registry entries and selected ASDF system source files whose authority is not :repo or :nix-store.

Persistence and inspection

Coherence events are persisted, when sqlite3 is available, to var/runtime-coherence.sqlite. Each event records the chunk id, status, kind, basis, evidence, repair action, condition class/message, and timestamp. Persistence is diagnostic: failure to write the SQLite event log must not turn a coherence report into a debugger break.

The plain report object is the inspectable surface. Helper functions expose the current chunk map, stale chunks, source-registry diff, selected ASDF source files, and restart/repair recommendation: 

(let ((report (ensure-running-image-coherent
               :profile :clog-moldable-inspector
               :persist-events nil)))
  (list :summary (runtime-coherence-report-summary-of report)
        :stale (mapcar #'coherence-chunk-id-of
                       (runtime-coherence-stale-chunks report))
        :source-registry-diff
        (runtime-coherence-source-registry-diff report)
        :selected-source-files
        (runtime-coherence-selected-asdf-source-files)
        :recommendation
        (runtime-coherence-restart-repair-recommendation report)))

HTML inspector environment coherence

A long-running SLY image can keep environment variables from an older Nix development shell after Codex changes the flake or the html-inspector-views override. In that case HTML_INSPECTOR_VIEWS_SRC may still point at an old Nix-store derivation, while the current runtime expectation for HTML_INSPECTOR_VIEWS_ASD is a different html-inspector-views.asd path.

This is environment coherence, not object coherence. A plan result, topic, or projection can still be a good object chunk while the image's shell environment names a stale or incomplete inspector source root. The environment chunk records the raw HTML_INSPECTOR_VIEWS_SRC value, whether the directory exists, whether it contains html-inspector-views.asd, whether HTML_INSPECTOR_VIEWS_ASD is set, whether that explicit ASD path exists, and whether ASDF can see both html-inspector-views and html-inspector-views/standard.

The repair advice is deliberately non-mutating. Re-enter the updated nix develop shell, or explicitly bind HTML_INSPECTOR_VIEWS_SRC and HTML_INSPECTOR_VIEWS_ASD to a current derivation. The report should name the stale or missing environment chunk; it should not repair this by restarting the Lisp image or by loading more ASDF systems during ordinary report construction.

repair-html-inspector-views-environment-from-asdf is the explicit mutating repair for the case where ASDF already sees the current html-inspector-views system but the process environment still names a stale derivation. It uses ASDF's visible base system as the source of truth, derives the source directory and html-inspector-views.asd pathname, binds HTML_INSPECTOR_VIEWS_SRC and HTML_INSPECTOR_VIEWS_ASD, and returns a runtime-coherence-report with before, mutation, and after evidence. If ASDF cannot see the base system, the repair reports :asdf-subsystem-not-visible instead of guessing a path.

ASDF visibility versus package presence

A Common Lisp package can remain present in a long-running image after ASDF loses visibility of the system definition that originally created it. Package presence, ASDF system visibility, and live method-table coherence are three different chunks. The package names HTML-INSPECTOR-VIEWS and HTML-INSPECTOR-VIEWS/STANDARD can be present while asdf:find-system no longer finds html-inspector-views or html-inspector-views/standard.

make-html-inspector-views-asdf-visibility-coherence-report models that mismatch directly. For the base and standard systems it records the package name and package presence separately from the ASDF system name, ASDF visibility, source file, source directory, and captured asdf:find-system condition. It also records the environment inputs that can explain the mismatch: HTML_INSPECTOR_VIEWS_SRC, HTML_INSPECTOR_VIEWS_ASD, CL_SOURCE_REGISTRY, the expected html-inspector-views.asd under the source root, the explicit ASD path when set, and the repo-local vendored ASD file.

The observed dirty-image state can therefore be represented without flattening it into a generic inspector failure: packages are present, the live method table has been repaired, ASDF systems are missing, and browser inspection remains blocked by :packages-present-asdf-missing or :asdf-subsystem-not-visible. The plan object remains a separate good chunk; the blocked chunk is ASDF visibility for optional inspector support.

SLY MREPL inspection helper

Pasteable MREPL snippets should not call SLYNK's Emacs-inspector entrypoint directly. That path relies on SLYNK private dynamic state that may be unbound in an MREPL evaluation. The stable local helper is: use the CLOG inspector only when CLOG-MOLDABLE-INSPECTOR:CLOG-INSPECT is already loaded; otherwise use cl:inspect. A textual report printer should be available for no-inspector verification. 

(require :asdf)
(asdf:load-system :hyperdoc)

(defun i (object)
  "Safe inspector helper for SLY mREPL.
Prefer CLOG only if it is already loaded; otherwise use CL:INSPECT.
Never calls SLYNK:INSPECT-IN-EMACS directly."
  (let* ((clog-package (find-package "CLOG-MOLDABLE-INSPECTOR"))
         (clog-symbol
           (and clog-package
                (find-symbol "CLOG-INSPECT" clog-package))))
    (cond
      ((and clog-symbol (fboundp clog-symbol))
       (handler-case
           (progn
             (funcall (symbol-function clog-symbol) :object object)
             object)
         (condition (condition)
           (format t "~&CLOG inspector failed; falling back to CL:INSPECT: ~A~%"
                   condition)
           (inspect object)
           object)))
      (t
       (inspect object)
       object))))

(defun print-runtime-coherence-report (report)
  (format t "~&~%Report type: ~S~%" (type-of report))
  (format t "~&Summary: ~S~%"
          (hyperdoc:runtime-coherence-report-summary-of report))
  (format t "~&~%Chunks:~%")
  (dolist (chunk (hyperdoc:runtime-coherence-report-chunks-of report))
    (format t "~&  ~A  ~S~%"
            (hyperdoc:coherence-chunk-id-of chunk)
            (hyperdoc:coherence-chunk-status-of chunk)))
  report)

(defparameter *example-result*
  (hyperdoc:ensure-running-image-coherent
   :profile :clog-moldable-inspector
   :persist-events nil))

(print-runtime-coherence-report *example-result*)

(i *example-result*)

Live method-table coherence

asdf:clear-system and source-level ASDF repair do not remove already-loaded generic functions, methods, ASDF hooks, or dependency caches from a running image. The patched source for html-inspector-views/standard and the live method table in SLY are therefore separate coherence chunks.

A long-running SLY image can keep a stale HTML-INSPECTOR-VIEWS/STANDARD::SYSTEM-DEPENDS-ON generic function that lacks the (null) method even after the source tree contains that method. In that state the source chunk may be repaired while (system-depends-on nil) still signals in the already-loaded image.

make-html-inspector-views-live-method-coherence-report probes only the running package and symbols. It records whether the standard package is present, whether SYSTEM-DEPENDS-ON and SYSTEM-DEPENDENCIES are fbound, whether the SYSTEM-DEPENDS-ON generic has a (null) method, and whether safe calls on nil return without escaping a condition.

repair-html-inspector-views-standard-live-methods is the explicit mutating operation for this chunk. It does not load :hyperdoc/inspector or :html-inspector-views/standard. When the package and generic function are already present but the (null) method is missing, it installs that method by runtime symbol resolution and records the before state, installation step, and post-repair safe-call evidence.

Optional inspector capability

html-inspector-views/standard currently reaches Graphviz support through s-graphviz. That is a real ASDF dependency in the current upstream design, but the runtime coherence report treats Graphviz-backed standard views as an inspector optional dependency boundary. Missing or broken Graphviz support becomes a chunk status such as :optional-unavailable. When html-inspector-views/standard itself is ASDF-visible and only the Graphviz-backed capability is unavailable, the standard-view chunk is :degraded, not :blocked. Non-Graphviz standard views remain usable; the missing capability is recorded as evidence instead of crashing a report about an unrelated plan object.

Plan object preservation

A SHOP3 plan result can be a good :plan-result chunk while the browser-inspection session is blocked by CLOG static assets, CLOG inspector loading, or optional view support. The session chunk says exactly that: "plan object is good; browser inspector is blocked by runtime support chunk X." The next action is to re-derive or repair that support chunk, not to discard the plan object.

Non-mutating default

Ordinary report construction probes with asdf:find-system, find-package, fboundp, probe-file, and environment classification. It does not call asdf:load-system. Any ASDF load probe belongs behind an explicitly named operation such as attempt-load-asdf-system-chunk, where failures are captured as chunk evidence.
