Review of the first merge-proposed-topic-additions HTML

The draft is mostly on the right track. The core rule is good: use the exact canonical topic title as the first merge key, and do not create a second topic factory with the same :title.

I would revise five parts.

1. Exact-title dedup is the first pass, not the whole policy

The current text makes exact-title matching sound sufficient by itself. It is not. It should be the first check, followed by editorial normalization for aliases, near-duplicates, and broader existing topics.

That matters immediately in the Drew McDermott slice. Nisp and YNisp are presented by McDermott as effectively the same software line, not obviously two separate concepts that each require their own topic page. So before creating both topics, decide whether one should be the canonical topic and the other mentioned inside the summary or references.

2. One HTML fragment is invalid

This fragment is broken HTML: 

<title keyed>

It will be parsed like an unknown HTML element, not shown as intended prose. Replace it with plain text such as title-keyed, or with an actual code term if you want to name a variable.

3. The justification should be stated more narrowly

The argument does not need the backlinks sentence, and it should avoid overstating internal implementation details unless you want to verify every one of them. The practical reason is simpler:

Authored topic links target the topic page by canonical title, so duplicate :title values are the operational collision domain.

That is enough to justify the merge rule.

4. "Keep the existing function name" is a workflow preference, not the semantic rule

The draft says that if a title already exists, you should keep the existing function name. That is a good low-churn editing habit, but it is weaker than keeping the existing :id and canonical :title. The important semantic continuity is title stability and stable topic identity. Function-name stability is useful, but secondary.

5. The procedure should add an alias-and-scope check

The recommended merge procedure should include one more step between exact-title lookup and adding a new topic:

  1. Check for the exact :title.
  2. If absent, check for an existing alias, synonym, or broader canonical topic that should absorb the new material.
  3. Only then add a new topic factory.

Without that step, you risk creating unnecessary parallel topics.

Suggested revised operational rule

Deduplicate first by exact :title. If there is no exact match, check for aliases, near-duplicates, or a broader existing canonical topic. Add a new factory only when the concept is genuinely new at the topic layer.

Suggested revised Drew McDermott guidance

For the Drew McDermott slice, do this per candidate concept:

  • Drew McDermott: probably a new topic if absent.
  • PDDL: likely merge into an existing topic if present.
  • Nisp / YNisp: treat as an alias-normalization decision first, not as automatically two topics.
  • Ontology translation, Estimated-regression planning, Autonomous process: check whether they are already covered under existing broader planning topics before adding fresh factories.

Suggested tightened replacement paragraph

Use the canonical topic title as the first merge key. If an exact title already exists in hyperdoc/topics.lisp, edit that factory in place rather than adding a second factory with the same :title. If no exact title exists, check for aliases, near-duplicates, or a broader existing topic that should absorb the new references. Add a new topic factory only when the concept is truly new at the Topics HyperBook layer.

Net assessment

So: the draft is directionally right, but I would change it from title-first and title-only to title-first, then normalize aliases and scope. I would also remove the broken <title keyed> fragment and soften the claims about internal mechanics unless you want to verify each one in code.
