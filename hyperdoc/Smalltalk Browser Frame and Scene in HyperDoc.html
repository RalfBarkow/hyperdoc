Evaluation for HyperDoc

The article's diagnosis maps well to HyperDoc: static pages and code browsers are necessary but not sufficient for dynamic work. HyperDoc already has the right primitives (links, inspectable objects, debugger/stepper surfaces, and graph-rooted publishing). The missing piece is to persist investigation context as first-class objects.

Adaptation verdict: yes, applicable now, if we treat each investigation step as a topic-like object and connect those steps by typed relations.

How to edit scene graphs in HyperDoc

  1. Create a scene node per meaningful step: entry point, object inspected, stack frame, experiment, decision.
  2. Create typed edges (led-to, inspected, retried, rejected, superseded) between nodes.
  3. Record outcome metadata in each node (status, confidence, next question, references).
  4. Render from the graph, not from a single linear narrative: derive task views, chronology views, and decision trails.
  5. Allow humans and robots to traverse the same graph; keep robot procedures human-written and inspectable.

This preserves Smalltalk's strength (context frame) while adding the missing IDE-level composition: scene-level continuity across tools and time.

Ward input and implications

Ward's input adds a concrete historical mechanism: collaboration diagrams emerged by combining three existing tool surfaces (class browser, object inspector, single-step debugger) and reading the stepping primitive CompiledMethod>>interpretNextInstructionFor: aContext.

For HyperDoc, this reinforces that scene-graph editing should not replace tools. It should compose tool outputs into one inspectable graph that records runtime evidence, explanatory diagrams, and decision paths.
