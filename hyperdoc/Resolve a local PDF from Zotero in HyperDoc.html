Resolve a local PDF from Zotero in HyperDoc

hyperdoc

This task page demonstrates the narrow end-to-end slice: start from the title Mind and Mechanism, look it up in a local read-only Zotero library, inspect the matched bibliographic item and attachment, then cross-check the same result through direct item-id lookup before resolving the local PDF path as an explicit report object. The underlying bridge is now optional; if HYPERDOC_ENABLE_ZOTERO=0, these entry points open an explicit unavailable-by-configuration object instead of a fake live Zotero surface.

Inspectable objects

  • Zotero library
  • Attachment path resolution
  • Stored attachment

  • (mind-and-mechanism-zotero-title-query)
  • (mind-and-mechanism-zotero-item-id-query)

  • (mind-and-mechanism-zotero-path-resolution-report)
  • (mind-and-mechanism-zotero-resolution-report)

Procedure

  1. Open (make-zotero-live-demo-library) and confirm the DB path and storage root are the intended local ones.
  2. Open (mind-and-mechanism-zotero-title-query) to inspect the general title-lookup path.
  3. Open (mind-and-mechanism-zotero-item-id-query) and (mind-and-mechanism-zotero-item-hit) to inspect the deterministic item-id verification path through its dedicated query object.
  4. Open (mind-and-mechanism-zotero-attachment-hit) and (mind-and-mechanism-zotero-path-resolution-report).
  5. Open (mind-and-mechanism-zotero-resolution-report) for the user-facing title-to-PDF report.

Local/dev environments can keep Zotero enabled. On dreyeck, the same page is expected to degrade explicitly when the optional Zotero backend is disabled by configuration.

Worked local example

The concrete live demonstrator defaults to the current known local facts: Zotero DB ~/Zotero/zotero.sqlite, title Mind and Mechanism, bibliographic item 75704, and stored PDF attachment key UULEU9Z7. In the current local Zotero library on this machine, the report resolves that chain to the stored attachment path ~/Zotero/storage/UULEU9Z7/McDermott - 2001 - Mind and Mechanism.pdf. Those values live at the demo boundary, not in the generic core lookup code. The resolved pathname is machine-local evidence for this environment, not a repo-global truth about every installation, so the report object stays the authoritative surface.

Why this page exists

HyperDoc already has a page-level bridge for Mind and Mechanism. This page adds the operational literature bridge: from authored topic/page material to a local bibliographic attachment path that can be inspected rather than guessed.

How the compatibility pages use this

The surrounding pages Mind and Mechanism, Mind and Mechanism compatibility with HyperDoc, Symbols and semantics in Mind and Mechanism, and Computationalism in Mind and Mechanism should treat this report as the runtime evidence boundary for the book's local availability. Their prose can then stay editorial and conceptual without restating a fixed local pathname as if it were repo-global fact.
