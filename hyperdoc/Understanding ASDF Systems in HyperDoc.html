Understanding ASDF Systems in HyperDoc

hyperdoc

This page is the conceptual entry point for ASDF in this repository. It explains what a system is, how systems differ from their internal components, how this repository uses slash-named systems, and why HyperDoc should use real ASDF system boundaries as the main scope for examples and tests.

What an ASDF system is

An ASDF system is the named top-level build/load/test unit defined by defsystem in a .asd file. It is what asdf:find-system resolves, what asdf:load-system loads, and what test-op or asdf:test-system conceptually target.

In this repository, hyperdoc, hyperdoc/explorer, and hyperbook/server are not labels for directories. They are named ASDF systems with their own dependency lists, component graphs, and operational roles.

System vs component vs module vs source file

A system is also a component, but it is the top-level one. Beneath it, ASDF organizes an internal component graph. In practical repository terms:

  • System: the named boundary declared with defsystem, such as hyperdoc.
  • Component: any node in that boundary's graph.
  • Module: a grouping component, usually corresponding to a directory such as hyperdoc, hyperdoc-explorer, or hyperbook-server.
  • Source file: a leaf component such as package.lisp, core.lisp, topics.lisp, or check-runner.lisp.

The hyperdoc system in hyperdoc.asd contains a module named hyperdoc whose files are loaded serially: package, core, topics, links-in-code, defining, check-runner, examples, tools, and hyperdoc. That ordering matters because definitions in later files may depend on packages, classes, or variables introduced earlier.

Operations on systems

ASDF operations act on systems and their components. For this repository, the most important ones are load-op and test-op.

  • load-op: loads the system and the component graph it depends on into the running image.
  • test-op: runs the system's test entry point, often by delegating to a separate test system.

The repository makes that delegation explicit. In hyperdoc.asd, hyperdoc declares :in-order-to ((test-op (test-op "hyperdoc/tests"))). That means the main system and the test-oriented system are related, but not identical. The boundary between them is a real ASDF fact, not just a UI preference.

asdf:find-system matters because it tells you whether a named system is visible in the current source registry and therefore available for these operations. If (asdf:find-system :hyperdoc/explorer) fails, that is a source-registry or system-definition problem before it is a HyperDoc UI problem.

In this repository, nix develop, dev.sh, and the server startup paths matter because they establish the source-registry context in which the local systems are visible. If the image was started in the wrong environment, system lookup can fail even when the source tree is present on disk.

How HyperDoc uses ASDF

HyperDoc is embedded in ASDF systems rather than floating above them. A HyperDoc lives in a system directory next to the system definition file, and its pages and Lisp source are loaded through the system's component graph.

This repository shows that clearly:

  • hyperdoc contains the core HyperDoc runtime and the hyperdoc module.
  • hyperdoc/explorer contains explorer-specific views in the hyperdoc-explorer module.
  • hyperdoc/server is a compatibility alias that depends on the explorer/server stack.
  • hyperdoc/tests contains smoke-test code in the tests module.
  • hyperbook/explorer contains the asdf-systems hyperbook that exposes real asdf:system objects for inspection.

This is why HyperDoc documentation should talk about systems directly. The documentation system is already embedded in ASDF's object model.

Slash-named systems in this repository

Slash-named systems such as hyperdoc/explorer, hyperdoc/server, hyperdoc/tests, and hyperbook/server are ordinary ASDF systems with names that signal a narrower role relative to a main system. They are not a package convention and not a fake subsystem layer invented by HyperDoc.

ASDF also supports package-inferred systems, where system structure follows package and file naming conventions. That is not the model used here. This repository uses explicit defsystem forms, explicit modules, and explicit file lists, so those declared system boundaries are the ones HyperDoc should surface.

In this repository they separate concerns cleanly:

  • hyperdoc owns the core documentation/runtime model.
  • hyperdoc/explorer owns explorer views and interaction surfaces.
  • hyperdoc/tests owns repo-local smoke tests.
  • hyperbook/server owns web-server/runtime hosting behavior.

That separation is exactly the kind of ownership boundary HyperDoc should reuse when deciding where examples and tests belong.

Why ASDF systems are the right scope objects

ASDF systems are better scope objects than packages because systems encode ownership, dependencies, loading, and testing. Packages are still useful, but they are primarily namespace boundaries. They do not by themselves say which files belong together, which operation boundary owns an example, or which test system is responsible for regression tests.

HyperBook Explorer already acknowledges this by exposing real systems through the asdf-systems hyperbook in hyperbook-explorer/asdf-systems.lisp. HyperDoc should build on that existing inspection surface instead of creating a second, HyperDoc-only notion of scope.

Examples and tests by system boundary

Once ASDF is understood this way, the architecture follows directly:

  • HyperDoc root views should express what HyperDoc is.
  • ASDF systems should be the main scope objects.
  • Examples should belong to the system whose source files define them.
  • Tests should belong to a test-oriented system such as hyperdoc/tests or to a root Tests surface that points to that system boundary.
  • Packages may remain visible as secondary code-archeology surfaces, but not as the primary organizing principle.

This is the ASDF-grounded translation of the GT-inspired design: choose a meaningful scope object, attach examples to it, make run an action on those examples, and keep verification tooling separate from root identity.
