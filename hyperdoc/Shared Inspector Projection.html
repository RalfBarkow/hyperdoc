Shared Inspector Projection

hyperdoc

A shared inspector projection is the collaboration artifact for sharing an inspector view between HyperDoc instances without sharing the live CLOG inspector session itself.

The rule is: 

Do not share the live inspector session as the collaboration artifact.
Share an inspector projection that another HyperDoc instance can inspect locally.

Problem

A local inspector URL such as http://127.0.0.1:8080/inspector is a live browser surface over one Lisp image. It can contain transient object identities, evaluation affordances, restarts, mutable image state, and browser-session state.

That makes the live inspector useful locally, but unsuitable as the object to synchronize between two HyperDoc instances or to expose directly through a public URL such as https://dreyeck.ch/inspector.

Design

The collaboration boundary is a projection: 

local inspector object
  -> inspectable projection object
  -> DMX topic
  -> DMX topicmap placement
  -> remote HyperDoc reads projection
  -> remote HyperDoc opens its own local inspector view

Live object identity remains local. The projection is the shared artifact. Each HyperDoc instance renders its own inspector pane from the shared projection data.

Example: page-lookup rebuild report

The current motivating object is the page-lookup rebuild report:

(defparameter *page-lookup-rebuild-report* (make-page-lookup-rebuild-report)) (clog-moldable-inspector:clog-inspect :object *page-lookup-rebuild-report*)

Instead of sharing the live pane, HyperDoc should derive a projection such as: 

{
  "kind": "hyperdoc.inspector.projection",
  "shareId": "page-lookup-rebuild-report/latest",
  "producer": "rgb-local-hyperdoc",
  "producerUrl": "http://127.0.0.1:8080/inspector",
  "publicUrl": "https://dreyeck.ch/inspector",
  "objectClass": "page-lookup-rebuild-report",
  "textRepresentation": "Page lookup rebuild gate: issues, 262 issues",
  "selectedView": "Summary",
  "views": [
    {"title": "Overview", "summary": "Status, pages scanned, issue count, reload status"},
    {"title": "Summary", "summary": "Counts grouped by issue classification"},
    {"title": "Issues", "summary": "Structured page/link/classification/status rows"},
    {"title": "Scanned pages", "summary": "Pages included in the rebuild gate scan"}
  ],
  "data": {
    "status": "issues",
    "issueCount": 262
  }
}

Active/alive pair of HyperDoc instances

An active/alive pair does not mean that two browser DOMs are synchronized. It means that two HyperDoc instances share the same durable projection topic and topicmap placement, while each instance keeps its own local Lisp image and inspector runtime.

Level Meaning Implementation
Snapshot Share one inspector projection once. DMX topic containing projection JSON.
Refreshable Re-run the local report and update the same projection topic. Journaled update of the projection payload.
Live-ish pair Both HyperDoc instances reread the same projection topicmap and re-render locally. DMX topicmap plus revision or journal polling.

DMX topicmap workflow

  1. Build the local inspector object.
  2. Build an inspector projection from that object.
  3. Preview the DMX write as a dry run.
  4. Create or update a DMX topic containing the projection JSON.
  5. Place the topic into the shared topicmap with view props.
  6. Remote HyperDoc reads the topicmap.
  7. Remote HyperDoc materializes a local projection object.
  8. Remote HyperDoc opens its own inspector view of that projection.

Proposed object model

(defclass inspector-share-projection ()
  ((id :initarg :id :reader id-of)
   (title :initarg :title :reader title-of)
   (producer-instance :initarg :producer-instance :reader producer-instance-of)
   (producer-url :initarg :producer-url :reader producer-url-of)
   (object-class :initarg :object-class :reader object-class-of)
   (object-text :initarg :object-text :reader object-text-of)
   (selected-view :initarg :selected-view :reader selected-view-of)
   (view-summaries :initarg :view-summaries :initform nil :reader view-summaries-of)
   (projection-json :initarg :projection-json :reader projection-json-of)
   (created-at :initarg :created-at :reader created-at-of)
   (dmx-topic-id :initarg :dmx-topic-id :initform nil :reader dmx-topic-id-of)
   (dmx-topicmap-id :initarg :dmx-topicmap-id :initform nil :reader dmx-topicmap-id-of)
   (status :initarg :status :reader status-of)))

Recommended inspector views

  • Overview: object text, producer, selected view, status, DMX placement.
  • Projection JSON: exact machine-readable payload to publish.
  • DMX placement: topic id, topicmap id, view props, last update.
  • Consumer instructions: how another HyperDoc instance reads and inspects it.

Boundary rule

The projection must not include arbitrary live Lisp object references, restart handles, evaluation closures, browser DOM state, or unaudited mutation affordances. It may include stable identifiers, textual representation, selected view name, summarized view data, and structured report data.

First implementation slice

  1. Add inspector-share-projection objects.
  2. Add inspector views for projections.
  3. Add a projection function for page-lookup-rebuild-report.
  4. Publish the projection as a DMX topic.
  5. Place the projection topic on a shared DMX topicmap.
  6. Read the topicmap from a second HyperDoc instance and inspect the projection locally.
