Incident summary

The live defect was not in the note topics themselves. The broken objects were two topicmap-scoped dmx.topicmaps.topicmap_context assocs: 921404 and 921471. Both had only the short keys x, y, visibility, and pinned while the checked DMX fetch path expected the long-form keys dmx.topicmaps.x, dmx.topicmaps.y, dmx.topicmaps.visibility, and dmx.topicmaps.pinned.

Forum and historical context

  • The same bug class had been discussed before in DMX admin/operator context.
  • Historically, the response was an admin-side database repair rather than a UI-only workaround.
  • That public context did not prove the original writer path; it framed the incident as a store-shape defect, not a normal topicmap usage error.

Conversation arc preserved as durable chronology

  1. Initial HyperDoc repro work found a separate local disconnect path: opening the repair runbook in HyperDoc eagerly instantiated an unrelated localhost promotion plan and crashed on a missing FedWiki source page file.
  2. That expectation was a disappointed one rather than a false one. The DMX failure was real, but the first local boundary was polluted by an unrelated HyperDoc fail-soft defect.
  3. HyperDoc was repaired first to stop the unrelated disconnect and keep inspectable issue objects for missing localhost source pages.
  4. A copied remote DB snapshot was then inspected read-only on the MacBook.
  5. The copied-store diagnosis proved the exact property-shape mismatch on 921404 and 921471.
  6. The same bounded defect was confirmed on the live store, repaired after backup, and verified with a wider audit.
  7. A read-side guard was added in dmx-topicmaps so malformed topicmap-context assocs fail with explicit diagnostics instead of raw property lookup crashes.
  8. Writer-boundary archaeology then proved a current permissive server write seam: generic DMX ViewProps endpoints can persist raw short-key payloads unchanged if a sender posts them.
  9. The original sender still remains unproven, so HyperDoc now treats DMX as a valuable but untrusted persistence boundary and validates its own writes explicitly.

Read-side evidence boundary

  • topicmaps/object/921464 failed on missing dmx.topicmaps.visibility for assoc 921471.
  • topicmaps/919822 failed on missing dmx.topicmaps.x for assoc 921471.

Canonical machine-readable topic read path

  • For direct tool or API reads, use /core/topic/<id>?children=true&assocChildren=true.
  • Confirmed example: https://dmx.ralfbarkow.ch/core/topic/907120?children=true&assocChildren=true returned the full note topic DMX incident remediation for HyperDoc.
  • DMX webclient hash-route URLs are browser navigation entry points, not the canonical machine-readable read boundary for tool fetches.
  • The DMX MCP server for shared workspace now wraps this canonical read path so Codex and future ChatGPT connector clients do not need raw DMX URL knowledge.

Validated minimal repair

The bounded repair was to copy the existing short-key values into the long-form keys and keep the short keys in place. 

START ctx=node(921404,921471)
SET ctx.`dmx.topicmaps.x` = ctx.x,
    ctx.`dmx.topicmaps.y` = ctx.y,
    ctx.`dmx.topicmaps.visibility` = ctx.visibility,
    ctx.`dmx.topicmaps.pinned` = ctx.pinned
RETURN ID(ctx) AS repairedCtxId,
       ctx.`dmx.topicmaps.x`, ctx.`dmx.topicmaps.y`,
       ctx.`dmx.topicmaps.visibility`, ctx.`dmx.topicmaps.pinned`;

Verification queries

START ctx=node(921404,921471)
RETURN ID(ctx) AS ctxId,
       ctx.`dmx.topicmaps.x`, ctx.`dmx.topicmaps.y`,
       ctx.`dmx.topicmaps.visibility`, ctx.`dmx.topicmaps.pinned`,
       ctx.x, ctx.y, ctx.visibility, ctx.pinned
ORDER BY ctxId;

START tm=node(919822)
MATCH (ctx)-[:`dmx.core.default`]->(tm), (ctx)-[:`dmx.topicmaps.topicmap_content`]->(content)
WHERE ctx.typeUri = 'dmx.topicmaps.topicmap_context'
  AND content.nodeType = 'topic'
  AND ctx.`dmx.topicmaps.x` IS NULL
RETURN ID(ctx) AS stillBrokenCtxId;

START ctx=node(*)
MATCH (ctx)-[:`dmx.core.default`]->(tm), (ctx)-[:`dmx.topicmaps.topicmap_content`]->(content)
WHERE ctx.typeUri = 'dmx.topicmaps.topicmap_context'
  AND ctx.`dmx.topicmaps.x` IS NULL
  AND ctx.x IS NOT NULL
RETURN ID(ctx) AS ctxId, ID(tm) AS topicmapId, ID(content) AS contentId,
       content.nodeType, content.typeUri, ctx.x, ctx.y, ctx.visibility, ctx.pinned
ORDER BY ctxId;

Why HyperDoc now narrows its own write boundary

The earlier dry-run framing was no longer sufficient once writer-boundary archaeology proved that generic DMX ViewProps endpoints can persist malformed short-key-only payloads unchanged. HyperDoc still does not claim to know the historical writer, but it now has enough evidence to prevent itself from recreating the same defect class.

  • Proven: stock checked read paths expect long-form keys.
  • Proven: current checked stock client paths use long-form keys.
  • Proven: generic DMX ViewProps endpoints can persist malformed short-key-only payloads unchanged if a sender submits them.
  • Proven: generic write endpoints can preserve malformed short-key payloads if a sender submits them.
  • Unproven: the exact original sender remains unknown and is still best classified as stale, external, or custom mutation.

Rollback

Preferred rollback is restoring the pre-repair filesystem backup. Logical rollback remains bounded to the four copied long-form keys: 

START ctx=node(921404,921471)
REMOVE ctx.`dmx.topicmaps.x`
REMOVE ctx.`dmx.topicmaps.y`
REMOVE ctx.`dmx.topicmaps.visibility`
REMOVE ctx.`dmx.topicmaps.pinned`
RETURN ID(ctx) AS rolledBackCtxId;
