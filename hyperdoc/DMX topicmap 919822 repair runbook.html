Problem capsule

The broken objects are not the note topics themselves. The readable notes still exist. The defect sits in the topicmap-scoped dmx.topicmaps.topicmap_context memberships and their missing view properties.

  • 921404 is the broken membership assoc for topic 921352.
  • 921471 is the broken membership assoc for topic 921464.
  • Both broken assocs had only short keys x, y, visibility, pinned.
  • The current DMX fetch path requires dmx.topicmaps.x, dmx.topicmaps.y, dmx.topicmaps.visibility, and dmx.topicmaps.pinned.
  • Healthy comparison specimen: topic 921494 resolves through assoc 921503.

Accepted evidence boundary

  • topicmaps/object/921352 fails on missing dmx.topicmaps.visibility for assoc 921404.
  • topicmaps/object/921464 fails on missing dmx.topicmaps.visibility for assoc 921471.
  • topicmaps/919822 fails on missing dmx.topicmaps.x for assoc 921471.
  • Offline inspection of the copied store and the stopped live store both proved the same short-key-only shape with x=160, y=120, visibility=true, pinned=false.

Containment

The bounded repair set is now confirmed and executed. No broader write is justified unless a future audit finds the same safe short-key-only shape on additional dmx.topicmaps.topicmap_context assocs.

Why HyperDoc code changes are not justified now

The public API proves which assocs are broken. The public API does not expose the exact write payload for /topicmaps/919822/assoc/<assoc-id>. The original writer still remains unproven and is best classified as a stale, external, or custom mutation path unless stronger evidence appears. That is still a DMX backend/admin contract problem, not a HyperDoc modeling problem.

Validated minimal repair

The validated minimal repair is to copy the existing short-key values into the long-form dmx.topicmaps.* keys and keep the short keys in place. 

START ctx=node(921404,921471)
SET ctx.`dmx.topicmaps.x` = ctx.x,
    ctx.`dmx.topicmaps.y` = ctx.y,
    ctx.`dmx.topicmaps.visibility` = ctx.visibility,
    ctx.`dmx.topicmaps.pinned` = ctx.pinned
RETURN ID(ctx) AS repairedCtxId,
       ctx.`dmx.topicmaps.x`, ctx.`dmx.topicmaps.y`,
       ctx.`dmx.topicmaps.visibility`, ctx.`dmx.topicmaps.pinned`;

Verification queries

START ctx=node(921404,921471)
RETURN ID(ctx) AS ctxId,
       ctx.`dmx.topicmaps.x`, ctx.`dmx.topicmaps.y`,
       ctx.`dmx.topicmaps.visibility`, ctx.`dmx.topicmaps.pinned`,
       ctx.x, ctx.y, ctx.visibility, ctx.pinned
ORDER BY ctxId;

START tm=node(919822)
MATCH (ctx)-[:`dmx.core.default`]->(tm), (ctx)-[:`dmx.topicmaps.topicmap_content`]->(content)
WHERE ctx.typeUri = 'dmx.topicmaps.topicmap_context'
  AND content.nodeType = 'topic'
  AND ctx.`dmx.topicmaps.x` IS NULL
RETURN ID(ctx) AS stillBrokenCtxId;

START ctx=node(*)
MATCH (ctx)-[:`dmx.core.default`]->(tm), (ctx)-[:`dmx.topicmaps.topicmap_content`]->(content)
WHERE ctx.typeUri = 'dmx.topicmaps.topicmap_context'
  AND ctx.`dmx.topicmaps.x` IS NULL
  AND ctx.x IS NOT NULL
RETURN ID(ctx) AS ctxId, ID(tm) AS topicmapId, ID(content) AS contentId,
       content.nodeType, content.typeUri, ctx.x, ctx.y, ctx.visibility, ctx.pinned
ORDER BY ctxId;

Rollback

Preferred rollback is restoring the pre-repair filesystem backup. Logical rollback is bounded to the four copied long-form keys: 

START ctx=node(921404,921471)
REMOVE ctx.`dmx.topicmaps.x`
REMOVE ctx.`dmx.topicmaps.y`
REMOVE ctx.`dmx.topicmaps.visibility`
REMOVE ctx.`dmx.topicmaps.pinned`
RETURN ID(ctx) AS rolledBackCtxId;
