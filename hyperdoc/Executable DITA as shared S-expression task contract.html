Executable DITA as shared S-expression task contract

hyperdoc

Executable DITA task objects give HyperDoc one canonical task contract for prompt, plan, evidence, and projection sharing. The source of truth is a Lisp-readable S-expression task object; DITA XML, HyperDoc HTML, SCXML, and SQLite rows are projections of that object.

Contract

The canonical shape is: 

(:executable-dita-task
 (:id "task.executable-dita-contract")
 (:title "Implement Executable DITA task objects")
 (:summary "Represent DITA-like task topics as canonical S-expression task objects with DITA, HyperDoc, SCXML, and SQLite projections.")
 (:context ...)
 (:pddl ...)
 (:scxml ...)
 (:preconditions ...)
 (:operators ...)
 (:postconditions ...)
 (:failure-modes ...))

The stable identity is :id. The mutable surfaces are status, evidence, next-task candidates, emitted projections, and implementation commits. SQLite is the durable store, but not the semantic authority.

Projection boundaries

  • DITA XML is a task-topic projection for document exchange.
  • HyperDoc HTML is a readable and clickable projection for local documentation.
  • SCXML is an execution-state contract. It classifies transitions but does not run arbitrary shell commands.
  • SQLite records canonical task S-expressions, emitted projection strings, and ranked next-task candidates.

Inspector views

The narrow system hyperdoc/executable-dita-tasks installs read-only moldable inspector views for the task object and its evidence rows. These views are projections. They do not replace the canonical S-expression and they do not execute operators.

  • Task object views: Summary, S-expression, DITA XML, HyperDoc HTML, SCXML, SQLite row, and Next tasks.
  • SQLite task-row view: Summary of persisted row metadata plus a reference back to the task object.
  • Next-task candidate view: Summary of candidate id, cost, risk, expected value, score, blocked flag, selected flag, and candidate S-expression.
  • Selection views: Ranked candidates and Selection for the SQLite-backed next-task decision.

SQLite selected_p records the candidate selected for the current implementation slice. Score ranking remains visible separately, so the inspector can show both the highest-scoring unblocked candidate and the currently selected candidate.

Planning boundary

PDDL and SHOP3-shaped fields are stored as data in this slice. The narrow system hyperdoc/executable-dita-tasks does not require shop3 and does not load full kioskbeerli. Planner execution belongs to a later runtime-coherence slice.

Safe execution boundary

Operator execution is guarded. The safe default is print and inspect. A task may name operators and checks, but mutation requires an explicit execution guard outside this first slice.

SQLite evidence

The default evidence database is: 

/Users/rgb/workspace/hyperdoc/var/shared-sexpression-plans.sqlite

It contains executable_dita_tasks and executable_dita_next_task_candidates. The ranking rule for next-task candidates is: 

score = expected_value / max(cost, 1) - risk

Goldberg questions

  1. What is the program about? It represents executable DITA tasks as canonical S-expressions with projections.
  2. What are the main objects? Executable task, PDDL plan lookup, SCXML contract, operator, precondition, postcondition, failure mode, SQLite record.
  3. What is the stable identity? :id in the canonical S-expression task object.
  4. What changes over time? Status, evidence, next-task candidates, projection files, and implementation commits.
  5. What is the source of truth? The canonical S-expression task object, with SQLite as durable store.
  6. What is only a projection? DITA XML, HyperDoc HTML, SCXML XML, and any rendered page.
  7. What is the safe default? Print and inspect. Do not mutate unless explicitly guarded.
  8. What is the planning boundary? PDDL/SHOP3 fields are data in this slice; actual SHOP3 execution is later.
  9. What is the execution boundary? SCXML classifies state transitions; it does not itself run arbitrary shell commands.
  10. What is the evidence boundary? Completion requires persisted evidence: SQLite rows, emitted projections, and smoke-test output.
  11. What should Codex not do? Do not use Quicklisp, do not load full :kioskbeerli, do not hide planner failures, do not commit generated SQLite DBs, and do not write implementation files under /Users/rgb/workspace/hauptsache.
  12. What is the next useful inspection? Inspect the task object, its projections, the SQLite row, and the ranked next-task candidates.

SLY mREPL replay

(require :asdf)
(asdf:load-system :hyperdoc/executable-dita-tasks)

(defun i (object)
  "Safe inspector helper for SLY mREPL.
Prefer CLOG only if it is already loaded; otherwise use CL:INSPECT.
Never calls SLYNK:INSPECT-IN-EMACS directly."
  (let* ((clog-package (find-package "CLOG-MOLDABLE-INSPECTOR"))
         (clog-symbol
           (and clog-package
                (find-symbol "CLOG-INSPECT" clog-package))))
    (if (and clog-symbol (fboundp clog-symbol))
        (funcall (symbol-function clog-symbol) object)
        (cl:inspect object))))

(defparameter *example-task*

(hyperdoc:persist-executable-dita-task
 *example-roundtrip*
 :db-path *example-db-path*)

(dolist (candidate
         '((:id "candidate.inspect-sqlite-evidence"
            :title "Inspect persisted SQLite evidence"

   :db-path *example-db-path*))

Boundary

This page documents the first implementation slice only. It does not promise SHOP3 execution, remote collaboration, generated projection files as committed artifacts, or unguarded operator execution from inspector views.
