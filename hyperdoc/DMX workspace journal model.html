DMX workspace journal model

hyperdoc

DMX workspace journal model defines the HyperDoc-owned revision layer for the DMX common workspace topicmap 919822. It is deliberately narrower than a generic DMX mutation framework: HyperDoc keeps journal ownership, replay, restore, and out-of-band detection inside its guarded boundary instead of assuming DMX already provides a native FedWiki-style revision store.

Storage model

The implemented storage model is companion-workspace-note. Every journal stream is stored as one hidden HyperDoc-owned workspace note whose URI starts with hyperdoc:mcp/workspace-journal/. The note lives in topicmap 919822, but HyperDoc places it off-canvas with hidden view props and excludes those companion topics from normal visible workspace counts.

Journal ownership attaches to the stable HyperDoc-managed subject key. When a preserved URI exists, that URI becomes the subject key. Otherwise HyperDoc falls back to a stable synthetic key such as dmx:topic/<id>.

Journal scope

  • Workspace notes and handovers managed through HyperDoc.
  • HyperDoc-owned workspace topics such as topic-factory snippet twins.
  • Topicmap membership changes in topicmap 919822.
  • Validated topicmap view-props changes when they are performed through HyperDoc.

Event model

Journal events are durable structured records with subject key, topic id when known, topicmap id when relevant, actor classification, timestamp, previous state, next state, and observation kind.

  • create-topic
  • update-topic
  • add-to-topicmap
  • remove-from-topicmap
  • archive-topic
  • delete-topic
  • restore-topic
  • restore-topicmap-membership

Delete flows are explicit. HyperDoc records an archive-topic or note-archive event before the destructive delete-topic or note-delete event, so the last complete state remains inspectable and replayable without rewriting history.

Replay and restore

Current state is reconstructed by replaying ordered journal events. Restore is also explicit: HyperDoc replays to a chosen revision, performs the minimal create/update/reattach steps needed to materialize that target state again, rereads the visible DMX state, and validates that the replayed target matches the live result.

  • read_workspace_journal reads the bounded workspace-wide overview.
  • read_topic_journal reads one subject stream with revisions and full events.
  • list_workspace_topic_revisions exposes the revision list without widening into raw event writes.
  • restore_workspace_topic_revision restores a topic revision.
  • restore_workspace_note_revision restores a note or handover revision.

Observed versus synthesized history

In-band HyperDoc writes emit journal events as part of the same guarded workflow, and dry run can preview the event shape through journal-event-preview. Out-of-band writes are different. HyperDoc has not proven an authoritative DMX event stream, revision feed, or native replay contract in the repo-used backend path.

For that reason, out-of-band detection for topicmap 919822 falls back to periodic snapshot reconciliation. Inferred events are marked synthesized-from-diff rather than being overclaimed as directly observed backend history.

Reconcile-on-read boundary

The live call-graph surface DMX workspace journal reconcile call graph makes one boundary explicit: reconcile-on-read may synthesize diff events in memory, but it must not persist or reattach the hidden companion journal notes while a read is in progress. The concrete incident anchor for that rule is companion journal note 924694 in topicmap 919822.

Restore safety

  • HyperDoc-owned absent topics can be recreated from the last complete journaled state.
  • Removed topicmap membership can be restored explicitly without hidden editor undo.
  • Foreign or non-owned absent topics are not hard-recreated blindly; restore returns a repair candidate instead.
  • If the backend cannot prove a safer native archive/tombstone contract, the journal's archive event is the bounded preserved tombstone signal HyperDoc owns.

Why this stays narrow

This model is intentionally smaller than "DMX as a revision database." It does not expose a raw "write arbitrary journal event" tool, does not claim a native DMX workspace event stream, and does not widen the shared workspace into generic mutation middleware. It only journals the guarded HyperDoc write surface plus bounded snapshot-diff reconciliation for topicmap 919822.

In the broader surface vocabulary, this page is the guarded runtime surface cluster within which the adjacent diagnostic, mutation, and failure surfaces stay distinct rather than collapsing into one tool.
