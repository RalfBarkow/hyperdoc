Emergency Host Overrides for Federated Sites

hyperdoc

This page documents the bounded operational logic behind using /etc/hosts during a federated naming incident. It is a continuity tactic for known sites, not a replacement for correct public DNS.

What /etc/hosts solves

When an operator already knows the correct IP for a trusted site, /etc/hosts bypasses the current DNS lookup path and pins that hostname to a chosen address on one machine.

  • It can preserve access to a small known-site set during unstable public DNS.
  • It is especially useful when the service itself is still running and only name resolution has become unreliable.
  • It gives the operator a simple, local, reversible continuity path.

What it does not solve

/etc/hosts does not repair the general naming system and it does not prove that the site has recovered.

  • It does not discover the correct IP for you.
  • It does not help if the origin service itself is down.
  • It does not fix wrong TLS state, stale origin mapping, or broken application behavior.
  • It does not scale well to a large, changing federation.

When it is appropriate

The tactic is appropriate when DNS Cache Decay in Browser-Centric Systems is the likely problem and all of these are true:

  • the site set is small and trusted
  • the operator has high confidence in the intended hostname-to-IP mapping
  • the continuity need is short-term and explicit
  • the operator also has a plan for removal after recovery

Risks of stale manual mappings

  • Manual entries can outlive the incident and silently route around recovered public DNS.
  • They can mask that an origin IP has changed legitimately.
  • They can bypass intended failover or infrastructure updates.
  • They can create local-only behavior that is hard to compare with what other users see.

Use in small trusted known-site sets

The safe operating style is to keep the mapping set deliberately small, note why each entry exists, and remove it once public resolution is trustworthy again.

  • prefer a short annotated block over many scattered entries
  • record when the override was added and what incident it belongs to
  • review or remove the block after the incident is stabilized

That is the right scale for Ward's workaround: a pragmatic continuity move for known sites, not a general federation repair mechanism.
