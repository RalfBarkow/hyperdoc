Review materialization issue surface

hyperdoc

A review should not stay a blob of prose once it contains actionable changes against durable HyperDoc pages, topics, sections, and tests. It can be transformed into a first-class inspectable object, parallel to page-lookup-issue, but aimed at materialization of proposed edits rather than lookup failure alone.

Proposed object name

I would not call the main object review-lookup-issue, because many review items are not lookup failures. A better pair is:

  • review-materialization-issue — one actionable review finding
  • review-materialization-plan — the scaffold or patch plan attached to that finding

If you want a narrower sibling specifically for missing pages discovered while reading a review, that can still be a subclass such as review-missing-page-issue.

Why this matches the existing surface model

  • page-lookup-issue already turns a failure into an inspectable object with provenance, classification, and repair context.
  • Diagramming Debugger Surface already treats execution steps as inspectable events that can be diagrammed.
  • A review is similar: it contains findings, each with source provenance, a target object, a classification, and a candidate change path.

So the natural move is: review prose → parsed findings → inspectable issue objects → materialization plan → optional write/apply → trace/diagram.

Suggested tabs on the inspector

  • Overview — same style as page-lookup-issue: source, target, classification, current status, suggested materialization
  • Evidence — the exact review sentence plus the target page paragraph(s) it refers to
  • Plan — the proposed edit, scaffold, or merge operation
  • Diff — textual before/after for the exact paragraph or list
  • Trace — event sequence for locating anchors, computing the change, and optionally applying it
  • Condition — any underlying failure or ambiguity object
  • Slots, Print, Operations, Playground — consistent with your other inspectable objects

Top-level actions

  • Open source
  • Open target
  • Show evidence
  • Scaffold
  • Preview diff
  • Apply or Export patch
  • Needs materialization
  • Fixed
  • Defer

Trace model

To make the surface diagrammable, wrap each issue's plan execution in a trace object: 

(defclass review-materialization-trace ()
  ((issue :initarg :issue :reader issue-of)
   (events :initarg :events :reader events-of)
   (result :initarg :result :reader result-of)))

Typical events:

  1. Locate source review paragraph
  2. Locate target page and section
  3. Read current target text
  4. Compute proposed insertion / replacement / merge
  5. Render preview diff
  6. Optionally apply or export patch
  7. Run verification

That gives you the same kind of inspectable sequence that the Diagramming Debugger surface gives for stepped execution.

Why the attached missing-page issue is a good clue

The screenshot you attached is actually a good motivator for this design. A review page already produces concrete actionable surfaces when it points at a page title that does not yet exist. But right now that only appears accidentally, via ordinary page lookup. The next step is to make all actionable review findings materialize deliberately, not only missing-page cases.

Recommended implementation path

  1. Create a plain domain object review-materialization-issue and one inspector view.
  2. Start with manual construction from a small list of known review findings.
  3. Add a review-materialization-plan object that can return scaffold text, paragraph insertion text, or a patch preview.
  4. Add a review-materialization-trace object and a Trace tab.
  5. Only after the inspectable path is good, add direct write/apply operations.

Smallest first slice

The smallest strong slice is:

  • one issue object
  • one inspector surface styled like page-lookup-issue
  • one issue bundle page for the Drew review
  • one plan type for paragraph insertion
  • one trace view showing source → target → proposed paragraph → verification

Bottom line

Yes: transform the review into a step-by-step instruction surface. Conceptually, the right generalization is not merely review-lookup-issue but review-materialization-issue plus review-materialization-trace. That would let each proposed review change appear as a first-class inspectable object with the same kind of provenance, classification, repair plan, and diagrammable execution path that you already value in page-lookup-issue and Diagramming Debugger Surface.
