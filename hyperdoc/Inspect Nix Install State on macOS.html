Inspect Nix Install State on macOS

hyperdoc

Use this page to inspect the current Nix state on macOS before choosing a recovery path.

Inspectable objects

Run these commands first

uname -m
ls -ld /nix /nix/store 2>/dev/null || true
ls /nix 2>/dev/null || true
file /usr/local/bin/determinate-nixd 2>/dev/null || true
nix --version 2>/dev/null || true

How to read the results

  1. If uname -m prints x86_64, the host is an Intel Mac. Do not fetch aarch64-darwin binaries for it.
  2. If file /usr/local/bin/determinate-nixd reports arm64 while the host is x86_64, you have a concrete architecture mismatch on disk.
  3. If /nix/store is missing and ls /nix prints nothing, the live store contents are gone even if /nix itself still exists.
  4. If nix --version prints nothing or fails, the CLI may be absent, broken, or no longer on the shell path.

Interpret the observed Intel-host state

On this machine, the inspection results show an Intel (x86_64) Mac with no active Nix store. /nix still exists, but /nix/store is missing and /nix is empty, which indicates that the store contents are gone and only the mountpoint or top-level directory remains. At the same time, /usr/local/bin/determinate-nixd is still present, but it is an arm64 Mach-O binary, which is the wrong architecture for this host. nix --version fails because no working nix command is installed. The combined reading is: the Determinate install is no longer functional, most of it has already been removed, and at least one stale wrong-architecture binary remains on disk.

An empty /nix after uninstall can still be a successful uninstall on macOS. The official Nix uninstall guidance notes that the empty mountpoint can remain until reboot.

An empty /nix by itself is not proof of a healthy installation. When /nix/store is missing, nix is not found, and only a stray helper binary remains, the correct reading is not “partially working” but “broken or mostly uninstalled.”

How to read the /nix markers

The Determinate installer uses /nix/nix-installer and /nix/receipt.json as install and uninstall markers. They can still help when the state is ambiguous, but in the concrete state above they are not decisive: the missing store, absent nix, and wrong-architecture residue already establish that the installation is no longer usable.

Wrong-architecture downloads to avoid

  • Do not download nix-installer-aarch64-darwin on an Intel Mac.
  • Do not download nix-installer-x86_64-linux on an Intel Mac.
  • Do not treat a random architecture-specific binary name as interchangeable with the host platform.

The correct first move is always: confirm the host architecture, inspect the on-disk state, and only then choose either the upstream reinstall path or the legacy fallback path.

Interpret the next blocker after cleanup

After removing the stale arm64 Determinate helper, the upstream Nix installer correctly targeted x86_64-darwin and advanced into normal multi-user installation. If the next stop is /etc/bashrc.backup-before-nix already existing, the platform mismatch is resolved. The reinstall is now blocked by leftover installer backup state from an earlier Nix attempt.

In the observed follow-on case, /etc/bashrc is not missing; it is a live symlink to /etc/static/bashrc. The blocker is therefore not absence of the original file but the presence of a stale /etc/bashrc.backup-before-nix left by an earlier installer run. In that state, do not restore the backup onto /etc/bashrc. Instead, inspect the stale backup, confirm whether it is merely an old pre-Nix copy, and then move it aside or remove it so the installer can create a fresh backup of the current /etc/bashrc.

At that point, go to Clear Stale Nix Installer Backup Files on macOS.

Interpret the first healthy install phase

After matching the installer to the pre-existing nixbld group ID (30000), the macOS multi-user installer proceeded normally. It verified the existing build users, created the /nix directory hierarchy, created /nix/store, copied the initial Nix closure into the store, and began loading the Nix database. This is the transition point from residue cleanup to successful installation.

Once the installer reaches nix-store --load-db, the earlier macOS recovery blockers have been resolved. Remaining failures, if any, are no longer about stale shell backups or mixed architectures, but about the final daemon/profile setup steps.

Interpret the later shell-setup failure

After the installer successfully created /nix/store and loaded the Nix database, shell profile setup can still fail at sudo touch /etc/bashrc. On the observed machine, /etc/bashrc was a symlink to /etc/static/bashrc, and /etc/static itself was a dangling symlink into /nix/store/.... That is leftover nix-darwin residue, not a normal directory tree. In this case, do not try to repair /etc/static with mkdir -p or touch. The correct recovery is to replace the specific broken shell-profile symlink such as /etc/bashrc with a plain file, then rerun the installer. 

[ -L /etc/bashrc ] && sudo mv /etc/bashrc /etc/bashrc.dangling-static-link
sudo touch /etc/bashrc
sudo chmod 644 /etc/bashrc

sudo test -d /etc/zsh || sudo mkdir -p /etc/zsh
sudo touch /etc/bash.bashrc /etc/zsh/zshrc
sudo chmod 644 /etc/bash.bashrc /etc/zsh/zshrc

export NIX_BUILD_GROUP_ID=30000
sh ./install-nix

Interpret the later SSL error

A later failure can show up only after installation and daemon restart, when nix profile add nixpkgs#direnv fails with SSL error 77 and specifically references /etc/ssl/certs/ca-certificates.crt. On the observed machine, the Nix-managed CA bundle already existed at /nix/var/nix/profiles/default/etc/ssl/certs/ca-bundle.crt. The winning fix was to write that path persistently into /etc/nix/nix.conf, restart the daemon, and retry the profile install.

Shell-only overrides such as NIX_SSL_CERT_FILE and SSL_CERT_FILE were not sufficient on their own. The successful fix was a daemon-visible Nix configuration change, not a temporary shell export. Go next to Fix Nix SSL Certificate Path on macOS.

What to do next

sudo rm -f /usr/local/bin/determinate-nixd
curl -L https://nixos.org/nix/install | sh

A tighter operational reading for this machine is:

  1. Host architecture is Intel: x86_64.
  2. No active Nix store is present.
  3. nix command is absent.
  4. A stale arm64 Determinate helper binary remains.
  5. Recommended recovery: remove the stale helper and reinstall upstream Nix.

Do not try to recover this Intel Mac by manually downloading nix-installer-aarch64-darwin or nix-installer-x86_64-linux. Those binaries target different platforms and can recreate the same mixed-architecture failure pattern.
