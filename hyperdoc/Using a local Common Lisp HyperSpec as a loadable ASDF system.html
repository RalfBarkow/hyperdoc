Using a local Common Lisp HyperSpec as a loadable ASDF system

The clean design is not “load all HyperSpec HTML into Lisp objects”. It is:

  1. keep a complete, unmodified local HyperSpec tree inside a dedicated ASDF system,
  2. have that system expose the filesystem root of the local copy,
  3. mount that root under your HyperDoc server on your own origin,
  4. generate local HyperSpec URLs from symbol lookups.

LispWorks explicitly provides a downloadable HyperSpec archive, and the official legal page allows copying, distribution, display, and transmission only if the copy is complete and unmodified and retains the required notices, links, and images. Modified copies and derivative works are expressly not permitted.

That means: package the HyperSpec verbatim, but do not rewrite its pages, inject HyperDoc chrome into them, or patch its links. Keep your own navigation outside the HyperSpec document.

Best practical choice

There is already a thin ASDF wrapper system named clhs. Its reference manual says the HyperSpec-7-0 directory in that system is a complete and unmodified copy of LispWorks’ Common Lisp HyperSpec 7.0, and that the wrapper exposes support such as hyperspec-root and install/setup helpers.

Separately, the hyperspec library provides a lookup function that maps a Common Lisp symbol to the appropriate HyperSpec URL, and a *hyperspec-root* variable that can point at a local root.

So the most robust split is:

  • clhs (or your own vendored equivalent) for the static corpus
  • hyperspec for symbol-to-page lookup

Minimal ASDF system

(defsystem #:hyperdoc/clhs
  :description "Local Common Lisp HyperSpec mount for HyperDoc"
  :author "Ralf Barkow"
  :license "Wrapper code only; HyperSpec remains under LispWorks terms"
  :serial t
  :depends-on (#:asdf #:uiop)
  :components ((:file "hyperdoc-clhs/package")
               (:file "hyperdoc-clhs/main")))

Package

(defpackage #:hyperdoc/clhs
  (:use #:cl)
  (:export
   #:*mount-path*
   #:root-directory
   #:root-url
   #:local-url
   #:register-static-mount))

Main implementation

(in-package #:hyperdoc/clhs)

(defparameter *mount-path* "/hyperspec/")

(defun root-directory ()
  (merge-pathnames #P"vendor/HyperSpec-7-0/HyperSpec/"
                   (asdf:system-source-directory :hyperdoc/clhs)))

(defun root-url (&optional (mount-path *mount-path*))
  mount-path)

(defun local-url (relative-path &optional (mount-path *mount-path*))
  (format nil "~A~A"
          mount-path
          (string-left-trim "/" relative-path)))

(defun register-static-mount ()
  ;; Replace this body with the exact HyperDoc/HyperBook server hook you use.
  ;; The important part is: mount ROOT-DIRECTORY at *MOUNT-PATH*.
  (values *mount-path* (root-directory)))

Using the existing lookup library

(ql:quickload '("clhs" "hyperspec"))

(setf hyperspec:*hyperspec-root* "http://localhost:8080/hyperspec/")
(hyperspec:lookup 'cl:defclass)
;; => "http://localhost:8080/hyperspec/Body/m_defcla.htm"

If you want the URL to stay origin-relative inside HyperDoc, either store only the relative tail or post-process the returned URL once and swap the canonical root for your local mount root.

How this fits HyperDoc

Your “HyperSpec page for defclass” pane should stop pointing at https://www.lispworks.com/... and instead point at something like /hyperspec/Body/m_defcla.htm on your own server. Then Firefox is no longer dealing with a foreign site that forbids framing.

The page remains the official HTML payload, just locally served.

Important constraint

Do not transform the HyperSpec files in place. If you want extra controls such as backlinks, annotations, provenance, or “open source definition” affordances, wrap them around the iframe or alongside it in HyperDoc. Do not inject them into the copied HyperSpec itself.

Recommendation

For your project, I would choose one of these two paths:

  1. Fastest: depend on the existing clhs system and mount its bundled HyperSpec-7-0/HyperSpec/ directory locally.
  2. Most reproducible for HyperDoc: vendor the official archive into your repository as vendor/HyperSpec-7-0/ and add a tiny hyperdoc/clhs wrapper system exactly like above.

I would prefer the second option for HyperDoc because it makes the documentation corpus an explicit part of the project state and avoids relying on an external Quicklisp artifact at runtime.
