Landing Page Redirect to Local Boot

A non-wiki landing page can redirect the browser to the local HyperDoc entry point boot.html. That part is viable.

What does not work is treating a remote landing page as if it were the local HyperDoc boot page and having it connect directly to a localhost CLOG websocket endpoint.

Viable pattern

  1. A remote HTML landing page is served from some public origin.
  2. That page redirects the browser to the local HyperDoc URL, for example http://127.0.0.1:8080/boot.html.
  3. The browser leaves the remote origin and navigates to the local origin.
  4. The local boot.html page loads boot.js and starts the normal local CLOG session.

This is ordinary browser navigation. The important point is that the browser is no longer running code from the remote origin once it reaches the local HyperDoc page.

Non-viable pattern

  1. A remote page remains loaded at its original public origin.
  2. That remote page tries to connect directly to ws://127.0.0.1:.../clog.

This crosses the same origin and private-network boundary that already blocks direct public-origin to localhost interaction in other FedWiki bridge cases. The remote page is still remote; it has not become the local HyperDoc boot page.

Why the distinction matters

The local HyperDoc boot page and the local CLOG websocket endpoint belong to the same local runtime. That pairing is intentional. The remote landing page can point the browser toward that runtime, but it should not try to act as the runtime itself.

Practical advice

  • Redirect to http://127.0.0.1:8080/boot.html or whatever local HTTP entry point you control.
  • Do not hardcode a transient websocket port in the remote landing page.
  • Let the local boot.html and boot.js discover and establish the websocket session the normal way.
