SBCL bootstrapping model

hyperdoc

This page explains what Christophe Rhodes means by a sanely bootstrappable Common Lisp in the case of SBCL. The paper is not mainly about replacing source files with saved images. It is about using a host Lisp image during bootstrap while containing that image dependence so the final build outcome does not depend on accidental host-image state.

What sanely bootstrappable means here

SBCL is built with the help of an existing host Common Lisp implementation, but the build is arranged so the final target result is reconstructed through explicit stages rather than inherited from whatever happened to be sitting in the host image. That is why bootstrap determinism matters: the build should succeed because the source and stages are right, not because the host image happened to carry the right accidental state.

This makes SBCL bootstrapping a useful architecture topic for HyperDoc. It separates live image convenience from durable source reconstruction without denying that images remain useful during implementation work.

Images still matter, but not as the durable truth

The paper's workflow boundary is narrower than some modern discussions imply. Ordinary Common Lisp application development is usually source-oriented development: source files stay authoritative, compile-file and reload remain normal, and saved images are often retained mainly as an image as deployment artifact.

What is more image-oriented in the paper is the implementation-development side. A host Lisp image is mutated far enough to build the target system, but SBCL's contribution is to keep that dependence explicit and bounded rather than letting the final build silently depend on host-image accidents.

Why this matters technically

  • A host Lisp compiles and loads the bootstrap machinery.
  • A cross-compiler running in that host emits target SBCL code.
  • The genesis build stage simulates loading target artifacts and writes the cold core.
  • The SBCL runtime starts from that core and performs cold init.

This pipeline is valuable because it makes host/target separation explicit. The host Common Lisp is a build tool; the target SBCL is the thing being built.

Why this matters socially

The paper also makes a social claim that fits HyperDoc directly. bootstrappability as social architecture lowers contributor friction: fewer special bootstrap exceptions mean less time spent wondering whether a change needs secret image magic and more time spent doing ordinary, reviewable development work.
