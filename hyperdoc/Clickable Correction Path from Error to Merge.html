Clickable Correction Path from Error to Merge

hyperdoc

A credible maintenance story should not stop at classifying a visible error. The error should lead to the source change, the verification step, and then the merge decision.

For the current kioskberrli failure, the path should be: 

visible error
  ->
remove obsolete option in source
  ->
rerun the SD-image build
  ->
either reach a verified build or expose the next distinct failure
  ->
merge only after the verified correction

1. Visible error

The starting point is the normalized failure object: kioskberrli-sd-image-failure-context

This object classifies the failure and records the pinned upstream context.

2. Suggested patch

The next click should not be another abstract explanation. It should point to the source edit that removes the obsolete option: suggested-patch

For this topic, the patch is intentionally minimal: remove the sdImage.imageSize setting from kiosk.nix. The important point is not to guess a replacement too early, but to clear the known invalid option first.

3. Verification command

The correction is not credible until the pinned build target is rerun: repro-build-command

This is the step that turns the repair from a source edit into a verified maintenance move.

In the current case, rerunning the build did not yet yield a successful image build. It did, however, prove that the original sdImage.imageSize failure is gone and expose the next concrete blocker: Kioskberrli Cross-Host Build Failure.

4. Merge step

Only once the verification build succeeds is the final step the normal repository decision:

  • commit the correction
  • review the result in the branch context
  • merge the verified fix

The correction path object should therefore remain explicit about the final step: correction-path

Why this matters

The maintenance story becomes credible only when the visible error can drive the whole repair sequence without forcing the maintainer to reconstruct the path from memory.

In that sense, the error object should behave less like a dead report and more like a small workflow capsule.
