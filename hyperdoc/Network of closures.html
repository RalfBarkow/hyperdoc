Network of closures

Feeley and Lapalme's phrase “network of closures” gives the precise compiler model for the NOR matcher. The matcher compiler does not generate Lisp source, bytecode, or machine code. It walks the source expression once and generates closures. Each closure implements one primitive part of the object language.

In the NOR matcher, leaf forms become predicate closures and nor forms become control closures. The resulting matcher is the root closure of this generated network. 

source form:
  (nor "moon" "lunar" "landing")

compiled control shape:
  test "moon"
    success -> final failure
    failure -> test "lunar"
                 success -> final failure
                 failure -> test "landing"
                              success -> final failure
                              failure -> final success

The important distinction from interpretation is that the source expression is classified once during compilation. During execution, the matcher follows the already-built closure network.

This makes the matcher a small embedded-language compiler. The source language contains strings, structured leaf predicates, and nor. The target language is an executable graph of closures connected by success and failure continuations.

Why this should be visible in HyperDoc

A closure prints opaquely, so the teaching object should preserve both the executable root closure and a serializable network description. The learner should be able to inspect:

  • the original expression,
  • the generated closure-network description,
  • the runtime trace for a target object,
  • the final result.

This separates three questions that beginners often confuse:

  1. What did we write?
  2. What did compilation build?
  3. What happened when the matcher ran?
