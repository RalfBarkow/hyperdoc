# Submit-boundary Connect session snapshot

A good topic title would be **“Submit-boundary Connect session snapshot”**.

Operationally, in this codebase, a **session snapshot** is not a browser session or a server session. It is a **serialized capture of the live Connect gesture state at the browser→server handoff**. The browser builds it with `debugSnapshot()`, which records `capturedAt`, `capturedAtLabel`, a `session` diagnostic, the set of live pane snapshots, and the accumulated transition log. On the Lisp side, that JSON is parsed into a `dom-connect-session-snapshot` object whose core fields include the capture time/label, session id and phase, source/target pane and provider info, source/target anchors, panes, and transitions.    

So an operational definition you can reuse in HyperDoc is: **a submit-boundary session snapshot is the browser-captured JSON image of the current Connect interaction state, taken immediately before the create/open request crosses into the server path, so the later evidence object can show what the Connect UI believed the session looked like at that exact handoff.** The request-evidence layer itself describes requests as being “recorded at the Connect submit boundary,” and the server logs that boundary with flags such as `snapshot-present?` and `snapshot-length`.  

The review of **“No submit-boundary session snapshot was captured.”** is straightforward at the UI level: that sentence is rendered only when the evidence object’s `session-snapshot` slot is `NIL`. The same view still shows the source and target anchors separately; only the optional snapshot pane/object is missing. So the sentence does **not** mean “the request definitely failed.” It means “this evidence object has no parsed snapshot object attached to it.” 

Mechanically, the evidence object tries to populate its snapshot from `snapshot-json`. `ensure-dom-connect-request-evidence` either reuses an existing snapshot or calls `maybe-dom-connect-session-snapshot-from-json-string`; that helper only runs when `snapshot-json` is present, and it wraps parsing in `ignore-errors`. That means the snapshot ends up absent in two broad cases: **the JSON never arrived**, or **it arrived but could not be parsed into a snapshot object**.  

Why this message is especially plausible in the current association flow: the browser comment explicitly says the hidden inputs are now **“for diagnostics only”** and that the clicked submit button carries the authoritative payload. In that same association path, `writeSubmitPayload()` writes source/target/context/provider data onto the authoritative `button-payload-v2` button, but it does **not** write `data-dom-connect-snapshot-json`. The snapshot is only mirrored into the legacy hidden snapshot input if `state.inspectInput` exists. So for ordinary association submits, snapshot capture is now a **best-effort fallback**, not part of the authoritative payload contract.  

On the server side, `dom-association-submit-payload` does try both places: first `data-dom-connect-snapshot-json` on the payload-bearing element, then the hidden control value addressed by `snapshot-field-id`. That means the current design can still recover a snapshot, but only if that hidden field is present, correctly bound, and readable at submit time. If not, `:snapshot-json` is `NIL`, the evidence object records the request anyway, and the payload view later shows exactly the sentence you saw.   

My review, then, is: the message is probably **accurate but slightly misleading in emphasis**. It reads like a mysterious failure, but in the current code it more likely means **“the request evidence was created without a reusable browser-state snapshot because snapshot transport is no longer authoritative in the standard association path.”** That interpretation is strengthened by the asymmetry in the JS: the explicit **Inspect** and **request evidence** paths do attach snapshot JSON directly, while the normal association submit path does not.   

A compact wording for the topic page could be:

**Submit-boundary Connect session snapshot**
A submit-boundary Connect session snapshot is the browser-captured JSON record of the live Connect gesture state at the moment a request crosses from the pane UI into the server-side create/open path. It preserves the Connect phase, selected source/target anchors, participating pane states, and transition history so later request evidence can be inspected against the exact browser-side state at handoff. When request evidence says *“No submit-boundary session snapshot was captured,”* the request may still exist and its source/target anchors may still be available; the sentence means only that no parseable snapshot object was attached to that evidence record.    

The likely fix direction is to make snapshot transport authoritative for `button-payload-v2` as well, instead of relying on the legacy hidden snapshot field.
