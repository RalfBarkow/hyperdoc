HyperDoc Checks Runner

hyperdoc

The HyperDoc checks runner is the first in-image runner for HyperDoc examples and smoke tests. It keeps the existing clickable defexample execution path, but adds one common runtime model for batch discovery, batch execution, inspectable failures, and rerun-failed workflows.

Why this runner exists

HyperDoc already had a good one-example interaction: open a source page, click the ► button before a top-level defexample, and inspect the resulting object in a new pane. What it did not have was a first-class way to treat examples and repo-local smoke tests as one inspectable set of checks that can be discovered, run together, and inspected after failures.

This runner adds that missing surface without changing the existing example affordance. Single-example execution still matters; the new runner adds a higher-level batch surface on top of it.

One common check model

HyperDoc now treats both examples and tests as checks.

  • Check spec: a runtime descriptor for one runnable check.
  • Check result: the inspectable outcome of one check execution.
  • Check run: a batch object containing discovered specs, collected results, and summary counts.

This keeps discovery separate from execution. A check can be discovered before it is run, and a check run remains inspectable after execution rather than collapsing into terminal-only text.

How discovery currently works

Discovery is explicit and repo-local in this first slice.

  1. Examples register themselves when defexample forms are loaded.
  2. That registration stores a stable check identifier, function locator, and source-page context.
  3. Tests come from an explicit list of existing repo-local smoke entrypoints.
  4. The runner combines both sets into one discovered check run.

This is deliberate. HyperDoc does not yet attempt broad automatic discovery across arbitrary third-party test frameworks or packages. The current design keeps the runner understandable and inspectable.

Pane surface

The main user-facing entrypoint is the new Checks view on the HyperDoc object.

  1. Open the HyperDoc object in the explorer.
  2. Open the Checks view.
  3. Click Inspect discovered checks to open the discovered check-run object.
  4. Click Run all checks to populate result objects.
  5. Inspect one failed or errored result to see its condition and captured backtrace.
  6. Use Rerun on one result or Rerun failed on the run object.

This keeps failures inside the same pane model as other HyperDoc runtime objects. The runner is inspectable first and HTML-visible second.

CLI surface

The terminal entrypoint is hyperdoc:run-ci-checks. It is a thin wrapper over the same runtime model, not a separate test-only subsystem.

For a step-by-step terminal procedure around one narrow test entry point, see Running DMX Topic Proxy Smoke Tests.

(hyperdoc:run-ci-checks :system "hyperdoc" :quit? nil)

It discovers checks, runs them, prints a compact textual summary, and can exit non-zero when used in non-interactive mode.

How to demonstrate it

There are two good demonstrations.

  1. Pane demo: open the HyperDoc object, then open Checks, inspect discovered checks, run all checks, and inspect one failure result.
  2. Terminal demo: run the smoke suite or hyperdoc:run-ci-checks from a non-interactive SBCL session.

The pane demo shows the architectural point more clearly: discovery objects, run objects, result objects, and rerun actions are all first-class runtime surfaces.

Current scope and intentional limits

  • No remote or distributed execution.
  • No persistent history or scheduler.
  • No broad automatic test discovery beyond the explicit repo-local registry.
  • No page-markup mutation.

One current follow-up is already visible: a batch run exposes that some existing examples are not yet classified as batch-safe versus interactive or environment-sensitive. The runner is doing useful work there, but the classification policy belongs to a separate slice.
