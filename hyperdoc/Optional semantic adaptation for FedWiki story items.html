Optional semantic adaptation for FedWiki story items

hyperdoc

This page records a now-stable boundary in HyperDoc's FedWiki handling: source-faithful story-item import stays primary, and semantic adaptation is an optional second stage used only where a story-item kind benefits from it.

Inspectable objects

  • Optional semantic adaptation for FedWiki story items

Stable pipeline

The stable pipeline is: 

FedWiki JSON
-> source-faithful story item
-> optional adaptation
-> adapted semantic object or adaptation-failure
-> preferred render + safe fallback

The source-faithful story item remains the authoritative imported object. Adaptation does not replace it. Adaptation derives a second object that is easier to inspect and render meaningfully without rewriting the imported source.

Why source-faithful import stays primary

HyperDoc already has a good import seam in make-story-item. That seam preserves the original FedWiki structure as a typed story-item with its original type, id, text, and remaining data.

That source-faithful object stays the right anchor for provenance, inspection, and raw fallback. The semantic adaptation layer is deliberately second-stage so that parsing or rendering improvements do not rewrite the imported meaning of the page.

Stable boundary now proven

  • source-faithful story item stays primary
  • adaptation is optional and second-stage
  • success and failure stay visibly distinct
  • the shared failure payload is normalized
  • Graphviz remains on its thin shared seam

Adaptation is not part of generic story-item construction. It is called only from selected render-story-item methods that explicitly opt into the extra step. The default method for adapt-plugin-like-story-item remains inert.

Three proving cases

Video: parse-first semantic normalization

The :video slice proves the parse-first case. HyperDoc supports: 

YOUTUBE <video-id>
caption...

The adapter derives provider, video id, caption, canonical URL, and embed URL. Rendering then uses an embedded player plus caption with a safe canonical-link fallback. Malformed or unsupported input does not silently degrade into a half-working embed. It becomes a story-item-adaptation-failure plus raw-source fallback from the original story item.

Frame: bounded embed with explicit rejection of raw HTML

The :frame slice proves a different but compatible case. HyperDoc supports: 

<url>
HEIGHT <pixels>

The adapter derives target URL and height, then renders a bounded iframe plus direct-open link. Raw <iframe ...> HTML is an explicit failure case, not a best-effort success path. That preserves the seam as semantic adaptation rather than ambient HTML reuse.

Audio: capability-sensitive success rendering from a typed semantic object

The :audio slice proves a third case: semantic validity is separate from inline playability. HyperDoc supports a narrow form in which the first non-empty line is an absolute http(s) URL and the remaining text is optional caption/body.

The adapter derives a typed semantic object and classifies the URL before rendering:

  • direct media gets bounded <audio> rendering plus caption/body and explicit open/download link
  • non-direct-media but semantically valid URLs get fallback-only success rendering plus caption/body and explicit open link
  • malformed or HTML-ish input stays on the explicit failure path

This matters because parse success and preferred inline rendering are not the same question. The typed semantic object keeps them separate.

Why raw iframe HTML is explicit failure

HyperDoc is not trying to inherit the FedWiki plugin runtime or accept raw plugin HTML as the main abstraction. A raw <iframe ...> string may contain meaningful source evidence, but in this stage it is not treated as a trusted semantic object. The correct outcome is an inspectable failure plus raw source, not a silent embed.

Why Graphviz is not the next proving case

Graphviz is important, but it is not the next proving case for this seam. Graphviz already has a good thin ownership boundary:

  • the FedWiki story-item side stays thin
  • the shared lower Graphviz seam owns transport, runtime, and raw fallback
  • the FedWiki renderer hands off quickly to views:graphviz-snippet

If Graphviz is ever wrapped into the same contract, it should be a light retrofit that preserves that handoff.

Current naming decision

Keep adapt-plugin-like-story-item and story-item-adaptation-failure for now. The shared failure payload is now normalized to partial-fields, which is enough for the currently proven cases without introducing per-type failure classes.

What would count as new evidence vs just more surface area?

New evidence would mean a new type forces a genuinely different boundary question than the three current cases. Examples would include a different kind of semantic parsing contract, a different safe-fallback contract, or a new separation between semantic validity and preferred inline rendering that is not already covered by :video, :frame, or :audio.

More surface area would mean another type merely repeats the same source-faithful import, optional adaptation, normalized failure, and bounded render/fallback pattern without changing what the seam needs to prove.

Recommendation

Pause further type additions unless a new type demonstrates a genuinely different boundary question.
