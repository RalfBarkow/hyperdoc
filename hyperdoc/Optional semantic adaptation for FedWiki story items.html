Optional semantic adaptation for FedWiki story items

hyperdoc

This page records a now-proven boundary in HyperDoc's FedWiki handling: source-faithful story-item import stays primary, and semantic adaptation is an optional second stage used only where a story-item kind benefits from it.

Inspectable objects

  • Optional semantic adaptation for FedWiki story items

Stable pipeline

The stable pipeline is: 

FedWiki JSON
-> source-faithful story item
-> optional adaptation
-> adapted semantic object or adaptation-failure
-> preferred render + safe fallback

The key point is that the source-faithful story item remains the authoritative imported object. Adaptation does not replace it. Adaptation derives a second object that is easier to inspect and render meaningfully.

Why source-faithful import stays primary

HyperDoc already has a good import seam in make-story-item. That seam preserves the original FedWiki structure as a typed story-item with its original type, id, text, and remaining data.

That source-faithful object is still the right anchor for inspection, provenance, and raw fallback. The semantic adaptation layer is deliberately second-stage so that parsing or rendering improvements do not rewrite the imported meaning of the page.

Why adaptation is opt-in

Adaptation is not part of generic story-item construction. It is called only from selected render-story-item methods that explicitly opt into the extra step. The default method for adapt-plugin-like-story-item remains inert.

That boundary matters because most story-item kinds do not need a second semantic object. Paragraphs, markdown blocks, references, and images already have direct rendering paths. The adaptation seam exists for kinds where parsing into a smaller, more explicit object improves both rendering and failure handling.

Two proving cases

Video: parse-first semantic normalization

The :video slice proves the parse-first case. HyperDoc supports the narrow form: 

YOUTUBE <video-id>
caption...

The adapter derives a small semantic object with provider, video id, caption, canonical URL, and embed URL. Rendering then uses:

  • preferred: embedded player plus caption
  • safe fallback: canonical external link plus caption

Malformed or unsupported input does not silently degrade into a half-working embed. It becomes a story-item-adaptation-failure plus raw-source fallback from the original story item.

Frame: bounded embed with explicit rejection of raw HTML

The :frame slice proves a different but compatible case. It supports only the narrow textual form: 

<url>
HEIGHT <pixels>

The adapter derives a semantic object with target URL and height. Rendering then uses:

  • preferred: bounded iframe plus direct-open link
  • safe fallback: direct-open link plus explicit height note

The important discipline in this slice is what does not happen: raw <iframe ...> HTML is an explicit failure case, not a best-effort success path. That preserves the seam as semantic adaptation rather than ambient HTML reuse.

Why raw iframe HTML is explicit failure

HyperDoc is not trying to inherit the FedWiki plugin runtime or accept raw plugin HTML as the main abstraction. The current :frame slice is therefore intentionally narrow.

A raw <iframe ...> string may contain meaningful source evidence, but in this stage it is not treated as a trusted semantic object. The correct outcome is an inspectable failure plus raw source, not a silent embed.

That keeps the boundary clear:

  • source-faithful import remains available
  • unsupported semantic input stays explicit
  • the renderer does not quietly become an HTML passthrough

Why Graphviz is not the next proving case

Graphviz is important, but it is not the next proving case for this seam. Graphviz already has a good thin ownership boundary:

  • the FedWiki story-item side stays thin
  • the shared lower Graphviz seam owns transport, runtime, and raw fallback
  • the FedWiki renderer hands off quickly to views:graphviz-snippet

If Graphviz is ever wrapped into the same contract, it should be a light retrofit that preserves that handoff.

Current naming decision

Keep adapt-plugin-like-story-item and story-item-adaptation-failure for now. Before a third type is added, normalize the failure payload so it is no longer shaped by the video-specific first slice.

Should a third type be attempted yet?

Recommendation: pause first. :video and :frame are enough to document the seam and review naming and failure-shape decisions before broadening it. If a third type is evaluated later, :audio is the most plausible candidate.
