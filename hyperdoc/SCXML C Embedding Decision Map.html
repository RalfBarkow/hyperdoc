SCXML C Embedding Decision Map

hyperdoc

This page documents the inspectable decision-space object for the SCXML-to-C HyperDoc integration path.

The architectural rule is: 

Do not embed HyperDoc into C.
Embed a generated SCXML protocol machine into C.
Let that machine call the HyperDoc service.
Let HyperDoc inspect, validate, replay, and document the same machine.

Why this page exists

The decision map is a live Lisp object with inspector views. This page is the durable explanation surface. Keep them separate: the page explains the design, while the object exposes the current decision matrix, roadmap, and option objects.

Boundary model

Layer Responsibility
Generated C state machine Owns deterministic protocol state, events, guards, and trace emission.
Transport adapter Owns HTTP, JSON-RPC, MCP, socket, or embedded-system transport calls.
HyperDoc service Owns pages, topics, inspector views, replay, validation, and documentation.
HyperDoc page Explains the architecture and links to the inspectable runtime object.

Current recommended sequence

  1. HyperDoc-first MVP: SCXML as contract, HyperDoc validates and replays, C client initially handwritten.
  2. Embedded-safe SCXML profile: restrict SCXML to deterministic, codegen-friendly constructs.
  3. Generated C machine plus handwritten transport: generate only the state/event/transition logic and keep I/O in callbacks.

Source artifacts

  • hyperdoc/decision-maps.lisp: decision-map object model and seed instance.
  • hyperdoc-inspector/decision-maps.lisp: inspector views for the map and options.
  • hyperdoc/SCXML C Embedding Decision Map.html: this durable explanation page.
