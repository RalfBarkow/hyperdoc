Why a runtime model matters

HyperDoc combines pages, links, inspectable objects, and neighboring systems. A runtime model helps contributors distinguish what is represented as data, what is represented as object behavior, and which layer is responsible for navigation, inspection, or collaboration traces.

Core runtime entities

  • ASDF system objects: scope boundaries that group code ownership, pages, examples, and test entry points.
  • Page objects: runtime representations of HyperDoc pages and their links.
  • Topic object code: inspectable concept handles currently implemented under hyperdoc/topics/; production project topic persistence belongs to the Dreyeck/DMX SQLite database.
  • Inspectable object references: expr-backed links to runtime symbols and objects.
  • HyperBook/FedWiki page records: externally stored page artifacts linked into workflows.
  • Inspector views: object-specific representations for runtime exploration.

Hypermedia items as objects

In the current Common Lisp implementation, each hypermedia item as in-memory object is represented by a live Lisp object. That object may directly contain the content, or it may act as a proxy to another representation such as a file, an ASDF component, or a network resource.

This matters because HyperDoc does not treat its browser surface as a thin wrapper around static files. The browser is already a runtime view onto live objects that can expose code, metadata, relations, and object-specific inspector views.

Page, topic, and inspectable object

A page is narrative structure. A topic is reusable semantic identity. An inspectable object link is a runtime handle inside page narrative.

These are related but not interchangeable: pages organize explanation, topics stabilize concept references, and inspectable links make runtime structures explorable in context.

Inspector as browser

HyperDoc currently treats the inspector as browser as a first-class browsing model. Any inspector that can render the relevant runtime objects could serve as a HyperDoc browser. The current web-facing inspector is implemented with CLOG and is strongly informed by Glamorous Toolkit's inspector practice, but that is a current browser realization, not the whole conceptual boundary.

Execution evidence should survive the run

HyperDoc already has one precedent for this design in HyperDoc Test Runner: a check-result remains an inspectable execution outcome, and a check-run remains an inspectable batch object rather than collapsing into terminal-only text. The inspector performance log points toward the same requirement for interactive exploration.

A pane creation, view selection, or render event should not survive only as a transient console stream. It should be promotable into an execution evidence object, grouped under an inspector session or pane run, so that the runtime account remains inspectable after execution instead of collapsing into ephemeral log lines.

That is the runtime consequence of same-protocol explanation. Evidence should be emitted during the run, but it should also survive the run as objectified execution evidence. This is one concrete form of persistence of investigation context.

Story and journal as runtime-facing structures

In FedWiki-related surfaces, story holds current visible content and journal holds replayable edit history. HyperDoc consumes these as linked artifacts rather than replacing their runtime semantics.

The journal layer is collaboration trace infrastructure, not a substitute for HyperDoc topic modeling.

Local and remote page relationships

  • Local HyperDoc pages provide durable architecture and inspectable references.
  • Localhost FedWiki pages provide parallel journaling and iterative trail.
  • Remote hyperbooks/external pages are linked as references with explicit boundaries.

Current browser versus protocol direction

The long-term direction is HyperDoc as protocol: a more explicit interaction layer between units that may be realized as different processes, services, or implementation technologies. That would support multiple browsers, including special-purpose browsers, without requiring every HyperDoc unit to live inside one monolithic runtime image.

The current repository does not claim that this protocol layer already exists. What is already true is the object-centered browser model above: the current in-image implementation is concrete, while the protocol-level decomposition remains a longer-term architectural direction.

Runtime boundaries and responsibilities

  • System scope layer: ASDF-system-centered grouping of examples and test surfaces.
  • HyperDoc page layer: durable narrative + object links.
  • Topic layer: curated semantic handles and references.
  • Inspector layer: runtime object exploration through views.
  • FedWiki layer: journaled page evolution and neighborhood context.
  • Boundary rule: link layers explicitly; do not collapse them into one implied model.

Common confusions and false equivalences

  • Treating page text as equivalent to topic-object identity.
  • Treating inspectable links as decorative navigation instead of explanatory runtime handles.
  • Treating FedWiki story/journal structures as direct replacements for HyperDoc page/topic structures.
  • Assuming local and remote references share identical lifecycle and ownership constraints.
  • Treating runtime evidence as disposable console output instead of a candidate inspectable object layer.
