s-graphviz Dependency Boundary

hyperdoc

The current s-graphviz problem is not a generic ASDF registry issue. It is a real dependency boundary in the HyperDoc stack.

What is required

html-inspector-views/standard depends on s-graphviz.

This is visible in the local source tree:

  • html-inspector-views.asd declares #:s-graphviz
  • s-graphviz.lisp provides the integration layer
  • system and dependency views call Graphviz-related support functions

So s-graphviz is not an optional shell extra in the current design.

What went wrong

The packaged Nix version of s-graphviz currently fails with a circular dependency involving literate-lisp.

Removing s-graphviz from the HyperDoc dev shell was therefore the wrong fix. It only changed the failure mode from:

  • broken s-graphviz load

to:

  • missing dependency for html-inspector-views/standard

In other words, the system did not become healthier. The dependency simply became absent instead of broken.

Why this matters

This is a useful example of a credible maintenance boundary. The problem is not “some shell package is inconvenient”. The problem is that the current runtime design really expects Graphviz support to be present.

That means any fix must address the dependency boundary itself.

Running-image gate

The current HyperDoc startup path models this as an ASDF visibility chunk, not as an instruction to clone a dependency by hand. For the :clog-moldable-inspector profile, :s-graphviz must be visible from the repo/Nix source universe before the gate allows :clog-moldable-inspector to load. 

(hyperdoc:repair-running-image-coherence
 :profile :clog-moldable-inspector)

(hyperdoc:load-coherent-system :clog-moldable-inspector
                               :profile :clog-moldable-inspector)

If asdf:find-system returns NIL for :s-graphviz, the report records s-graphviz-asdf-visibility with the most specific available visibility status. :asdf-subsystem-not-visible means the current image cannot see the system while the dev-shell probe can still name a candidate ASD. :dev-shell-asdf-system-not-visible means the authoritative repo/Nix probe could not find s-graphviz.asd either. If another dependency, such as :clog-ace, resolves from ~/common-lisp, that is a separate source-registry contaminant. The gate refuses the load before ASDF can mix those bases. The repair step may import the repo/Nix dev-shell source registry, clear ASDF's source-registry cache, reload selected .asd definitions, and rederive :s-graphviz visibility. If that is unsafe or incomplete, it returns a repair plan that records the stale chunk and concrete next repair action.

The :s-graphviz deriver now prefers an explicit ASD file discovered by the dev-shell probe. If it finds /nix/store/.../s-graphviz.asd, it calls asdf:load-asd on that exact pathname, pushes the parent directory into asdf:*central-registry*, clears the selected ASDF cache entry, and reruns asdf:find-system. The action evidence includes every ASD path tried and every captured condition. 

(hyperdoc:explain-asdf-visibility
 :s-graphviz
 :profile :clog-moldable-inspector)

Current boundary

  • s-graphviz must remain in the dev environment as long as html-inspector-views/standard requires it.
  • The packaged Nix s-graphviz is currently broken in this environment.
  • No local checkout of s-graphviz or literate-lisp is currently available for override.

Real next options

  • Provide a working source checkout of s-graphviz and likely literate-lisp, then override it in the ASDF source registry.
  • Patch html-inspector-views so Graphviz support becomes optional instead of a hard ASDF dependency.

The first option is operationally smaller. The second option is the cleaner architectural change, but it reaches into a dependency boundary rather than only the local dev shell.

Pragmatic conclusion

The immediate local correction is no longer an ad hoc Downloads or Quicklisp repair. Run the coherence repair gate first. If the report says :s-graphviz is not visible, derive the repo/Nix ASDF visibility or re-enter the updated dev shell as a fallback. Do not allow a foreign ~/common-lisp registry entry to satisfy adjacent inspector systems silently.
