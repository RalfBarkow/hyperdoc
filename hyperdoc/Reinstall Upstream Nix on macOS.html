Reinstall Upstream Nix on macOS

hyperdoc

This is the main operational recovery path for Intel macOS hosts after the Determinate support drop.

Inspectable objects

  • Reinstall Upstream Nix on macOS
  • Inspect Nix Install State on macOS
  • Determinate Nix on macOS Intel

Why this is the primary recommendation

Current Determinate host support no longer covers Intel macOS. For an Intel Mac host, upstream Nix is now the stable reinstall target.

Procedure

  1. Confirm the host architecture and current state: 
    uname -m
ls -ld /nix /nix/store 2>/dev/null || true
ls /nix 2>/dev/null || true
file /usr/local/bin/determinate-nixd 2>/dev/null || true
nix --version 2>/dev/null || true
  2. If Determinate-managed Nix is present, uninstall it: 
    if [ -x /nix/nix-installer ]; then
  sudo /nix/nix-installer uninstall
fi
  3. Inspect the post-uninstall state: 
    ls -ld /nix /nix/store 2>/dev/null || true
ls /nix 2>/dev/null || true
  4. If the installer later stops on an existing *.backup-before-nix file, clear that blocker before retrying.
  5. Reinstall upstream Nix with the official macOS installer path: 
    curl -L https://nixos.org/nix/install | sh -s -- --daemon
  6. Open a fresh shell and verify: 
    nix --version

Reading the post-uninstall state

If /nix is left as an empty mountpoint, that can still be a clean uninstall on macOS. Reboot once if you want the mount state to settle before rechecking. An empty /nix by itself is not evidence that uninstall failed.

Clear stale backup-before-nix files

If the upstream installer correctly targets x86_64-darwin and then stops because /etc/bashrc.backup-before-nix already exists, the architecture problem is already resolved. The new blocker is stale installer backup state from a previous Nix attempt. 

sudo ls -l /etc/bashrc /etc/bashrc.backup-before-nix 2>/dev/null || true
sudo sh -c 'printf "\n--- /etc/bashrc.backup-before-nix ---\n"; sed -n "1,200p" /etc/bashrc.backup-before-nix 2>/dev/null'
sudo sh -c 'printf "\n--- /etc/bashrc ---\n"; sed -n "1,200p" /etc/bashrc 2>/dev/null'

Distinguish these two cases before changing anything:

  • If /etc/bashrc does not exist, but /etc/bashrc.backup-before-nix exists and looks like a normal non-Nix shell file, move it back into place: 
    sudo mv /etc/bashrc.backup-before-nix /etc/bashrc
  • If /etc/bashrc already exists, for example as a live symlink to /etc/static/bashrc, do not restore the backup onto it. Inspect both files first: 
    # inspect first
sudo sh -c 'sed -n "1,200p" /etc/bashrc.backup-before-nix 2>/dev/null'
sudo sh -c 'sed -n "1,200p" /etc/bashrc 2>/dev/null'
    If the backup looks like an ordinary old shell file and not something you need to preserve, move it aside instead of deleting it immediately: 
    sudo mv /etc/bashrc.backup-before-nix /etc/bashrc.backup-before-nix.stale
  • If /etc/bashrc.backup-before-nix already contains Nix-added lines, do not restore it blindly and do not treat it as a clean pre-Nix backup.
  • Inspect the other stale backup files as well: /etc/profile.d/nix.sh.backup-before-nix, /etc/zshrc.backup-before-nix, /etc/bash.bashrc.backup-before-nix, and /etc/zsh/zshrc.backup-before-nix.

See Clear Stale Nix Installer Backup Files on macOS for the focused checklist.

Rerun the installer after backup cleanup

curl -L https://nixos.org/nix/install | sh

Successful transition into live installation

After matching the installer to the pre-existing nixbld group ID (30000), the macOS multi-user installer proceeded normally. It verified the existing build users, created the /nix directory hierarchy, created /nix/store, copied the initial Nix closure into the store, and began loading the Nix database. This is the transition point from residue cleanup to successful installation.

Once the installer reaches nix-store --load-db, the earlier macOS recovery blockers have been resolved. Remaining failures, if any, are no longer about stale shell backups or mixed architectures, but about the final daemon/profile setup steps.

Dangling /etc/bashrc symlink during shell setup

After the installer successfully created /nix/store and loaded the Nix database, shell profile setup can still fail at sudo touch /etc/bashrc. On the observed machine, /etc/bashrc was a symlink to /etc/static/bashrc, and /etc/static itself was a dangling symlink into /nix/store/.... That is leftover nix-darwin residue, not a normal directory tree. In this case, do not try to repair /etc/static with mkdir -p, touch, or chmod. The correct recovery is to replace the specific broken shell-profile symlink such as /etc/bashrc with a plain file, then rerun the installer. 

[ -L /etc/bashrc ] && sudo mv /etc/bashrc /etc/bashrc.dangling-static-link
sudo touch /etc/bashrc
sudo chmod 644 /etc/bashrc

sudo test -d /etc/zsh || sudo mkdir -p /etc/zsh
sudo touch /etc/bash.bashrc /etc/zsh/zshrc
sudo chmod 644 /etc/bash.bashrc /etc/zsh/zshrc

export NIX_BUILD_GROUP_ID=30000
sh ./install-nix

The warnings about unknown settings such as eval-cores or lazy-trees are not the hard stop here. The hard stop is the dangling /etc/bashrc target and the broken /etc/static residue link.

Verify after the installer returns

When the installer finally returns to the prompt, verify the active shell path first: 

nix --version

If fish does not see nix yet, try the daemon profile script: 

source /nix/var/nix/profiles/default/etc/profile.d/nix-daemon.fish
nix --version

If that fish file does not exist, use the POSIX fallback: 

bash -lc '. /nix/var/nix/profiles/default/etc/profile.d/nix-daemon.sh && nix --version'

Fix a post-install SSL certificate path error

If the installer completes but nix profile add nixpkgs#direnv still fails with SSL error 77 against /etc/ssl/certs/ca-certificates.crt, the next problem is not shell residue. On the observed machine, the durable fix was to pin the working CA bundle explicitly in /etc/nix/nix.conf so the daemon saw it: 

sudo sh -c 'printf "build-users-group = nixbld\nssl-cert-file = /nix/var/nix/profiles/default/etc/ssl/certs/ca-bundle.crt\n" > /etc/nix/nix.conf'
sudo launchctl kickstart -k system/org.nixos.nix-daemon
nix config show | grep '^ssl-cert-file'
nix profile add nixpkgs#direnv

The successful fix was not a shell-only environment override. It was a persistent daemon-visible Nix configuration change. Once ssl-cert-file was written into /etc/nix/nix.conf and the daemon was restarted, Nix stopped trying to use the broken /etc/ssl/certs/ca-certificates.crt path and profile installation succeeded.

sudo launchctl setenv NIX_SSL_CERT_FILE ... and sudo launchctl setenv SSL_CERT_FILE ... may fail under System Integrity Protection. On the observed machine, those failures were not fatal. Prefer the persistent /etc/nix/nix.conf fix over relying on launchctl setenv.

See Fix Nix SSL Certificate Path on macOS for the focused checklist.

Distinguish working direnv from a broken flake

If type -a direnv, direnv --version, and the nix-direnv direnvrc check all pass, then a failing direnv reload is no longer a missing-direnv problem. In the observed recovery, direnv was healthy and the actual failure belonged to the project flake, specifically the clog-src-patched derivation in patchPhase.

See Fix Fish direnv Hook Error for the small troubleshooting commands that separate working nix-direnv from a broken dependency build.

What not to do

  • Do not try a fresh current Determinate reinstall first on an Intel Mac host.
  • Do not manually substitute aarch64-darwin or x86_64-linux binaries on an Intel Mac.
  • Do not treat the fish/direnv shell hook warning as the root Nix failure.
