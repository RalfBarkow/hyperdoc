Mech CODE Block analysis

I read Ward's page as a proposal for one new Mech capability layered on top of a much larger client-side Mech that already exists: execute a dynamically created JavaScript module against the current Mech state and then continue with the rest of the block. chatgpt

What already exists

The newer Mech already has the surrounding execution path that Ward's example wants. CLICK runs an indented body on demand. NEIGHBORS populates state.neighborhood from sitemap entries collected from the browser's neighborhood cache. PREVIEW can open a result page, and PREVIEW ... items already expects state.items. SOLO is also already present in the current Mech block catalog.

This means the proposed example is structurally coherent: 

CLICK
  NEIGHBORS next
  CODE
  PREVIEW synopsis items

The missing step is simply: after NEIGHBORS, run code that turns state.neighborhood entries into reference items and stores them in state.items.

Why the state shape matches

The current NEIGHBORS block stores an array of neighborhood page records in state.neighborhood. Those records come from site sitemaps and include the fields needed for this example: domain, slug, title, and synopsis. The current wiki-server tests also confirm that sitemap entries include synopsis and links.

So the proposed module body is the right transformation: 

export async function doit({state}) {
  state.items = state.neighborhood.map(info => ({
    type: "reference",
    site: info.domain,
    slug: info.slug,
    title: info.title,
    text: info.synopsis
  }))
}

What is still underspecified

As written, Ward's example shows CODE as a command, but the JavaScript source is not shown as an indented Mech body beneath that command. That leaves two possible designs.

Option A: inline source under CODE

Example: 

CLICK
  NEIGHBORS next
  CODE
    export async function doit({state}) {
      state.items = state.neighborhood.map(info => ({
        type: "reference",
        site: info.domain,
        slug: info.slug,
        title: info.title,
        text: info.synopsis
      }))
    }
  PREVIEW synopsis items

This is the easiest first slice. The existing Mech tree parser already preserves nested body structure, and CODE can serialize that body back into JavaScript source instead of asking Mech to execute it as more block commands.

Option B: source from a neighboring page item

This may be closer to Ward's page sketch, because the source line appears outside the command sequence. In that model, CODE would scan nearby page items for a code-bearing source item, much like the existing SOURCE block scans earlier items for topic-specific source providers.

This design fits the page-authoring story better, but it needs one more protocol: how a preceding item exposes code text to Mech.

Security note

Dynamic module import is not, by itself, a sandbox. Browsers do support dynamic import of blob URLs, but that still executes code in the page's JavaScript environment. If actual isolation is wanted, this must move into a worker or a sandboxed iframe with an explicit message protocol.

Best first implementation

The shortest truthful path is:

  1. Add a client-side CODE block to wiki-plugin-mech/client/mech.js.
  2. Have it consume indented source as literal JavaScript text.
  3. Create a Blob from that text and import() it.
  4. Call await module.doit({state, elem, wiki, context: state.context}).
  5. Resume the remaining Mech body after the module returns.

That gets Ward's example running without inventing a new page-level source protocol first. After that, the block can be generalized to fetch code from neighboring items if that authoring style proves more natural.

Bottom line

Ward's example is viable right now. The current Mech already has the input state and the output surface. The only missing seam is a CODE block that turns page-authored JavaScript into a callable module. For a first slice, keep it client-side, keep it inline, and treat sandboxing as a separate concern.
