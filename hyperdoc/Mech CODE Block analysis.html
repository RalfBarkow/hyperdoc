Observed upstream contract

The current upstream client already contains the two seams this example needs.

  • src/client/blocks.js code_emit reads code story items from the current page, concatenates them into one JavaScript module, selects default or a named export from the first argument, and calls that export with the Mech state proxy as this.
  • src/client/blocks.js preview_emit has two distinct output routes that matter here:
    • PREVIEW items passes story items through unchanged from state.items
    • PREVIEW graph expects state.aspect graph objects and turns them into graphviz story items via dotify(graph)
  • src/client/library.js dotify is the current graph-object-to-DOT seam. It is separate from the literal-DOT path used by Ward's Quick Brown Fox sketch.

One practical boundary matters immediately: CODE does not scan the whole lineup and it does not consume an indented Mech body as JavaScript source. It reads code items from the same page that contains the running mech item.

Inference for the Quick Brown Fox example

Ward's character-walk kernel is a literal text-to-DOT transformation: 

.split('').map((c, i, v) => `"${c}"->"${v[i + 1] || '.'}";`)

The closest current upstream mapping is therefore not PREVIEW graph but PREVIEW items. The code module can emit a normal graphviz story item directly, keep DOT in the item's text, and let Mech preview that item unchanged. 

export default async function () {
  const text = "Quick Brown Fox"
  const edges = text
    .split("")
    .map((c, i, v) => `"${c}"->"${v[i + 1] || "."}";`)
    .join("\n")
  this.items = [{ type: "graphviz", text: `digraph {\n${edges}\n}` }]
}

That authoring shape is already executable on the tracked repo. The proof run for this slice produced a Mech Preview page whose first story item was { type: "graphviz", text: "digraph { ... }" }. No production Mech change was required.

PREVIEW graph remains a second, different seam. It is the right path when the module wants to populate state.aspect with graph objects and let upstream dotify own the DOT serialization. That is closer to neighborhood/aspect workflows than to the literal Quick Brown Fox kernel.

Discourse Graphs adaptation boundary

The tracked wiki-plugin-mech checkout shows no local code delta against Ward upstream at 47cba6d57bef6db43e237abcbad60829d78b691c. The dreyeck Discourse-Graphs behavior therefore cannot be claimed here as an in-tree Mech modification.

The truthful boundary is narrower:

  • Upstream Mech already supplies the executable CODE seam.
  • Upstream Mech already supplies two preview routes: direct story-item preview and graph-object preview.
  • The local dreyeck adaptation is downstream of that tracked contract: it changes how graph output is consumed or embedded, not the fact that Mech can already produce the graph-oriented preview artifact.

Until the dreyeck adaptation itself is brought into an inspectable repo or trace, HyperDoc should describe it as an external adaptation boundary rather than as local code in wiki-plugin-mech.

Recommendation for this slice

The smallest truthful slice is a documentation repair, not a Mech redesign. Earlier HyperDoc prose that treated CODE as the missing seam is now stale relative to the actual repo. The current repo already supports the Quick Brown Fox preview flow through page-local code items, CODE, and PREVIEW items, while PREVIEW graph remains the separate graph-object path.

If a later slice wants to document the dreyeck Discourse-Graphs behavior in more than boundary terms, it should first bring that adapted runtime into an inspectable code or trace surface. This page does not pretend that surface is already present in the tracked repo.
