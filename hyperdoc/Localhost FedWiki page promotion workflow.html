Localhost FedWiki page promotion workflow

hyperdoc

Localhost FedWiki page promotion workflow is the reusable path for reading a real localhost FedWiki page, normalizing story items and fragments, promoting topic chunks, composing a durable local HyperDoc page, and then optionally planning or executing a guarded DMX snippet twin write on a separate dry-run-first boundary.

Current real-page instances

The current two real localhost FedWiki promotions intentionally exercise two different fail-soft states on top of the same workflow.

  • The Life Cycle of Collective Knowledge: the durable HyperDoc page and topic-factory snippet remain present, but the configured localhost FedWiki source page file is currently missing, so the plan degrades to an inspectable :source-unavailable issue state.
  • Reproducible DevEnv as Knowledge Artifact: the source page remains available and the plan stays healthy, fresh, and dry-run capable on the guarded DMX boundary.

Workflow boundary

The promotion plan object remains the inspectable contract. It surfaces the localhost source page id and path, normalized story items, normalized fragments, promoted topic chunks, provenance classifications, local page target, topic-factory snippet metadata, and the separate DMX dry-run plan summary.

Execution boundaries

  1. inspect/plan: open a promotion plan object's Overview, Source page, Story items, Fragments, Promoted topics, and DMX dry-run views.
  2. compose/write local HyperDoc artifacts: use (write-localhost-fedwiki-page-promotion-plan-artifacts plan) to regenerate the durable local page and snippet asset from the plan's configured writer.
  3. dry-run DMX snippet write: inspect the plan object's DMX dry-run view or call (localhost-fedwiki-page-promotion-plan-dmx-dry-run-summary plan) / (localhost-fedwiki-page-promotion-plan-dmx-dry-run-evidence plan).
  4. optional live DMX write: remain on the separate explicit writer path through (execute-topic-factory-snippet-dmx-write ... :dry-run nil) with an explicit workspace topicmap id.

DMX boundary after the 919822 incident

This workflow no longer treats generic DMX writes as safe by default. Any topicmap-context-like write now goes through the HyperDoc-side long-form payload normalizer/validator first.

  • Dry-run surfaces expose view-props-validation-status.
  • Dry-run surfaces expose forbidden short keys when present.
  • Dry-run surfaces expose the normalized topicmap view payload JSON.
  • Live writes remain conservative and explicit; dry-run evidence stays first-class.
  • HyperDoc treats DMX as synchronizable/projected, not as sole authority for the authored local page and snippet artifacts.

Continuation path

The accepted continuation is to keep the existing localhost FedWiki -> normalized topic chunks -> composed HyperDoc page -> topic-factory snippet -> DMX snippet twin flow, but only on top of the guarded write boundary.

  • Keep plan-first inspection.
  • Keep dry-run-first DMX evidence.
  • Preserve fail-soft issue objects when source pages or payloads are invalid.
  • Use the context-window workspace and MCP handover seam as the collaboration layer between durable HyperDoc pages and ongoing DMX work.
  • Do not broaden this workflow into full DMX sync until the contract is better understood.
