Mech Execution Context and Emit Protocol

This page records the concrete Mech architecture around Mech op/args and emit dispatch. The key move is compact but consequential: command text is normalized into an operation plus argument list, assembled with body, element, and state, and dispatched through the block registry's emit protocol.

Operation and argument normalization

Mech begins from a user-facing command line. The command is split into an operation name and an argument list. That operation/argument normalization step matters because it turns raw authored text into a stable executable vocabulary before block-specific behavior begins. 

const [op, ...args] = code.command.split(/ +/)

Execution context bundle

Mech then assembles command text, normalized operation, arguments, optional body, resolved element, and current state into one execution context bundle. This is the point where source form and runtime state become available together. 

const stuff = { command, op, args, body, elem, state }

Block registry and emit protocol

The bundle is handed to the block registry via blocks[op].emit. That implicit interface is the block registry protocol. It is where execution happens, but it is also the correct place for validation, instrumentation, run recording, and explanation. 

await blocks[op].emit.apply(null, [stuff])

Why this seam is the right place for diagnostics

Once the command and runtime state have been bundled, each emit call can do more than produce output:

  • validate whether the block has the body or state it requires
  • publish warnings and errors as explicit findings
  • record state changes and emitted artifacts
  • attach provenance to the same execution event that produced the result
  • emit an execution evidence object, boundary report, or replay trail where the workflow needs them

That is why the seam matters architecturally. The system does not need a second retrospective pass to explain itself. Explanation can be generated from the same protocol that performs the work.

A retrospective explanation pass would reconstruct behavior after output already exists. The stronger model is generation/explanation twin output: the dispatch event can produce the visible artifact and an execution evidence object, runtime provenance, and a boundary report from the same authoritative seam.

Why moving capabilities into api matters

The recent Mech shift of download into a shared api is not only refactoring tidiness. It shows capability moving from one block's local implementation toward a shared protocol surface. That makes it easier to standardize instrumentation and to treat findings and artifacts as publishable, inspectable results rather than incidental side effects.

Current boundary

This is still a block-level seam, not a full debugger or a complete run object model. It is therefore narrower than the Smalltalk stepping primitive. But it is already rich enough to support structured findings, graph-rooted publication, and future first-class execution objects.
