DMX FedWiki Write Model

This page documents the current write model exposed by dmx-fedwiki, an early-stage DMX plugin under development. It extends DMX with FedWiki-oriented functionality, but it should be read as an emerging plugin model rather than a finalized DMX platform contract.

WIP plugin boundary

dmx-fedwiki is a DMX plugin, not settled DMX core. The current fedwiki.page topic type, child-topic conventions, and materialization behavior are useful for integration work, but they remain plugin-level extensions of DMX while the plugin is still very early-stage.

That means documentary and topic-level integration can move ahead now, while runtime assumptions, importer bindings, and API-contract claims should remain conservative until the plugin behavior is stabilized or absorbed into a broader platform contract.

Current plugin-level write model

The current HyperDoc importer reuses the plugin's fedwiki.page topic type together with typed children such as fedwiki.slug, fedwiki.title, and fedwiki.page.json. For idempotent synchronization, HyperDoc stores the stable external key fedwiki:<domain>/<slug> as the DMX topic uri and keeps the fuller FedWiki provenance envelope inside fedwiki.page.json.

The HTTP endpoints used for lookup and write are DMX core REST endpoints, but the choice to model imported FedWiki pages this way comes from the plugin-level extension, not from a finalized FedWiki write contract in DMX core itself.

Runtime caution

It is reasonable to document this boundary now and to add authored topic handles for it. It is not yet reasonable to claim that all future DMX FedWiki-related importers, proxies, or synchronization tools should assume this model is permanent.

Proof boundary

A plugin-level write model can be correctly implemented and still remain not yet live-proven. For this slice, the importer path is implemented and config-guarded, and its dry-run behavior has been verified, but operational proof still requires replay against a configured target.

Until a real create-then-update cycle has succeeded against such a target, the correct evidence language stays conservative: implemented, config-guarded, dry-run verified, and not yet live-proven.
