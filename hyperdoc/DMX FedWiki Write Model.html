DMX FedWiki Write Model

hyperdoc

DMX FedWiki Write Model records the write contract HyperDoc now accepts for DMX integration after the topicmap 919822 incident. The key conclusion is narrow and durable: DMX is a valuable but untrusted persistence boundary, so HyperDoc must validate topicmap-context payloads before every write.

Why this page changed

Earlier DMX/FedWiki notes described an emerging plugin-level write model. The 919822 incident tightened the boundary. We now know that the checked DMX read path expects long-form topicmap view props, while the generic DMX ViewProps write endpoints can persist malformed short-key-only shapes unchanged if a sender submits them.

  • Proven read expectation: dmx.topicmaps.x, dmx.topicmaps.y, dmx.topicmaps.visibility, dmx.topicmaps.pinned.
  • Proven malformed shape: bare x, y, visibility, pinned on dmx.topicmaps.topicmap_context assocs.
  • Proven effect: topicmap fetch can fail with NotFoundException on the missing long-form key.
  • Unproven part: the original sender that wrote the malformed live assocs remains unknown.

Canonical topicmap-context payload contract

HyperDoc's topicmap-context-like writes now accept only the canonical long-form keys. Short keys are treated as invalid input at the HyperDoc boundary rather than being forwarded to DMX. 

{
  "dmx.topicmaps.x": 160,
  "dmx.topicmaps.y": 120,
  "dmx.topicmaps.visibility": true,
  "dmx.topicmaps.pinned": false
}

Forbidden short keys for this payload class:

  • x
  • y
  • visibility
  • pinned

HyperDoc-side guarded write boundary

HyperDoc now keeps the DMX write seam narrow and typed. Topic creation and update still go through the shared import client, but topicmap-context view writes must pass through the canonical payload normalizer/validator first.

  1. dmx-import-create-topic / dmx-import-update-topic: typed topic upsert payloads for the DMX topic itself.
  2. dmx-import-add-topic-to-topicmap / dmx-import-set-topic-view-props: guarded topicmap-context view writes.
  3. dmx-import-delete-topic: hard delete on /core/topic/<id>, used only behind ownership checks.
  4. dmx-import-remove-topic-from-topicmap: typed unlink helper with memory-client support for smoke coverage; live HTTP unlink stays unsupported until the membership DELETE contract is proven.
  5. plan-topic-factory-snippet-dmx-write: dry-run planning that surfaces normalized payload and validation status before write.
  6. execute-topic-factory-snippet-dmx-write: explicit dry-run or live execution on the same guarded boundary.
  7. localhost-fedwiki-page-promotion-plan-dmx-dry-run-summary and related handover surfaces: promotion-plan wrappers that keep the normalized payload inspectable.

Adjacent read and note boundaries

  • Machine-facing reads should use the canonical topic and topicmap JSON paths documented in DMX machine-readable read paths.
  • Note updates should respect the parent-note boundary documented in DMX note read/write boundary.
  • The MCP server reuses these same boundaries instead of exposing a generic raw DMX write surface.

MCP boundary on the same contract

The DMX MCP server for shared workspace does not introduce a second write model. It reuses the same HyperDoc-side guarded contract.

  • workspace/context-window, topic/<id>, and topicmap/<id> resources wrap canonical DMX read paths instead of teaching clients raw URLs.
  • validated_dmx_write_dry_run exposes normalized payload and validation status before mutation, including topicmap_context_upsert and topicmap_context_remove.
  • append_workspace_note, update_workspace_note, delete_workspace_note, and create_handover stay on typed note/topic payloads rather than arbitrary raw DMX writes.
  • upsert_workspace_topicmap_context and upsert_workspace_topic_factory_snippet provide the supported typed path for placing HyperDoc-managed topics into workspace topicmap 919822.
  • delete_workspace_topic is ownership-limited to HyperDoc-owned workspace artifacts; foreign topics are rejected.
  • remove_workspace_topic_from_topicmap exists as a typed unlink tool, but live HTTP execution remains intentionally unsupported until the membership DELETE contract is proven.
  • read_hyperdoc_workspace_journal, read_hyperdoc_topic_journal, list_hyperdoc_topic_revisions, inventory_legacy_dmx_workspace_journal_artifacts, plan_legacy_dmx_workspace_journal_cleanup, restore_workspace_topic_revision, and restore_workspace_note_revision add bounded history inspection, explicit dry-run cleanup planning, and explicit restore without exposing raw journal writes.
  • No generic raw ViewProps passthrough is exposed through MCP.

HyperDoc-owned journal layer

The shared workspace now has a HyperDoc-owned journal layer documented in DMX workspace journal model. The storage model is companion-workspace-note: one hidden journal note per stable subject stream. That is intentionally narrower than claiming DMX itself is already a replayable revision database.

In-band guarded writes emit direct journal events, while out-of-band changes in topicmap 919822 are synthesized from snapshot diff and labeled synthesized-from-diff. This remains a bounded collaboration and repair model, not a generic DMX mutation framework.

Delete and unlink boundary

  • Proven backend contract: OPTIONS /core/topic/<id> advertises DELETE, so HyperDoc can support ownership-limited hard delete on the parent topic endpoint.
  • Unproven backend contract: OPTIONS /topicmaps/<topicmap>/topic/<topic> did not advertise DELETE, so HyperDoc does not claim live HTTP unlink support on that route.
  • Current safe result: HyperDoc-owned workspace notes, handovers, and topic-factory snippet twins may be hard-deleted; foreign topics default to non-destructive handling.
  • No archive or tombstone mutation contract is claimed yet because the backend boundary for that shape remains unproven.

Diagnostics and fail-soft behavior

Validation failures now become explicit structured errors or bounded inspectable issue summaries instead of silent malformed writes.

  • dmx-topicmap-view-props-validation-error names the boundary, missing long-form keys, forbidden short keys, and invalid field types.
  • Promotion-plan dry-run and handover surfaces expose view-props-validation-status, forbidden short keys, and the normalized payload JSON.
  • Missing localhost FedWiki source pages degrade separately to :source-unavailable issue objects; they are not silently conflated with DMX payload validation.

Scope boundary

This write model is intentionally narrow. It does not claim to redesign DMX storage, implement a general migration framework, or prove the identity of the original writer. It only states what HyperDoc now requires before it sends DMX writes.
