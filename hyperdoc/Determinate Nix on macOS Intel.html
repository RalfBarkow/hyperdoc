Support boundary on Intel Mac

The boundary for this documentation slice is explicit: current Determinate host support no longer includes Intel macOS, and the v3.13.0 release line explicitly drops x86_64-darwin. That means a fresh current Determinate reinstall is no longer the recommended recovery path on an Intel Mac host.

This is a host-support statement, not a claim about every possible build target. A supported machine elsewhere may still build or evaluate x86_64-darwin outputs, but that does not restore current vendor support for installing Determinate Nix on an Intel Mac host itself.

What usually goes wrong

  1. The host is really x86_64, but one installed binary on disk is arm64.
  2. A manual download mixes platform names such as x86_64-linux, aarch64-darwin, and Intel macOS expectations.
  3. The presence of an empty /nix directory after uninstall is misread as failure, even though macOS can leave an empty mountpoint until reboot.

The first troubleshooting step is therefore architecture inspection, not downloading another installer at random.

Recommended path now

  1. Inspect the current state with Inspect Nix Install State on macOS.
  2. If Determinate-managed Nix is present, uninstall it first.
  3. Reinstall upstream Nix using the official macOS installer path described in Reinstall Upstream Nix on macOS.

For Intel macOS hosts, upstream Nix is now the stable recommendation.

Legacy fallback

A bounded best-effort fallback still exists if you need to recover the last plausible pre-drop Determinate line on Intel. That path is documented in Restore Last Working Determinate Nix on macOS Intel. It is legacy, unsupported, and explicitly not the primary recommendation.

Shell noise is separate

Fish-shell startup errors from direnv are not the root Nix problem. Treat them as cleanup after the install state is understood. See Fix Fish direnv Hook Error.
