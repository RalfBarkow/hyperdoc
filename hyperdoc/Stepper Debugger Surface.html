Stepper Debugger Surface

hyperbook/server

This page documents the existing stepper/debugger surface used by HyperDoc Playground evaluation in development mode.

What this surface is

The stepper/debugger surface is the set of runtime objects and views that allow you to run code incrementally, inspect intermediate results, and handle errors without collapsing the whole server session.

It is analogous in spirit to GT's monitor/runner flow: start a run, observe step state, inspect errors, stop or reset safely.

Runtime components

  • Playground stepper surface: stepper model and step/run/reset operations
  • Diagramming Debugger Surface: step-derived collaboration/message diagram object and view
  • Playground debug report surface: structured debug report object and debug view
  • Web debugger surface: debugger registry and web-facing handoff
  • Playground eval surface: Playground wiring for eval/inspect/step/debug actions

Operational flow

  1. Load server in development mode (HYPERDOC_DEVELOPMENT=1).
  2. Open a Playground-enabled inspector pane.
  3. Use step/eval controls to run selected forms.
  4. If evaluation fails, inspect the debug report object and retry/abort.
  5. Use the Diagram action to inspect a diagramming debugger object and export Graphviz DOT traces.
  6. Reset or stop the stepper state when done.

Design boundary

The stepper/debugger surface belongs to runtime and interaction wiring (hyperbook-server), not to static page rendering.

This keeps page content declarative while execution control remains explicit, inspectable, and bounded.
