Authored relation artifacts in HyperDoc

hyperdoc

HyperDoc now treats authored relation artifacts as a reusable reconstruction pattern, not a feature-local trick. The pattern keeps authored intent, compiled behavior, and compiled layout separate while preserving explicit derivation links between them.

Pattern in one line

repo-native authored source -> reconstructed authored relation artifact -> compiled behavior artifact + compiled layout artifact -> feature runtime glue.

What each artifact means

  • Authored relation artifact: semantic coordination object containing role definitions, layered relations, and compiled target intent.
  • Compiled behavior artifact: lifecycle machine projection derived from authored behavior relations.
  • Compiled layout artifact: pane/comparison layout projection derived from authored layout relations.

The compiled artifacts are first-class objects, not anonymous intermediate plists. They remain inspectable and keep explicit derivation fields back to the authored artifact.

Implementation contract

This is the stable reusable contract enforced by runtime and tests.

  • Source identity contract: authored-relation-artifact-source carries stable id, artifact-id, schema-version, role definitions, relation definitions, and explicit compiled target ids.
  • Reconstruction contract: reconstruction yields exactly one authored-relation-artifact whose id matches source artifact-id and whose relations remain partitionable by layer (:semantic, :behavior, :layout).
  • Derivation contract: each compiled artifact keeps authored-artifact, compiler-stage, and compiler-inputs so derivation remains machine-checkable.
  • Separation contract: behavior and layout stay distinct compiled artifacts; neither collapses into the other.
  • Boundary contract: consumer-specific runtime glue stays narrow (hooking existing domain objects to artifacts). The generic layer is not a generic unrestricted mutation surface.

Consumer responsibilities vs generic layer

  • Consumer must provide: repo-native source definitions (roles/relations), domain-specific behavior compiler rules, domain-specific layout compiler rules, and narrow object-to-artifact glue.
  • Generic layer provides: common CLOS object family, relation-layer partitioning helpers, source relation/role counters, compiled-derivation checks, and shared inspector views.

Current proof cases

  • Snippet playground: authored snippet relation source reconstructs into a snippet authored artifact and compiles into snippet behavior/layout artifacts.
  • Page lookup issue: authored lookup-failure source reconstructs into a lookup authored artifact and compiles into lookup behavior/layout artifacts.

These two consumers are intentionally different in scope and UI density. The same pattern serves both, which is the current reuse proof.

Imperative glue that remains

  • provider-specific input extraction
  • browser click/dispatch routing
  • pending-pane open/replace mechanics where relevant

Keeping this imperative glue narrow is deliberate. The authored relation artifact pattern is about reconstruction and derivation contracts, not about replacing all runtime dispatch code.

Non-goals in this slice

  • No third consumer.
  • No DMX or MCP integration widening.
  • No editor surface work.
  • No UI prose expansion in snippet-playground or page-lookup surfaces.
