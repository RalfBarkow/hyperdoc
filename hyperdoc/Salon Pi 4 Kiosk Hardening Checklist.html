Salon Pi 4 Kiosk Hardening Checklist

This page is a practical checklist for turning the declared Kioskberrli build target into a credible maintenance story. The target is a wall-mounted Raspberry Pi 4 Model B in the hauptsache hairdressing salon.

The current repository state gives a declared SD-image build path. That is necessary, but it is not yet the same as a demonstrated kiosk artifact.

1. Build evidence

  • Run the build target successfully at least once.
  • Record the exact command and resulting artifact name.
  • Record the nixpkgs input revision used for the image.
cd kioskberrli
nix build .#nixosConfigurations.kioskberrli.config.system.build.sdImage

2. Flash and boot evidence

  • Flash the image to an SD card.
  • Boot it on the actual Raspberry Pi 4 Model B with HDMI attached.
  • Confirm that the system reaches a usable graphical kiosk session.

Without this step, the image is only a declaration, not a maintained system.

3. Network practicality

  • Confirm salon network bring-up on first boot.
  • Decide whether Ethernet is primary and Wi-Fi is fallback.
  • Decide how NetworkManager should be provisioned for on-site recovery.

A kiosk that needs a developer laptop for routine reconnects is not yet a credible salon installation.

4. Remote maintenance

  • Add SSH key-based maintenance access.
  • Disable password login once key access is confirmed.
  • Verify that the device can be recovered without on-site keyboard use.

This is the minimum operational standard for a wall-mounted device.

5. Browser and session recovery

  • Verify that Cage restarts after browser failure.
  • Verify that Chromium returns to the landing page after crash or reboot.
  • Consider additional Chromium kiosk flags only after the basic loop works.

The proof here is observed behavior on the target device, not only service declarations in kiosk.nix.

6. SD-card durability

  • Keep generated image artifacts out of Git.
  • Plan for rebuild-and-reflash as the normal recovery path.
  • Consider read-only or reduced-write patterns only after the first kiosk is stable.

Durability work should follow a working kiosk, not replace it with theory.

7. Landing-page handoff

  • Verify the exact URL loaded in the salon.
  • Verify what the visitor can do next from that page.
  • Keep the distinction clear between landing page, FedWiki, and kiosk device.

The kiosk is not just a browser. It is the physical expression of the project entry model.

8. Definition of done for the first kiosk

  • The image builds.
  • The SD card boots on the real Pi 4.
  • The network comes up in the salon.
  • The kiosk session starts automatically.
  • The landing page is displayed after reboot and after crash recovery.
  • SSH maintenance works without a local keyboard.

Only after these points are demonstrated do we have the beginning of a credible maintenance story for Kioskberrli.
