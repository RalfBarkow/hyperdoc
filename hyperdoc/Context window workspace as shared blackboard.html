Context window workspace as shared blackboard

hyperdoc

Context window workspace as shared blackboard defines the collaboration model for DMX topicmap 919822, the context-window workspace with sharing mode Common: a small curated blackboard where me, ChatGPT, and Codex can inspect current state, exchange handovers, and post bounded work notes without turning the workspace into a raw transcript archive or a substitute for durable HyperDoc pages.

In the stronger journal architecture, this Common workspace is a rebuildable shared projection. The authoritative append-only journals live with the participating HyperDoc instances. Today's hidden DMX companion notes still matter for replay, restore, and repair, but the workspace itself should stop being read as the final authority merely because it is the visible shared surface.

For the short operator-facing front door across this shared-workspace cluster, start with How to work safely in topicmap context-window (919822).

Workspace identity

  • Topicmap id: 919822
  • Workspace name: context-window
  • Sharing mode: Common

What belongs here

  • Current incident and repair status that multiple agents need to share.
  • Stable contract notes such as the note read/write boundary and machine-readable read paths.
  • Shared workflow surfaces such as the localhost FedWiki promotion workflow and its handover seam.
  • Short current-state mirrors of durable HyperDoc pages that should be reachable through DMX read paths and MCP resources.

What does not belong here

  • Raw transcript blobs copied in full.
  • Speculative backend repair experiments against DMX.
  • Generic unsafe write tools that bypass HyperDoc validation.
  • The sole authoritative copy of architecture or workflow decisions.

Authority versus projection

  • Authority: each HyperDoc instance keeps its own append-only journal as the causal record for owned subjects.
  • Projection: the context-window workspace exposes a shared current-state view, plus DMX companion notes that replay and repair the projected state.
  • Recovery target: deleting the Common workspace should be recoverable by replaying journaled boundaries into a fresh shared projection rather than mourning the workspace as the only durable record.

Exchange artifacts

When a workspace readout is too large or awkward for one safe note or one chat message, materialize it as one exchange artifact: one manifest note plus one or more chunk notes. Those transport topics are not the underlying content topics.

  • Do not use bare chunk for transport here; keep bare Chunk for HyperDoc's running-image coherence model.
  • Every exchange artifact has exactly one manifest note, and that manifest is the entrypoint.
  • Every chunk note declares artifact membership, part number and total count, and declared coverage such as topic ids or ranges.
  • Chunk notes are transport-layer topics: durable enough for replay and audit, but not automatically conceptual notes.
  • Content topics remain authoritative for the subject matter being described.
  • If chunk exchange yields durable conclusions, promote those conclusions into normal content topics instead of leaving them only inside chunk notes.

The current exhaustive workspace readout in topicmap 919822 is one exchange artifact with one manifest note and 12 chunk notes.

Read and write boundary

The workspace should be readable both through the direct DMX machine-readable paths and through the MCP resource surface. Writes stay conservative: workspace notes and handovers may be appended or updated through the guarded parent-note boundary, HyperDoc-owned snippet twins may be upserted through the guarded topic/topicmap adapter, and validated topicmap-context upsert can place an existing topic into the workspace or update its long-form view props. Every guarded write also emits a HyperDoc-owned journal event, and restore stays explicit through typed restore tools instead of hidden editor undo. Generic raw topicmap mutations remain out of scope. In the stronger architecture, those writes are projections of authoritative local journal events rather than the only durable copy of collaboration state.

Workspace model

The context-window topicmap remains a shared blackboard, not a raw database playground.

  • Read the current workspace summary through workspace/context-window.
  • Read durable note topics such as topic 907120 through topic/<id>.
  • Create a new handover with create_handover.
  • Add a narrow work note with append_workspace_note.
  • Revise an existing note with update_workspace_note.
  • Delete a HyperDoc-owned workspace note or handover with delete_workspace_note.
  • Create or update a HyperDoc-owned topic twin with upsert_workspace_topic_factory_snippet.
  • Add an existing topic to topicmap 919822 or update its validated view props with upsert_workspace_topicmap_context.
  • Plan a typed topicmap unlink with remove_workspace_topic_from_topicmap, while treating live HTTP unlink as intentionally unsupported until the membership DELETE contract is proven.
  • Delete a HyperDoc-owned snippet twin with delete_workspace_topic.
  • Inspect journal history through read_workspace_journal, read_topic_journal, and list_workspace_topic_revisions.
  • Restore an owned note or topic through restore_workspace_note_revision or restore_workspace_topic_revision.
  • Keep a simple durable history in the workspace rather than overwriting arbitrary unrelated topics.

Journaled history boundary

Topicmap 919822 now has a HyperDoc-owned journal layer. In-band writes are recorded directly through the same guarded workflow, while out-of-band changes are reconciled by snapshot diff and marked synthesized-from-diff. The workspace therefore offers bounded replayable history without claiming that DMX already provides a native revision feed. The implemented hidden companion notes remain important for today's replay, restore, and repair behavior, but they are better understood as projection journals than as the ultimate journal authority.

Rebuild boundary

The target design is that the Common workspace can be rebuilt. That claim is trustworthy only where boundaries are actually journaled, subject identity is stable, and replay order plus conflict policy are explicit. DMX-only drift discovered later through snapshot diff remains synthesized or foreign history until some authoritative journal boundary claims it.

Why this stays narrow

The workspace is useful precisely because it is constrained.

  • It gives collaboration tools a common handoff surface.
  • It avoids making every DMX topic editable by every integration.
  • It preserves a plan-first and dry-run-first workflow for writes that affect topicmap state.
  • It keeps destructive actions ownership-limited instead of turning the workspace into a generic delete surface.
  • It keeps fail-soft issue reporting separate from operational work notes.

Current shared-workspace evidence

The MCP live-read smoke showed the current workspace topicmap id 919822, confirmed that topic 907120 is readable as DMX incident remediation for HyperDoc, and confirmed that another workspace topic 921464 remains readable as codex uri-title-text probe.

Relation to the localhost FedWiki -> DMX pipeline

The shared blackboard does not replace the localhost FedWiki promotion plan. It complements it.

  • The promotion plan remains the inspectable source/plan/workflow object.
  • Dry-run DMX evidence remains first-class on the plan.
  • A handover note can summarize the plan state and point the next agent to the right local artifact or dry-run result.
  • Live DMX snippet or topicmap writes still go through the same guarded HyperDoc adapter.

Why this is needed now

The shared workspace only serves its real purpose when the important incident, architecture, workflow, and handover context is actually present and reachable there. HyperDoc remains the richer diagnostic and authoring side, but the workspace must hold enough curated state to work as a common blackboard between the human operator, ChatGPT, and Codex.
