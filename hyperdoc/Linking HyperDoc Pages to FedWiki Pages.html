Linking HyperDoc pages to FedWiki pages

HyperDoc pages can already link well to Lisp objects and HyperBooks, but they currently have no first-class link form for FedWiki pages such as FIND, WALK, PRINT, or REVIEW.

The immediate problem is not rendering a URL. It is choosing a link model that respects federation. A FedWiki page is not identified by title alone; it lives at a site, has a slug, and may have remote/local variants.

Requirements

  • A HyperDoc author should be able to name a FedWiki page explicitly.
  • The link must preserve the owning site, not just the page title.
  • The same syntax should work for local and remote FedWiki pages.
  • The link target should remain inspectable inside HyperBook, not only as an external browser URL.

Proposed model

Add a HyperDoc link form that names a FedWiki page by hyperbook id plus page slug or title. Conceptually it should look like one of these: 

<a hyperbook="fedwiki:wiki.ralfbarkow.ch" page="find">FIND</a>
<a hyperbook="fedwiki:wiki.ralfbarkow.ch" page="walk">WALK</a>
<a hyperbook="fedwiki:wiki.ralfbarkow.ch" page="print">PRINT</a>
<a hyperbook="fedwiki:wiki.ralfbarkow.ch" page="review">REVIEW</a>

In other words: treat the FedWiki site as the HyperBook id and the page as a normal HyperBook page lookup inside that book.

Why this is the right level

  • It reuses the existing HyperBook linking model instead of inventing a second link system.
  • It keeps site identity explicit.
  • It fits startup auto-registration of known FedWiki books.
  • It allows the same destination to be inspected through normal HyperBook views such as Story, Links, and Context.

What must exist for this to work smoothly

  • The relevant FedWiki hyperbook must already be registered or auto-loadable from its id.
  • HyperDoc page linking should accept non-local HyperBook ids such as fedwiki:wiki.ralfbarkow.ch.
  • Page lookup should resolve slug/title consistently for FedWiki pages.

Fallback behavior

If the FedWiki hyperbook is not yet present, the link system should prefer to create or resolve it through hyperbook:find-hyperbook rather than fall back immediately to an external browser URL. External open remains useful, but it should be the secondary path, not the only path.

Why this matters for Story Neighborhood Workflow

The workflow around FIND, WALK, PRINT, and REVIEW is most useful when the pages themselves are directly inspectable from HyperDoc. That would let a conceptual HyperDoc page describe the workflow and also open the concrete FedWiki pages that implement or demonstrate each step.

This would make HyperDoc documentation less isolated from the live federated material it is describing.
