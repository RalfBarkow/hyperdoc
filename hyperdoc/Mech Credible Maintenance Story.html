Mech Credible Maintenance Story

A credible maintenance story for Mech should be told in the same terms as Drawing Automation: the workflow should make it possible to move from a visible defect in an automatically generated artifact to the precise source location that must be changed, and then to review that change through normal version-control practice.

In the Mech repository ~/workspace/wiki-plugin-mech, the commit range from 4b8051417dec6b0eff40878290a703b1fa60fb52 up to current upstream/main does not tell one continuous story from the beginning. The credible maintenance story emerges later, once a bounded neighborhood workflow is assembled and then made diagnostic.

Why 4b80514 is only a baseline

Commit 4b80514 is a small environment adjustment: chore(nix): default wiki port to 80. It is part of the history, but it is not yet part of the maintenance story. It establishes a working base, not the narrative of maintainable generated output.

The credible sequence

The maintenance story becomes visible in this later sequence on upstream/main:

  1. 007a9db add WALK clicks
  2. 2d7c6b3 add PRINT block
  3. 37c34a2 Use FROM to identify story
  4. 1cb65e6 fetch and expand page json
  5. 6083e07 expand links as anchors
  6. 4ed345e systematic tally; download in api

This is the point where Mech stops being just a block toy and starts looking like a maintainable workflow for bounded graph extraction and accountable output.

How this matches Drawing Automation

In Drawing Automation, the key claim is that diagrams should be generated from maintained source annotations, and that a visible mistake in a generated drawing should lead back to the source that generated it. The repair path is:

visible defect
  ->
linked generated artifact
  ->
source location / annotation
  ->
edit
  ->
pull request

The Mech sequence above does not yet produce that exact drawing workflow, but it does establish the same maintenance discipline for story-neighborhood artifacts.

Step 1: bounded neighborhood extraction

WALK clicks gives the workflow a bounded graph expansion primitive. This is the Mech equivalent of saying: start from a defined seed and derive a neighborhood rather than wandering the whole federation.

Without that bounded scope, there is no believable maintenance story because there is no stable claim about what the generated artifact covers.

Step 2: artifact generation

PRINT turns the bounded neighborhood into a concrete artifact. At first this is mainly generative: collect story slugs, collect garden slugs, emit HTML. Useful, but still not yet credible maintenance.

A generated artifact alone is not enough. A maintenance story needs the artifact to expose what it could and could not account for.

Step 3: identify the actual story source

Use FROM to identify story tightens the provenance of the workflow. The story is no longer inferred only from surrounding state. It becomes an explicit source in the block language itself.

This matters because a credible repair path needs traceable origin.

Step 4: fetch the actual page material

fetch and expand page json moves the workflow closer to maintained source. Instead of printing from partial neighborhood summaries alone, it fetches page JSON and expands what it can from the real page content.

That is analogous to the Drawing Automation move from detached diagram editing toward generated views over maintained source.

Step 5: make links actionable

expand links as anchors is easy to underestimate, but it is central to maintenance. A visible relation in the output becomes a navigable reference.

This is the beginning of the same pattern seen in raw linked SVG in Drawing Automation: a generated artifact becomes a navigable surface for inspection and repair.

Step 6: account for what the workflow could not do

Commit 4ed345e systematic tally; download in api is where the credible maintenance story becomes explicit.

Instead of keeping only one flat missing-page list, PRINT now keeps a structured tally of:

  • missing pages
  • referenced domains
  • item-type wishes
  • runtime errors

This is the decisive step. The generated output now comes with an account of its own limits. That makes the workflow reviewable and maintainable rather than merely productive.

Why the dispatch seam makes this possible

The credible maintenance story is not only about one block becoming more diagnostic. Its architectural basis is the normalized block registry protocol and shared execution context bundle behind Mech dispatch. The authored command text is normalized into operation/argument normalization, carried together with body, element, and state, and then handed to blocks[op].emit.

That seam is why PRINT can move from raw emission toward diagnostic publication. The same place that performs the work can also tally losses, report boundaries, and eventually support more explicit runtime provenance. Credible maintenance depends on preserving that seam between authored command text and inspectable runtime behavior.

What makes the story credible

The story is credible because each improvement narrows the gap between output and its generating source:

  • scope is explicit
  • source is identified
  • page material is fetched from real JSON
  • references become actionable anchors
  • failures are tallied by type instead of hidden

That is exactly the maintenance discipline described in the Drawing Automation cluster, translated from diagrams into story-neighborhood publication.

What is still missing

This is still not the full Drawing Automation model.

  • Mech PRINT does not yet carry source-location links back to the exact relation or annotation that generated each output fragment.
  • non-paragraph item types are tallied as wishes rather than rendered with their own first-class adapters.
  • the report is still assembled inside the browser block implementation rather than surfaced as an inspectable object model.
  • there is no first-class source-location provenance per generated fragment yet.
  • there is no persistent first-class run record or fully inspectable execution ledger yet.
  • the tally is real, but it is not yet a durable structured findings tally object published across runs.

So the progress is real, but the final maintenance story remains incomplete.

Pragmatic conclusion

The credible maintenance story for Mech does not begin at 4b80514. That commit is part of the background. The real story begins when Mech acquires a bounded extraction workflow and then learns to report its own boundaries and losses.

That is why the commits from 007a9db through 4ed345e matter more than the earlier infrastructure changes when judged by the standards of Drawing Automation.
