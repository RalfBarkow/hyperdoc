Compact inventory

  • auth/session bootstrap: get_session_id() sends GET /core/topic/0 with Basic auth, captures JSESSIONID from a cookie jar, and later get_response() adds dmx_workspace_id for workspace-scoped non-GET requests. HyperDoc landing: DMX session bootstrap and JSESSIONID as external comparison evidence, not as a new in-repo login surface.
  • host/config resolution: create_default_config(), read_default_config_file(), read_dmx_config_properties_file(), set_host_url(), and get_host_url() resolve protocol, host, port, path, credentials, and default workspace. HyperDoc landing: keep this on the py4dmx page; HyperDoc does not need a generic cloned host-config layer.
  • workspace lookup: get_ws_id() queries core/topics/query/"<workspace>"?topicTypeUri=dmx.workspaces.workspace_name and then follows related-topics to the parent workspace topic. HyperDoc landing: DMX machine-readable read paths.
  • topicmap lookup: get_topicmap_id() uses the same query-plus-related-topics pattern for dmx.topicmaps.topicmap_name. HyperDoc landing: DMX machine-readable read paths and Concepts, DMX Topics, and Topic Maps.
  • topic and assoc creation: send_data(), create_note(), create_topicmap(), and create_assoc() expose raw create paths for /core/topic/, /core/assoc/, and /topicmaps?name=.... HyperDoc landing: DMX note read/write boundary and Using guarded workspace topic lifecycle tools; the generic raw create surface stays external.
  • note creation: note_example.json and the -N/-B CLI path both create a parent dmx.notes.note payload with dmx.notes.title and dmx.notes.text. HyperDoc landing: DMX note read/write boundary.
  • workspace creation and membership: create_ws() and create_member() call the generic workspace and access-control endpoints. HyperDoc landing: HyperDoc DMX architectural implications; HyperDoc keeps only the guarded shared-workspace subset in-repo.
  • reveal-on-topicmap: reveal_topic() and reveal_assoc() POST view props to /topicmaps/<map>/topic/<topic> and /topicmaps/<map>/assoc/<assoc>. HyperDoc landing: Using guarded workspace topic lifecycle tools and HyperDoc DMX architectural implications; this is comparison material for guarded topicmap-context operations, not a reason to add raw reveal helpers.
  • plugin GET/POST: send_get() and send_post() send direct requests to plugin endpoints. HyperDoc landing: DMX plugin extension boundary; raw plugin endpoint access remains external.
  • vCard import: import_vcard() plus person_example.vcf and person_example.json show payload shaping into dmx.contacts.person with addresses, phones, emails, birthday, and note fields. HyperDoc landing: keep this as py4dmx-specific evidence rather than minting a new generic HyperDoc topic.
  • topic/data fetch and delete helpers: get_topic(), get_data(), get_items(), get_related(), get_creator(), get_modifier(), get_topic_ws(), get_ws_owner(), and delete_topic() expose a generic scripting surface for DMX JSON reads and hard delete. HyperDoc landing: reads reinforce DMX machine-readable read paths; generic delete stays external.

What HyperDoc should absorb

  • Py4dmx is useful evidence that DMX automation uses machine-readable JSON routes rather than browser hash routes.
  • Py4dmx is useful comparison material for session-cookie aftermath and workspace-cookie transport context.
  • Py4dmx is useful as a compact external inventory of operations HyperDoc deliberately narrows into typed guarded surfaces.

What should remain external

  • Generic host/config parsing for arbitrary DMX installations.
  • A raw login/session CLI or cookie-entry surface.
  • Unbounded topic, assoc, workspace, plugin, and delete helpers.
  • vCard import as a generic HyperDoc runtime feature.

The merge rule for this slice is therefore conservative: treat py4dmx as an external reference implementation and source-evidence cluster, then connect it to the existing HyperDoc DMX pages that already own auth, read-path, note, and guarded-write concepts.
