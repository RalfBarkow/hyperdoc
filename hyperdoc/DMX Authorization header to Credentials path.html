DMX Authorization header to Credentials path

hyperdoc

DMX Authorization header to Credentials path records the backend sequence that HyperDoc is teaching rather than reinterpreting: DMX reads an Authorization header, constructs Credentials, resolves AuthorizationMethod for non-Basic methods, checks credentials, and then attaches the username to the servlet session. If that chain does not establish an authenticated user, DMX can still fall back to AnonymousAccessFilter for allowed prefixes.

Backend sequence

  1. DMX request filter sees Authorization: ....
  2. DMX constructs Credentials(authHeader).
  3. If the method is not Basic, DMX resolves AuthorizationMethod.
  4. DMX checks credentials through either the default credential checker or the resolved non-Basic authorization method.
  5. On success, DMX attaches the username to the servlet session.
  6. If no authenticated path succeeds, DMX may still consult AnonymousAccessFilter for request-prefix fallback.

What this sequence does not mean

  • It does not make workspace assignment the same thing as topicmap visibility.
  • It does not remove object-level ACL on existing topics such as /core/topic/<id>.
  • It does not imply that a JSESSIONID cookie is a primary operator input mode.

HyperDoc crosswalk relevance

HyperDoc's username/password, authorization header, and bearer token inputs are teachable because they can all be aligned against this backend path. What differs is which parts are DMX-core-native, which are HyperDoc-derived, and which remain installation-dependent.
