Codex commit hygiene and staging boundaries

hyperdoc

This page records a durable operational pattern for Codex work in this repository: sometimes the slice itself is correct, but the current HEAD, index, and worktree state is too mixed to justify an automatic commit. In that case the right move is to stop automated committing, preserve the slice boundary, and cut a slice-pure cached diff by manual staging.

Core boundary

The commit boundary is not defined only by the requested slice. It is defined by whether the staged diff can still represent only that slice. When the staged set is slice-pure, committing is straightforward. When the staged set or index/worktree relationship is mixed, automation should stop and the boundary should be repaired explicitly.

State distinctions that matter

Slice-pure commit

A slice-pure commit is the normal path: the cached diff contains only the intended files and hunks for the current slice, and the commit message still describes the staged content exactly.

Mixed staged set

A mixed staged set means the index already contains unrelated files or hunks. Even if the current slice content is correct, an automated commit would blur history by absorbing material from outside the slice.

Mixed index/worktree state

A mixed index/worktree state means one or more target files already differ between HEAD, the index, and the worktree. In that situation, patch-selection decisions depend on which layer currently carries the older edits. Resetting the index to HEAD while preserving the worktree can be the necessary first step before patch staging becomes meaningful.

New-file special case

A file that is not in HEAD has no patch baseline after git restore --staged; it becomes untracked. In that case, either stage the whole new file directly or create an intent-to-add entry with git add -N before using git add -p.

When to stop automation

  • Stop when the staged diff still contains unrelated prompt history, test work, or runtime files outside the current slice.
  • Stop when the target files already have older staged state that makes a plain commit broader than the requested slice.
  • Stop when you cannot show a slice-pure cached diff that matches the intended commit message.
  • Stop before committing if the uncertainty is about commit boundary rather than about implementation correctness.

This is not a failure of the slice itself. It is a boundary-management problem. The right response is to preserve the slice, report the mixed state, and switch from automated commit flow to manual staging.

Manual staging boundary

  1. Enter nix develop once for interactive Git work.
  2. Unstage unrelated files or hunks that do not belong to the current slice.
  3. For mixed files, use git restore --staged ... to reset the index to HEAD while preserving worktree edits.
  4. Stage whole files that belong entirely to the slice with git add.
  5. Use git add -p only for the specific hunks that belong to the slice.
  6. For new files that need partial staging, use git add -N first so patch mode has a baseline.
  7. Inspect the cached diff until it is slice-pure by content, filenames, and commit-message fit.
  8. Commit only after the cached diff is clean.

Repo-shell execution style

In this repository, the practical split is deliberate: do interactive staging inside nix develop, and use explicit repo-shell verification commands for the final proof surface. 

nix develop
git add -p AGENTS.md
git diff --cached --stat

nix develop --command git diff --cached -- [exact files]

This keeps staging usable while still preserving the repo rule that the authoritative reported git verification should come from the same repo shell used for validation.

Durable pattern, not incident report

The underlying pattern is general: when the repository state prevents a clean slice commit, the system should preserve the requested slice boundary rather than pretending the boundary is cleaner than it is. Journal entries and review exports can supply evidence, but this page carries the durable rule.
