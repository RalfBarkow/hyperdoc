Guarded local Neo4j repair boundary in HyperDoc

hyperdoc

Guarded local Neo4j repair boundary in HyperDoc is the narrow local-first repair surface for one known DMX datastore failure class: duplicate username topics that make login ambiguous. It documents the runtime objects already implemented for this slice and keeps the difference explicit between inspection, reviewed repair planning, guarded execution, and post-repair verification.

This is not a raw Neo4j console. HyperDoc does not accept arbitrary Cypher, does not expose a generic local shell runner, and does not treat datastore reachability as permission to mutate internal state freely. The supported surface is one bounded workflow with one bounded local repair verb.

Narrow surface, not console

The runtime boundary is intentionally smaller than “run local Neo4j command”. Read-only inspection is modeled as a fixed neo4j-read-query-operation. Classification becomes a neo4j-username-ambiguity-report. The only supported mutation shape becomes a neo4j-duplicate-username-repair-plan and then a neo4j-repair-operation. Unsupported or ambiguous cases stay inspectable refusals.

  • No arbitrary Cypher entry.
  • No generic database administration surface.
  • No hidden mutation path in explorer or inspector views.
  • No repair without an explicit reviewed plan object.

This boundary is intentionally capability-scoped to avoid ambient authority: datastore reachability does not imply broad mutation permission.

Adapter boundary

Datastore adapter boundary is explicit in this slice. Lisp owns supported-case classification, refusal, approval, offline confirmation, backup preconditions, and post-repair verification. The Java helper exists only because Neo4j 1.8.1 store access is native to the Java library stack and HyperDoc needs one narrow old-store touch point for this case.

The helper is not the feature center. It reports duplicate-username evidence and performs one rename when Lisp passes fully explicit values. It does not decide which username topic is canonical or stale, does not decide whether repair is allowed, and does not select backups or approvals.

Offline-only guarded repair

The guarded repair verb remains separate from inspection and is narrower than a generic local execution seam. Execution is allowed only when the plan object is already fully determined.

  • The local DMX/Neo4j instance must be explicitly confirmed stopped.
  • An explicit backup path must already be present on the plan.
  • The inspection report must prove the supported duplicate-admin shape.
  • The plan must already carry deterministic canonical id, stale id, and rename target.

If any one of those preconditions fails, HyperDoc returns a refusal object. It does not fall back to a broader manual command path from within the same runtime surface.

Plan before execution, verification after repair

The materialization views render the exact helper-build, backup, rename, and verification commands before execution. Review happens against those rendered commands and against the report object. Verification remains a separate read-only step after the guarded verb returns, including store-side reinspection and the later live HTTP username probe.
