Graham Closures and the NOR Graph Matcher

hyperdoc

This page relates Paul Graham's Section 6.5 explanation of closures to the NOR graph matcher teaching story. Graham's beginner move is: a function can be returned as a value, and the returned function can keep using a lexical variable from the place where it was created. The NOR matcher uses the same mechanism, but the remembered values are not just numbers; they are the next success and failure exits of a compiled matcher graph.

Boundary

This is a teaching page, not the production graph matcher. The graph is a small property-list model with agents, ports, and edges. The goal is to make the closure boundary visible: what value is remembered by each returned function, and why swapping success and failure implements NOR.

1. Graham's smallest closure: remembered n

Click: run the example below. Observe: add3 and add27 are produced by the same function, but each returned function remembers a different value of n. Why this matters: the matcher builder will use the same idea to remember a form, a graph predicate, and two exits.

2. Graham's complement: negation as a returned function

Click: run the complement example. Observe: our-complement returns a new predicate that calls the old predicate and reverses the result. Why this matters: this prepares the learner for the matcher version of negation, where the two continuations are reversed instead of calling not on a Boolean value.

3. A graph leaf closure: remembered predicate and remembered exits

Click: run the graph leaf example. Observe: the leaf matcher remembers the form (:agent :moon) and the two exits it should call. Why this matters: a matcher leaf is Graham's closure pattern with a richer environment: the function remembers both what to test and where to continue.

4. NOR over graph predicates

Click: run the NOR absence example. Observe: (nor (:agent :shuttle) (:agent :joke)) succeeds on a graph that contains neither forbidden agent. Why this matters: the logical connective is no longer attached to string search. It now works over graph-inspection leaves.

5. NOR short-circuiting as continuation choice

Click: run the short-circuit example. Observe: when (:agent :shuttle) succeeds, the enclosing NOR fails immediately and records a :nor-short-circuit event. Why this matters: Xach's compiler target is a tree of closures whose control flow is already wired. It does not need eval, and it does not need a fresh call to compile for this query.

6. The original query, graph-shaped

The original string query was: 

(or (and "space" "mission")
    (and (or "moon" "lunar") "landing"))

For the graph matcher, the leaves become graph predicates such as (:agent :moon) and (:agent :landing). The closure compiler does not care whether the leaf is a string search or a graph inspection; it only needs the leaf to choose success or failure.

Click: run the positive graph query. Observe: the Apollo graph matches because it has :moon and :landing agents. Why this matters: the teaching story can move from strings to graph objects without changing the continuation idea.

closure-nor-demo-original-query-graph-positive-example

7. A negative graph for the same query

Click: run the negative graph query. Observe: the shuttle graph has neither the :space/:mission pair nor the :moon/:landing pair. Why this matters: the same compiled closure tree can explain both the match and the non-match by returning an inspectable trace.

Teaching choreography

  1. Start with make-adder: one function remembers one number.
  2. Move to our-complement: one returned function reverses a predicate.
  3. Move to a matcher leaf: one returned function remembers a graph predicate and two exits.
  4. Show NOR: the connective is implemented by choosing which exit to call.
  5. End with the graph-shaped original query and inspect the trace.
