Diagnosing DMX workspace assignment and topicmap placement

hyperdoc

This page is the read-only walkthrough for diagnosing one DMX object through HyperDoc without collapsing two different layers: workspace assignment and topicmap placement. The runtime object is still the existing hyperdoc::dmx-topic-proxy; the difference is that its inspector now exposes a dedicated Workspace diagnostics tab.

How to inspect one object by id

Use either of these runtime handles:

  • (make-dmx-topic-proxy :topic-id <id> :topicmap-id 919822)
  • (make-dmx-shared-workspace-topic-proxy <id>)

The second helper fixes the topicmap context to 919822, the context-window topicmap. It does not infer or synthesize workspace assignment. The inspector reads that separately from the live /workspaces/object/<id> endpoint.

Title-first canary opener

For the current canary, you do not need to start from the raw id. Open Operational definition: chunk, chunk note, manifest note, content topic, then launch the real object through (make-operational-definition-note-proxy).

What the new inspector view shows

Open a DMX topic proxy and then select the Workspace diagnostics tab. The tab shows at least:

  • topic id, URI, topic type, and title/value
  • workspace assignment and workspace owner
  • topicmap memberships, with the selected topicmap called out explicitly
  • whether the object is HyperDoc-owned or foreign
  • note key or handover key when the URI exposes one
  • derived status and whether repair is needed
  • the exact source endpoints and raw readouts used for the diagnosis

The ownership boundary for this tab must treat both hyperdoc:mcp/workspace-annotation/ and hyperdoc:mcp/workspace-journal/ URI families as HyperDoc-owned. If an older summary path reports one of those families as foreign, treat that as a classifier false negative and confirm ownership through the guarded workspace-topic classifier before deciding that no action is needed.

This is intentionally read-only. Diagnosis remains read-only and needs no login because this inspector only reads machine-readable DMX endpoints. The new authenticated mutation surface is separate: the Repair console tab on the same object, documented in Using authenticated workspace assignment repair console.

Acceptance cases

Case 1: 922464

Open (make-operational-definition-note-proxy). The expected diagnosis is:

  • topicmap placement present in 919822
  • workspace assignment missing
  • derived status: in topicmap but unassigned
  • repair needed: yes

Case 2: 922586

Open (make-dmx-shared-workspace-topic-proxy 922586). The expected diagnosis is:

  • topicmap placement present in 919822
  • workspace assignment present as 919815
  • workspace owner present as rgb
  • derived status: OK

Case 3: 922451

Open (make-dmx-shared-workspace-topic-proxy 922451). This is the stray probe topic kept as a foreign maintenance case. The expected diagnosis is:

  • topicmap placement visible in 919822
  • no workspace assignment
  • ownership class: foreign
  • derived status: foreign object

Why the distinction matters

Topicmap placement answers: “Is this object visible in the shared blackboard topicmap?”

Workspace assignment answers: “Does DMX consider this object to belong to workspace 919815?”

They are related operationally, but they are not the same fact. The pre-fix defect existed precisely because a note could be visible in topicmap 919822 while still lacking workspace assignment.

Canonical single-object statuses

  • healthy: workspace readback is 919815 and selected topicmap presence is true
  • foreign-no-action: the object is not HyperDoc-owned for this guarded repair boundary
  • in-topicmap-but-unassigned: workspace read succeeds, assignment is missing, and selected topicmap presence is true
  • credentials-pending: the object is confirmed repairable, but the first live assignment write hit the authentication boundary
  • repair-succeeded: the guarded assignment repair completed and read back as assigned
  • repair-failed-non-auth: auth was crossed, but the repair failed later for another reason

Follow-up boundary

If the diagnostics tab shows a HyperDoc-owned topic as in topicmap but unassigned, the separate follow-up path is the guarded repair tool: repair_workspace_topic_assignment. In HyperDoc that follow-up now lives in the separate authenticated Repair console tab, which threads explicit ephemeral credentials into the same guarded repair executor without collapsing workspace assignment into topicmap placement.

If the first live assignment attempt returns 401 on the guarded workspace-assignment endpoint, stop retrying the same server-side service-auth path for that object. Reclassify it as credentials-pending and continue only through the explicit-auth repair console.

When the question is not about one object but about the current repair set, use the companion batch page Diagnosing DMX workspace repair triage. It enumerates topicmap 919822 first and then applies the same diagnostics model row by row.
