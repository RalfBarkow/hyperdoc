Document capability as DITA-like click-through cluster

hyperdoc

Use this pattern when one concrete capability deserves step-by-step learning rather than a single static explanation page. The capability is documented as a small click-through neighborhood with four distinct functions: concept, task, verification or training, and troubleshooting.

When to use this pattern

Use it when a reader must move from understanding to procedure to checking to diagnosis without leaving the capability boundary. This works especially well when the capability already exists in the system and needs a teachable path, not a new implementation.

When not to use this pattern

Do not use it for broad methodology theory, for abstract architecture without a concrete capability, or for tiny changes that do not need verification and troubleshooting surfaces. If the capability does not yet exist, implement the capability first and document the working behavior afterward.

Required four-part cluster

  • Concept: explain what the capability does and why it matters.
  • Task: show the explicit procedure for using or checking it.
  • Verification or training: show how to confirm the expected outcome.
  • Troubleshooting: explain why the expected result might not appear.

Page graph and navigation pattern

The page graph should let a reader move in this order: concept, then task, then verification, then troubleshooting. Each page should backlink narrowly to the others, so the cluster reads like one instructional path rather than four unrelated notes.

Authoring constraints

  • Keep the capability narrow and concrete.
  • Prefer existing topic handles over new vocabulary.
  • Avoid methodology sprawl for one local capability.
  • Do not mix the instructional docs slice with parser, helper, or runtime repairs.

Worked example

The Software Heritage commit-link capability is the local worked example. It is documented as:

  • concept
  • task
  • verification
  • troubleshooting

That cluster stays focused on one capability: turning a full Git commit hash in story text into a Software Heritage revision link. It teaches the reader how to understand the feature, use it, verify it, and diagnose common failure cases without turning into a larger parser or FedWiki theory page.

Anti-patterns

  • Writing broad documentation theory before any concrete capability pages exist.
  • Creating a topic explosion for one small capability.
  • Mixing instructional documentation with implementation repair in the same slice.
  • Omitting verification or troubleshooting, so the path is not actually teachable.
