Relating the review contents to existing HyperDoc topics and pages

hyperdoc

This note maps the review points onto the existing HyperDoc surface model so the Drew McDermott slice can be edited in the same style as the rest of the repository.

See also Review of the first merge-proposed-topic-additions HTML

1. Relate the merge-rule review to the existing Topic factory page

The strongest existing anchor is topic factory. That page already says that a topic factory in hyperdoc/topics.lisp is the durable reconstruction point for a topic page, that the authored fields are :id, :title, :summary, and :references, and that the canonical title is the exact topic-page title. Use that page as the explicit justification for the first-pass exact-title check.

Then tighten the new merge-guidance page so it does not overclaim. The rule should read: first check exact :title; then check aliases, near-duplicates, or broader existing topics; only then add a new factory.

2. Relate the function-name review to the existing stable-id paragraph

The existing Topic factory page already separates stable id from canonical title. That is the right place to ground the review point that function-name stability is only a workflow preference, while :id and :title are the semantic continuity points.

So in the merge-guidance page, replace “keep the existing function name” with a narrower formulation: keep the existing :id and canonical :title; keep the existing function name when that reduces churn.

NB: On which page can I find instructions on how to merge? Merge proposed … or How to merge …

3. Relate the alias/scope review to the existing Documentation Surfaces page

The page Documentation Surfaces in HyperDoc already explains that arrangement pages record editorial neighborhood without asserting full semantic equivalence, and that topic objects are inspectable semantic handles with stable identity. That is exactly the surface boundary you need for the review’s alias-and-scope point.

So the place to record decisions like Nisp versus YNisp is not only the merge-guidance page. It should also appear in Drew McDermott topic arrangement as an editorial normalization note.

4. Apply that alias/scope step directly to the Drew pages

Right now the patch links both Nisp and YNisp as if they are already settled as separate topic pages. But the review point says that this must first be treated as an alias-normalization decision.

So edit the Drew pages in this order:

  1. In Drew McDermott topic arrangement, add one short paragraph under Boundary that says the import first checks whether later names such as YNisp should be absorbed into an existing canonical topic such as Nisp.
  2. In Drew McDermott Lisp, Planning, and Software, do not keep both links until that decision is made. Use one canonical link, or prose like Nisp / YNisp with only the canonical topic linked.
  3. In YTools, Nisp, Nity, Opt, and Optop, move the naming distinction into the paragraph text if you decide there should be only one topic.

5. Relate “Running image coherence” to the existing source/image boundary page

The patch introduces Running image coherence. Existing HyperDoc already has the page Source-oriented and image-oriented development in Common Lisp plus the topic Live image versus durable source. That means the new title should not float alone.

If you keep Running image coherence as a new topic, add one explicit paragraph in A framework for maintaining the coherence of a running Lisp that distinguishes it from the existing source/image boundary: the older page is about workflow modes and rebuild authority, while the new topic is about internal consistency and intelligibility of an evolving live image.

6. Relate the repair/trace page to the existing Diagramming Debugger Surface

The page Diagramming Debugger Surface already says that the debugger is an inspectable object that wraps the existing Playground stepper and records one event per attempted top-level form. That is the direct model for your proposed repair trace.

So in Repair Drew McDermott missing topic page, sharpen the “Recommended next slice” paragraph to say that lookup-repair-trace should be a sibling design: an inspectable wrapper around repair-thunk execution that records phase events and then renders a diagram surface.

7. Relate the slice boundary to the existing Definitive Common Lisp Books page

The existing books page is a practical reading map, not a catch-all import sink. That supports the earlier editorial decision that the McDermott material belongs as a narrow software/source cluster rather than as another “definitive book” unit.

So the Drew pages should keep pointing outward to Definitive Common Lisp Books only as a neighbor, not as their primary home.

8. Relate the merge-guidance pages to existing HyperDoc page form

The current patch adds two full-document HTML files: Merge proposed topic additions into hyperdoc:topics.lisp.html and Review of the first merge-proposed-topic-additions HTML.html. That does not match the prevailing HyperDoc page form, where pages are HTML fragments with <h1>, optional <in-package>, and body content, not full <html>/<head>/<body> wrappers.

So the review should be integrated into one normal HyperDoc page, not kept as a second full HTML document. The better outcome is: merge the revised review points into one durable page such as How to merge proposed topic additions into hyperdoc/topics.lisp, and delete the duplicate full-document variants.

9. Relate the title-lookup claim to the existing code

The current topics implementation registers topics by both id and title, and make-topic reuses an existing topic when either id or title already matches. That supports the review’s claim that duplicate :title values are operationally dangerous, but it also means that id continuity matters alongside title continuity.

So the merge-guidance page should mention both: exact title is the first practical lookup key for authored links, and stable id is the durable identity key for the topic object itself.

10. Relate the slice to existing smoke-test practice

Your current smoke-test file already uses the pattern: assert the topic function is fboundp, then assert the topic page resolves by title, then assert the durable HyperDoc page exists. The Drew slice should follow exactly that pattern.

So the review content should end with a repository-local acceptance step: add a small McDermott slice smoke test instead of leaving verification only as prose.

Net result

The review becomes much stronger once it is tied to the repository’s existing surface model: Topic factory for identity and reconstruction, Documentation Surfaces in HyperDoc for page/topic/arrangement boundaries, Source-oriented and image-oriented development in Common Lisp for the live-image boundary, Diagramming Debugger Surface for inspectable trace design, and the existing smoke-test file for acceptance.
