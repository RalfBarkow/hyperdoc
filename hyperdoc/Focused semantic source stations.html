Focused semantic source stations

hyperdoc

Focused semantic source stations is the durable source-oriented review surface: a way to name semantically meaningful source stations, inspect them in the Source pane, and attach first-class route judgments before any code removal patch lands. The tactical first use case was the journal-projection contract cleanup around dmx-mcp-workspace-summary and dmx-mcp-topicmap-projection. That first slice is now complete, but the journal-specific station list is not the lasting essence of the concept.

The strengthened reading is that a semantic source station is not only a review label. It can act as a grounded semantic station: an inspectable proxy for the meaningful source state, evidence locus, or interpretation path that a reviewer needs to re-enter later. HyperDoc route language matters here because the goal is not merely to point at code, but to preserve durable retrieval paths back into the source meaning that justified a judgment.

The first tactical slice has now removed journalTopicCount and journalTopics from the public workspace/topicmap projections in DMX MCP. The durable review surface remains useful because it preserved those leakage sites as routeable source judgments rather than reducing the change to an inline source edit. The broader HyperDoc-owned journal migration, replay-parity proof, and later companion deletion remain deferred.

Durable concept

The durable idea is a general source-review view, not a permanent list of journal-specific locals. Earlier alternatives such as Function path stations are too implementation-shaped. The preferred durable label is Focused semantic source stations because the station names should stay legible at the review level even when the implementation underneath them is later rewritten.

A focused source-station slice can therefore be curated narrowly for one review question without pretending that its current station vocabulary is the whole long-term ontology of source review.

In that narrower sense, a station name succeeds when it helps the reviewer retrieve the right source meaning again. A route from station to Annotation is therefore not merely a connective edge. It is a first-class retrieval relation that keeps the judgment reopenable as the source changes underneath it.

Completed first tactical slice

The first tactical slice was the journal-projection contract cleanup around dmx-mcp-workspace-summary and dmx-mcp-topicmap-projection. Before the cleanup, both functions computed journal-summaries and emitted journalTopicCount plus journalTopics into public topicmap/workspace payloads. That contract-removal patch is now complete in DMX MCP, while current journal inspection and repair tooling remains in place for operations that still depend on companion state.

The review target is therefore stronger than merely hiding two fields. The architectural move is to shift journal authority first, then let the public topicmap/workspace projection describe visible shared state only, and only then delete the obsolete DMX companion machinery after replay parity is proven.

Initial curated station slice

For that first completed slice only, the source stations were grouped into two kinds:

  • Pipeline stations: topic-summaries, journal-summaries, visible-topic-summaries, and note-summaries.
  • Emitted output stations: journalTopicCount and journalTopics, now removed from the public projection contract.

This station set is intentionally volatile: as the journal-projection refactor lands, these stations are expected to change, shrink, or disappear, while the source-station review view itself remains the durable concept.

Source-station workflow

The intended workflow is: source station -> Lay route -> Annotation -> note "Remove".

The user's judgment is a first-class route object, not an inline source mutation. A reviewer selects a source station such as journal-summaries or journalTopics, uses Lay route to target Annotation, and records a note such as Remove, Demote to projection backend, or Keep temporarily until parity is proven. That keeps the judgment reopenable and inspectable even while the source changes.

Follow route then means semantic re-entry: reopen the evidence chain, interpretation path, and note that made the source judgment meaningful in the first place, rather than guessing again from the current code snapshot alone.

Architectural target

The documented target model is:

HyperDoc journal -> shared workspace projection

The current implementation still passes through DMX journal companions for replay, restore, and repair, so today's practical review model is:

HyperDoc page -> authoritative local journal -> optional DMX projection journal companion -> shared DMX workspace/topicmap projection

The end state should not be long-term coexistence. Once replay parity is proven, deleting the obsolete DMX journal companions is a migration milestone, not merely a future aspiration.

Practical cut line

  • Completed first slice: public dmx-mcp-topicmap-projection and dmx-mcp-workspace-summary no longer emit journalTopicCount or journalTopics.
  • Keep read_workspace_journal, read_topic_journal, restore, and repair tools for now because current operations still depend on them.
  • Recenter journal authority on stable HyperDoc-managed page or subject identity in a later migration.
  • After replay parity is verified, run an explicit cleanup step that deletes obsolete companion topics instead of preserving them as shadow baggage.

Deferred follow-on

The broader HyperDoc-owned journal migration remains deferred here. This review surface does not yet introduce new HyperDoc journal resources keyed by stable page or subject identity, and it does not yet prove replay parity or delete the remaining DMX journal companions.

Boundary

This page does not itself broaden into the full journal migration, and it does not redesign datastore repair. Existing guarded Neo4j/datastore repair pages remain the bounded maintenance lane when the substrate itself is wrong.
