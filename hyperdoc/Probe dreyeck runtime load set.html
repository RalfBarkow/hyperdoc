Probe dreyeck runtime load set

This diagnostic task makes the running image explicit: inspect loaded systems, then inspect scoped example discovery by system to confirm whether the intended load before serve for scoped examples rule is active.

Inspectable objects

  • Probe dreyeck runtime load set
  • Startup load-set mismatch
  • HyperBook server vs HyperDoc server load set
  • Load before serve for scoped examples
  • Live parity evidence

Purpose

Distinguish an under-loaded service image from a discovery bug.

Prerequisites

  • Access to a REPL, Playground, or equivalent live evaluation surface on dreyeck.
  • The service is already up.

Steps

  1. Inspect loaded systems: 
    (asdf:already-loaded-systems)
  2. Inspect base, portable, and ops example scopes: 
    (mapcar #'hyperdoc::check-id-of
        (hyperdoc::discover-example-checks :system "hyperdoc"))

(mapcar (lambda (spec)
          (getf (hyperdoc::check-locator-of spec) :function))
        (hyperdoc::discover-example-checks :system "hyperdoc/examples"))

(mapcar (lambda (spec)
          (getf (hyperdoc::check-locator-of spec) :function))
        (hyperdoc::discover-example-checks :system "hyperdoc/examples/ops"))
  3. If portable/ops are empty, test the load hypothesis explicitly: 
    (asdf:load-system :hyperdoc/examples)
(asdf:load-system :hyperdoc/examples/ops)
  4. Rerun the two scoped discovery calls.

Expected results

  • If the service was correctly started from :hyperdoc/server, the portable and ops scopes are already nonempty.
  • If the scopes only appear after explicit loads, the issue is startup/load-set drift.

Failure interpretation

  • Empty scopes before explicit loads do not by themselves indicate a broken discoverer.
  • Change after explicit load is strong evidence of a startup path problem.
