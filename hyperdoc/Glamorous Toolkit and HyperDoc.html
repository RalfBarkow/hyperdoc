Why compare GT and HyperDoc

HyperDoc and GT are both concerned with explainability, inspectability, and developer-facing knowledge work. Comparing them clarifies which ideas HyperDoc inherits directly, which it reinterprets, and which it intentionally leaves out.

Shared concerns

  • Software should be understandable through active exploration, not only static reading.
  • Tools should expose inspectable runtime objects and contextual views.
  • Documentation and debugging artifacts should remain close to executable systems.

Key differences

  • GT is an integrated moldable development environment; HyperDoc is a hypertext documentation component for computational systems.
  • HyperDoc emphasizes cross-linkable pages and object references as a publication medium; GT emphasizes environment-integrated exploratory tooling.
  • HyperDoc intentionally keeps heterogeneous links (pages, objects, external systems) central, rather than assuming one unified runtime workspace.

Inspectors and inspectable objects

Both systems treat inspectable objects as first-class. In HyperDoc, pages can expose object entry points via expr links and inspector views. GT serves as a reference for moldable inspection practice, while HyperDoc applies that style to page-centered, link-driven documentation.

Knowledge artifacts: Lepiter, FedWiki, HyperDoc pages

HyperDoc works alongside other knowledge artifacts instead of replacing them. Lepiter notebooks, FedWiki pages, and HyperDoc pages each provide different strengths for inquiry, curation, and publishing. HyperDoc's role is to keep object-level references and navigable semantics explicit across those surfaces.

Moldable development as a design pressure

HyperDoc uses moldability as a design pressure: developer tools should make adaptation and explanation cheaper. This pressure informs how pages, links, inspectable objects, and examples are authored.

What HyperDoc adopts, reinterprets, or leaves out

  • Adopts: inspectable objects, contextual views, exploratory understanding.
  • Reinterprets: moldability as hypertext-linked documentation and workflow artifacts, not only IDE-local interaction.
  • Leaves out: assumptions that one environment form should dominate all knowledge workflows.
