Implement Missing Function References as Inspectable Objects

hyperdoc

This task explains how to move the current HyperDoc code base from a message-only undefined-function failure path to a two-level inspectable failure path modeled after the existing page-lookup-issue precedent.

The desired end state is:

  • a primary bounded issue object for a failed <source-of-function> reference
  • the underlying Lisp condition preserved as an inspectable secondary object
  • the rendered message The function ... is undefined. preserved as additional condition text
  • a clickable correction path analogous to the existing page-lookup repair flow

Prerequisites

  • You can load and run the current HyperDoc image.
  • You can reproduce the current message-only failure for a broken <source-of-function> reference.
  • You can inspect the existing page-lookup issue workflow in the running system.
  • You have the current files for page lookup, lisp-function resolution, and inspector views available for editing.

Context

The current project already contains the right architectural precedent: page-lookup-issue as created by hyperbook:make-page-lookup-issue. That precedent does two important things:

  1. It exposes a bounded issue object as the primary workflow surface.
  2. It keeps the underlying condition inspectable behind that issue.

The missing-function case should follow the same two-level pattern rather than stopping at the raw message: 

The function HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE is undefined.

Goal

After completing this task, a failed <source-of-function> lookup no longer presents only a terminal undefined-function message. Instead, it opens a bounded issue object first and preserves the undefined-function condition and message as secondary inspectable artifacts.

Step 1. Reproduce the current failure path

Open a page that contains a broken <source-of-function> reference and confirm the current behavior.

  1. Choose a page whose function reference is currently unresolved.
  2. Open that page in the running HyperDoc image.
  3. Trigger the rendering path that resolves the function reference.
  4. Record the exact visible result and the exact symbol name involved.

At this stage you should still see the message-only behavior.

Step 2. Identify the exact resolution path for source-of-function

Find the code path that takes a page-level function reference and resolves it into a callable function or source object.

  1. Locate the code that handles <source-of-function> page markup.
  2. Follow the handoff into the Lisp-functions HyperBook lookup path.
  3. Identify the exact point where the system currently calls or resolves the function.
  4. Mark the place where the undefined-function condition currently escapes.

The implementation work should happen at the boundary where the missing definition becomes known, not later in generic UI code.

Step 3. Inspect the page-lookup-issue precedent in the code base

Before introducing a new issue type, study the current page-lookup issue object and its surrounding workflow.

  1. Read the constructor path rooted at hyperbook:make-page-lookup-issue.
  2. Inspect which fields are required for classification, repair, and provenance.
  3. Inspect how the issue exposes its underlying condition.
  4. Inspect how the current inspector tabs are provided.

Use this as the model for the new missing-function issue rather than inventing a new error style from scratch.

Step 4. Define a bounded issue object for missing function references

Add a new issue type for failed function references during page rendering.

  1. Choose a concrete object or class name, for example missing-function-reference-issue.
  2. Keep the issue bounded to one failed reference and one failure stage.
  3. Ensure it can store both workflow metadata and the underlying condition.

The issue should capture at least the following fields: 

:reference-kind
:source-page-title
:source-section
:reference
:expected-symbol
:stage
:package
:classification
:status
:suggested-repair
:repair-description
:repair-thunk
:underlying-condition
:underlying-condition-message

Step 5. Construct the issue object where the failure occurs

Replace the current message-only escape path with issue construction at the point where the missing function is detected.

  1. Wrap the function-resolution step in a handler for the relevant missing-function condition.
  2. When the condition is signaled, build the new issue object immediately.
  3. Populate it with the triggering page reference and source context.
  4. Attach the original condition object unchanged.
  5. Also store the human-readable condition message as separate text.

Do not discard the condition after constructing the issue.

Step 6. Preserve the two-level structure explicitly

The result must keep three distinct layers visible.

  1. Primary issue object for navigation and repair.
  2. Underlying condition object for low-level diagnosis.
  3. Underlying condition message for compact human-readable display.

The structure should look conceptually like this: 

missing-function-reference-issue
   ├─ reference-kind: :source-of-function
   ├─ expected-symbol: HYPERDOC::...
   ├─ suggested-repair: ...
   └─ underlying-condition
         ├─ condition-object: #<UNDEFINED-FUNCTION ...>
         └─ message: "The function ... is undefined."

Step 7. Provide inspector views modeled after page-lookup-issue

Add a small stable inspector surface rather than a generic debugger dump.

  1. Add an Overview view with source page, reference kind, and expected symbol.
  2. Add a Details view with package, stage, likely causes, and ASDF clues.
  3. Add a Repair view with suggested repair, description, and retry or reload affordance.
  4. Add a Condition view that exposes the underlying undefined-function condition and message.

Keep the view set narrow and repeatable.

Step 8. Define the default repair path

The issue object should not only diagnose the failure. It should also point to the next correction step.

  1. Decide which repair classification is appropriate for the current slice.
  2. Add a repair description that explains what to reload, rewire, or rename.
  3. Provide a repair thunk when the correction can be mechanized safely.
  4. Ensure the repair path can be retried after the correction step.

For the current Mech slice, likely causes include:

  • defining file not loaded
  • ASDF component mismatch
  • stale server process
  • symbol or filename drift

Step 9. Wire the page-rendering surface to show the issue object first

After issue construction and view definition, the page-rendering path must use the issue object as the first visible result.

  1. Return or render the new issue object instead of flattening the condition into bare text.
  2. Keep the condition object reachable from the issue.
  3. Keep the rendered message reachable from the issue.
  4. Confirm that the user reaches diagnosis and repair from the primary object without dropping into a generic debugger first.

Step 10. Add a narrow smoke test for the new failure class

Add a replayable test that proves the new behavior on one known broken function reference.

  1. Create or reuse a controlled broken <source-of-function> fixture.
  2. Trigger the rendering path in a test context.
  3. Assert that the result is a missing-function issue object.
  4. Assert that the issue contains the expected symbol.
  5. Assert that the issue retains the underlying condition object.
  6. Assert that the issue retains the rendered undefined-function message.

This prevents regression to the current message-only behavior.

Step 11. Validate against the existing screenshot-level precedent

Compare the new missing-function UI against the existing page-lookup UI.

  1. Open an existing page-lookup-issue object and inspect its tabs and field density.
  2. Open the new missing-function issue object and compare the same surfaces.
  3. Confirm that the primary workflow object appears first in both cases.
  4. Confirm that the underlying condition remains inspectable in both cases.

The two flows do not need identical field names, but they should feel like the same family of inspectable issue objects.

Step 12. Update the documentation pages

Once the code path works, update the documentation so the new behavior is part of the documented architecture.

  1. Keep Failure as Inspectable Object.html as the conceptual page.
  2. Add the new concrete issue object name and its two-level structure.
  3. Link it explicitly to page-lookup-issue as precedent.
  4. Document the step-by-step repair path for <source-of-function> failures.

Result

The code base has reached the desired state when all of the following are true:

  • A broken <source-of-function> reference no longer yields only the text The function ... is undefined.
  • The first visible object is a bounded missing-function issue.
  • The undefined-function condition is still inspectable as a secondary object.
  • The rendered condition message is still preserved.
  • The issue exposes a repair path analogous to the current page-lookup workflow.

Troubleshooting

If you still see only the raw undefined-function message, check the following:

  • The handler is attached at the actual function-resolution boundary rather than after rendering has already flattened the error.
  • The new issue object is returned to the page surface instead of being logged and discarded.
  • The inspector views are defined for the correct object type.
  • The running image has been reloaded after changing the issue type and views.
