SCXML Architect

hyperdoc

SCXML Architect is the inspectable surface for viewing, validating, replaying, and explaining SCXML-backed workflows in HyperDoc.

It is not the workflow itself. It is the architectural viewing surface around a workflow: current state, legal events, guards, preview path, mutation boundary, trace evidence, and the source SCXML that produced the run.

Purpose

HyperDoc uses SCXML to make procedural knowledge explicit. A workflow should not be hidden inside an ad hoc sequence of REPL commands, shell commands, or server-side callbacks. SCXML Architect gives that workflow an inspectable shape.

  • Show the active state path of an SCXML-backed run.
  • Show the next legal semantic events.
  • Show preview paths before mutation.
  • Separate deterministic state-machine structure from transport and mutation effects.
  • Expose source, trace, and boundary evidence next to the object being inspected.

Current implementation surfaces

  • hyperdoc/scxml-architect.lisp: runtime session and view-model objects.
  • hyperdoc-inspector/scxml-architect.lisp: inspector views for SCXML Architect sessions.
  • assets/hyperdoc/css/scxml-architect.css: Architect surface styling.
  • assets/hyperdoc/js/scxml-architect.js: client-side statechart interaction.

Relation to the SCXML C embedding decision map

The SCXML C decision map keeps HyperDoc as a long-running Lisp service and embeds only a generated SCXML protocol machine into C. SCXML Architect is the inspection surface for that protocol machine and for the corresponding HyperDoc-side replay.

Relation to running-image coherence

Drew McDermott's running-image coherence problem is a natural workflow target for SCXML Architect. In a long-running Lisp image, source files, loaded definitions, registered pages, generated views, topic materializations, and lookup results can drift out of coherence.

The corresponding HyperDoc workflow should make those dependencies explicit: source changed, reload systems, reload text pages, refresh derived objects, scan links, classify lookup issues, propose repairs, and verify that no open page-lookup issues remain.

Boundary model

Layer Responsibility
SCXML source Declares states, transitions, legal events, guards, and terminal states.
SCXML Architect session Presents active state, preview path, selected event, diagnostics, and source evidence.
Mutation adapter Performs concrete effects only through explicit guarded actions.
HyperDoc page Explains the workflow and links to inspectable objects.

Near-miss and page-lookup repair role

Exact HyperBook lookup remains authoritative. A matcher such as the NOR matcher should only assist diagnosis by ranking possible repairs when an exact page target is missing. It should not silently rewrite authored links. 

exact lookup -> page-lookup issue -> ranked repair candidates -> human review -> authored page or link correction
