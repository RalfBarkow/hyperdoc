Runbook - Build and Flash NixOS SD Image for Kioskberrli

This runbook is the operational sequence for creating an SD card for the Raspberry Pi 4 kiosk. It follows the SD-image model from the nix.dev tutorial.

Inspectable objects

  • Runbook - Build and Flash NixOS SD Image for Kioskberrli

  • Hydra artifact SHA-256
  • Verify Hydra artifact checksum
  • Procedure step 4: verify integrity
  • nixos-rebuild boot
  • nixos-rebuild switch

Scope

  • build or obtain a NixOS ARM64 SD image
  • flash it safely to a physical SD card
  • boot and apply first configuration changes
  • run pre-flight checks before first reboot

Inputs

  • target hardware: Raspberry Pi 4 Model B (aarch64)
  • image source: either official prebuilt SD image or project build target
  • project build target: .#nixosConfigurations.kioskberrli.config.system.build.sdImage

Path A - Official Prebuilt Image

  1. Open Hydra job nixos.sd_image.aarch64-linux and select latest successful build.
  2. Download artifact URL ending in aarch64-linux.img.zst.
  3. Use the exact artifact URL and published filename for explicit local artifact naming.
  4. Post-download verification: exactly one new *.img.zst file is present and filename contains nixos-image-sd-card-, pre-release id, aarch64-linux, and .img.zst.
  5. Resolve the exact build URL and record artifact URL, build URL, and published SHA-256 for build product 1.
  6. Compare the local checksum to Hydra's published value for that exact build, then decompress to .img.
  7. Flash the resulting .img to the SD card.
nix-shell -p curl wget zstd python3

LATEST_URL="https://hydra.nixos.org/job/nixos/unstable/nixos.sd_image.aarch64-linux/latest/download/1"
BUILD_DOWNLOAD_URL="$(curl -fsSI "$LATEST_URL" | awk 'tolower($1)=="location:" {gsub(/\r/, "", $2); print $2; exit}')"
test -n "$BUILD_DOWNLOAD_URL"
BUILD_URL="${BUILD_DOWNLOAD_URL%/download/*}"
BUILD_JSON="$(curl -fsS -H 'Accept: application/json' "$BUILD_URL")"
PUBLISHED_NAME="$(printf '%s' "$BUILD_JSON" | python3 -c 'import json,sys; print(json.load(sys.stdin)["buildproducts"]["1"]["name"])')"
EXPECTED_SHA256="$(printf '%s' "$BUILD_JSON" | python3 -c 'import json,sys; print(json.load(sys.stdin)["buildproducts"]["1"]["sha256hash"])')"
ARTIFACT_URL="$BUILD_DOWNLOAD_URL/$PUBLISHED_NAME"
test -n "$PUBLISHED_NAME"
test -n "$EXPECTED_SHA256"
test ! -e "$PUBLISHED_NAME"
ARTIFACT="$PUBLISHED_NAME"
wget -O "$ARTIFACT" "$ARTIFACT_URL"
test -f "$ARTIFACT"

echo "$ARTIFACT" | grep 'aarch64-linux\\.img\\.zst$'
echo "$ARTIFACT" | grep 'nixos-image-sd-card-'

LOCAL_SHA256="$(shasum -a 256 "$ARTIFACT" | awk '{print $1}')"
# Linux alternative:
# LOCAL_SHA256="$(sha256sum "$ARTIFACT" | awk '{print $1}')"
test "$LOCAL_SHA256" = "$EXPECTED_SHA256"

unzstd -d "$ARTIFACT"

# Inspect resulting files with a portable command
ls -la

Why this works: the Hydra latest endpoint redirects to a URL path that ends at the concrete build. That exact build page publishes the SHA-256 in both HTML and JSON, so the runbook can compare the local file hash to buildproducts["1"]["sha256hash"] for the same artifact before decompression. The resolved artifact URL already carries the exact filename, so wget -O "$PUBLISHED_NAME" "$ARTIFACT_URL" makes the local artifact identity explicit.

Postcondition (primary path): local directory contains a newly downloaded file named nixos-image-sd-card-*.img.zst, and no manual rename from 1 is required.

Comparison: naive wget "$LATEST_URL" may save as 1; corrected wget -O "$PUBLISHED_NAME" "$ARTIFACT_URL" writes the file under Hydra's published product name directly.

Verification object: local SHA-256 must equal the published Hydra SHA-256 from the exact build JSON field buildproducts["1"]["sha256hash"]. A mismatch is failure.

Step Boundary Checks

  1. After download verification: expect nixos-image-sd-card-26.05pre958961.aca4d95fce49-aarch64-linux.img.zst.
  2. After decompression verification: expect nixos-image-sd-card-26.05pre958961.aca4d95fce49-aarch64-linux.img. The working directory may still also contain the .img.zst artifact.
  3. Flashing target selection: flash the decompressed .img file only.

Warning: do not accidentally flash the .img.zst; the flash input must be the decompressed .img.

Directory inspection in this runbook uses ls -la. Do not assume a user-local alias such as la exists.

Fallback path - filename-loss recovery only

If local output was saved as file 1, classify it as filename-loss failure mode and recover the true artifact filename from the Hydra build page/redirect chain before decompression. Do not treat this as normal flow.

Path B - Build Project Image

cd ~/workspace/hauptsache/kioskberrli
nix build .#nixosConfigurations.kioskberrli.config.system.build.sdImage
ls -lah result/sd-image/

Use the generated image artifact from result/sd-image/ for flashing.

Flash Procedure (macOS host)

# 1) Identify target disk
diskutil list

# 2) Unmount target disk (replace diskN)
diskutil unmountDisk /dev/diskN

# 3) Flash image (replace IMAGE and diskN)
sudo dd if=IMAGE.img of=/dev/rdiskN bs=4m status=progress conv=sync
sync

# 4) Eject
diskutil eject /dev/diskN

Safety rule: verify diskN twice before running dd.

First Boot on Pi

  1. Boot from flashed SD card.
  2. Edit /etc/nixos/configuration.nix for local network/SSH settings.
  3. Run first rebuild with nixos-rebuild boot (not switch).
  4. Reboot into the new generation.

Pre-flight Gate Before Reboot

df -h /boot
ls -la /boot/extlinux
ls -la /boot/nixos
ls -la /dev/disk/by-label | grep -E 'FIRMWARE|NIXOS_SD' || true

If /boot is below 128MB, or extlinux.conf is missing, stop and re-image.

Acceptance Criteria

  • image build/download is reproducible and recorded
  • SD card boots on physical Pi 4
  • network and SSH come up
  • kiosk session shows landing page after reboot
