Kioskberrli

Kioskberrli is the Swiss German working title for the hardware and system slice of the hauptsache project: a Raspberry Pi 4 Model B based kiosk that displays the landing page inside the hairdressing salon.

The concrete target is not a generic browser on a developer laptop. It is a wall-mounted screen in the salon that should reliably show https://hauptsache.dreyeck.ch/assets/home/index.html.

Idea 1: treat the kiosk as part of the project

The landing page is only half of the system. The other half is the device that turns that page into a persistent public presence in the physical space of the salon.

That means the kiosk hardware and operating system are not deployment details outside the project. They are part of the project boundary.

Idea 2: start with Raspberry Pi 4 Model B on ARM64

The first implementation target is a Raspberry Pi 4 Model B. That is the hardware baseline for the first Kioskberrli and fixes the target architecture as ARM64 (aarch64-linux).

The immediate task is not to generalize across many devices. The immediate task is to make one reproducible kiosk image that boots, connects, starts a browser, and displays the landing page reliably.

Idea 3: build the kiosk from a NixOS SD card

The system should be provisioned from a NixOS-based SD card rather than by a manually configured mutable install.

This gives the project a reproducible system image and a clear boundary between:

  • the public landing page content
  • the FedWiki working surface
  • the kiosk operating system that renders the landing page in the salon

Idea 4: the first system goal is modest

The first kiosk image does not need to solve every management problem. It only needs to do these things reliably:

  • boot on the Raspberry Pi 4 Model B
  • bring up the network
  • start a browser or kiosk shell automatically
  • open https://hauptsache.dreyeck.ch/assets/home/index.html
  • recover cleanly after reboot or power loss

That is enough to turn the landing page into a working physical installation.

Idea 5: the NixOS work belongs in the same story

The NixOS SD-card work is therefore not a side experiment. It is the concrete implementation path for the salon use case.

In project terms, the next question becomes: 

What NixOS configuration and SD-image build output are needed to turn a
Raspberry Pi 4 Model B into the first Kioskberrli?

Idea 6: the kiosk and the wiki still have different roles

Even in the kiosk setup, the landing page and the wiki should remain distinct.

  • The kiosk should display the landing page by default.
  • The FedWiki remains the working memory and editorial surface behind it.

The kiosk should not collapse those roles into one screen unless that is a later deliberate design decision.

Pragmatic next step

The hauptsache project now contains a dedicated kioskberrli/ flake that declares an SD-card image build path for the Raspberry Pi 4 Model B.

The current build target is: 

.#nixosConfigurations.kioskberrli.config.system.build.sdImage

This is not yet the same as a demonstrated kiosk artifact. A credible maintenance story still requires build, flash, boot, network, kiosk-startup, and landing-page evidence on the target hardware.

The next checklist should make explicit:

  • SSH-based maintenance without on-site keyboard use
  • browser/session recovery after crashes and power loss
  • network fallback in salon conditions
  • SD-card durability and image rebuild workflow
  • the exact landing-page handoff behavior in production

The repo root can also provide a development shell for this work, but the SD image artifact itself belongs in hauptsache/kioskberrli.
