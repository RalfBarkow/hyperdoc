Ward's Idiomatic Survey

hyperdoc

Ward Cunningham's Idiomatic Survey is best read as a small exploratory corpus survey over source code, not as a style guide, linter, or finished doctrine. It parses JavaScript from ../wiki-client/lib, inventories recurring abstract-syntax-tree shapes, and lets a human drill from counts to occurrences, context, nesting, and structural similarity through a localhost web UI.

Purpose and corpus

The local repo at ~/workspace/idiomatic surveys the JavaScript in ../wiki-client/lib. The README frames the job as interactively browsing abstract syntax trees for idioms from an earlier interface style that might be better expressed with more modern interfaces.

That wording matters. The survey is not trying to prove a style doctrine from one isolated line. It gathers a corpus, counts recurring structures, and then lets a reader inspect examples before deciding whether a repeated form is merely common, historically contingent, or a plausible refactoring target.

Architecture

The program is a Node/Express localhost app that listens on port 1954. It reads every file in ../wiki-client/lib, parses the source with Acorn, and stores each file's source text together with the parsed tree.

Its companion visitor.js is a handwritten walker over many ESTree node kinds. The walker keeps an explicit stack while it descends, which is why the UI can talk about an occurrence and also about the enclosing path that led to that occurrence.

Navigation surfaces

  1. /index: counts non-terminal AST node kinds across the corpus.
  2. /terminal: lists distinct terminal values for a chosen node type/field combination.
  3. /usage: shows every occurrence of a selected value with adjustable structural context.
  4. /nesting: shows the enclosing AST path and JSON for one selected hit.
  5. /similar: finds other structurally normalized occurrences of the same nested pattern.

Why "survey" is the important word

The point is not to turn one micro-observation into a codebase-wide verdict. The point is to move from corpus inventory, to drill-down, to enclosing context, to similar cases. That progression turns idiomatic feedback into inspectable evidence.

Survey before doctrine, examples before verdicts, recurrence before refactoring, and context before prescription are the useful lessons to carry into HyperDoc.

What the survey does not decide

Ward's survey discovers recurring code shapes and lets a reader inspect them. It does not, by itself, tell us that a recurring pattern is bad, non-idiomatic, obsolete, or in need of refactoring. Recurrence is evidence, not a verdict.

For HyperDoc, that implies an explicit editorial layer above any future recurrence or similarity survey. The survey result is the machine- or corpus-derived finding. A human note explains what that finding may mean.

Limits and unfinished status

The README explicitly says the project has evolved through several iterations and has not yet fully realized the vague ambition from which it began. That is the right way to present it in HyperDoc as well: an exploratory instrument, not a finished methodology.

The README also notes that ongoing history is sometimes recorded on a FedWiki page named Static Aspects. This page does not rely on that page's current contents.
