Story Neighborhood Workflow

What Ward describes is a tightening of the feedback loop between story, neighborhood, book artifact, and editorial repair inside Federated Wiki, driven by Mech blocks.

This page summarizes that workflow structurally rather than historically. The key point is that the workflow starts from a page of links and treats it as the seed for bounded graph expansion, artifact generation, and repair.

The Story as executable spine

At the center is a page of links: the story. This is not prose-first. It is a curated graph frontier.

  • FIND retrieves the story by slug.
  • The story defines a seed set of pages.
  • WALK, PRINT, and PREVIEW operate relative to that seed.

This is graph-rooted publishing rather than document-rooted publishing.

WALK as controlled graph expansion

The upgraded WALK explores via sitemaps, not inline links alone. 

WALK 2 clicks

This defines a radius in the page graph.

  • 1 click = gateway
  • 2 clicks = neighborhood
  • 3 clicks = aspirational book scope

In abstract form: 

Given seed S
Return nodes within distance <= N

Editorially, this is powerful because scope is explicit, drift is visible, and expansion is intentional. The book becomes a bounded graph extraction rather than an accidental crawl.

Aspects as residue

WALK leaves graph aspects. These are reusable structural artifacts that downstream steps can consume.

  • PREVIEW can summarize them.
  • SOLO can browse them.
  • PRINT can render them.

This is compositional publishing: the exploration step produces metadata that later steps reuse, without needing to traverse the graph again.

PRINT as deterministic materialization

The newer PRINT block has three editorial surfaces:

  • PRINT outline for structure only
  • PRINT draft for full content aggregation
  • a warnings list for structural quality reporting

This turns a wiki neighborhood into a single HTML artifact that can then be converted to PDF, EPUB, or print-on-demand formats. The important step is not just generation but diagnostics: PRINT emits warnings.

Dangling references as boundary signals

A dangling reference is not merely an error. It signals a mismatch between the current graph boundary and the references found within it.

Typical resolutions are:

  1. Enlarge the neighborhood.
  2. Investigate the page origin.
  3. Repair the reference.
  4. Accept the boundary.

This is editorial topology rather than simple link checking.

The ghost page insight

When a page cannot be found, a ghost page opens and the same interface can be used to inspect backlinks such as "pages link here". Instead of a dead-end 404, the system turns the missing page into a diagnostic object.

That is workflow-aware error handling: the structural hole remains inspectable with the same UI affordances used elsewhere.

Conceptual pipeline

Story (seed links)
   ->
WALK (bounded graph expansion)
   ->
Aspects (structured representation)
   ->
PRINT (materialization + diagnostics)
   ->
PREVIEW (targeted repair)

The ghost page closes the loop by making missing nodes inspectable.

Why this matters here

This model aligns well with work that emphasizes journal integrity, provenance preservation, neighborhood correctness, and local versus remote authority. The same mechanism that supports book assembly can also support federation hygiene.

  • PRINT could become a journal-aware export.
  • WALK radius could encode replication boundaries.
  • Dangling slugs could signal fork-provenance gaps.
