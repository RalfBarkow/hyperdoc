Codex handover for HyperDoc

hyperdoc

This page is the single canonical durable guidance for handing a HyperDoc slice to Codex. Keep repository-wide operating rules in AGENTS.md, and use the task prompt only for the current slice contract and end-state inventory target.

Inspectable objects

  • Single-slice Codex thread
  • Filled task slice
  • Prompt-local slice contract
  • Authoritative nix develop validation
  • Inventory outcome
  • Continuity shell by design
  • Exact outcome reporting
  • Reconstruction protocol

Canonical structure

  1. State one concrete task slice and keep one Codex thread on that slice only.
  2. Name the exact files in scope and the exact paths out of scope.
  3. Record the architectural boundary that must stay intact.
  4. State the done-when end state, including any durable inventory target when page consolidation or replacement is part of the slice.
  5. Name the authoritative validation command and any repo-shell git verification command that must be reported.
  6. Require the standard return format with exact reporting of files changed, commands run, and outcomes.

Boundary between AGENTS and the task prompt

AGENTS.md holds durable repo rules such as execution-environment policy, validation triage, documentation-surface distinctions, and return-shape conventions. The prompt should stay slice-local: the current task, the file boundary, the done-when state, the validation command, any inventory target, and the completion contract.

Stable handover rules

  • Use one Codex thread for one slice only.
  • Do not send placeholders when the task is already concrete enough to fill in.
  • Prefer an explicit file boundary over a broad subsystem request.
  • Keep AGENTS.md authoritative for repo-wide execution, validation, and environment-triage rules; do not restate long host-vs-repo-shell guidance in slice prompts.
  • Prefer nix develop --command git ... when a prompt asks Codex to show repo diff or status.
  • Prefer fewer authored HyperDoc guidance files over preserving prompt iteration history as durable pages.
  • Keep adjacent documentation edits tightly coupled to the slice that justified them.
  • Ask for exact validation outcomes rather than generic success language.

Inventory outcome

For this Codex-guidance cluster, the durable target is explicit: keep exactly one authoritative page, Codex handover for HyperDoc, and keep exactly one minimal non-authoritative continuity shell at the immediately previous canonical title, Best handover to Codex for HyperDoc. That shell remains by design, not as cleanup debt. Do not create or restore any additional Codex-guidance pages; preserve older iteration history in git, counterpart notes, or FedWiki journals instead.

Docs coupling
- Update HyperDoc pages only when they directly document this slice.
- Keep any adjacent documentation edit directly coupled to the task that justified it.

Validation
- Authoritative repo-shell validation:
  nix develop --command [exact command]
- Repo diff or status, if needed:
  nix develop --command git [diff|status] -- [exact files]

Return format
- Surface answer
- Artifact answer
- Exact files changed
- Conventional commit message
- Remaining risks or unresolved edges

History handling

Do not keep multiple authoritative HyperDoc prompt pages that differ only by iteration wording such as best, updated, or v2. Preserve working history in counterpart working notes, FedWiki journals, or git history, while keeping this page as the single durable reference point. For this cluster, the immediately previous canonical title remains as one intentional minimal continuity shell and no more.
