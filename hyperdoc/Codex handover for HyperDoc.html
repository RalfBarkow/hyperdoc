Codex handover for HyperDoc

hyperdoc

This page is the single canonical durable guidance for handing a HyperDoc slice to Codex. Keep repository-wide operating rules in AGENTS.md, use a manifest-qualified Repomix snapshot bundle for repository context, and use the task prompt only for the current slice contract and end-state inventory target. A lone Repomix output file is never authoritative.

Canonical structure

  1. State one concrete task slice and keep one Codex thread on that slice only.
  2. Name the exact files in scope and the exact paths out of scope.
  3. Record the architectural boundary that must stay intact.
  4. State the done-when end state, including any durable inventory target when page consolidation or replacement is part of the slice.
  5. Name the authoritative validation command and any repo-shell git verification command that must be reported.
  6. Require the standard return format with exact reporting of files changed, commands run, and outcomes.

Boundary between AGENTS and the task prompt

AGENTS.md holds durable repo rules such as execution-environment policy, validation triage, documentation-surface distinctions, and return-shape conventions. A manifest-qualified snapshot bundle is the authoritative read-only packed repo context when supplied. The prompt should stay slice-local: the current task, the file boundary, the done-when state, the validation command, any inventory target, and the completion contract.

When a slice touches executable prompt design, page-to-topicmap projection, FedWiki story generation, or split inspector views, use the compact prompt reference S-Expression Prompt Split View Contract. That page points to the durable S-expression program contract without duplicating the full repo-wide rule in AGENTS.md.

Repo truths to preserve

  • HyperBook is the abstract page-and-link substrate; HyperDoc is the documentation-oriented realization layered on top of it.
  • Keep authored pages, stable topic objects, and live runtime objects distinct unless the slice explicitly bridges them.
  • When a slice touches Connect, Dock, Annotation, Touch-Fahrplan, or DMX association authoring, keep the Touch-Fahrplan-first route metaphor durable: topics are stations, associations are routes between stations, the route is itself first-class, and Lay route is the preferred user-facing label.
  • Use drag-to-connect only for low-level mechanics and two-tap route-laying for the non-drag fallback; do not use plain swipe as the canonical term.
  • Preserve the distinction between laying a route and following a route, and keep richer route/traversal UI in the pane body or another dedicated surface while the Dock remains the capability-introduction layer.
  • For touch-first McCLIM slices, treat the gesture grammar as the operational form of Touch-Fahrplan route language: gestures are the input language, stations/routes are the conceptual layer, presentation-backed semantic objects are the nouns, CLIM commands are the verbs, and command execution is the only way application state changes.
  • Keep Browse mode safe by default: plain drag previews or reveals a route, while Lay route requires explicit press-then-drag or Author mode. Use drag-to-connect only for the underlying mechanic.
  • Interactive targets in this area should be presentation-backed doc-node, doc-link, doc-collection, doc-view, doc-anchor, doc-tool, doc-selection, or doc-blank-area objects, with dispatch handled through translators and command objects rather than hidden widget mutation.
  • Keep core :hyperdoc loadable without Zotero; optional Zotero behavior belongs in :hyperdoc/zotero and :hyperdoc/inspector/zotero.
  • HYPERDOC_ENABLE_ZOTERO is the authoritative runtime seam for Zotero; disabled mode should surface explicit unavailable objects rather than crashing or pretending live behavior exists.
  • Bibliography authoring is review-first: live/import objects and generated plans may propose materialization, but they must not silently rewrite authored pages or topics.lisp.
  • Keep deployment-aware seams explicit around public origin, reverse-proxy domain, data directory, git repository root, and optional Zotero enablement.

Stable handover rules

  • Use one Codex thread for one slice only.
  • Do not send placeholders when the task is already concrete enough to fill in.
  • Prefer an explicit file boundary over a broad subsystem request.
  • Keep AGENTS.md authoritative for repo-wide execution, validation, and environment-triage rules; do not restate long host-vs-repo-shell guidance in slice prompts.
  • Read the supplied snapshot manifest first. Trust only the numbered parts it names, after their sizes, hashes, file-section counts, required-file coverage, and closing boundaries validate.
  • Prefer named validation surfaces and smoke checks over ad hoc success claims.
  • When authoritative repo-shell validation uses sbcl --eval, require ASDF before any asdf:load-system form: use --eval '(require :asdf)' first instead of making bare asdf: the first package read.
  • Prefer nix develop --command git ... when a prompt asks Codex to show repo diff or status.
  • Prefer fewer authored HyperDoc guidance files over preserving prompt iteration history as durable pages.
  • Keep adjacent documentation edits tightly coupled to the slice that justified them.
  • Ask for exact validation outcomes rather than generic success language.
  • When prompts describe route authoring, prefer Touch-Fahrplan route-laying language over generic connect/swipe/provider-first wording.
  • Distinguish page genre in prompts: reference/contract pages for definitions/contracts/inventories, walkthrough example pages for story-driven click-through demonstrations.
  • If the user asks for an example page, default to a walkthrough example page with Goal, Starting situation, step sequence, Expected result/Why this matters, and Boundary.
  • Require per-step Click / Observe / Why this matters wording for walkthrough examples; reject bare object-list pages even if links are clickable.
  • For mutation/rewrite/debug walkthroughs, require explicit before -> cause -> action -> after payoff.

Manifest-qualified snapshot bundle

Repository context is transferable only as a bounded bundle. The normal handover consists of the stable core pack and exactly one task-specific pack such as roots, their detailed pack manifests, and one top-level bundle manifest that hashes those manifests and names every supplied part in delivery order. A stale unnumbered output, an isolated numbered part, or a packed file absent from the top-level manifest is supporting evidence at most, never the authoritative snapshot.

  1. Generate the stable core with tools/repomix-pack.sh core.
  2. Generate one task pack, for example tools/repomix-pack.sh roots.
  3. Create the single transfer authority with tools/repomix-snapshot-manifest.sh bundle roots-handover repomix-output-hyperdoc.roots-handover.manifest.json repomix-output-hyperdoc.core.manifest.json repomix-output-hyperdoc.roots.manifest.json.
  4. Supply the top-level manifest, the two pack manifests it hashes, and every numbered part it names.
  5. Run tools/repomix-snapshot-manifest.sh verify repomix-output-hyperdoc.roots-handover.manifest.json before treating any part as context.

Transfer-targeted configurations use stable source ordering rather than Git change-frequency ordering, exact uncompressed Common Lisp and authored HTML, a documented token budget, and a 500,000-byte split limit. The pack runner verifies actual part sizes because split configuration alone is not delivery evidence. Pack manifests record the Repomix version, HEAD, short Git status, configuration hash, ordered parts, byte and line counts, SHA-256 hashes, file-section counts, required-file coverage, and complete closing-boundary checks. Each pack manifest also records the source state under repository.source_state. Its schema is hyperdoc-repomix-source-state/v1; its fingerprint is a Git object ID over the observed index metadata, tracked worktree bytes, and non-ignored untracked files. Verification recomputes this fingerprint and rejects the manifest after any such source-state change; ignored files remain outside the fingerprint. Bundle verification recursively verifies every child pack manifest, so a stale child source state invalidates the bundle. The top-level manifest covers both pack manifests and all of their parts. No manifest receives completion_status: complete until its checks pass.

This boundary responds to an observed transfer failure: a delivered 741,376-byte file contained one assets/dm6-elm/app.js section and stopped inside that generated bundle even though the local full snapshot continued through its final file and closing fence. Size similarity must not be used as a substitute for hash and boundary verification. The generated DM6 application bundle is excluded from core, Roots, validation, every other non-DM6 task pack, and the archival full pack. Its implementation evidence belongs only in the dedicated dm6 pack.

Touch-first prompt-local rule

When a slice touches touch-first McCLIM interaction, keep the prompt-local form shorter than AGENTS.md but preserve the same route-language primacy: Touch-Fahrplan stations/routes first, gesture grammar second, command dispatch as the semantic authority, safe Browse-mode defaults, and explicit distinction between route preview, Lay route, and Follow route.

  • Prefer Touch-Fahrplan wording first: stations, routes, Lay route, Follow route, route preview. Use drag-to-connect only as the mechanic term and two-tap route-laying as the non-drag fallback.
  • Use doc-node, doc-link, doc-collection, doc-view, doc-anchor, doc-tool, doc-selection, and doc-blank-area as the semantic target vocabulary.
  • Use the normalized gesture names from AGENTS.md, including hd-tap, hd-double-tap, hd-press, hd-drag, hd-swipe-*, hd-pinch-*, hd-two-finger-tap, hd-lasso, and hd-scrub.
  • Map gestures to CLIM commands rather than direct UI mutation: tap focuses, double-tap opens, press shows actions, plain drag previews or reveals a route, press-then-drag lays routes, tap on a route follows it, and blank-area gestures handle safe navigation and clearing.
  • Keep destructive or authoring semantics off plain tap; relation creation requires explicit arm state or Author mode.
  • Frame implementation in McCLIM terms: presentation-backed output, translators, gesture names, pointer tracking, command objects, and redisplay.
