Mech Plugin Progress March 2026

This page records the current state of the local repository ~/workspace/wiki-plugin-mech with specific attention to upstream commit 4ed345e1aa902947173c34a71e0114da320ba75a on upstream/main.

The latest upstream commit is systematic tally; download in api. It is a focused change in src/client/blocks.js, but it matters mainly as the final step in a more credible maintenance sequence. See Mech Credible Maintenance Story for that sequence in the terms of Drawing Automation.

Current local plugin shape

The local Mech repository is already structured as a modernized plugin rather than a single script. It has:

  • client entry points such as src/client/mech.js and src/client/blocks.js
  • a small API surface exposed through api
  • tests for parsing, edges, folds, neighborhoods, and walk scope
  • wiki pages such as About Mech Plugin and Catalog of Mech Blocks

That means the interesting question is not whether Mech exists, but how its workflows are being made more inspectable and more report-oriented.

What commit 4ed345e changes

Commit 4ed345e changes only one file, but the conceptual shift is clear.

  • download is added to the exported Mech api instead of being local to the PRINT block.
  • PRINT stops keeping only a flat missing list.
  • PRINT now accumulates a structured tally with categories for missing pages, referenced domains, item-type wishes, and runtime errors.
  • PRINT can publish those findings into state.items as report objects rather than only burying them in console output or one generated HTML file.

In short: the commit turns PRINT from a mostly generative step into a generative-plus-diagnostic step.

Before and after

Before this commit, the block mostly did three things:

  1. collect story slugs
  2. collect garden slugs
  3. record only one broad failure bucket: missing pages

After this commit, the same process also keeps a more systematic account of what happened while materializing the neighborhood:

  • which domains were actually referenced
  • which slugs were missing, grouped by section
  • which non-paragraph item types were encountered and therefore represent rendering wishes
  • which runtime errors occurred while fetching or printing pages

Why this matters

This is aligned with the Story Neighborhood Workflow. A workflow like Story -> WALK -> PRINT -> PREVIEW is stronger when the print stage not only emits an artifact but also emits a structured account of its own boundaries and losses.

The new tally categories are especially important because they separate different kinds of editorial work:

  • missing pages are neighborhood boundary problems
  • domains show federation spread
  • item type wishes show rendering gaps
  • errors show program failures rather than editorial boundaries

That separation is the real progress. It makes the output more inspectable and more actionable.

Connection to HyperDoc and HyperBook

This is relevant for HyperDoc work because the same shift is needed here as well: workflows should surface structured findings as objects, not only as files or ad hoc console logs.

  • Story-neighborhood export should produce diagnostics alongside artifacts.
  • Rendering wishes should become inspectable categories, not incidental observations.
  • Federation spread should be made visible as domains and source sites.
  • Errors should be distinguished from boundary conditions.

In that sense, 4ed345e is small in code but significant in workflow semantics.

Current limitations still visible

The commit does not solve everything.

  • PRINT still privileges paragraph text in the generated draft.
  • non-paragraph items are only tallied as wishes, not rendered.
  • the tally is still assembled inside the block implementation rather than exposed as a first-class report object API.
  • the underlying workflow is still browser/plugin-centric rather than inspectable in Lisp object terms.

So this is progress, not completion.

Pragmatic reading of the commit

The key move is: make the printing workflow account for what it could not do, not just what it successfully emitted.

That is the same discipline needed for journal checking, collaborative-link resolution, and neighborhood-aware publishing more generally.
