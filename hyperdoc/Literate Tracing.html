Literate Tracing

Literate Tracing is a recent execution-centered documentation approach. The paper and project materials describe it as explaining software through annotated, concrete execution traces rather than through source exposition alone.

For HyperDoc, this matters as adjacent reference material for explanation from execution, execution evidence objects, and persistence of investigation context. It is not the same as HyperDoc's Mech or inspector seams, but it sharpens the same architectural question: how much of the account of execution can be produced from execution itself instead of reconstructed afterward.

What the paper claims

The paper defines a literate trace as an explanation of a software system using annotated, concrete execution traces. The related project material presents TReX as the tooling surface for producing interactive visual traces.

Those claims should stay attributed. HyperDoc can use them as a conceptual comparison point without silently converting them into canonical repository truth about all execution-trace systems.

Literate tracing versus retrospective explanation

The useful contrast for HyperDoc is not primarily with static documentation. It is with a retrospective explanation pass that tries to reconstruct behavior after execution has already collapsed into output. Literate Tracing argues for explanation that stays grounded in real executions instead of describing systems only at a distance.

That makes it close to HyperDoc's own direction. The same-protocol view says that execution and explanation should be twin outputs of one semantic event. Literate Tracing approaches that question through annotated traces; the Mech and inspector work in this repository approach it through runtime dispatch seams and inspectable runtime objects.

Why it matters here

HyperDoc already has the raw ingredients for execution-grounded explanation: dispatch seams, render events, run records, findings tallies, and a growing vocabulary for preserving investigation context. What it still lacks in many places is a stronger published form for that evidence.

Literate Tracing is useful here because it makes the missing step legible. Raw traces are not enough, but neither is narrative added later. The richer form is an execution-grounded account that stays close to the real run while remaining inspectable and explainable as a document surface.

Boundary with HyperDoc

HyperDoc does not currently implement a full literate-trace tool. Its recent INSPECTOR-PERF lines are still a weaker form: they are already execution evidence, but they remain console-bound and transient. That makes them a precursor, not yet the same thing as a published annotated trace.

The practical consequence is modest but important. HyperDoc should not treat execution evidence as exhaust. It should keep promoting that evidence toward first-class objects and toward document surfaces that can explain those objects without needing a second forensic pass.
