A framework for maintaining the coherence of a running Lisp

hyperdoc

This page now imports one narrow but real part of Drew McDermott's 2005 Lisp Conference paper: the chunk model and the paper's freshness vocabulary for keeping those chunks up to date. It still does not claim that the whole paper has been imported. The durable anchor here is the paper's account of what counts as a chunk, how given and derived chunks differ, and why that matters in a long-lived Lisp image.

What McDermott means by a chunk

In the imported portion of the paper, a chunk is a piece of information in a particular state, form, or location. The point of the definition is that the same broad subject matter can appear as different chunks when its form or location changes.

The paper's examples make the scope concrete:

  • a file on disk,
  • that Lisp file after it has been loaded into memory,
  • a subset of the S-expression handlers currently installed in the running image,
  • and an association between a source directory and a compile directory.

That breadth is exactly why the model is useful for a running Lisp. A live session does not only contain source files and functions. It also contains registries, directory relations, loaded definitions, and other pieces of state that can become stale independently.

The paper also treats manages as an explicit relation, not just a casual verb. One can speak loosely about the chunks a system manages, or more declaratively say that a chunk is managed when the coherence machinery takes responsibility for keeping it current. Chunks that exist but are outside that responsibility are better understood as dormant rather than as magically current.

Given and derived chunks

The imported distinction is asymmetric. A given chunk is supplied to the system as an input or observed state. A derived chunk is produced from other chunks and therefore depends on them.

For HyperDoc, a source file, a page file on disk, or a directory relation can be treated as given. A topic index in the running image, a registered runtime object, or a loaded page surface is derived from those inputs. The paper's vocabulary matters because it stops us from calling all of these things “state” and then guessing what must be refreshed.

Once the distinction is explicit, a derived chunk can be described by its basis, the chunks it depends on, and by a deriver, the mechanism that rederives it. Some derivations also need an update basis: other chunks that must be available during the refresh even when they are not the lasting product of that refresh.

What “up to date” means

The paper's freshness model is not just “does the thing exist”. A given chunk is current only insofar as the chunk still represents the source state it is meant to stand for. A derived chunk is current only when it still reflects an up-to-date basis. If one of its supporting chunks is fresher than the derived chunk, then the derived chunk is stale even if it is still present in the image.

That is the part worth importing into HyperDoc: freshness is a dependency claim. Existence alone is too weak. A topic registry entry, a page index, or a live handler table can all continue to exist while no longer being coherent with the source or runtime inputs from which they were derived.

Why the model matters for a running Lisp

A long-lived Lisp image accumulates multiple forms of the “same” information: source files, compiled outputs, loaded definitions, dynamic tables, and local associations that tell the system where to find or rebuild things. McDermott's chunk model makes those forms explicit instead of treating reload as an ad hoc ritual.

That matters because running image coherence is about the internal consistency and intelligibility of an evolving live image. It is therefore distinct from Live image versus durable source, which is about rebuild authority and durable source of truth across sessions. The chunk model helps explain the former. It does not remove the need for the latter boundary.

Why this is relevant to HyperDoc

HyperDoc works in exactly the kind of environment where this vocabulary helps:

  • a long-lived Lisp image used for iterative development,
  • reload and revise workflows where definitions and indexes move at different speeds,
  • derived state such as topic registries, page availability, and runtime support surfaces,
  • and a need to track dependencies explicitly instead of relying on manual “repair” sequencing.

The local follow-on notes already start operationalizing this import. McDermott Running Image Coherence Crosswalk maps the vocabulary into the existing corpus. Core Chunk Classes sketches the minimal executable kernel for chunks, basis, update basis, derivers, and freshness checks.
