Portable examples in HyperDoc

hyperdoc

Portable examples are example functions that belong to the separate ASDF system :hyperdoc/examples rather than to the minimal base :hyperdoc system. In this repository, that means they are part of the existing system-scoped examples model, not a root-global pool of example functions that should always be present in every running image.

The architectural point is not merely organizational convenience. A example system boundary lets HyperDoc keep its base image small and predictable while still exposing richer example material when the corresponding ASDF subsystem is explicitly loaded. Portable examples are therefore an ASDF design choice about scope and load boundaries, not an ad hoc implementation quirk.

Base, portable, and ops-specific example layers

HyperDoc currently uses three distinct example layers. Base examples belong to :hyperdoc and are expected to be available whenever the minimal core system is loaded. Portable examples belong to :hyperdoc/examples and stay outside the base layer until that system is requested. Ops-specific examples belong to :hyperdoc/examples/ops and remain a still narrower layer for local or operational workflows.

This is best understood as example system layering. The layers are cumulative, but not identical. Loading :hyperdoc/examples should expose the portable example scope without silently changing which examples count as part of base :hyperdoc. Loading :hyperdoc/examples/ops should expose its own ops-specific layer without retroactively redefining the earlier boundaries.

Why the load boundary matters

HyperDoc's examples surfaces are scoped by ASDF system. That means example presence in the image should track the systems actually loaded into that image. If portable examples were loaded eagerly with base :hyperdoc, the system boundary would become misleading: the image would look as if the portable layer were part of the base system even though it is defined and maintained separately.

The separation also keeps repo-local workflows honest. Base HyperDoc can stay focused on the small set of examples that belong to the core system, while the portable layer can depend on additional translation or FedWiki-facing logic without forcing those dependencies into every core-only session.

Why the discovery boundary matters

Lazy example discovery is the discoverability consequence of that same ASDF design. Example discovery should report only what the current image has actually loaded for the requested system. Before :hyperdoc/examples is loaded, discovery for that system should remain empty. After it is loaded, the portable examples should become visible as discoverable runnable checks.

This keeps the Examples surface meaningful. A system-scoped examples view should show the examples that belong to that system and are currently available to run. It should not guess across unloaded layers or flatten all example registrations into one root-wide registry.

Relation to the existing Examples surface

Portable examples still use the same run action for examples as the base layer. They are not a second execution mechanism. What changes is which examples become discoverable under which ASDF system and when they enter the image. In other words, the run affordance stays the same, but the owning ASDF system and its discovery/load boundary remain explicit.

That is why the best place to understand portable examples is inside the existing ASDF systems as scope model. HyperDoc does not need a new global examples browser for this distinction. It needs the system-scoped Examples surface to remain faithful to the repo's layered ASDF structure.
