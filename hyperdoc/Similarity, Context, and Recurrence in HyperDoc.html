Similarity, Context, and Recurrence in HyperDoc

hyperdoc

A useful code-shape survey needs more than counts. It needs recurrence, enclosing context, and enough structural similarity to distinguish a one-off expression from a recurring codebase pattern.

Inspectable objects

  • Structural recurrence
  • Usage view
  • Nesting view
  • Similar idioms
  • Survey-driven refactoring
  • HyperDoc code survey

Counts alone are too weak

A frequent operator or helper name is only a starting signal. Counts can tell us where to look, but not whether a recurring form is idiomatic, accidental, historically layered, or already the clearest available shape.

Context changes the reading

The same local form can mean different things inside a top-level defview, a mapping helper, a restart branch, or a test harness. That is why a useful survey needs a nesting/context view rather than only a list of hits.

Similarity makes recurrence actionable

A similar-forms view is the point where idiomatic feedback becomes stronger than a nitpick. If several occurrences normalize to the same structural pattern, then the reviewer can talk about a recurring shape instead of a lone local line.

Clusters are evidence, not verdicts

A cluster summary should never be mistaken for an automatic judgment. The cluster shows recurrence. A human editorial note explains what that recurrence seems to mean in the contexts where it appears.

A cluster records a recurring code shape. An editorial note records a human interpretation of that shape. The note may recommend refactoring, contextual caution, or explicit retention. A repeated form is not a defect merely because it recurs.

That means idiomaticity is editorial, not automatic. A survey without notes is only an inventory.

What this would mean in HyperDoc

HyperDoc does not yet compute these clusters automatically. As a proposal, though, a HyperDoc code survey should treat similarity as the main bridge from micro-cleanup to survey-driven refactoring.

  • Usage evidence: where does the pattern occur and in which file/system?
  • Context evidence: what enclosing definition or helper layer shapes the meaning?
  • Similarity evidence: which other occurrences share the same normalized code shape?
