Process model

  1. Each SBCL process has its own image state and does not share loaded definitions with other processes.
  2. asdf:load-system affects only the current process image.
  3. Package/function visibility depends on what has been loaded in that exact process.
  4. A Playground/CLOG event handler runs inside the server process and sees only that process state.

Operational checks

(require :asdf)
(asdf:find-system :hyperdoc)
(asdf:load-system :hyperdoc)
(fboundp 'hyperdoc::journal-checker-commit-gate-topic)

If this succeeds in one shell but fails in the UI, the UI is connected to a different SBCL process/image.

Running process image versus bootstrap image

A running HyperDoc server process is one instance of image-oriented development: it has current package state, loaded systems, active threads, and mutable runtime data. That should not be confused with the bootstrap image state used while building SBCL itself.

Rhodes's SBCL bootstrapping paper is useful here because it distinguishes the live host image used during build from the durable source path that must still rebuild cleanly. HyperDoc's own server/runtime workflow follows the same boundary in miniature: the current process image is valuable for exploration, debugging, and deployment, but it is not the durable source of truth for the repository.

Failure signatures

  • Package ... does not exist: system/package not loaded in this process.
  • function ... is undefined: symbol may exist but function definition is absent in this image.
  • COMPILE-FILE-ERROR while loading: dependency resolution or compile-time failure in current process context.

Runtime policy

  • Isolate risky evaluation in worker processes or sandboxes only where needed.
  • Keep page identity/content in FedWiki; keep runtime execution policy in HyperDoc/inspector tooling.

This split keeps collaborative content durable and journaled while making execution behavior explicit, inspectable, and replaceable without rewriting page identity.
