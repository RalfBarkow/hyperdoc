Drawing Automation and review materialization

hyperdoc

Ward's Drawing Automation note is directly relevant here. It shows a pattern where durable annotations embedded at the point of interaction are turned into automatically maintained diagrams, diffable in GitHub, and correctable through ordinary edit and pull-request workflows.

Why it matters for the current discussion

The current discussion is about turning review prose into inspectable review points and then into materializable issue objects. Drawing Automation adds one more important move:

annotated source surface → extracted relations/events → generated visual maintenance surface

That is very close to:

review prose → extracted review points → review-materialization issues → generated trace/diagram surface

Relevant carry-over from Drawing Automation

  • Annotations live close to the place where the important interaction happens.
  • The generated diagram is derivative, not the primary authored artifact.
  • The SVG diff becomes part of the maintenance story.
  • Errors in the model are corrected by editing the source annotation, then regenerating.
  • Different perspectives can be rendered from the same underlying relation stream.

What the equivalent would be here

For HyperDoc review materialization, the authored source would not be shell-script comments but durable review points or issue objects. The generated outputs would be:

  • a review-materialization issue inspector
  • a review-materialization trace
  • a generated SVG or similar diagram of source page → target page/section → proposed change → verification

Perspective is the key imported idea

Ward's examples use perspectives such as Index, Query, Status, and Debug. That same design move should be reused here. For example, one review bundle could be rendered from several perspectives:

  • Authoring — what pages/sections need edits
  • Topics — what topic merges, aliases, or new factories are proposed
  • Lookup — what review points correspond to missing pages or topic links
  • Verification — what smoke tests or acceptance checks are still missing

Why this is stronger than prose review alone

A prose review mixes findings, evidence, recommendations, and ordering. Drawing Automation suggests separating those: author the durable relation/event annotations once, then derive multiple maintenance surfaces from them. That reduces duplication and makes correction local.

Suggested HyperDoc vocabulary additions

  • Drawing Automation as a topic
  • Review points as a topic
  • Generate review materialization diagram as an operation
  • Review materialization issue surface as the inspectable page/object

Concrete relation to the Drew slice

The Drew review could become the first worked example. Each accepted review point would be encoded as a small structured object with: source page, source section, target page, target section, classification, suggested materialization, and verification. From that bundle, HyperDoc could generate:

  • a list view of open review points
  • a page-lookup-issue-like inspector for each point
  • a diagram showing how the review changes propagate across pages, topics, and tests

Minimal first slice

  1. Add a durable topic/page pair for Drawing Automation.
  2. Define one machine-readable review-point structure.
  3. Render one issue inspector from that structure.
  4. Render one simple SVG from the same structure.
  5. Use Git history or generated diff surfaces to compare revisions of the review diagram.

Bottom line

Yes: Drawing Automation is not just adjacent inspiration. It gives the missing automation pattern for the review-materialization work: keep the authored semantics close to the source, generate visual maintenance surfaces automatically, and let corrections happen by editing the underlying review-point annotations rather than hand-redrawing the diagrams.
