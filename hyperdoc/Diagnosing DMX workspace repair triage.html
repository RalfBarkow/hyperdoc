Diagnosing DMX workspace repair triage

hyperdoc

This page adds the read-only batch companion to Diagnosing DMX workspace assignment and topicmap placement. Instead of opening one DMX object, it reads the selected topicmap projection from /topicmaps/919822?children=true, reuses the same per-topic diagnostics model, and filters to the actionable defect class: HyperDoc-owned, in topicmap 919822, workspace assignment missing.

In the broader surface vocabulary, this page is the worked diagnostic surface adjacent to the mutation surface and the related failure surface. In the broader boundary vocabulary, it is the adjacent read-only diagnostic surface for the same worked transition boundary that later blocks or crosses in the repair and journal flows.

How to invoke the batch view

Use either of these runtime handles:

  • (make-dmx-workspace-repair-triage :topicmap-id 919822)
  • (make-dmx-shared-workspace-repair-triage)

The second helper is the convenience entrypoint for the context-window shared blackboard. The inspector view title is Repair triage.

What the triage view shows

The batch view remains read-only and keeps workspace assignment distinct from topicmap placement. The matching mutation surface is now the separate authenticated Repair console tab on the same object. It shows at least:

  • topic id
  • title or value
  • ownership classification
  • whether the object is in the selected topicmap
  • workspace assignment
  • derived status

The raw evidence remains inspectable in the separate Raw projection tab, which exposes the source endpoint, the raw topicmap projection, and the enumerated topic ids used for the triage. The repair console uses that same filtered backlog but still keeps explicit authentication and mutation separate from the diagnosis view.

Canonical status vocabulary

Treat the shared-workspace backlog as a narrow state vocabulary, not as one generic list of broken topics. The canonical statuses for this workflow are:

  • healthy: HyperDoc-owned, assignment present as 919815, and topicmap presence intact
  • foreign-no-action: visible in the shared topicmap but not HyperDoc-owned for this guarded repair boundary
  • in-topicmap-but-unassigned: HyperDoc-owned, visible in 919822, and missing workspace assignment
  • credentials-pending: the object still needs guarded assignment repair, but the first live write attempt hit the authentication boundary
  • repair-succeeded: guarded assignment repair completed and read back cleanly
  • repair-failed-non-auth: guarded repair crossed auth but failed later for another reason

The ownership filter for this backlog must recognize both hyperdoc:mcp/workspace-annotation/ and hyperdoc:mcp/workspace-journal/ as HyperDoc-owned families. A classifier that misses those URI prefixes creates a false foreign-no-action result.

Why this view exists

The single-object diagnostics view proves the distinction for one object. The triage view turns the same distinction into an inspectable maintenance list: “show the HyperDoc-owned objects that are visible in the shared blackboard but still need authenticated workspace-assignment backfill.”

That is why the filter is intentionally narrow. It is not a general list of all unassigned objects, and it does not mix repair actions into the read-only triage table.

Operator rule after the first 401

If the first live workspace-assignment repair attempt returns 401 on the guarded PUT /workspaces/<workspace>/object/<topic> boundary, stop retrying the same server-side service-auth path for that object. Reclassify the object as credentials-pending and move to the explicit-auth Repair console boundary for the next live attempt.
