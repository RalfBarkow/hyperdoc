Layout as Topicmap

hyperdoc

Page genre: reference/contract. Inspector layout is modeled as first-class topics and relations so a visible chrome move can be inspected as a patch before renderer or durable layout mutation.

Claim

The reel controls are not another isolated CSS exception. They are a layout topic whose parent box can change through a visible, inspectable patch while native horizontal scrolling and button accessibility remain invariant.

Content Model

  • layout-topic: selector, element id, class list, bounding box capture status, scroll context, role/kind, evidence, and stability classification.
  • layout-relation: containment, control, and scroll relations between layout topics.
  • layout-topicmap: immutable snapshot of the reel/inspector-pane subset.
  • move-topic-into-box-patch: before topology, after topology, source evidence, target evidence, proposed implementation effect, and preview/apply policy.
  • layout-rule: named invariant evaluator for deciding whether a patch can be previewed, repaired, or blocked.
  • layout-rule-result: pass/repair/fail status, evidence, renderer effects, and optional failure object for one rule.
  • layout-repair-plan: rule-derived plan for a layout patch, including rule results, renderer effects, failure modes, and preview/apply boundary.
  • layout-renderer-effect: declarative preview/apply effect consumed by the renderer instead of direct ad hoc DOM mutation.

              :disabled-boundary-states
              :keyboard-reachability))

Rule-Based Repair Layer

Direct manipulation creates the patch. The rule engine derives a layout-repair-plan from that patch before the renderer previews or applies anything. A failed rule produces a failure object; it does not silently corrupt layout.

  • Native horizontal overflow is preserved.
  • Previous/next buttons remain real labelled buttons.
  • Controls remain keyboard reachable.
  • The pane reserves bottom clearance for a local control rail.
  • The control rail remains chrome, not document content.
  • Preview does not become durable state.
  • Apply creates a durable override object or explicit replayable artifact.

Inspector View Specification

The Layout topicmap view on a HyperDoc object renders the topics as boxes, the relations as tables, and the standard contract sections: Content Model, Box Contract, Priority Policy, Actions, Evidence, and Failure Modes. Dragging hyperdoc-reel__buttons onto inspector-pane reveals an inspectable move-topic-into-box-patch and a derived layout-repair-plan.

The repair plan exposes these views: Overview, Before topology, After topology, Rule results, Renderer effects, Evidence, Failure modes, and Preview/apply boundary.

Preview and Apply Boundary

  • Preview consumes preview-phase layout-renderer-effect objects only.
  • Preview may align the existing control rail over the pane as runtime evidence.
  • Preview reserves bottom clearance in the active pane body so the rail does not cover readable content.
  • Preview records live selector, class, bounding box, and scroll-context evidence.
  • The DOM is not the source of truth; the source of truth is the Lisp layout object and patch object.
  • Apply consumes an apply-phase durable-override renderer effect and records replay metadata for the inspectable patch object.

Invariants

  • The existing overflowable reel model remains intact.
  • .hyperdoc-reel__scrollable remains native horizontal overflow and preserves scrollLeft.
  • Previous/next remain real keyboard-focusable buttons.
  • Existing labels and disabled boundary states remain intact.
  • The patch has before/after topology and source/target evidence.

SHOP3 Task

(:task layout-topicmap-move-reel-buttons-into-pane)

(:method layout-topicmap-move-reel-buttons-into-pane
  ((:precondition
    (and (layout-subject hyperdoc-reel)
         (layout-topic hyperdoc-reel__buttons)
         (layout-topic inspector-pane)))
   (:ordered-tasks
    (!capture-layout-snapshot hyperdoc-reel)
    (!project-layout-snapshot-to-topicmap)
    (!render-layout-topicmap-view)
    (!enable-drag-source hyperdoc-reel__buttons)
    (!enable-drop-target inspector-pane)
    (!create-move-topic-into-box-patch hyperdoc-reel__buttons inspector-pane)
    (!preview-layout-patch)
    (!verify-reel-accessibility-invariants)
    (!commit-periodically))))

SCXML Sketch

<scxml initial="capture-layout">
  <state id="capture-layout">
    <transition event="snapshot.ready" target="render-topicmap"/>
  </state>
  <state id="render-topicmap">
    <transition event="drag.started" target="dragging-topic"/>
  </state>
  <state id="dragging-topic">
    <transition event="drop.accepted" target="create-patch"/>
    <transition event="drop.rejected" target="render-topicmap"/>
  </state>
  <state id="create-patch">
    <transition event="patch.created" target="inspect-patch"/>
  </state>
  <state id="inspect-patch">
    <transition event="preview.requested" target="preview-patch"/>
    <transition event="cancel" target="render-topicmap"/>
  </state>
  <state id="preview-patch">
    <transition event="invariants.pass" target="ready-to-apply"/>
    <transition event="invariants.fail" target="inspect-patch"/>
  </state>
  <state id="ready-to-apply">
    <transition event="apply" target="done"/>
  </state>
  <final id="done"/>
</scxml>

Rule-Based Repair SCXML Sketch

<scxml initial="patch-created">
  <state id="patch-created">
    <transition event="derive.requested" target="derive-rules"/>
  </state>
  <state id="derive-rules">
    <transition event="rules.pass" target="previewable"/>
    <transition event="rules.fail" target="blocked"/>
  </state>
  <state id="previewable">
    <transition event="preview" target="preview-active"/>
    <transition event="cancel" target="patch-created"/>
  </state>
  <state id="preview-active">
    <transition event="apply" target="durable-override"/>
    <transition event="revert" target="previewable"/>
  </state>
  <state id="blocked">
    <transition event="inspect-failure" target="patch-created"/>
  </state>
  <final id="durable-override"/>
</scxml>

Goldberg Questions

  • What are the visible layout parts?
  • Which box owns which child?
  • Which object controls scrolling?
  • Which box is the user actually reading in?
  • Which part is an affordance rather than content?
  • What changes when the Buttons topic moves into the Pane topic?
  • What invariant must not be broken?
  • What evidence proves the patch is only previewed?
  • What evidence proves the patch is durable when applied?
  • Where is the source of truth: DOM, layout snapshot, or Lisp layout object?
  • How can a reader undo or inspect the layout patch?
  • How does this generalize from reel buttons to other pane chrome?

Boundary

This first slice covers the reel controls and inspector pane only. It does not replace the accessible Reel implementation, introduce a custom carousel, or generalize arbitrary layout editing beyond rule-based repair of the single hyperdoc-reel__buttons into inspector-pane move.
