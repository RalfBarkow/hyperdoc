DMX note read/write boundary

hyperdoc

DMX note read/write boundary records the smallest stable contract HyperDoc can rely on for note mutation: read the note through the full parent-note projection, but write by updating the parent dmx.notes.note payload. The text child is replaced through the parent update; it is not a stable in-place mutation target on its own.

Expectation preserved

  • Expectation: the visible dmx.notes.text child topic could be mutated directly in place.
  • Observed reality: the reliable public write boundary is the parent dmx.notes.note, not the child topic.
  • Why the expectation was plausible: direct machine-readable reads expose the child topic id and value.
  • Classification: disappointed expectation.
  • Resolution: update the parent note with the new child value and reread the parent to verify the persisted result.

Read boundary

  • Read the full note through /core/topic/<id>?children=true&assocChildren=true.
  • Treat children["dmx.notes.text"] as the readable note body projection.
  • Use direct child-topic reads for diagnosis only, not as proof of the write boundary.

Write boundary

  • Write the parent dmx.notes.note payload.
  • Set the updated note body in children["dmx.notes.text"].value.
  • Expect the text child topic to be replaced or reassigned during that parent update.

Verification boundary

After a live note write, reread the parent note through the machine-readable path with cache-busting or no-cache semantics. Do not treat a stale plain reread as authoritative proof that the write failed.

MCP implication

The narrow MCP write tools append_workspace_note, update_workspace_note, delete_workspace_note, and create_handover keep this same parent-note boundary. They should not be widened into arbitrary child-topic mutation tools.

Delete boundary

  • Hard delete is proven for the parent topic endpoint /core/topic/<id>.
  • delete_workspace_note resolves the parent note by noteKey or uses a concrete topicId, then hard-deletes that parent note topic.
  • Hard delete is ownership-limited to HyperDoc-owned workspace notes and handovers. Foreign notes are rejected.
  • This is a different boundary from topicmap unlink. If the caller only wants to remove workspace placement, use the typed topicmap remove planning surface instead of assuming note delete semantics.

noteKey boundary

  • append_workspace_note is intended to be idempotent by noteKey when the read client can resolve the existing parent note URI.
  • That guarantee is currently limited to HyperDoc-created notes whose preserved URI remains readable as hyperdoc:mcp/....
  • Dry run and live execution both plan through the same URI lookup before choosing create vs. update.
  • A dry run with non-empty existing-topic-id proves that the reused noteKey resolved to an existing note.
  • A dry run with empty existing-topic-id does not prove create semantics; it means the note is absent or the current read surface cannot resolve it.
  • If a live note projection comes back with uri="", HyperDoc currently has no title-based fallback resolver for noteKey; that lookup remains unproven.
  • update_workspace_note still requires a concrete topicId, so callers need a prior read lookup or explicit id when revising an existing note.

topicmap-context implication

The guarded topicmap_context_add, topicmap_context_upsert, and topicmap_context_remove boundaries remain separate from note idempotency. They require concrete topicmap and topic ids; callers must read or resolve the concrete topic first rather than inferring it from note text alone. Live HTTP unlink is still intentionally unsupported until DELETE on the topicmap membership route is proven.
