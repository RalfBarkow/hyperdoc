Implement function-lookup-issue from the page-lookup-issue precedent

hyperdoc

This page now records the current stable function-lookup model. A function-lookup-issue is no longer just a planned sibling of page-lookup-issue. It is a real specialization of the shared bounded-lookup-issue protocol in hyperbook-explorer/lookup-failures.lisp.

Current layering

  • Shared issue model: lookup-issue, bounded-lookup-issue, page-lookup-issue, and function-lookup-issue all live in hyperbook-explorer/lookup-failures.lisp.
  • Shared bounded hook API: status, suggested repair, repair description, repair thunk, details, and the extra Overview or Repair hooks are shared across bounded issue classes.
  • HyperDoc-specific page repair: hyperdoc-explorer/lookup-repairs.lisp owns page and topic repair semantics only. It does not own the function-lookup diagnosis or correction policy.
  • Generic presentation: the shared Overview, Repair, and Condition views render the current function state through the bounded protocol.

What is preserved when the issue is created

Function lookup still starts by preserving authored evidence at the point where the undefined-function condition is available.

  • Source provenance: source page, source page id, source section, source HyperBook, and link text.
  • Lookup target: target HyperBook, target site, and the requested Lisp Functions page id via the shared expected-page-id slot.
  • Underlying evidence: the original undefined-function condition plus its rendered message text.
  • Function-specific evidence in details: expected symbol, reference kind, package context, and later runtime evidence.

This corrects the earlier design note that suggested replacing the shared expected-page-id vocabulary. The current implementation keeps the shared issue shape intact and preserves the concrete expected symbol in details and in the correction object.

Current runtime truth

The live status of a function-lookup-issue is derived from preserved evidence plus the current running image:

  • function-lookup-issue-runtime-load-state checks fboundp for the preserved expected symbol.
  • If the symbol is now fbound, the current issue status is :fixed and the suggested repair is :reopen-lisp-function-page.
  • If the symbol is still missing, the current issue status is :needs-runtime-load and the suggested repair is :load-or-reload-definition.
  • If no concrete symbol can be confirmed, HyperDoc falls back to inspect-the-reference guidance rather than inventing page repair.

That status is runtime-owned. The issue records the evidence once, and the current answer is recomputed whenever the issue is rendered.

Current correction path

  1. If the expected symbol is now fbound, the repair action retries the real Lisp Functions lookup and reopens the actual function page.
  2. If the symbol is still missing, the repair action returns a function-lookup-correction object instead of pretending the page can be reopened.
  3. The correction object preserves expected symbol, expected page id, source provenance, package context, and plain-language guidance about loading or reloading the definition.
  4. The Condition tab still shows the original undefined-function evidence, so the correction path does not erase the failure that created the issue.

Shared presentation without shared policy

The shared explorer stays presentation-only here as well.

  • Overview renders shared provenance rows plus function-specific runtime rows such as current load state, current-state reason, and whether retry is available now.
  • Repair renders shared repair description text plus function-specific extra content and a function-specific repair button label.
  • Condition renders the preserved condition message and the original Lisp condition object.

The shared bounded-lookup-issue protocol makes those tabs reusable, but the actual truth remains function-specific and comes from fboundp, not from the page/topic chunk model.

Most important corrections to the earlier precedent note

  • function-lookup-issue and page-lookup-issue are siblings under bounded-lookup-issue, not one-off special cases.
  • The function path keeps its own runtime semantics and does not borrow HyperDoc topic-page repair policy.
  • The shared issue vocabulary, including expected-page-id, stays intact; function-specific evidence is preserved alongside it.
  • Generic explorer presentation now reads dynamic bounded-issue state instead of storing a second copy of truth in the view layer.

Result

The stable model is now:

  1. record authored evidence once when the failure happens,
  2. derive current function status from the current running image,
  3. return either a retry or an inspectable correction object,
  4. and let the shared Overview, Repair, and Condition views present that state without owning the policy.
