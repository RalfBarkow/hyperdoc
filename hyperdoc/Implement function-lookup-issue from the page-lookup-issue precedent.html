Implement function-lookup-issue from the page-lookup-issue precedent

hyperdoc

This task explains how to derive a new function-lookup-issue from the existing page-lookup-issue machinery so that failed <source-of-function> references produce a primary inspectable issue object, preserve the underlying Lisp condition, and preserve the rendered condition message.

Goal

After completing this task, a failed function reference no longer stops at the message: 

The function HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE is undefined.

Instead, HyperDoc presents:

  1. a primary function-lookup-issue object,
  2. the underlying undefined-function condition as a secondary object,
  3. and the rendered message as additional condition text.

Prerequisites

  • You can run the current HyperDoc image.
  • You can reproduce a failing <source-of-function> reference.
  • You can inspect the current page-lookup-issue object in the inspector.
  • You have the current lookup and HyperBook source files available for editing.

Context

The current project already contains the architectural precedent needed for this work. In the HTML page lookup path, failed links are converted into structured issue objects by calling hb:make-page-lookup-issue and then hb:enrich-lookup-issue. This means HyperDoc already knows how to turn a lookup failure into a bounded issue object with source context, classification, repair metadata, and underlying condition.

The missing-function case arises in a different seam. The Lisp Functions HyperBook resolves a function page by reading the page id as a symbol and then calling symbol-function on that symbol. That is the exact place where an undefined-function condition appears when the requested function is not present in the current image.

Preserve the page-lookup seam carefully here: HyperDoc-specific repair thunks belong only on HyperDoc-owned targets such as hyperdoc, topics, or HyperDoc-managed FedWiki twins. A failed lookup against a different HyperBook should stay a generic HyperBook issue rather than being misrouted into HyperDoc page scaffolding.

Procedure

Step 1. Inspect the current page-lookup-issue object

Open a known page-lookup-issue in the inspector and look at its Slots tab. Record the stable structural fields that should also exist for function lookup issues.

Keep these fields as the compatibility baseline: 

source-object
source-hyperbook
source-page-id
source-page-title
source-section
link-text
classification
default-status
suggested-repair
repair-description
repair-thunk
details
underlying-condition
link

Do not redesign these fields yet. The task is to preserve as much of the existing issue vocabulary as possible.

Step 2. Locate the function-resolution seam

Open the Lisp Functions HyperBook implementation and identify the method that resolves a function page. Confirm that the function page is created by calling symbol-function on the symbol named by the page id.

This is the seam to wrap. The missing-function issue should be created here or immediately above this seam, not in a distant generic error handler.

Step 3. Decide which page-lookup slots stay unchanged

Reuse the provenance and repair slots unchanged. A function-lookup-issue should still tell the reader:

  • which page triggered the lookup,
  • which section triggered it,
  • what the classification is,
  • what the suggested repair is,
  • and which underlying condition occurred.

That keeps the new issue object visually and structurally close to page-lookup-issue.

Step 4. Replace page-target fields with function-target fields

Do not reuse expected-page-id for function lookup. It is misleading in this context. Replace the page-target fields with function-resolution fields.

Use this mapping: 

page-lookup-issue                 function-lookup-issue
-------------------------------   ----------------------------------
target-hyperbook-id               target-hyperbook-id
target-site                       target-site
expected-page-id                  expected-symbol
target-kind                       target-kind
                                  reference-kind
                                  lookup-stage

The minimum added function-specific fields should be: 

reference-kind
expected-symbol
lookup-stage

Step 5. Define the desired Slots view first

Before writing the constructor, write down the desired slot shape for the failing Mech example. This makes the implementation target concrete. 

source-object            First-class Mech Run Records in HyperDoc
source-hyperbook         hyperdoc
source-page-id           First-class Mech Run Records in HyperDoc
source-page-title        First-class Mech Run Records in HyperDoc
source-section           Example (Lisp)
link-text                mech-run-record-story-neighborhood-example

reference-kind           :SOURCE-OF-FUNCTION
target-hyperbook-id      lisp-functions
target-site              lisp-functions
expected-symbol          HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE
lookup-stage             :SYMBOL-FUNCTION
target-kind              :HYPERDOC-LISP-FUNCTION-PAGE

classification           :MISSING-LISP-FUNCTION-DEFINITION
default-status           :OPEN
suggested-repair         :RELOAD-ASDF-SYSTEM
repair-description       Load the defining ASDF component or repair the
                         symbol/file/system mismatch before retrying.
repair-thunk             (lambda () ...)

details                  (...)
underlying-condition     #
underlying-message       The function HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE is undefined.
link                     COMMON-LISP:NIL

This is the target view to implement, not merely an example to describe later.

Step 6. Add a narrow constructor helper

Add a small helper that mirrors the role of hb:make-page-lookup-issue, but for function lookup. Keep it narrow. It should only package the current failure into a bounded issue object.

At this step, aim only for slot population. Do not add inspector views yet.

The intended result of this step is the smallest viable constructor shape: 

(defun make-function-lookup-issue
    (condition
     &key source-object
          source-hyperbook
          source-page-id
          source-page-title
          source-section
          link-text
          reference-kind
          target-hyperbook-id
          target-site
          expected-symbol
          lookup-stage
          target-kind
          classification
          suggested-repair
          repair-description
          repair-thunk
          details
          link)
  ...)

Step 7. Preserve the two-level failure structure

The new issue object must not replace the underlying condition. Preserve both:

  1. the issue object as the primary workflow surface,
  2. the underlying condition as the secondary technical object.

Also preserve the human-readable condition text: 

The function HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE is undefined.

Store that message explicitly as additional condition text, for example in an underlying-message slot.

Step 8. Route the function-resolution failure through the helper

Wrap the symbol-function lookup seam so that a failing <source-of-function> reference yields a function-lookup-issue instead of stopping at raw message-only output. The issue should be created at the point where the symbol name, page context, and condition are all still available.

At the end of this step, the current red error line should no longer be the only visible artifact.

Step 9. Add only the smallest useful details payload

Do not turn the issue into a giant debugger dump. Put secondary diagnostics into details, for example: 

(:current-package "HYPERDOC"
 :symbol-name "MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE"
 :symbol-package "HYPERDOC"
 :fboundp nil
 :candidate-systems (...)
 :candidate-files (...))

Keep the top-level slot list short and stable.

Step 10. Implement the 10-line skeleton

Once the slot vocabulary and seam are clear, reduce the first implementation to the smallest constructor that proves the design. The first target is this compact skeleton: 

(defun make-function-lookup-issue (condition &key expected-symbol source-page-title source-section)
  (list :kind :function-lookup-issue
        :reference-kind :source-of-function
        :source-page-title source-page-title
        :source-section source-section
        :expected-symbol expected-symbol
        :lookup-stage :symbol-function
        :classification :missing-lisp-function-definition
        :underlying-condition condition
        :underlying-message (princ-to-string condition)))

This is not the final object model. It is the first checkpoint. It proves that the function-resolution seam can produce the same two-level structure that the existing page-lookup path already has.

Step 11. Expand the skeleton toward parity with page-lookup-issue

After the compact skeleton works, extend it by adding the remaining stable issue fields: 

source-object
source-hyperbook
source-page-id
link-text
target-hyperbook-id
target-site
target-kind
default-status
suggested-repair
repair-description
repair-thunk
details
link

Keep each addition justified by the existing page-lookup precedent rather than inventing new vocabulary casually.

Step 12. Verify the inspector behavior

Re-open the failing page and confirm that the failure now appears in three layers:

  1. primary issue object: function-lookup-issue
  2. secondary condition object: undefined-function
  3. preserved condition text: The function ... is undefined.

The result should feel parallel to the current page-lookup-issue / underlying-condition pattern, not like a separate ad hoc subsystem.

Result

The task is complete when a failed <source-of-function> reference opens first as a bounded issue object whose Slots view is recognizably parallel to page-lookup-issue, while still preserving the underlying Lisp condition and its rendered message.

Troubleshooting

If you still see only the raw undefined-function message, the wrapping code is too late in the pipeline or not on the actual symbol-function resolution path. Recheck the Lisp Functions HyperBook seam first.

If the issue object exists but lacks provenance, copy the field set from the existing page-lookup constructor path before adding more diagnostics.

If the function becomes available only after reload, verify the runtime load state with an fboundp check before assuming the issue-object design is wrong. The repo already uses that style of runtime check in nearby undefined-function recovery guidance.
