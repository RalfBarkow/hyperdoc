Dreyeck Git readiness for upstream-backed inspection

hyperdoc

Dreyeck Git readiness for upstream-backed inspection is the operator-facing readiness layer for a narrow question:

  • Can this dreyeck runtime actually inspect Konrad's upstream/main history locally?
  • If not, which bounded state explains the gap?
  • Which explicit preparation objects should the operator inspect next?

This model sits beside the read-only proof and example surfaces. It does not mutate remotes or fetch history as a side effect of opening a page or clicking ► / Run example.

What this readiness model answers

The graphviz upstream assimilation example can reach a Git-backed path. When the runtime cannot resolve Git state safely, HyperDoc now returns git-runtime-unavailable as a bounded result instead of crashing. This readiness model explains what is missing and points to the explicit preparation seam.

  • git-runtime-unavailable is a bounded result, not a hidden no-op.
  • Proof and example surfaces remain read-only.
  • Readiness is inspected separately from repair.
  • Repair stays explicit through inspectable add-remote and fetch objects.

Typical failure path from ► / Run example

  1. Open Graphviz story item upstream assimilation example and click ► / Run example.
  2. If the current runtime cannot inspect the local Git repository safely, the result degrades to git-runtime-unavailable.
  3. That bounded result now points to the dreyeck readiness run plus the explicit add-remote and fetch objects.
  4. Inspect readiness first, then inspect the operation materializations if the state shows missing remote or missing fetched history.
  5. Only after readiness reaches ready-for-git-backed-inspection should the operator rerun the assimilation example.

HyperDoc does not silently add upstream or fetch upstream/main from the example path. The repair seam is explicit so the operator can inspect exactly what would run on dreyeck before doing it.

Readiness states

  • packaged-source-no-repo: the runtime points at packaged source rather than a live checkout, so Git-backed inspection cannot inspect local branch state.
  • repository-metadata-unavailable: a checkout root exists, but the runtime cannot see usable .git metadata there.
  • live-checkout-no-upstream-remote: the runtime sees a live checkout, but Konrad's upstream remote is missing.
  • upstream-remote-present-not-fetched: the remote exists, but the local checkout still lacks fetched upstream/main history.
  • ready-for-git-backed-inspection: the runtime can inspect the local checkout and the upstream history needed by Git-backed proof/example surfaces.

The full state machine also records earlier inspection phases and bounded failure states such as no-git-executable and git-command-failed. The run object keeps those details inspectable in Summary, Trace, and Failure analysis.

Explicit preparation/repair operations

The readiness run exposes the operational seam as inspectable objects:

  • dreyeck Git readiness
  • Add upstream remote
  • Fetch upstream/main

Those operation objects render the exact host-aware shell materialization, but they do not execute it from inside HyperDoc. That keeps the boundary explicit: readiness inspection is read-only, preparation remains separately invokable.

Worked example on dreyeck

The motivating case is the graphviz upstream assimilation example. Its happy path is a real assimilation check ending in :already-assimilated. Its bounded unhappy path is git-runtime-unavailable, followed by:

  1. inspect readiness,
  2. materialize add-upstream-remote if the remote is missing,
  3. materialize fetch-upstream-main if history is not fetched,
  4. rerun the example after the repository is ready.

That keeps the semantic boundary intact. The assimilation skill still answers whether the upstream payload is already present in effect. The readiness layer answers whether the current runtime can even ask that Git-backed question locally.
