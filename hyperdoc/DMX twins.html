DMX twins

hyperdoc

A DMX twin is a DMX-side artifact, or small artifact set, that corresponds to a HyperDoc page/topic by stable intent and navigable identity. This is a correspondence model, not a claim that the DMX artifact and the HyperDoc artifact are literally the same structure.

What a DMX twin is

A DMX twin is a parallel DMX representation of a HyperDoc subject. It may be a topicmap, a bookmark, an association pattern, or another DMX-side handle that preserves stable intent and explicit navigability back to the HyperDoc side.

The important point is not literal structural matching. The important point is that the DMX artifact and the HyperDoc artifact can be recognized as corresponding anchors for the same documented subject.

What a DMX twin is not

  • It is not the HyperDoc HTML page itself.
  • It is not the HyperDoc topic object in topics.lisp.
  • It is not the same thing as a live DMX runtime proxy object.
  • It is not a FedWiki twin.
  • It is not a claim of automatic bidirectional synchronization.

Minimal correspondence pattern

The minimal correspondence pattern is conservative:

  • a HyperDoc page/topic on one side
  • a DMX topicmap/bookmark relation on the other side
  • an explicit way to navigate between them

That is enough to preserve cross-system identity by intent without claiming that every field, relation, or representation must match in detail.

Current worked example

Definitive Common Lisp Books is the current concrete example. On the DMX side, there is a topicmap whose value is definitive-common-lisp-books, a bookmark whose URL points to the HyperDoc page, and an association linking the bookmark and topicmap.

On the local HyperDoc side, the corresponding anchor is the page/topic title Definitive Common Lisp Books. This is enough to speak about a DMX twin for that subject without claiming a full import, sync framework, or permanent serialization contract.

When to add a DMX twin

  • when a HyperDoc topic should be discoverable from DMX
  • when a DMX-side anchor usefully preserves external navigability
  • when correspondence is useful even without live runtime proxy inspection

Boundary rules

  • A DMX twin is correspondence, not proof of full structural equivalence.
  • A DMX twin is not the same thing as a live write path.
  • Plugin-level modeling details should not be described as permanent too early.
