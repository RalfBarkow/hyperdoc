WebXDC-style Story Items for FedWiki and HyperDoc

A WebXDC-style story item is a design note about a packaged app surface for HyperDoc and FedWiki story items. The attractive part is not "iframe plus code." It is the possibility of an item-local shared state model where a story item carries an app container, serialized state, and a bounded message contract together.

Why a packaged app fits a story-item model

A story item is already a bounded editorial unit. A WebXDC-like app package or app container fits that unit better than a plain remote iframe because it can carry its own assets, metadata, and host-facing contract with the item.

Item-local shared state changes the design

Once the state is stored with the item, the design stops looking like a remote embed and starts looking like a portable collaboration artifact. The item can preserve shared inputs, derived outputs, or session state as part of the story itself.

That is interesting for HyperDoc because inspectable objects and published traces can now point to a stateful story-item artifact rather than only to an external app URL.

How this differs from plain remote iframe embedding

A remote iframe embed mainly gives presentation containment and URL-based indirection. A packaged app story item adds a container format, a local state story, and a clearer contract about what the parent and child owe each other.

That difference is important, but it does not erase the boundary described in The iFrame Is Not the Compute Sandbox. Packaging is not the compute sandbox. An iframe alone still does not make arbitrary code safe.

Nearest current analogue: SOLO popup and message seam

The nearest in-tree analogue is the existing SOLO popup / postMessage seam: a parent-controlled surface hands a bounded view problem to a child surface and keeps interaction legible through explicit messages. A WebXDC-style story item would widen that pattern into a more durable parent/app contract, not replace the need for one.

What a bounded parent/app contract should contain

  • an app package or app container identifier
  • item-local shared state with explicit serialization rules
  • a narrow message contract between parent and app
  • explicit user consent before privileged actions
  • a published capability profile for requested powers

Why this is promising but non-trivial

The model is promising because it offers a portable, inspectable extension surface for story items. It is non-trivial because packaging, state migration, replay, capability review, consent UI, and host mediation all have to align before it is safe and explainable.

Non-goal: iframe alone makes code safe.
