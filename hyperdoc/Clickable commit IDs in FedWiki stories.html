Clickable commit IDs in FedWiki stories

hyperdoc

Full Git commit hashes in FedWiki story text can now be rendered as clickable archived-reference links instead of inert text. The implementation is intentionally narrow: it is a renderer-local enhancement in the FedWiki story rendering path, not a new HyperBook and not a navigation-history framework.

What changed

In paragraph, markdown, and reference text rendered through the FedWiki story renderer, a full 40-character Git commit hash is now treated as an archived reference token. It is converted into an external link targeting a Software Heritage revision link of the form swh:1:rev:<hash>.

This gives the immediate UX win Konrad asked for without changing page authoring, without requiring a new syntax in stories, and without turning commit references into live runtime objects.

Why Software Heritage is used

Software Heritage provides stable archival identifiers and resolver URLs for revision objects. For commit links, the relevant first target is the revision SWHID form swh:1:rev:<hash>. That makes a full commit hash useful as a direct archived reference rather than only as a repository-local token.

Why this stays renderer-local

The right insertion point is the FedWiki story-item rendering path itself, where story text is already turned into wiki links, HyperBook links, and ordinary external links. Commit-hash linkification belongs there because it is purely presentational and reversible. It does not need page-authoring changes, ad hoc HTML rewriting, or a second reference system layered outside the renderer.

What this is not

This slice does not add a full software-heritage HyperBook. It also does not add global navigation history, object replay, or retention of previously displayed computed objects. Those are larger architectural moves with the memory and recomputation costs Konrad pointed out, and they belong in a separate design discussion.

The current design point is narrower: treat commit hashes first as archived reference tokens, not as live runtime objects.

Why that boundary matters

HyperDoc's pane/object model already keeps object state and view context in live panes. Making commit hashes clickable in story text is nearly free. Retaining full navigation history of computed objects is not. Keeping those concerns separate preserves a small UX gain without silently committing the system to a bigger retention model.
