HyperDoc DMX architectural implications

hyperdoc

HyperDoc DMX architectural implications captures the durable design consequences of the topicmap 919822 incident. The incident did not justify abandoning DMX, but it did justify a tighter HyperDoc-side contract: DMX is useful, yet generic DMX persistence boundaries cannot be assumed safe by default.

Strategic conclusions

  • HyperDoc should never rely on generic DMX writes being safe by default.
  • HyperDoc should send DMX writes only through narrow typed normalized adapters.
  • Plan-first and dry-run-first behavior should remain the default operational discipline.
  • HyperDoc should validate payloads before every DMX write.
  • HyperDoc should treat DMX as synchronizable/projected persistence, not as sole authority for authored HyperDoc artifacts.
  • HyperDoc should keep bounded issue objects and fail-soft degradation when a source or write boundary fails.
  • HyperDoc should maintain a small DMX hygiene toolkit rather than a broad migration framework.

Shared workspace implication

The incident also changed how collaborative tooling should touch DMX.

  • Shared-workspace access should happen through a narrow MCP server, not through copied terminal transcripts or raw DMX endpoint knowledge.
  • The context-window workspace should act as a shared blackboard with typed note/handover tools, not as a general-purpose DMX mutation surface.
  • Machine-readable topic reads should use /core/topic/<id>?children=true&assocChildren=true, not hash-route webclient URLs.
  • That keeps Codex and future ChatGPT connector clients on the same validated HyperDoc-side adapter boundary.

Expectation handling

The incident created two different expectation classes and both matter architecturally.

  • Disappointed expectation: the first local HyperDoc disconnect looked like the DMX database defect, but part of the observed crash came from an unrelated eager promotion-plan instantiation boundary. HyperDoc had to repair that fail-soft seam so the real DMX defect could be isolated.
  • False expectation: once the copied-store and live-store diagnosis were complete, it was no longer defensible to assume that generic DMX ViewProps writes were safe simply because current checked stock client code uses long-form keys.

Current architectural rule set

  1. Keep authored HyperDoc pages and topic-factory snippets durable and local.
  2. Use inspectable plan objects as the operational surface.
  3. Show the normalized DMX payload before any live write.
  4. Reject malformed topicmap-context payloads at the HyperDoc boundary.
  5. Preserve source ids, source paths, and provenance when degradation is necessary.
  6. Keep live DMX writes explicit, bounded, and easy to audit or roll back.
  7. Use the context-window workspace as a curated shared blackboard, not as the sole authority.
  8. Keep the MCP server narrow enough that multiple agents can share it without inheriting raw DMX write power.

Remaining unknowns

  • The original writer that created the malformed short-key-only assocs is still unproven.
  • The strongest current evidence points to a stale, external, or custom sender using the generic DMX ViewProps write seam.
  • That uncertainty is precisely why HyperDoc now narrows its own contract instead of assuming the surrounding ecosystem is clean.
