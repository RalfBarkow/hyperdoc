What a first-class run record adds

A future Mech execution model could preserve the same information as a first-class run record with chronology, provenance, findings, and artifact links. That is stronger than logging. Logging says that blocks ran. A run record preserves what they consumed, what they produced, what was excluded, and how the final draft or preview page came to be.

For story-neighborhood work this means that the walk itself becomes part of the durable result. A volume draft is no longer the only surviving artifact. The path that selected the pages, the warnings about borderline pages, the graph aspects that were handed from WALK to PRINT, and the report pages emitted by PREVIEW can all remain inspectable as one run ledger.

Chronology

Chronology is the ordered account of execution. For Mech this is not just a timestamp list. It is the sequence of authored blocks and the sub-results they yield. In the story-neighborhood case the chronology should answer questions such as: which walk happened first, what aspect set did it yield, when was the draft assembled, and which preview pages were emitted from the assembly report.

This matters editorially because Thompson-style book work is iterative. One click, two clicks, and three clicks are not merely three outputs. They are a sequence of increasingly broad editorial hypotheses. A chronology-preserving run record lets an author or editor compare those hypotheses without relying on memory or scattered notes.

Provenance

Provenance asks where an artifact came from. In this setting the relevant artifacts are not only files. They also include aspect sets, overlap views, preview pages, report pages, and assembled drafts. A provenance-preserving run record can answer: which walked aspect produced this draft section, which report page summarized that choice, and which earlier walk was compared or discarded.

This is the difference between "here is the draft" and "here is the warrant for the draft". HyperDoc is well placed to preserve that warrant because it already values inspectable runtime objects and explanation emitted at the same seam as generation.

Findings

Findings are the humanly relevant consequences of execution. They include warnings, exclusions, missing pages, changed neighborhoods, unstable gateway pages, and assembly decisions that deserve review. In a first-class run record these findings should not be buried in console noise. They should be kept as a dedicated inspectable collection that can be sorted by severity, page, distance, or producing block.

This matters especially for PRINT and PREVIEW. Those blocks do not merely transform data. They summarize editorial decisions. A saved run ledger should therefore expose what was accepted, what was omitted, and what should be reviewed before the next draft is considered authoritative.

Artifact links

Artifact links bind the ledger back to durable outputs. They are what make the run record navigable rather than merely descriptive. A chronology entry that says "produced draft" is much stronger when it also links to the exact draft, the preview page that summarized it, and the graph browser view that shows the walked aspects behind it.

This also fits Ward's practice of saving timestamped report pages for later comparison. The run record can link to those reports, and the reports can link back to the exact run object and its walked aspects. Draft and explanation can remain side by side.

Relation to existing scholarly work

W3C PROV

W3C PROV offers the clearest generic vocabulary for this design. A Mech run naturally contains activities such as WALK, PRINT, and PREVIEW; entities such as aspect sets, drafts, and report pages; and agents such as authors, sites, or concrete block implementations. What PROV contributes is a portable lineage model rather than page-local prose about where things came from.

VisTrails and workflow evolution

VisTrails is especially relevant because it treats workflow change history as first-class. That matches the editorial staircase of one-click, two-click, and three-click neighborhood exploration. The history of changed walks is part of the knowledge product, not just a prelude to the final book draft.

noWorkflow and script-level provenance

noWorkflow matters because it captures provenance from ordinary scripts instead of requiring users to rewrite everything into a special workflow language. That is a close precedent for Mech. The preservation of run evidence should emerge from normal Mech execution, not from a separate formalism that authors must learn before they can keep a credible history.

Moldable inspection

Moldable Inspector and related moldable-development work supply the decisive HyperDoc lesson: preserved provenance is only fully useful when it can be explored through domain-specific views. A Mech run ledger should therefore be inspectable by chronology, by findings, by artifact lineage, and by editorial questions such as which gateway pages were admitted or excluded.

Literate programming and executable publication

Literate programming and later executable-publication work explain why code, narrative, and result should remain linked. A first-class Mech run record goes one step further by preserving not only the narrative and the output, but also the intermediate editorial evidence that connects them.

HyperDoc-specific opportunity

The main opportunity for HyperDoc is not merely to adopt a generic provenance vocabulary. It is to treat the run ledger as a moldable publication object. An editor should be able to inspect one run by chronology, compare two runs by changed findings, open the preview page emitted from a report, and jump from a draft section back to the walked aspect that justified it.

In that form, a Mech run record becomes both an operational artifact and a scholarly one. It supports rerunning, auditing, teaching, and explaining the editorial process that produced a volume from a federated neighborhood.
