FedWiki Graphviz story item render trace

hyperdoc

This page explains one concrete localhost FedWiki page example for a hypothetical FedWiki graphviz story item and traces how HyperDoc handles it today versus how it would flow through the shared Graphviz renderer if a typed story-item adapter existed. The example is explanatory only. It does not mean that the current repo already implements a dedicated FedWiki :graphviz renderer.

Localhost page example

Real localhost FedWiki page example: Graphviz Demo, slug graphviz-demo, path /Users/rgb/.wiki/wiki.ralfbarkow.ch/pages/graphviz-demo.

This page is now a real writable localhost FedWiki page example with replayable journal history. Its story contains one hypothetical graphviz item, and its journal contains the minimal valid page history for that story: one create action followed by one add action.

The item type is still hypothetical in the renderer layer. The point of the example is to show the adapter boundary against a realistic writable page artifact, not against an empty-journal stub.

Current behavior

  1. The page JSON would be read by hyperbook/fedwiki::fetch-page-json in hyperbook-fedwiki/utilities.lisp.
  2. hyperbook/fedwiki::reload-page in hyperbook-fedwiki/pages.lisp would call hyperbook/fedwiki::set-page-data.
  3. set-page-data would call make-story, which calls make-story-item. The JSON string "graphviz" becomes the keyword :GRAPHVIZ, and the real localhost page keeps the stable story-item id 677664656d6f3031 in both story and journal.
  4. The FedWiki page story view in hyperbook-fedwiki/pages.lisp loops over (story-of page) and dispatches each item through render-story-item.
  5. In the current repo there is no (defmethod render-story-item ((type (eql :graphviz)) ...)) in hyperbook-fedwiki/story-items.lisp.
  6. Dispatch therefore falls through to the generic fallback method in hyperbook-fedwiki/story-items.lisp.
  7. The fallback method renders a small type label plus a gray <pre> block containing the raw text digraph { a -> b }.
  8. Result today: raw text / fallback rendering, not SVG. The shared Graphviz browser runtime is not reached from a FedWiki graphviz story item because no dedicated typed adapter method exists yet, even though the page itself is now a realistic journaled localhost FedWiki example.

Intended future behavior

  1. A future FedWiki story-item adapter in hyperbook-fedwiki/story-items.lisp could add a method like (defmethod render-story-item ((type (eql :graphviz)) item page) ...).
  2. That future method would treat (text-of item) as derived DOT input and would call the shared lower-layer Graphviz helper views:graphviz-snippet.
  3. The shared helper comes from the lower reusable layer carried locally by nix/patches/html-inspector-views-graphviz-unification.patch.
  4. That helper emits placeholder HTML carrying data-inspector-graphviz="true", data-inspector-graphviz-dot="...", pending state, and a raw DOT fallback block.
  5. The same lower-layer helper includes the shared browser assets and retrying init hook so the current inspector view calls window.inspectorGraphviz.initCurrentView(...).
  6. The browser runtime reads the DOT from the shared placeholder, asks the vendored Viz.js runtime to run renderSVGElement(dot), and inserts the resulting SVG into the placeholder canvas.
  7. If rendering succeeds, the state becomes rendered. If rendering fails, the shared error block appears and the raw DOT fallback remains visible and inspectable.
  8. Result in that future path: the FedWiki story item renderer would stay thin, while DOT-to-SVG transport, pending state, error handling, and raw DOT fallback would all come from the shared Graphviz layer rather than from a FedWiki-specific duplicate implementation. The localhost page would then become a realistic end-to-end example instead of only a parser/dispatch example.

Why commit 325d6ecb6b314de736b20b6abcf55932bc52c4d4 mattered

The commit did not add a FedWiki :graphviz story-item renderer. It changed no files in hyperbook-fedwiki/. Instead, it unified the lower shared DOT-to-SVG seam through nix/patches/html-inspector-views-graphviz-unification.patch so higher layers can reuse one Graphviz renderer contract.

That matters because a future FedWiki :graphviz story-item adapter should not invent a second browser Graphviz stack. The lower-layer patch already provides the reusable contract: entity-safe DOT transport, shared browser init, pending/error state, and raw DOT fallback.

Mental model

FedWiki JSON -> typed story item -> story-item renderer -> shared Graphviz snippet/runtime -> browser SVG. Today the hypothetical graphviz path stops at the generic story-item fallback before it reaches the shared Graphviz snippet because the typed adapter method does not exist yet, even though the example page is now a real journaled localhost FedWiki page.
