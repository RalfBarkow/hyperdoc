FedWiki page example

Real page example: Graphviz Demo, slug graphviz-demo, path /Users/rgb/.wiki/wiki.ralfbarkow.ch/pages/graphviz-demo.

This page is now a real writable localhost FedWiki page example with replayable journal history. Its story contains one typed graphviz item, and its journal contains the minimal valid page history for that story: one create action followed by one add action. 

{
  "title": "Graphviz Demo",
  "story": [
    {
      "id": "677664656d6f3031",
      "type": "graphviz",
      "text": "digraph { a -> b }"
    }
  ],
  "journal": [
    {
      "type": "create",
      "item": { "title": "Graphviz Demo", "story": [] },
      "date": ...
    },
    {
      "type": "add",
      "id": "677664656d6f3031",
      "item": {
        "id": "677664656d6f3031",
        "type": "graphviz",
        "text": "digraph { a -> b }"
      },
      "date": ...
    }
  ]
}

The page artifact is real and writable. The story-item type is now implemented as a thin typed adapter in the renderer layer, while DOT-to-SVG behavior still belongs to the shared lower Graphviz seam rather than to a FedWiki-specific browser stack.

Current implemented behavior

  1. The page JSON would be read by hyperbook/fedwiki::fetch-page-json in hyperbook-fedwiki/utilities.lisp.
  2. hyperbook/fedwiki::reload-page in hyperbook-fedwiki/pages.lisp would call hyperbook/fedwiki::set-page-data.
  3. set-page-data would call make-story, which calls make-story-item. The JSON string "graphviz" becomes the keyword :GRAPHVIZ, and the real localhost page keeps the stable story-item id 677664656d6f3031 in both story and journal.
  4. In HyperDoc's right-side FedWiki Story tab, the view in hyperdoc-explorer/dom-annotations.lisp loops over (story-of page), wraps each story item as a connectable anchor, and dispatches content rendering through render-story-item.
  5. The current repo now includes (defmethod render-story-item ((type (eql :graphviz)) item page) ...) in hyperbook-fedwiki/story-items.lisp.
  6. That method is intentionally thin. It does not embed custom browser JavaScript. It calls the shared lower-layer helper views:graphviz-snippet with the story item's DOT text.
  7. views:graphviz-snippet emits the shared placeholder HTML carrying entity-safe DOT transport, pending state, and the raw DOT fallback block.
  8. Result today: the FedWiki Story view can reach the shared Graphviz browser runtime and render the item as SVG, while still preserving the shared raw DOT fallback and error handling.

Edit parity

Graphviz story items in the HyperDoc FedWiki Story view now keep one authoritative DOT source in story item text while adding a narrow edit shell around the shared Graphviz placeholder. The rendered SVG is the normal view state; the edit state exposes a textarea seeded from the same text value.

Preview updates the existing shared placeholder by replacing data-inspector-graphviz-dot and reusing the shared Graphviz runtime. Save writes the edited DOT back to story item text and appends a normal FedWiki journal edit action keyed by the stable story item id.

Shared render path

  1. The typed FedWiki story-item adapter lives in hyperbook-fedwiki/story-items.lisp and stops at the call to the shared helper.
  2. From there, the lower-layer helper carried locally by htmlInspectorViewsSrcPatched in flake.nix takes over.
  3. It injects the shared Graphviz assets, retrying init script, and the placeholder HTML contract.
  4. That helper emits placeholder HTML carrying data-inspector-graphviz="true", data-inspector-graphviz-dot="...", pending state, and a raw DOT fallback block.
  5. The shared browser init hook then calls window.inspectorGraphviz.initCurrentView(...).
  6. The browser runtime reads the DOT from the shared placeholder, asks the vendored Viz.js runtime to run renderSVGElement(dot), and inserts the resulting SVG into the placeholder canvas.
  7. If rendering succeeds, the state becomes rendered. If rendering fails, the shared error block appears and the raw DOT fallback remains visible and inspectable.
  8. Result in the current path: the FedWiki story item renderer stays thin, while DOT-to-SVG transport, pending state, error handling, and raw DOT fallback all come from the shared Graphviz layer rather than from a FedWiki-specific duplicate implementation.

Why commit 325d6ecb6b314de736b20b6abcf55932bc52c4d4 mattered

The commit did not add a FedWiki :graphviz story-item renderer. It changed no files in hyperbook-fedwiki/. Instead, it unified the lower shared DOT-to-SVG seam through the htmlInspectorViewsSrcPatched source rewrite in flake.nix so higher layers can reuse one Graphviz renderer contract.

That matters because the now-implemented FedWiki :graphviz story-item adapter does not need to invent a second browser Graphviz stack. The lower-layer rewrite already provides the reusable contract: entity-safe DOT transport, shared browser init, pending/error state, and raw DOT fallback.

Dreyeck Discourse-Graphs boundary

This page is also the first concrete boundary for the later dreyeck claim that Mech is "adapted for Discourse Graphs." The first tracked code/config seam outside ~/workspace/wiki-plugin-mech that changes what a Mech graph looks like on dreyeck is not a Mech fork. It is this shared Graphviz-rendering path.

  • hyperbook-fedwiki/story-items.lisp treats a FedWiki graphviz story item as a thin typed adapter and forwards DOT from story item text into views:graphviz-snippet.
  • flake.nix packages dreyeck with htmlInspectorViewsSrcPatched, which applies deterministic postPatch source rewrites for the shared Graphviz path.
  • That rewrite supplies the shared browser/runtime contract: data-inspector-graphviz-dot, pending/rendered/error state, raw DOT fallback, and window.inspectorGraphviz.

So any upstream Mech page that emits a normal graphviz story item already acquires a dreyeck-specific rendering behavior through this tracked HyperDoc packaging seam, even when wiki-plugin-mech itself is still exactly at Ward upstream.

The inspected repo surfaces did not contain a tracked Discourse Graphs-named Mech code path. The first explicit Discourse-Graphs-specific adaptation evidence was instead local and untracked:

  • ~/workspace/wiki-plugin-mech/mech.patch contains downstream Mech edits around EXTRACT, EDGES, and WALK role names such as questions and claims.
  • The localhost FedWiki page Discourse Graphs uses exactly those commands in its authored mech items.
  • Those commands are absent from the tracked upstream checkout currently at 47cba6d57bef6db43e237abcbad60829d78b691c.

The truthful classification is therefore split:

  • tracked code/config boundary: the shared Graphviz rendering seam on dreyeck
  • untracked local artifact boundary: ~/workspace/wiki-plugin-mech/mech.patch
  • content convention boundary: the localhost FedWiki page discourse-graphs that assumes those downstream blocks

That is the smallest honest account of the adaptation boundary visible from the inspected surfaces. The server-side Mech effect on dreyeck is real, but the Discourse-Graphs-specific block vocabulary is not currently present as tracked code in this repo snapshot.

Runtime sourcing status

The tracked HyperDoc deployment surfaces inspected for this slice do not source ~/workspace/wiki-plugin-mech/mech.patch or any local Mech bundle directly.

  • flake.nix and the release packaging path contain no reference to wiki-plugin-mech, mech.patch, or client/mech-build-info.js.
  • hyperbook-fedwiki/story-items.lisp has no :mech renderer; the tracked local story-item runtime covers types such as graphviz, video, frame, audio, and text-derived items, but not a Mech execution stack.
  • hyperbook-fedwiki/fedwiki.lisp and hyperbook-fedwiki/plugins.lisp show the last confirmed boundary instead: HyperDoc discovers FedWiki site/plugin state over HTTP through /system/sitemap.json, /system/plugins.json, and /plugin/plugmatic/plugins.

So this slice can disprove only the tracked local-sourcing story: the inspected HyperDoc/dreyeck repo surfaces do not prove that dreyeck is running the local patched Mech artifact. If that patched Mech is active at runtime, its source must be on the external wiki/plugin server side or another deployment surface not present in the tracked repos inspected here.

Host-by-host live runtime comparison

Live probing of wiki.ralfbarkow.ch and discourse.dreyeck.ch shows that both hosts are real Mech runtime surfaces, not just passive content mirrors.

  • Both hosts answer /system/plugins.json and /plugin/plugmatic/plugins with a live mech plugin entry.
  • Both hosts serve /plugins/mech/mech.js and companion files such as blocks.js, interpreter.js, and library.js.
  • Both hosts also serve /discourse-graphs.json with a real mech story item whose text uses the downstream vocabulary EXTRACT, EDGES, WALK 60 questions, and WALK 30 claims.

Neither live host matches Ward upstream commit 47cba6d57bef6db43e237abcbad60829d78b691c. Upstream now reports package version 0.1.42-0 and its tracked src/client/blocks.js does not contain EXTRACT, EDGES, questions, claims, renderEdgesHtml, or parse_walk_command.

By contrast, both live hosts advertise plugmatic package version 0.1.32-dev.1 and their served blocks.js does contain those downstream signatures. That puts both hosts on the patched side of the upstream/local split.

The proof is strongest on discourse.dreyeck.ch. Its served /plugins/mech/mech.js embeds MECH_GIT_COMMIT: "abd88d2da6c89029515f2a456356832dffe038ab", and the served blocks.js, library.js, and interpreter.js byte-hashes match that exact commit in the local wiki-plugin-mech history.

wiki.ralfbarkow.ch also serves patched Mech, but its mech.js omits a build stamp. The served blocks.js and library.js hashes match older patched commits in the local history, so the host is clearly not serving plain upstream Mech, but the exact commit cannot be pinned from the live bytes alone as narrowly as on discourse.dreyeck.ch.

The host relationship is therefore not "wiki host supplies content while discourse host alone supplies runtime." Both hosts supply content and a patched Mech runtime. The live difference is that discourse.dreyeck.ch exposes a stronger provenance trail for its deployed plugin bytes.
