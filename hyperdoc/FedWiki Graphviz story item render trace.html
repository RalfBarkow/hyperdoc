hyperdoc

This page explains one concrete localhost FedWiki page example for a FedWiki graphviz story item and traces how HyperDoc handles it today versus how it would flow through the shared Graphviz renderer. The example is explanatory, but it now reflects the current typed adapter path rather than a merely hypothetical one.

Current implemented behavior

  1. The page JSON would be read by hyperbook/fedwiki::fetch-page-json in hyperbook-fedwiki/utilities.lisp.
  2. hyperbook/fedwiki::reload-page in hyperbook-fedwiki/pages.lisp would call hyperbook/fedwiki::set-page-data.
  3. set-page-data would call make-story, which calls make-story-item. The JSON string "graphviz" becomes the keyword :GRAPHVIZ, and the real localhost page keeps the stable story-item id 677664656d6f3031 in both story and journal.
  4. In HyperDoc's right-side FedWiki Story tab, the view in hyperdoc-explorer/dom-annotations.lisp loops over (story-of page), wraps each story item as a connectable anchor, and dispatches content rendering through render-story-item.
  5. The current repo now includes (defmethod render-story-item ((type (eql :graphviz)) item page) ...) in hyperbook-fedwiki/story-items.lisp.
  6. That method is intentionally thin. It does not embed custom browser JavaScript. It calls the shared lower-layer helper views:graphviz-snippet with the story item's DOT text.
  7. views:graphviz-snippet emits the shared placeholder HTML carrying entity-safe DOT transport, pending state, and the raw DOT fallback block.
  8. Result today: the FedWiki Story view can reach the shared Graphviz browser runtime and render the item as SVG, while still preserving the shared raw DOT fallback and error handling.

Edit parity

Graphviz story items in the HyperDoc FedWiki Story view now keep one authoritative DOT source in story item text while adding a narrow edit shell around the shared Graphviz placeholder. The rendered SVG is the normal view state; the edit state exposes a textarea seeded from the same text value.

Preview updates the existing shared placeholder by replacing data-inspector-graphviz-dot and reusing the shared Graphviz runtime. Save writes the edited DOT back to story item text and appends a normal FedWiki journal edit action keyed by the stable story item id.

Shared render path

  1. The typed FedWiki story-item adapter lives in hyperbook-fedwiki/story-items.lisp and stops at the call to the shared helper.
  2. From there, the lower-layer helper carried locally by nix/patches/html-inspector-views-graphviz-unification.patch takes over.
  3. It injects the shared Graphviz assets, retrying init script, and the placeholder HTML contract.
  4. That helper emits placeholder HTML carrying data-inspector-graphviz="true", data-inspector-graphviz-dot="...", pending state, and a raw DOT fallback block.
  5. The shared browser init hook then calls window.inspectorGraphviz.initCurrentView(...).
  6. The browser runtime reads the DOT from the shared placeholder, asks the vendored Viz.js runtime to run renderSVGElement(dot), and inserts the resulting SVG into the placeholder canvas.
  7. If rendering succeeds, the state becomes rendered. If rendering fails, the shared error block appears and the raw DOT fallback remains visible and inspectable.
  8. Result in the current path: the FedWiki story item renderer stays thin, while DOT-to-SVG transport, pending state, error handling, and raw DOT fallback all come from the shared Graphviz layer rather than from a FedWiki-specific duplicate implementation.

Why commit 325d6ecb6b314de736b20b6abcf55932bc52c4d4 mattered

The commit did not add a FedWiki :graphviz story-item renderer. It changed no files in hyperbook-fedwiki/. Instead, it unified the lower shared DOT-to-SVG seam through nix/patches/html-inspector-views-graphviz-unification.patch so higher layers can reuse one Graphviz renderer contract.

That matters because the now-implemented FedWiki :graphviz story-item adapter does not need to invent a second browser Graphviz stack. The lower-layer patch already provides the reusable contract: entity-safe DOT transport, shared browser init, pending/error state, and raw DOT fallback.

Mental model

FedWiki JSON -> typed story item -> story-item renderer -> shared Graphviz snippet/runtime -> browser SVG. The important ownership boundary is that the FedWiki adapter stops at the typed renderer method, and the shared lower layer still owns DOT transport, pending/error/fallback behavior, and Viz.js runtime use.
