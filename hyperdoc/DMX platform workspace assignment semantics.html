DMX platform workspace assignment semantics

This page documents the dmx-platform permission semantics behind the current workspace-assignment failure for topic 936040. It is a semantics reference, not a repair execution page. It does not report a completed workspace assignment.

Public REST route

The public REST route is PUT /workspaces/{workspaceId}/object/{objectId}. In dmx-platform it enters WorkspacesPlugin.assignToWorkspace. The route loads the target object, checks assignment arguments, and then writes the workspace facet and workspace-id property.

The route is the correct endpoint for normal workspace assignment on this DMX version. The current failure is not an endpoint mismatch and not a py4dmx request-shape mismatch.

Permission checks

The public REST route performs two checks before assignment:

  • target workspace WRITE required
  • object write access required

The important point is that object write access is checked by the public REST route even for an initial assignment. That is why this route can fail before it creates the very workspace context that would later grant write access.

Unassigned object policy

dmx-platform has an explicit unassigned object policy. For an unassigned object, READ is permitted and WRITE is refused. Topic 936040 currently has no workspace assignment, so it has no object write context for the public route to use.

For topic 936040, the request reaches the public route with a request shape that matches py4dmx's authenticated non-GET pattern. The route then checks object write access, the unassigned object write check is refused, a nested access-control exception is produced, and the exception mapper returns HTTP 401.

Initial assignment helper

dmx-platform also has a private initial assignment helper path. The helper is used from internal creation/listener paths when initial assignment must create the permission context. It deliberately skips the object write check but still checks the target workspace. This helper is different from the public REST route and must not be treated as if HyperDoc can call it directly.

The helper exists because initial assignment is the operation that makes object permission meaningful. Requiring object write access before initial assignment can be a circular requirement for objects that were created without a workspace.

Ownership, membership, and write permission

dmx-platform derives write permission from workspace sharing semantics, ownership, and membership. Private and confidential workspaces are owner-write in the relevant code path. Collaborative and public workspaces allow write for owner or member. Common workspaces allow write by sharing mode. The exact principal used for topic 936040 must therefore be able to write the target workspace 919815, and it must pass the public route's object write check for topic 936040.

Implication for topic 936040

The current classification is :REQUEST-SHAPE-MATCHES-PY4DMX-BUT-PERMISSION-DENIED. In platform terms, the failure class is :DMX-PERMISSION-SEMANTICS. The repair is permission repair outside the HyperDoc write loop, not a HyperDoc reconstruction fix.

The operational choices are administrative: grant the intended principal the needed permission, use an existing principal that already has permission, use DMX admin/operator tooling to assign topic 936040 to workspace 919815, or add a DMX-side admin repair route only if the platform supports that safely.

Why keep topic 936040

The correct recommendation is to keep topic 936040. The deterministic URI already resolves to it, the write plan is :UPDATE, topicmap 919822 already contains it, and deleting it would turn a single permission problem into a destructive migration with association/reference risks. Recreating the topic would still require workspace assignment.

Unsafe for HyperDoc

  • delete or recreate topic 936040
  • topic upsert
  • topicmap placement
  • full annotation continuation
  • DMX workspace-journal writes
  • bypassing DMX permissions from the HyperDoc write loop
  • raw SQL or database mutation from HyperDoc

Unknowns

The remaining unknown is operational, not reconstructive: which existing or operator-provided principal has the required DMX permission to perform the assignment safely. HyperDoc should inspect and report this boundary, not bypass it.
