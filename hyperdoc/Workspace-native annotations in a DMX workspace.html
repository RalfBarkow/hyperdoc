Workspace-native annotations in a DMX workspace

hyperdoc

Workspace-native annotations in a DMX workspace defines the v1 pattern that preserves a pane-local dock annotation as a durable workspace annotation in DMX topicmap 919822, context-window. The semantic contract stays native annotation semantics and coherent reopen as a workspace-dock-annotation. The conceptual native form is a hyperdoc.annotation payload model, but on current live HTTP backends the normal persist path uses deliberate compatibility storage through a dmx.notes.note carrier that stores the full native payload losslessly. Authored HyperDoc/FedWiki promotion still stays separate, and the guarded shared-workspace rule remains narrow, typed, dry-run-first writes instead of generic raw DMX mutation.

Pattern summary

  1. A pane-local dock-annotation remains the runtime front end while the user is drafting or editing.
  2. A dry-run write plan materializes the intended native annotation payload and the chosen workspace/topicmap destination for topicmap 919822.
  3. On current live HTTP backends, the normal persist path writes a deliberate dmx.notes.note compatibility carrier whose envelope stores the full native annotation payload under nativePayload.
  4. Raw hyperdoc.annotation create-topic remains a diagnostic/backend-capability boundary unless that type family is installed explicitly.
  5. The persisted workspace topic still reopens as a stable workspace-dock-annotation inspectable object by workspace topic id.
  6. Journal and restore operate on that owned workspace topic through the existing typed workspace journal boundary.

Semantic contract

Save preserves annotation semantics, not merely visibility. Workspace assignment remains distinct from topicmap placement, and authored promotion remains a separate review path.

  • Live save must reopen coherently as a workspace-dock-annotation.
  • The stored object must preserve source/target/context/supersedes structure, runtime relation id, and provenance.
  • Topicmap placement in 919822 is shared-blackboard visibility, not a substitute for workspace assignment to 919815.
  • Compatibility storage is acceptable only because it preserves the full native annotation payload losslessly and reconstructs the workspace annotation on reopen.

Native payload model and current live carrier

The native or ideal model is still one workspace-owned hyperdoc.annotation payload with typed child binding payloads. Current live HTTP backends do not expose that type family, so HyperDoc uses a deliberate compatibility carrier instead of pretending that native backend support exists.

  • Conceptual native form: hyperdoc.annotation.
  • Current live carrier type: dmx.notes.note.
  • Carrier payload: a compatibility envelope whose nativePayload field stores the full native annotation payload losslessly.
  • Reopen result: workspace-dock-annotation, not “just a note”.
  • Native hyperdoc.annotation create-topic is a diagnostic/backend-capability probe unless the backend installs that type family explicitly.

Preserved annotation payload fields

These fields belong to the native annotation payload model. If a backend ever supports hyperdoc.annotation directly, they can live on that native topic. On current live HTTP backends, HyperDoc stores them losslessly inside the dmx.notes.note compatibility carrier under nativePayload.

  • Textual fields: title, summary, text, relation_kind, status.
  • Anchor fields: source_anchor_json, target_anchor_json.
  • Context fields: context_object_id, context_view_title.
  • Object refs: source_object_ref, target_object_ref.
  • Runtime/provenance fields: runtime_relation_id, provenance_json, workspace_topicmap_id.

Binding status in v1

In v1, the binding objects are payload-only, not first-class typed workspace topics or generic DMX associations. This statement describes the native annotation payload model, not a promise that the current live backend physically stores a native hyperdoc.annotation topic.

  • The semantic parent object is the native hyperdoc.annotation payload model.
  • On current live HTTP backends, the physical workspace topic is a dmx.notes.note carrier whose compatibility envelope stores that payload under nativePayload.
  • annotation-source-binding, annotation-target-binding, annotation-context-binding, and annotation-supersedes are durable typed child payloads inside that native annotation payload.
  • Those binding payloads keep explicit player1 and player2 refs so the authored relation boundary stays readable and reviewable.
  • They are inspectable, journaled, and reopened as part of the workspace annotation state.
  • They are not created through a separate guarded assoc-create surface in v1.

Why bindings stay payload-only in v1

  • The guarded workspace model already has a proven typed topic write path, while generic assoc creation is still intentionally out of scope.
  • Payload-only bindings preserve explicit player-role structure without widening HyperDoc into a raw association writer.
  • Journal replay and restore stay simpler because one owned parent topic remains the restore subject.
  • This keeps authored promotion separate: workspace save persists runtime annotation state, not reviewed repo content.

Write and restore boundary

  • Dry run and live execution follow the same typed workspace-annotation write plan and surface the chosen destination plus storage mode.
  • On current live HTTP backends, the normal save path preflights raw hyperdoc.annotation support and then uses compatibility storage via dmx.notes.note when native create-topic is unsupported.
  • Live save emits journal events through the workspace journal layer rather than bypassing it.
  • When the write path needs credentials, it still follows the same three-mode auth learning boundary documented in HyperDoc three-mode DMX auth crosswalk; that page does not widen live behavior or claim service auth is already present.
  • Reopen by topic id yields a stable workspace-dock-annotation object for later inspection and revision.
  • Superseding an annotation creates a new workspace annotation record whose payload records the typed annotation-supersedes child binding.
  • Restore uses the existing typed revision tools for owned workspace topics rather than hidden editor undo.

What save does not do

  • It does not use chunk notes or manifest notes as transport for annotation state.
  • It does not treat compatibility storage as “just a note” or discard annotation structure.
  • It does not infer workspace assignment from topicmap visibility or treat topicmap-only placement as saved enough.
  • It does not mutate hyperdoc/topics.lisp, authored HyperDoc pages, or localhost FedWiki pages on annotation save.
  • It does not turn runtime workspace save into automatic authored promotion.
  • It does not introduce a generic unsafe DMX mutation surface.

Promotion boundary

The persisted workspace annotation is a durable runtime/content topic in the shared workspace. If an annotation should become reviewed authored source, that promotion still goes through the separate relation-topic proposal path and normal documentation review, not through the live workspace save action itself.
