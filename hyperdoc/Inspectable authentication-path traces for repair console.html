Authentication state machine

State Meaning Primary evidence
S0 no credentials entered The repair console is open, but no credential fields have been used for an action yet. UI inputs are blank and result table is still old or empty.
S1 credentials captured in UI User has typed values into the currently relevant inputs. Visible UI inputs change, but no network traffic exists yet.
S2 auth mode selected The active mode is username/password, authorization header, or bearer token. The repair console shows the active mode label.
S3 explicit auth client built HyperDoc has constructed an ephemeral authenticated DMX client for the current action only. No credential persistence appears in readback tables or topic content.
S4 bootstrap request prepared Only for username/password: the client has decided it must log in first and obtain a session. The next network request should be POST /access-control/login.
S5 bootstrap request sent The DMX login bootstrap request is on the wire. Browser network panel shows POST /access-control/login.
S6 bootstrap response received DMX has responded to the login bootstrap. Expected success shape: 204 No Content plus Set-Cookie: JSESSIONID=....
S7 session material extracted HyperDoc has extracted JSESSIONID ephemerally from the bootstrap response. Next guarded request should carry Cookie: JSESSIONID=...; dmx_workspace_id=919815.
S8 guarded repair request prepared The existing guarded executor has planned the workspace-assignment repair for the selected topic. The next request should be PUT /workspaces/919815/object/<topic-id>.
S9 guarded repair request sent The workspace-assignment request is on the wire. Browser network panel shows the PUT request.
S10 guarded repair response received DMX has answered the guarded repair request. Success should stop the 204 defect on /workspaces/object/<topic-id>.
S11 result readback refreshed HyperDoc has re-read topic, workspace, topicmap membership, and derived diagnostics. The result table and diagnostics tab change without storing credentials.
S12 terminal success The topic is assigned to workspace 919815 and still present in topicmap 919822. Result table says verified; workspace readback is no longer 204.
S13 terminal failure The action ended in an error and the result table records the failure without persisting credentials. Result table says error and shows the failing endpoint/message.

Worked examples: direct-header modes

Header and bearer-token modes stay narrower than username/password mode. They do not perform a login bootstrap. They pass the caller-supplied authorization material directly to the same guarded repair executor. These modes are builder-proven and request-shape-proven in HyperDoc, but not yet claimed as live-successful for 922464.

Authorization header mode

PUT /workspaces/919815/object/922464 HTTP/1.1
Authorization: <caller-supplied header>
Cookie: dmx_workspace_id=919815
Accept: application/json
Content-Length: 0

<empty body>

No POST /access-control/login is expected in this mode. The explicit header is used verbatim by explicit-http-dmx-import-authorization-header and make-http-dmx-import-client-from-explicit-auth in hyperdoc/dmx-import.lisp.

Bearer token mode

PUT /workspaces/919815/object/922464 HTTP/1.1
Authorization: Bearer <token>
Cookie: dmx_workspace_id=919815
Accept: application/json
Content-Length: 0

<empty body>

No bootstrap is expected here either. The token path is synthesized by explicit-http-dmx-import-authorization-header and then passed through the same guarded executor.

Current 401 on 922464: breakpoint checklist

  1. Confirm you are using the patched local HyperDoc instance at http://127.0.0.1:8080/boot.html, not an older browser tab or runtime.
  2. Open the single-object repair console for 922464 and verify the active mode label is username/password.
  3. Click Repair selected topic and inspect the browser network panel.
  4. Did POST /access-control/login run at all? If not, the runtime is stale or the mode was not normalized to :basic.
  5. Did the bootstrap response return success with Set-Cookie: JSESSIONID=...? If not, the credentials or login policy failed before the guarded PUT.
  6. Was JSESSIONID actually captured and attached to the guarded PUT? The Cookie header must be JSESSIONID=...; dmx_workspace_id=919815.
  7. If the PUT still returns 401, inspect the response body. A body that still reports user <anonymous> points to missing or ignored session state. A body that names rgb points to an authorization or ownership boundary instead.
  8. Did the same credentials succeed anywhere else? The minimum proof is that the login bootstrap itself succeeds. If needed, compare against the DMX webclient login trace, which also uses POST /access-control/login with Basic auth.
  9. After each attempt, re-check /workspaces/object/922464 and /topicmaps/object/922464. Success must clear the workspace 204 without changing topicmap placement.
