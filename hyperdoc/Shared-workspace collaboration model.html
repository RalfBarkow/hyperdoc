Shared-workspace collaboration model

hyperdoc

Shared-workspace collaboration model states the operating model between me, ChatGPT, and Codex. HyperDoc remains the durable reference and inspection side, the context-window workspace becomes the curated shared blackboard, and the MCP server is the typed machine-facing boundary that keeps both reads and writes narrow enough to trust.

Role split

  • HyperDoc: durable pages, inspectable topics, diagnostics, and design conclusions.
  • Context window workspace: current shared state, curated mirrors, handovers, and short collaboration memory.
  • MCP server: typed shared entry point that exposes the same resources and guarded tools to multiple agents, including validated topic placement and ownership-limited delete.

Operating loop

  1. Capture stable conclusions in durable HyperDoc pages and topics.
  2. Mirror the high-value current state into the shared workspace as curated notes or existing DMX workflow topics.
  3. Let Codex, ChatGPT, and the operator read the same machine-facing workspace state through MCP or direct machine-readable DMX reads.
  4. Use the same MCP boundary for live note writes, HyperDoc-owned topic upsert, ownership-limited delete, and explicit restore only when the client is attached to the same guarded server with live writes enabled.
  5. Push clarified conclusions back into HyperDoc instead of treating DMX as the sole authority.

History discipline

Collaboration stays explicit about history. HyperDoc-managed writes emit durable journal events, read_topic_journal and read_workspace_journal expose bounded inspection surfaces, and restore is an explicit action rather than editor magic. Out-of-band changes can be discovered only through bounded snapshot diff today, so those entries are marked synthesized-from-diff instead of being advertised as a native DMX event stream.

Boundaries

  • Do not use the workspace as a raw transcript archive.
  • Do not widen the write surface into generic unsafe DMX mutation.
  • Keep dry-run-first behavior where the backend contract is still uncertain.
  • Keep topic hard delete limited to HyperDoc-owned workspace artifacts, and treat live topicmap unlink as unsupported until the backend contract is proven.
  • Keep undo/redo explicit through restore tools, journal replay, and repair candidates rather than hidden mutable state.
  • Keep the original malformed writer classified as unknown until it is actually proven.

Why this model matters now

The accepted DMX and HyperDoc work already proved that a sparse or implicit workspace does not function as a real common blackboard. The collaboration model becomes useful only when the key incident, contract, workflow, and deployment context is durably documented in HyperDoc and explicitly mirrored into the shared workspace.
