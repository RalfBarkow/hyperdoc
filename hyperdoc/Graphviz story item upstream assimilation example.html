Case summary

Upstream commit ceae9d2739c181ce566103e5773e1e08bfdc859b, summary Handle story item type "graphviz", touched only hyperbook-fedwiki/story-items.lisp. The target branch is hauptsache. The earlier local commit carrying the live effect is b1e8d4041ab5f584886dfa12e5952b0a6bb6173c, summary feat(fedwiki): render graphviz story items via shared graphviz seam.

The final classification is therefore :already-assimilated, but that answer depends on semantic evidence in addition to the reused graph/history proof.

Graph/history evidence

The embedded graph/history proof deliberately stays separate. It does not prove replay-equivalent content on the target branch:

  • ceae9d... is not in hauptsache ancestry.
  • The reused proof object does not expose a replayed-equivalent target commit.
  • So graph/history proof alone is not the full answer for this case.

That is precisely why this example belongs at the assimilation layer rather than being folded back into the older graph/history-only framing.

Semantic evidence

The semantic edge under review was upstream's extra data["dot"] fallback versus the current repo's text-backed canonical graphviz item shape.

  • Earlier local commit b1e8d40... already introduced the live shared-graphviz renderer path on hauptsache.
  • The current constructor shape in hyperbook-fedwiki/story-items.lisp still reads DOT from (text-of item).
  • The current constructor only reads "engine" from item data, so the live path does not depend on data["dot"].
  • The semantic conclusion is that the upstream payload effect is already present in this repo snapshot.

Corpus and constructor evidence

The durable corpus trace is FedWiki Graphviz story item render trace. That page records a real localhost graphviz story item with:

  • "type": "graphviz"
  • "text": "digraph { a -> b }"
  • an explanation that the current renderer calls views:graphviz-snippet with the story item's DOT text

So the corpus and constructor layers agree on the same ownership boundary: graphviz DOT is text-backed here, and no compatibility patch for data["dot"] was needed in this slice.

Validation

The focused validation stays narrow. It constructs a text-backed FedWiki :graphviz story item with data NIL and checks that current rendering still produces the shared graphviz placeholder, DOT transport attribute, and raw DOT fallback.

That validation is enough for this example because the question is not whether every historical graphviz shape still exists; it is whether the upstream payload needs to be reapplied to preserve the live behavior in the current ownership boundary.

Final decision

The correct result for this repo snapshot is:

  • no cherry-pick
  • no source edit
  • no compatibility patch in this slice
  • final decision :already-assimilated

The reason is concrete: the upstream commit touched only the FedWiki graphviz renderer slice, hauptsache already had the live effect earlier via b1e8d40..., and constructor/corpus/runtime evidence all still point to the text-backed graphviz shape as the canonical path in this checkout.
