Understanding Kioskbeerli sdImage Failure Context

hyperdoc

The Print view for the kioskbeerli-sd-image-failure-context object is already showing a normalized failure capsule rather than a raw log.

A printed shape such as: 

(TOPIC SDIMAGE-IMAGESIZE-FAILURE FLAKE-LOCK ...)

should be read as a structured explanation of the failure, not just as a Lisp data dump.

Topic

TOPIC SDIMAGE-IMAGESIZE-FAILURE is the classification label for this failure mode. The issue is not a generic kiosk error. It is specifically that the pinned upstream NixOS SD-image module set does not provide an sdImage.imageSize option, so any configuration that still sets it fails option evaluation.

Flake lock

FLAKE-LOCK .../kioskbeerli/flake.lock records the exact lock file used as input. That makes the failure reproducible and tied to a concrete project artifact rather than a vague upstream state.

In the running inspector this can be represented as an inspectable pathname object rather than only plain text.

Locked nixpkgs input

The nested input object for nixpkgs pins the exact upstream revision, ref, and repository. This means the failure is not abstract. It means: the option set defined by nixpkgs at revision cf59864ef8aa2e178cccedbe2c178185b0365705 no longer matches the older kiosk configuration.

That is why the failure belongs in a credible maintenance story. It is a historically specific mismatch between a declared configuration and a pinned upstream module API.

Modules involved

The module list records the upstream sources that define the current SD-image behavior:

  • nixos/modules/installer/sd-card/sd-image-aarch64.nix
  • nixos/modules/installer/sd-card/sd-image.nix

This matters because it shows the failure lives in the standard NixOS SD-card image pipeline, not in a private local module invented by the project.

Removed/absent option

REMOVED-OPTION sdImage.imageSize is the crux. The old kiosk configuration still sets: 

sdImage.imageSize = 4096;

But in the pinned upstream SD-image module set, total image size is computed internally from the size of the generated root filesystem image plus the firmware partition and gap settings.

In other words: the SD-image builder auto-sizes the image to fit its contents and then grows the root partition on first boot.

This is why the failure capsule should be read as: the option is not part of the pinned API anymore, whether you describe that as removed or simply absent, therefore the configuration must stop setting it.

Verification step before claiming replacements

The truthful next step is to verify the pinned option set against the kiosk configuration. The failure context object should therefore expose an operation such as: 

#optionExists? "sdImage.imageSize"

That lets the inspector show evidence directly instead of relying on memory of upstream changes.

The current HyperDoc object now exposes that check directly: option-exists? sdImage.imageSize

What operations to add to the failure context object

The failure object already stores the who, what, and where. The next useful step is to make it operational by giving it obvious inspector-visible operations.

1. Provenance and reproduction operations

  • #flakeLockPath, #nixpkgsRevision, #nixpkgsRef, and #nixpkgsRepo
  • #reproBuildCommand to emit the exact build invocation
  • #explainWhyPinnedRevisionMatters to explain why the option set looks this way at this revision
  • #sdImageModuleSource and #sdImageStatesAutoSized to expose the upstream evidence directly

These operations turn the object into a reproducible debugging capsule.

2. Option-resolution operations

  • #removedOptions
  • #optionExists? "sdImage.imageSize"
  • #suggestedPatch for this topic should mean: remove the obsolete option
  • #sizingKnobsStillAvailable for the settings the pinned module still accepts

This is the "what should I change next?" layer. It reduces the need to keep re-reading upstream module internals during maintenance.

3. Module and documentation operations

  • #modulesInvolved plus #openModuleSource:
  • #sdImageSizingExcerpt to point directly at the sizing algorithm
  • #docLinks for the relevant external references

That makes the object self-documenting rather than only descriptive.

4. Classification and routing operations

  • #topic
  • #severity
  • #recommendedNextStep
  • #affectedFiles

This would let HyperBook show collections such as "all blocking kiosk build failures" as ordinary inspector views.

Minimal Nix-level implication

The immediate configuration consequence is simple: the old sdImage.imageSize setting must not remain in kiosk.nix.

The important documentation point is not to overstate a replacement before the pinned module set is verified. The failure context object should first tell the truth about the missing option, then point to the next verification step.
