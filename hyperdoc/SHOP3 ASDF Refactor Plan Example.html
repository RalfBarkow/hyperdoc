SHOP3 ASDF Refactor Plan Example

hyperdoc

This page documents the first concrete SHOP3 plan currently shipped with HyperDoc: a symbolic ASDF refactor plan. The plan demonstrates how commit discipline can be represented as an HTN planning constraint rather than as an external reminder.

The planner call

(find-plans 'hyperdoc-asdf-refactor-001
            :which :first
            :verbose 0
            :plan-tree t)

The exported wrapper is: 

(hyperdoc/shop3:run-hyperdoc-asdf-refactor-plan-object)

Expected primitive plan

  1. !add-recursive-component-collector
  2. !commit-stage recursive-component-collector-added add-recursive-hyperdoc-source-component-discovery
  3. !create-asdf-system hyperdoc/kernel
  4. !create-asdf-system hyperdoc/topics
  5. !commit-stage hyperdoc/topics introduce-hyperdoc-kernel-and-topics-systems
  6. !split-topic-family asdf
  7. !load-system hyperdoc
  8. !run-smoke-test compile-order-smoke
  9. !commit-stage compile-order-smoke split-asdf-topic-family-and-verify-load-order

Checklist projection

The checklist projection is intentionally simple. It classifies each SHOP3 primitive action into one of three HyperDoc-facing step kinds:

  • :source-edit
  • :commit
  • :verification
(defparameter *plan*
  (hyperdoc/shop3:run-hyperdoc-asdf-refactor-plan-object))

(defparameter *checklist*
  (hyperdoc/shop3:hyperdoc-plan-checklist *plan*))

(length *checklist*)
;; => 9

Fixture comparison

To compare the live projection to the committed fixture, read the fixture in the HYPERDOC/SHOP3 package so symbols are interned consistently. 

(let* ((*package* (find-package "HYPERDOC/SHOP3"))
       (fixture
        (uiop:read-file-form
         (asdf:system-relative-pathname
          :hyperdoc
          "hyperdoc-shop3-asdf-refactor-plan.sexp")))
       (checklist
        (hyperdoc/shop3:hyperdoc-plan-checklist
         (hyperdoc/shop3:run-hyperdoc-asdf-refactor-plan-object))))
  (list :fixture-length (length fixture)
        :checklist-length (length checklist)
        :matches? (equal fixture checklist)))

;; => (:fixture-length 9 :checklist-length 9 :matches? t)

Operator list order

The domain source must preserve SHOP3's operator order: 

(:operator task preconditions delete-list add-list)

Reversing delete and add lists makes the planner remove progress facts instead of adding them.

Execution boundary

A checklist item is a proposal. It is not an executor. In this first slice, SHOP3 never performs the source edit, load, smoke test, or git commit represented by an operator.
