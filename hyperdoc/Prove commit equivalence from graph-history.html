Prove commit equivalence from graph/history

hyperdoc

Prove commit equivalence from graph/history is the reusable skill for separating two different questions:

  • Is the original commit hash directly reachable from the target branch ancestry?
  • If not, is the commit's content still present as a replay-equivalent patch under a different hash?

This skill is read-only graph/history inspection. It does not repair branches, move refs, or execute merge recovery. Its proof is built from ancestry, git cherry, left/right history, and git range-diff anchored to an explicit shared base.

If the next question is not only whether a commit was replayed equivalently, but whether it should now be cherry-picked, manually assimilated, or treated as already present in effect, use Check upstream commit assimilation equivalence. That higher-layer skill wraps this proof object but keeps graph/history, semantic evidence, and final decision rationale visibly separate.

For a concrete contrast, see Graphviz story item upstream assimilation example. That worked example reuses this proof layer but still ends with :already-assimilated even though no replay-equivalent target commit is proven from graph/history alone.

Worked example

The worked example uses the preserved pre-merge hauptsache target branch so the replay-equivalent state remains inspectable even after the original lineage was later merged. It proves that the original 4fd5e78c0e3afd9f14a0fda4f9d379b2ecc4286c remains on backup/hauptsache-before-remote-sync-4fd5e78, while f7dd5540d3f7497a4d76f2b75db6f15d65485c0b on backup/hauptsache-before-merging-original-4fd5e78-d969ef5 is its replayed equivalent. The explicit shared base for the proof is d6ff2f4881533dbc26510d47bd085bb4c9a4b1bc.
