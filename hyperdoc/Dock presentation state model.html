Dock presentation state model

hyperdoc

This page makes the Dock coachmark model inspectable as a first-class HyperDoc object instead of leaving it only in prose or JS. The model records the desktop coachmark states, mobile route-strip states, transitions, UX claims, and the implementation evidence that grounds those claims in source files and tests.

Inspection itself is not a Dock capability in this slice. Inspector tabs are the durable inspection surface; the Dock governs only transient action-oriented capabilities plus route-laying and route-following introductions.

States

  • latent: no expanded coachmark is visible, but compact access remains.
  • introduction: the Dock expands because the capability is newly relevant and needs teaching.
  • active: Lay route / Connect is mid-gesture, so the Dock stays expanded with task-state UI.
  • degraded: the richer chrome has receded after use or dismissal, while compact access remains.
  • rediscovery: the user explicitly reopens the richer coachmark layer with Guide.
  • idle: the narrow route strip says Tap a station.
  • source-latched: the route strip says From: <source> and asks for a target station or operation.
  • destination-candidate: the second tap has identified an endpoint and route safety is evaluated.
  • confirming: an operation route that is not safe direct-open exposes only Dry run, Confirm, and Cancel.
  • completed: the first-class route is saved or reopened, with Open route and Evidence when available.

Inspect the States view on (chunk-dock-presentation-model) to see compact representation rules, expanded representation rules, entry triggers, exit conditions, and participating capabilities.

Transitions

  • Introduction -> Active: starting Lay route turns teaching chrome into task-state chrome.
  • Introduction -> Degraded: dismissing the coachmark retracts to compact capabilities.
  • Active -> Degraded: when the stateful route-laying gesture ends, the Dock recedes.
  • Degraded -> Rediscovery: Guide reopens the richer coachmark layer.
  • Rediscovery -> Degraded: closing rediscovery returns the pane to compact capabilities.
  • Idle -> Source latched: the first mobile tap selects the source station.
  • Source latched -> Destination candidate: the second mobile tap selects a destination station or operation.
  • Destination candidate -> Completed: safe direct-open routes such as source -> Annotation complete immediately.
  • Destination candidate -> Confirming: mutating operation routes require explicit confirmation.
  • Confirming -> Confirming: dry run adds evidence without committing the operation route.
  • Confirming -> Completed: confirm opens or saves the route.
  • Completed -> Idle: opening the route/evidence or starting another route returns the strip to Tap a station.

Claim-code evidence

The Claims view on the model does not stop at prose. Each major UX claim is materialized as a claim-code relation that points to concrete implementation evidence objects with repo paths and focused tests:

  • Degrade chrome, not capability: JS state runtime, CSS coachmark styling, and the focused Playwright regression.
  • Active route-laying keeps task state visible: JS task-state handling, pane snapshot parsing, explorer views, and the same browser regression.
  • Route/traversal workflows stay in the pane body: Touch-Fahrplan topic view, DMX pane surfaces, and the coachmark runtime.
  • Dock presentation state is inspectable: current pane snapshots, explorer views, and the focused Lisp smoke.
  • Mobile Dock uses route-first two-tap flow: the DOM Connect runtime, CSS route strip, Playwright mobile check, and Annotation smoke keep the narrow viewport contract grounded.

Shared UX grammar

The same grammar now covers the Dock capabilities and the optional route/traversal handoffs:

  • Lay route (Connect capability): can be introduced, kept active with task state, degraded, and rediscovered.
  • Annotation: remains a sibling capability in the same compact and coachmark system, and can act as the target tap that completes an active route-laying gesture.
  • Touch-Fahrplan: appears only as a contextual station/route handoff; the richer route and report workflow remains in the pane body.
  • DMX: appears only as a contextual traversal handoff to the richer surface instead of a permanent Dock identity, while preserving first-class association objects and explicit roles such as player1 and player2 where relevant.

Durable wording stays one layer above mechanics: the user is laying a route between stations. The first implementation may still surface low-level drag-to-connect or click-target mechanics, with two-tap route-laying as the non-drag fallback, but those mechanics are subordinate to the route metaphor rather than a replacement for it.

For the route-as-retrieval reading that sits one layer above this Dock teaching surface, see Iconic route language in HyperDoc.

In the current desktop runtime, active Connect uses the cue Click a target anchor or tap Annotation. That keeps the teaching layer honest: the Dock introduces Annotation as a valid target completion path, while the richer relation inspection still happens in the opened annotation pane.

In the current mobile runtime, the corresponding cue is route-first: Tap a station, then From: Text pages, then tap Annotation. Connect remains the internal capability name behind that route, but it is not the durable mobile label.

Runtime inspection seam

The current pane snapshot carries the active presentation state, presentation reason, coachmark visibility, compact capabilities, coachmark capabilities, and route/traversal handoffs. The model therefore answers both:

  • what the Dock states mean in general
  • why the Dock is visible in a particular pane right now
