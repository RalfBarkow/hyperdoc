Dock presentation state model

hyperdoc

This page makes the Dock coachmark model inspectable as a first-class HyperDoc object instead of leaving it only in prose or JS. The model records the presentation states, transitions, UX claims, and the implementation evidence that grounds those claims in source files and tests.

Inspection itself is not a Dock capability in this slice. Inspector tabs are the durable inspection surface; the Dock governs only transient action-oriented capabilities and provider handoffs.

States

  • latent: no expanded coachmark is visible, but compact access remains.
  • introduction: the Dock expands because the capability is newly relevant and needs teaching.
  • active: Connect is mid-gesture, so the Dock stays expanded with task-state UI.
  • degraded: the richer chrome has receded after use or dismissal, while compact access remains.
  • rediscovery: the user explicitly reopens the richer coachmark layer with Guide.

Inspect the States view on (chunk-dock-presentation-model) to see compact representation rules, expanded representation rules, entry triggers, exit conditions, and participating capabilities.

Transitions

  • Introduction -> Active: starting Connect turns teaching chrome into task-state chrome.
  • Introduction -> Degraded: dismissing the coachmark retracts to compact capabilities.
  • Active -> Degraded: when the stateful Connect gesture ends, the Dock recedes.
  • Degraded -> Rediscovery: Guide reopens the richer coachmark layer.
  • Rediscovery -> Degraded: closing rediscovery returns the pane to compact capabilities.

Claim-code evidence

The Claims view on the model does not stop at prose. Each major UX claim is materialized as a claim-code relation that points to concrete implementation evidence objects with repo paths and focused tests:

  • Degrade chrome, not capability: JS state runtime, CSS coachmark styling, and the focused Playwright regression.
  • Active Connect keeps task state visible: JS task-state handling, pane snapshot parsing, explorer views, and the same browser regression.
  • Provider-specific workflows stay in the pane body: Touch-Fahrplan topic view, DMX pane surfaces, and the coachmark runtime.
  • Dock presentation state is inspectable: current pane snapshots, explorer views, and the focused Lisp smoke.

Shared UX grammar

The same grammar now covers the Dock capabilities and the optional provider handoffs:

  • Connect: can be introduced, kept active with task state, degraded, and rediscovered.
  • Annotation: remains a sibling capability in the same compact and coachmark system, and can act as the target tap that completes an active Connect gesture.
  • Touch-Fahrplan: appears only as a contextual handoff when the provider is available; the route and report workflow remains in the pane body.
  • DMX: appears only as a contextual handoff to the richer traversal surface instead of a permanent Dock identity.

In the current runtime, active Connect uses the cue Click a target anchor or tap Annotation. That keeps the teaching layer honest: the Dock introduces Annotation as a valid target completion path, while the richer relation inspection still happens in the opened annotation pane.

Runtime inspection seam

The current pane snapshot carries the active presentation state, presentation reason, coachmark visibility, compact capabilities, coachmark capabilities, and provider handoffs. The model therefore answers both:

  • what the Dock states mean in general
  • why the Dock is visible in a particular pane right now
