SHOP3 Planning Layer for HyperDoc

hyperdoc

This page records the first successful live experiment in mapping HyperDoc maintenance work to a SHOP3 Hierarchical Task Network planning problem. The result is not an executor. It is a plan-only bridge: SHOP3 proposes an ordered maintenance plan, and HyperDoc preserves the plan as an inspectable documentation and runtime artifact.

What was established

SHOP3 was loaded into the live SLY MREPL connected to the HyperDoc Lisp image. The useful boundary was narrow ASDF registration: expose the planner system and the PDDL tools, but not the whole SHOP3 checkout. 

(asdf:initialize-source-registry
 `(:source-registry
   (:directory "/Users/rgb/workspace/shop3/shop3/")
   (:directory "/Users/rgb/workspace/shop3/jenkins/ext/pddl-tools/")
   :inherit-configuration))

Registering the whole checkout as an ASDF tree exposed vendored dependencies under jenkins/ext, in particular Alexandria, and caused package conflicts in the already-running HyperDoc image. The working rule is therefore: do not register /Users/rgb/workspace/shop3/ as a broad ASDF tree inside this image.

Dependency loading notes

The live load needed fiveam-asdf from Quicklisp and pddl-utils from the SHOP3 checkout. Once those were visible, (ql:quickload "shop3") loaded SHOP3 successfully. 

(ql:quickload "fiveam-asdf")
(ql:quickload "shop3")

The loaded image reported SHOP3 version 4.3.1 and created the packages needed for the planner, theorem-prover, PDDL utilities, plan tree support, and user-facing SHOP3 work.

Scratch package

The first mapping was done in a scratch package, not in production HyperDoc code. This kept the experiment reversible while allowing SHOP3 domain syntax to be evaluated directly. 

(defpackage #:hyperdoc-shop3.scratch
  (:use #:cl #:shop3))

(in-package #:hyperdoc-shop3.scratch)

The first planning domain

The first SHOP3 domain was named hyperdoc-maintenance. It models a narrow ASDF refactor workflow as a maintenance plan. The primitive operators are symbolic. They do not edit files, run tests, or commit automatically.

  • !add-recursive-component-collector
  • !create-asdf-system
  • !split-topic-family
  • !load-system
  • !run-smoke-test
  • !commit-stage

The important correction from the first failed attempt was the SHOP3 operator shape. The correct form is: 

(:operator task preconditions delete-list add-list)

The initial attempt accidentally reversed add and delete lists, which made the planner remove progress facts instead of adding them.

The first planning problem

The first problem was named hyperdoc-asdf-refactor-001. Its high-level task was: 

(refactor-hyperdoc-asdf-systems)

The initial state said that HyperDoc has a root system, needs a recursive source component collector, plans two new systems hyperdoc/kernel and hyperdoc/topics, has an ASDF topic family that still needs splitting, has the compile-order-smoke test, and starts from a clean git state.

Successful plan result

SHOP3 found one plan with nine primitive steps. The key result is that commit discipline became part of the HTN plan rather than an external prose reminder.

  1. !add-recursive-component-collector
  2. !commit-stage recursive-component-collector-added add-recursive-hyperdoc-source-component-discovery
  3. !create-asdf-system hyperdoc/kernel
  4. !create-asdf-system hyperdoc/topics
  5. !commit-stage hyperdoc/topics introduce-hyperdoc-kernel-and-topics-systems
  6. !split-topic-family asdf
  7. !load-system hyperdoc
  8. !run-smoke-test compile-order-smoke
  9. !commit-stage compile-order-smoke split-asdf-topic-family-and-verify-load-order

Checklist projection

The first HyperDoc-facing projection is a checklist. It classifies SHOP3 primitive steps into three kinds:

  • :source-edit
  • :commit
  • :verification

Every step is currently marked :manual? t. This is the execution boundary for the first slice: SHOP3 proposes the plan; HyperDoc records and renders it; a human or later guarded tool decides whether any step is executed. 

((:index 1 :kind :source-edit :operator !add-recursive-component-collector
  :arguments nil :manual? t)
 (:index 2 :kind :commit :stage recursive-component-collector-added
  :message add-recursive-hyperdoc-source-component-discovery :manual? t)
 (:index 3 :kind :source-edit :operator !create-asdf-system
  :arguments (hyperdoc/kernel) :manual? t)
 (:index 4 :kind :source-edit :operator !create-asdf-system
  :arguments (hyperdoc/topics) :manual? t)
 (:index 5 :kind :commit :stage hyperdoc/topics
  :message introduce-hyperdoc-kernel-and-topics-systems :manual? t)
 (:index 6 :kind :source-edit :operator !split-topic-family
  :arguments (asdf) :manual? t)
 (:index 7 :kind :verification :action :load-system
  :system hyperdoc :manual? t)
 (:index 8 :kind :verification :action :run-smoke-test
  :test compile-order-smoke :manual? t)
 (:index 9 :kind :commit :stage compile-order-smoke
  :message split-asdf-topic-family-and-verify-load-order :manual? t))

Plan tree and final state

SHOP3 also returned a plan tree and a final state. The useful bridge for HyperDoc is not to expose all SHOP3 internals directly, but to normalize them into inspectable objects:

  • shorter-plan removes internal operator costs from the raw plan sequence.
  • plan-tree:plan-tree->sexp provides a HyperDoc-friendly S-expression view of the plan tree.
  • state-atoms exposes the final state's facts for summary and postcondition views.

Object model to promote next

The next implementation slice should promote the scratch result into an optional hyperdoc/shop3 ASDF system, not into the root hyperdoc system. 

(defclass hyperdoc-htn-plan-result ()
  ((problem-name :initarg :problem-name :reader problem-name-of)
   (plans :initarg :plans :reader plans-of)
   (raw-plans :initarg :raw-plans :reader raw-plans-of)
   (plan-trees :initarg :plan-trees :reader plan-trees-of)
   (final-states :initarg :final-states :reader final-states-of)
   (time :initarg :time :reader time-of)
   (execution-mode :initarg :execution-mode
                   :initform :plan-only
                   :reader execution-mode-of)))

Boundary

This page documents a successful planning experiment and the intended first integration boundary. It does not claim that HyperDoc should become autonomous, and it does not authorize automatic source edits, shell commands, DMX mutations, or git commits.

The first durable design rule is:

SHOP3 proposes ordered maintenance plans. HyperDoc makes those plans inspectable. Execution remains manual until a later guarded execution boundary is explicitly designed.

Next Codex handoff

Codex should integrate this as an optional, plan-only slice: documentation first, then hyperdoc/shop3, then the symbolic ASDF refactor domain and checklist example. The root hyperdoc system must continue loading without SHOP3.
