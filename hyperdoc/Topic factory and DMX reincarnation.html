Topic factory and DMX reincarnation

hyperdoc

This page clarifies the interplay between a HyperDoc topic factory, the page it reconstructs in the Topics HyperBook, and the corresponding DMX topic that may exist as a graph-native counterpart.

The important distinction is that HyperDoc intentionally keeps two surfaces in play. The topic-page surface in HyperBook topics is stable, authored, and rebuildable. The DMX runtime-object surface is live, fetched, and shaped by the current state of the external DMX graph.

Three layers, not two

It is useful to think in three layers rather than collapsing everything into a single notion of topic.

  1. The subject matter: the concept under discussion.
  2. The HyperDoc authored layer: the topic factory and the stable page it reconstructs in HyperBook topics.
  3. The DMX graph layer: the DMX topic object, with its own id, type, children, and associations.

The concept may be the same across all three layers, but the representations are not the same object and should not be treated as if they were.

What a topic factory is

A topic factory is not merely a title string and not merely a convenient wrapper around a topic object. In HyperDoc it is the durable local reconstruction point for a topic in the Topics HyperBook.

The factory preserves the local editorial identity of the topic by reconstructing stable authored material such as the canonical title, summary, references, and backlinks. This makes the topic-page surface rebuildable even when runtime proxy mechanisms change.

In that sense, the topic factory itself is part of the durable authoring layer, not just a helper for runtime access.

What the DMX reincarnation is

A DMX reincarnation is the graph-native counterpart of the same subject in DMX. It is identified by DMX-native identity such as a numeric topic id and a type uri, and it participates in DMX-native structures such as children, associations, and topic-map placement.

When HyperDoc exposes a live hyperdoc::dmx-topic-proxy, it is not reconstructing the authored topic page. It is exposing a runtime view onto the current DMX-backed state.

Why HyperDoc keeps both surfaces

HyperDoc keeps both surfaces on purpose.

  • Topic-page surface: stable authored/documentary concept page in HyperBook topics.
  • Runtime-object surface: live DMX-backed proxy with fetched JSON, relations, and inspector views.

The first surface is suited for durable explanation, local reconstruction, and editorial curation. The second surface is suited for live inspection of the external graph and its current state.

The systems are related, but neither should erase the role of the other.

Identity should not be reduced to title equality

The clean bridge is not title equality.

  • HyperDoc identity: a stable local key preserved by the topic factory.
  • DMX identity: the DMX topic id and related graph metadata.
  • Presentation: the canonical title currently shown in HyperDoc or DMX.

Titles can match and often should match, but title equality is presentation agreement, not identity. If the DMX title changes, HyperDoc should not lose the local topic identity. If the HyperDoc canonical title changes, the DMX topic id should not be forgotten.

What import from DMX should mean

If HyperDoc can read a topic from DMX and add it to the Topics HyperBook, the cleaner model is materialization rather than substitution.

In other words, DMX should be able to serve as a source for a local authored topic factory, while the Topics HyperBook remains a stable authored surface.

A DMX import should therefore do two things at once:

  • materialize or refresh a local authored topic factory and its topic-page surface, and
  • preserve an explicit correspondence to the DMX topic id and optional live proxy entry point.

This preserves offline rebuildability and local editorial control while still allowing live graph inspection.

Recommended correspondence model

The correspondence should be explicit rather than implicit. 

HyperDoc stable key <-> DMX topic id

The mapping can then support title synchronization, reference enrichment, runtime proxy access, and later reconciliation work, without collapsing the HyperDoc topic into the DMX object or collapsing the DMX object into the HyperDoc page.

Applied example: Encryption boundaries on the small web

For a topic such as Encryption boundaries on the small web, the HyperDoc side and the DMX side can be treated as two incarnations of one subject.

  • HyperDoc side: a stable local topic factory and a page in HyperBook topics.
  • DMX side: a DMX topic object with DMX-native identity and graph relations.

The right interpretation is not that the two records are literally the same object. The right interpretation is that they are explicit counterparts. The HyperDoc topic factory is the durable reconstruction point for the local documentary surface; the DMX topic is the live graph reincarnation of the same subject in a different system.

Operational rule for implementation

A useful implementation rule is this:

Import from DMX into Topics HyperBook by materializing or refreshing a local authored topic factory, while preserving explicit correspondence to the DMX topic id and optional live DMX proxy access.

That rule keeps the authored layer durable, the runtime layer inspectable, and the correspondence auditable.
