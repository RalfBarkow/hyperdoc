Topic factory and DMX reincarnation

hyperdoc

This page explains the relation between a stable topic page in HyperDoc and a live DMX view of the same subject.

For readers, the simplest explanation is that HyperDoc intentionally keeps two surfaces in play.

  • Topic-page surface: a stable authored page in HyperBook topics.
  • DMX surface: a live DMX-backed view reached through a runtime proxy.

The topic page is the durable documentary surface. The DMX view is the live graph surface. They can concern the same subject without being the same object.

Two reader-facing surfaces

HyperDoc uses two reader-facing surfaces because they do different jobs.

The page in HyperBook topics is stable, authored, and rebuildable. It preserves the canonical title, summary, references, and derived backlinks that belong to the local documentary surface.

The DMX side is live, fetched, and shaped by the current state of the external graph. A hyperdoc::dmx-topic-proxy can expose current JSON, relations, and topic-map context without pretending that this fetched state is the same thing as the authored topic page.

What a topic factory contributes

A topic factory belongs to the authored side.

It is not merely a title string and not merely a convenience wrapper around make-topic. In this repository it is the durable local reconstruction point for the topic-page surface in HyperBook topics.

That is why the factory matters even when readers mostly encounter the topic as a page. The page remains rebuildable from authored topic factories rather than depending on whatever the external graph happens to say today.

What the DMX reincarnation contributes

The DMX reincarnation belongs to the live graph side.

It has DMX-native identity such as topic id, type, children, associations, and topic-map placement. When HyperDoc opens a live DMX-backed proxy, it is exposing a runtime view onto that external structure.

This is useful because it keeps fetched graph state inspectable. But it should not replace the local authored topic page.

Applied example

For Encryption boundaries on the small web, the HyperDoc page and the DMX topic can be understood as two views of one subject.

  • HyperDoc side: a stable local topic factory and a stable topic page in HyperBook topics.
  • DMX side: a DMX topic with DMX-native id and graph relations.

The practical point is that a reader can treat these as two ways to approach the same subject: one documentary and one live.

Implementation note: the deeper three-layer model

For implementation work, there is still a useful deeper distinction.

  1. The subject matter: the concept under discussion.
  2. The HyperDoc authored layer: the topic factory and the stable page it reconstructs.
  3. The DMX graph layer: the DMX topic object with its own identifiers and relations.

That deeper split matters for import, rename, rebuild, and correspondence. It is mainly an engineering concern and does not need to be the first explanation for ordinary readers.

Identity is not title equality

The bridge should not be reduced to title equality.

  • HyperDoc identity: the stable local key preserved by the topic factory.
  • DMX identity: the DMX topic id and related graph metadata.
  • Presentation: the title currently shown in HyperDoc or DMX.

Titles can match and often should match, but matching titles are presentation agreement, not full identity collapse.

What import from DMX should mean

If HyperDoc can read a topic from DMX and add it to the Topics HyperBook, the cleaner model is materialization rather than substitution.

DMX should be able to serve as a source for a local authored topic factory, while the Topics HyperBook remains a stable authored surface.

  • materialize or refresh a local authored topic factory and its topic-page surface, and
  • preserve explicit correspondence to the DMX topic id and optional live proxy access.

This keeps local reconstruction durable while still allowing live graph inspection.

Operational rule

Import from DMX into Topics HyperBook by materializing or refreshing a local authored topic factory, while preserving explicit correspondence to the DMX topic id and optional live DMX proxy access.

That rule keeps the reader-facing explanation simple while leaving the deeper implementation model available when needed.
