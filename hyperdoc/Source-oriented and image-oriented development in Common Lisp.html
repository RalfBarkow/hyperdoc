Source-oriented and image-oriented development in Common Lisp

hyperdoc

This page distinguishes two real workflow modes in Common Lisp without collapsing them into slogans. The important correction is that ordinary application work is usually still source-oriented even when saved images exist and live image state is useful.

Source-oriented development

In source-oriented development, source files remain the durable artifacts that developers check in, rebuild, and verify from scratch. Loading through compile-file and rebuild paths remains normal, and developers periodically verify that sources still reconstruct the system cleanly.

This is the usual frame for Common Lisp application programmers, including repositories like this one where ASDF system definitions, source-registry visibility, and rebuilds from source are the durable workflow layer.

Image-oriented development

In image-oriented development, a live Lisp image is incrementally mutated during exploration, debugging, implementation work, or delivery preparation. This mode is real and useful, but it does not by itself remove the need for durable source reconstruction.

SBCL's bootstrapping paper is important precisely because it contains image dependence rather than denying it. A host image helps with bootstrap, but the final target build should not depend on accidental host-image state.

Images as deployment artifacts

A saved image can still be valuable as an image as deployment artifact. That is narrower than saying the image replaces source. It means the saved runtime state is convenient for shipping or starting a program, while source remains the durable form that developers rebuild and audit.

Why the boundary matters

The useful comparison is therefore not source versus image in an absolute sense, but live image versus durable source. Live image state is excellent for exploratory and implementation work. Durable source is what keeps the system rebuildable, reviewable, and portable across releases and implementations.
