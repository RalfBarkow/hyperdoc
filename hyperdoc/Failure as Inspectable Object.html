Failure as Inspectable Object

hyperdoc

A HyperDoc failure should not stop at a raw condition message when the condition can be turned into an inspectable object with preserved provenance, classification, and recovery context.

This matters especially for documentation surfaces that promise a live object reference, such as expr= links and <source-of-function>...</source-of-function> references. When one of those references fails, the reader should be able to inspect what failed, at which layer it failed, what object or symbol was expected, and what the next correction step is.

Problem

At the moment, some failure paths still collapse to a message-only situation. A representative case is a page that tries to resolve a function reference, but the running image does not contain the expected definition. The visible result is often only an undefined-function message, for example: 

The function HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE is undefined.

That message is real and useful, but it is too thin as a navigational surface. By itself it does not preserve the triggering page reference, the intended symbol, the evaluation stage, the likely cause, or the correction path.

Existing precedent: page-lookup-issue

HyperDoc already has a concrete precedent for this design move: page-lookup-issue. In the page-lookup work, a failed reference is not treated as a dead string only. It is turned into a bounded inspectable object that preserves source-page context, target context, classification, status, repair metadata, and the underlying condition.

A concrete constructor anchor for that precedent is hyperbook:make-page-lookup-issue.

That precedent is important because it shows that HyperDoc already prefers structured, inspectable failure objects over flattened error text when a failure belongs to a known navigation or rendering class.

Two-level precedent: issue object and underlying condition

The strongest current precedent is not merely that HyperDoc can objectify a failure. It is that HyperDoc can present the failure at two levels.

  • Primary level: a bounded issue object for workflow, classification, and repair
  • Secondary level: the underlying condition object for low-level diagnosis

In the page-lookup-issue case, the issue object exposes source-page context, target context, classification, status, suggested repair, and repair thunk. The underlying failure condition remains inspectable behind that issue.

The missing-function case should follow the same pattern. The first visible result should be a bounded runtime-reference issue, while the underlying undefined-function condition remains inspectable as a secondary object, and the rendered message The function ... is undefined remains available as additional condition text.

Why the object matters

HyperDoc already distinguishes evaluation, inspection, and navigation. A raw message loses that distinction at the exact moment the distinction matters most. A bounded failure object can keep the layers explicit:

  • reference layer: what page markup asked for
  • lookup layer: what symbol or object was sought
  • runtime layer: what the current image actually contains
  • correction layer: what to reload, inspect, or repair next

This turns the failure from a dead end into an explanatory affordance.

Representative case: source-of-function

A <source-of-function> reference is not ordinary prose. It declares that a function should be present in the running image and that its source should be reachable through the Lisp-functions HyperBook. If that lookup fails, the user should not be left with a bare message only.

In the current Mech run-record slice, this is the practical issue behind a missing or miswired function reference. The page-level promise and the image load set have diverged.

Wanted sibling object

The undefined-function case during page rendering should become a sibling of page-lookup-issue, not a one-off debugger escape. A suitable shape would be a bounded runtime-reference issue such as:

  • runtime-reference-issue
  • missing-function-reference-issue
  • render-time-definition-issue

The exact class name can vary. The architectural point is that the missing function is not merely printed; it is objectified as one inspectable issue.

Desired behavior

The first visible result should be an inspectable failure object. Its compact title-bar text can be something like: 

Missing function reference: HYPERDOC::MECH-RUN-RECORD-STORY-NEIGHBORHOOD-EXAMPLE

Opening that object should reveal fields analogous to the page-lookup-issue inspector:

  • the original page reference that triggered the lookup
  • the source page title and source section
  • the exact symbol that failed to resolve
  • the reference kind, such as :source-of-function
  • whether the failure occurred while reading, resolving, or calling
  • the current package and image context
  • candidate ASDF systems and source files expected to provide the definition
  • a classification and current status
  • a suggested repair, repair description, and repair thunk when available
  • the underlying condition
  • the rendered condition message

The underlying undefined-function condition should remain inspectable as a secondary object, and the human-readable message should remain preserved as additional condition text rather than disappearing behind the issue wrapper.

Relation to existing inspector practice

HyperDoc already has the right general direction in nearby surfaces. The Playground preserves parse and evaluation failures as inspectable debug reports, and the page-lookup work preserves failed page references as structured issue objects. The missing-function case should continue that line rather than falling back to a terminal message.

A missing function reference should therefore be handled less like an ordinary exception escaping to the UI and more like a first-class runtime issue object with views for diagnosis, repair, and retry.

Boundary discipline

Not every error should become a giant universal report object. The issue must stay bounded to one failure class and one triggering reference. This keeps the page understandable and avoids collapsing unrelated problems into one generic debugger surface.

  • One failed reference.
  • One failure stage.
  • One primary correction path.

If the first correction step succeeds but reveals a second failure, that second failure should become its own inspectable object.

Pragmatic implication for the current Mech slice

For the current Mech run-record work, the immediate goal is not a perfect global error architecture. It is narrower: when a <source-of-function> reference does not resolve, HyperDoc should show a bounded sibling issue object in the spirit of page-lookup-issue that tells the reader what was expected, why the reference likely failed, and where to go next, while still preserving the underlying condition and its rendered message.

That would already be a material improvement over the current message-only situation.
