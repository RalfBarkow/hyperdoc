FedWiki Story Item IDs

hyperdoc

FedWiki story item ids identify journaled items for add/edit/move/remove replay. In this workflow, ids should be opaque and stable, using the canonical 16-hex format.

Inspectable objects

  • FedWiki story item id policy
  • FedWiki id runtime contract

  • Journal checker commit gate
  • Chronology violation
  • Replay precondition violation

How wiki-client and wiki-server use item IDs

  1. The client stores page content as ordered story items, each with an id.
  2. User edits are expressed as journal actions (add, edit, move, remove) keyed by item id.
  3. The server persists journal actions and reconstructs current story state by replaying those id-addressed actions.
  4. Checks like revision replay and chronology validation therefore depend on stable ids and consistent after/id references.

Canonical 16-hex IDs vs semantic IDs

DimensionCanonical 16-hex IDSemantic ID (for example summary-20260306)
Primary roleOpaque identity keyIdentity key mixed with human meaning
Refactor safetyHigh; text/title can change freelyLower; wording changes tempt id rewrites
Replay stabilityPredictable with consistent journal refsHigher risk when ids are renamed or partially migrated
Human readabilityLow in raw JSONHigh in diffs/logs

Why semantic ids cause trouble

  • Semantic ids are tempting for readability but couple identity to editorial wording.
  • Renaming or restructuring content can silently invalidate journal references.
  • Mixed id styles in one page increase replay and chronology repair friction.

Effect of using semantic item IDs instead

FedWiki will generally accept semantic ids as plain strings. The short-term effect is easier manual reading of page JSON and journal actions. The operational cost appears later: ids become part of content semantics, so content rewrites can trigger accidental id rewrites, partial migrations, and replay-precondition failures.

Practical rule: keep semantics in page text, topic ids/slugs, and links; keep story item ids opaque and stable. If semantic ids already exist, normalize once across both story and journal, then stop encoding meaning in item ids.

Recommended policy

  1. Use canonical 16-hex ids for all story items in localhost FedWiki pages.
  2. Keep meaning in title, paragraph text, topic ids/slugs, and links.
  3. When semantic ids already exist, normalize them consistently in story and journal.
  4. Run python3 -m json.tool plus journalmatic checks before commit.

Expanded operating policy

  1. Treat story-item id as an internal replay pointer, not a human label.
  2. Do not rename item ids when wording changes; edit text/title/slug instead.
  3. Preserve id consistency across story and all journal references (id, after, item.id).
  4. If semantic ids already exist, run one full normalization migration and stop encoding meaning in item ids afterward.
  5. Use slug-keyed links for lookup (page="<slug>") and keep titles for display.
  6. Require both syntax and replay validation before commit: json.tool plus journalmatic checks.

Net effect: content can evolve freely while identity pointers remain stable, so replay and revision checks keep working.

Operational note

Syntax validation (json.tool) confirms JSON structure, but only journalmatic replay checks confirm that current story state is reconstructible from journal actions.
