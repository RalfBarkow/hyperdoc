Shared Projection IR

hyperdoc

Shared Projection IR is the narrow architecture layer that lets HyperDoc expose a rebuildable shared coordination surface without turning the visible context-window topicmap into the durable authority or into a compiler intermediate representation. It keeps semantic coordination, behavior, and execution/backend concerns separate while making each layer inspectable.

The three-layer split

  • Semantic coordination IR: objects such as shared-projection-context-window, shared-projection-entity, shared-projection-relation, and shared-projection-journal-event model the curated shared blackboard as a rebuildable projection.
  • Behavior IR: objects such as behavior-machine-definition, behavior-state, behavior-transition, behavior-run, and behavior-trace model machine structure and concrete traversals as first-class inspectable objects.
  • Execution/backend IR: JavaScript, Common Lisp, and any native execution backends remain separate execution concerns. The shared projection layer should not become a compiler IR, and the topicmap should not become a backend-neutral mutation graph.

SCXML belongs to the behavior layer as import/export and transport. It is useful for round-trip and interchange, but it is not the canonical store for the whole architecture.

Authority boundary

  • The shared context-window surface is a rebuildable shared projection and a bounded shared blackboard.
  • Authoritative state remains HyperDoc-side and journal-backed; the visible projection is derived, inspectable, and replayable rather than the only durable record.
  • Topicmap visibility stays a projection fact. It does not imply ownership, and it does not imply workspace assignment.
  • Workspace assignment remains distinct from topicmap placement, exactly as documented in Diagnosing DMX workspace assignment and topicmap placement.

The broader shared-blackboard reasoning and shared-workspace collaboration contract already live in Context window workspace as shared blackboard and Shared-workspace collaboration model. This page only adds the IR split that keeps those boundary claims inspectable in runtime objects.

Worked example

The first worked example is the workspace annotation lifecycle projection. Its projection object has stable id context-window/919822, its active behavior machine id is workspace_annotation_lifecycle, and it carries explicit provenance plus journal linkage so the shared projection is not just another anonymous graph DTO.

Inspector entry points

  • Summary: shows workspace name, topicmap id, projection status, focus ids, and the primary machine/run/trace handles.
  • Graph / relations: shows the projection entities and typed relations, including ownership/workspace/topicmap distinctions.
  • Behavior machine: opens the linked behavior definition without collapsing the projection layer into the machine layer.
  • Current run / trace: shows the concrete traversal separately from the reusable machine definition.
  • Provenance / source evidence: keeps provenance payloads and journal linkage explicit.
  • SCXML: exposes the behavior-layer transport form.
  • JavaScript / JSON: exposes the plain-object and JSON forms, including the versioned JSON shape.

What this page does not change

  • No DMX write widening.
  • No MCP integration work.
  • No backend or runtime execution changes.
  • No attempt to make SCXML the canonical storage format.

Those boundaries are deliberate. The point of this first page is to make the new object family and inspection path legible without claiming a larger integration surface than the code currently provides.
