Collaborative Link Model and Resolution

Three ideas need to stay connected when discussing Federated Wiki links in HyperDoc:

  • the link model
  • the navigation semantics of collaborative links
  • the resolution model that decides which page is actually loaded

If these are discussed separately, the design becomes misleading. A link is not just a piece of syntax, and navigation is not just URL construction. Collaborative linking is a compact user gesture backed by federation-aware resolution rules.

1. Link model

The link model defines what a link is. In Federated Wiki, a collaborative link begins as visible page text inside [[...]]. In the Java reference implementation, the visible text is converted into a slug. This means the operational identity of the link target is not only the displayed title but also the derived slug.

For HyperDoc, this means a FedWiki link model cannot stop at “page title”. It must account for site and slug as first-class parts of the target model.

2. Navigation semantics

Navigation semantics describe what should happen when a user follows a collaborative link. In the reference implementation, following a link is not a simple open-by-title action. It means:

  1. extract the collaborative link from the current item
  2. derive a slug from the link text
  3. collect the current page context from journal provenance
  4. search origin and then context sites in a defined order
  5. open the first page that resolves successfully

So the navigation semantics are federation-aware. The same visible link text may resolve differently depending on origin, context, and item-level site hints.

3. Resolution model

The resolution model is the concrete lookup algorithm. In the fedwiki-java reference implementation it is roughly: 

slug := collaborative-link text normalized to slug
context := sites from current page journal
if current item has site, prioritize that site in context
try origin site first
then try each context site in order
load the first site/slug pair that returns a page

This model explains why collaborative linking is more than local wiki navigation. It is a lightweight federation protocol embedded in page text.

Why these three belong together

A poor design can get one layer right while breaking the others.

  • A title-only link model loses slug and site identity.
  • A URL-only navigation model loses provenance-aware lookup.
  • A resolution algorithm without a clear link model becomes opaque to authors.

The design goal is therefore not merely “link to a FedWiki page”. It is: represent the same conceptual link object that the collaborative-link system expects, and make its navigation and resolution behavior inspectable.

Implication for HyperDoc

A HyperDoc page that wants to point to concrete FedWiki concepts such as FIND, WALK, PRINT, or REVIEW should not use a naive title-only convention. It should eventually expose or derive:

  • the FedWiki site
  • the target slug
  • the current origin/context assumptions

Only then will the HyperDoc design match the actual semantics of collaborative links instead of approximating them.
