Add HyperDoc MCP beside the authoritative host config on dreyeck.ch

hyperdoc

Add hyperdoc-mcp as a sidecar service in dreyeck's existing host configuration. Do not switch the live host to nixosConfigurations.dreyeck-ch for this slice.

Inspectable objects

  • dreyeck MCP additive host integration
  • DMX MCP server for shared workspace
  • Deployment command locality
  • NixOS generation rollback

Boundary correction

The plausible expectation was that the repo-owned nixosConfigurations.dreyeck-ch would be the cleanest activation path because it already described the MCP service, nginx route, and ACME intent.

The observed reality is that switching that full host profile on dreyeck.ch replaced core host-owned definitions such as rgb, sshd, and other production-local settings. Rollback restored the real host model.

This is a disappointed expectation, not a merely false one, because the repo already shipped a full host profile that looked deployable for the production host. The repair is to move production activation authority back to /etc/nixos and keep the repo responsible only for reusable MCP artifacts.

Integration split

HyperDoc repo

  • Owns the MCP Lisp runtime and guarded tool contract.
  • Owns the reusable NixOS module nix/modules/hyperdoc-mcp-release.nix.
  • Owns the recovery-bridge sidecar file nix/integration/dreyeck-hyperdoc-mcp-sidecar.nix.
  • Owns the installer tools/install-dreyeck-hyperdoc-mcp-sidecar.sh that materializes a host-owned steady-state copy inside /etc/nixos.
  • Must not become the authoritative definition of the whole dreyeck.ch host.

/etc/nixos on dreyeck

  • Owns the active host definition, imported modules, users, sshd, firewall, and other production-local settings.
  • Activates the additive MCP sidecar beside the existing hyperdoc.service.
  • Owns the final steady-state import path ./hyperdoc/dreyeck-hyperdoc-mcp-sidecar.nix.
  • Owns the final nginx and ACME activation path because those are host-wide concerns.

Temporary bridge

The repo-side bridge file is /home/rgb/workspace/hyperdoc/nix/integration/dreyeck-hyperdoc-mcp-sidecar.nix. It is acceptable only as a temporary recovery bridge when the host-owned copy is missing and MCP must be restored quickly. 

imports = [
  ./hardware-configuration.nix
  /home/rgb/workspace/hyperdoc/nix/integration/dreyeck-hyperdoc-mcp-sidecar.nix
];

This bridge still evaluates a mutable checkout at activation time, so it is not the hardened steady-state recommendation.

Hardened steady-state path

The steady-state path installs host-owned copies under /etc/nixos/hyperdoc:

  • /etc/nixos/hyperdoc/hyperdoc-mcp-release.nix - host-owned copy of the reusable module.
  • /etc/nixos/hyperdoc/dreyeck-hyperdoc-mcp-sidecar.nix - host-owned sidecar with services.hyperdocMcp.packagePath pinned as a quoted concrete /nix/store path and useACMEHost = "dreyeck.ch".

That keeps /etc/nixos authoritative while removing mutable checkout imports from the final production activation path.

The quoted packagePath form matters for flake-based /etc/nixos: it keeps evaluation pure while still pointing systemd at the pinned release root.

The sidecar should reuse dreyeck's existing wildcard-certificate model via useACMEHost = "dreyeck.ch". Do not add a dedicated security.acme.certs."mcp.dreyeck.ch" lifecycle for MCP on this host.

Operator steps

  1. Install the hardened host-owned copy from the repo checkout: 
    sudo mkdir -p /etc/nixos/hyperdoc
sudo /home/rgb/workspace/hyperdoc/tools/install-dreyeck-hyperdoc-mcp-sidecar.sh --target-dir /etc/nixos/hyperdoc
  2. Import the host-owned sidecar from the authoritative host config: 
    sudoedit /etc/nixos/configuration.nix
  3. Add or keep the durable import path: 
    imports = [
  ./hardware-configuration.nix
  ./hyperdoc/dreyeck-hyperdoc-mcp-sidecar.nix
];
  4. If dreyeck already uses a host-owned flake in /etc/nixos, keep using that host-owned activation path. Do not replace it with /home/rgb/workspace/hyperdoc#dreyeck-ch.
  5. Test the additive activation without making it persistent: 
    sudo nixos-rebuild test
  6. Probe the service contract on the host and through nginx: 
    systemctl status hyperdoc-mcp --no-pager --lines=20
curl -i http://127.0.0.1:8787/mcp
curl -i https://mcp.dreyeck.ch/mcp
DMX_MCP_URL=https://mcp.dreyeck.ch/mcp python3 /home/rgb/workspace/hyperdoc/tools/probe-dmx-mcp-server.py
DMX_MCP_URL=https://mcp.dreyeck.ch/mcp DMX_MCP_TOPIC_URI=dmx://topic/907120 python3 /home/rgb/workspace/hyperdoc/tools/probe-dmx-mcp-server.py
  7. If all probes remain green, persist the same /etc/nixos generation: 
    sudo nixos-rebuild switch
  8. Refresh the pinned package after a newer HyperDoc MCP build by rerunning the installer, then repeating test before switch.

Good outputs

  • systemctl status hyperdoc-mcp shows active (running) and hyperdoc-mcp-release-start.
  • curl -i http://127.0.0.1:8787/mcp returns HTTP 405 with the JSON error method_not_allowed.
  • curl -i https://mcp.dreyeck.ch/mcp returns HTTP 405 through nginx, and HTTP 405 over HTTPS means TLS terminated successfully and the live /mcp route reached the MCP handler.
  • The probe still reports INIT_STATUS 200, WORKSPACE_READ_STATUS 200, WORKSPACE_TOPICMAP_ID 919822, and DRY_RUN_VALIDATION_STATUS canonical.

Certificate boundary on dreyeck

The plausible expectation was that adding mcp.dreyeck.ch would require its own dedicated ACME lifecycle because it is a separate nginx virtual host.

The observed reality on dreyeck is different: curl -i https://mcp.dreyeck.ch/mcp returning HTTP 405 proves the HTTPS vhost is already live, nginx is terminating TLS, and the request reaches the MCP route. A 405 method_not_allowed at that URL is an application contract signal, not a certificate failure.

This is a disappointed expectation because introducing an isolated MCP vhost made a separate certificate flow look plausible. The repaired boundary is to reuse the host's existing wildcard certificate model from /etc/nixos/nginx-wiki.nix with useACMEHost = "dreyeck.ch" instead of creating security.acme.certs."mcp.dreyeck.ch".

Failure checks

  • If the host-owned activation proposes unrelated core host changes, stop; this MCP slice is meant to be additive.
  • If http://127.0.0.1:8787/mcp fails, inspect hyperdoc-mcp.service, not nginx.
  • If https://mcp.dreyeck.ch/mcp stops returning HTTP 405, inspect nginx vhost wiring or wildcard-certificate reuse on the host; do not add a dedicated MCP ACME flow as a first response.
  • If the host-owned copy is missing or broken and recovery cannot wait, temporarily import the repo bridge path, restore service, then reinstall the host-owned steady-state copy before the next persistent activation.

Rollback

  1. Rollback the host-owned generation: 
    sudo nixos-rebuild switch --rollback
  2. If a specific generation must be restored: 
    sudo /nix/var/nix/profiles/system-<generation>-link/bin/switch-to-configuration switch
  3. Re-run the local MCP and nginx probes before attempting another activation.
