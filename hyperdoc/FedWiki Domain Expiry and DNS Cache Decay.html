FedWiki Domain Expiry and DNS Cache Decay

hyperdoc

This page records the March 2026 fed.wiki outage described in Ward's thread as a bounded incident-analysis slice. It is a case study in federated web fragility and operational resilience, not a permanent architectural truth claim or a conclusive hijack narrative.

Incident summary

  • Porkbun had granted Ward a long lease on fed.wiki, but the domain appears to have expired around 18:00 Pacific on the incident day.
  • Roughly 500 *.fed.wiki subdomains were affected.
  • wiki.org remained paid up, so its subdomains kept resolving.
  • Ward used /etc/hosts overrides as a short-term continuity technique for known sites.
  • Time-bound note from March 13, 2026: public discovery still surfaced fed.wiki and fed.wiki.org pages, but live fetches were inconsistent, so this slice records recovery uncertainty at that date rather than a closed postmortem.
  • Working conclusion: the observed behavior is most consistent with DNS expiry plus cache decay across browser, OS, resolver, and connection layers. Uneven client failure timing and lingering traffic are expected in that model and should not be overinterpreted.

What failed

The directly observed failure surface is narrower than a generic "the site was taken over" story. What is actually described is a domain-expiry event with cascading resolution symptoms and uneven client-side failure visibility.

  • Domain-expiry symptoms: loss or degradation of name resolution for fed.wiki and its subdomains.
  • DNS/cache propagation behavior: different layers stopped serving old state at different times.
  • Application/browser behavior: browsers showed different failure timing and different degrees of partial reachability.
  • Operational continuity: manual host overrides could still work for a bounded set of known destinations.

Why different clients failed at different times

The best-fitting explanation is DNS Cache Decay in Browser-Centric Systems plus DNS Propagation Lag Across Resolver Layers. That is an inference from the observed symptoms, not a packet-level reconstruction of every resolver involved.

Here, "propagation lag" should be read narrowly: not mainly as fresh DNS records slowly propagating after an intentional change, but as different layers shedding stale resolver and connection state at different times.

  • Registrar/domain state can change before every downstream client has forgotten old state.
  • Authoritative DNS can stop answering usefully before recursive resolvers stop serving cached answers.
  • Recursive resolvers can disagree for a while because their cache state and refresh timing differ.
  • OS caches can outlive upstream freshness for a short period.
  • Browser caches can differ again, so Chrome, Safari, and Firefox need not fail together.
  • Existing live connections can keep an already-open session useful a bit longer than fresh navigation.

That layered decay explains the reported sequence: Chrome failed first, Safari partly worked, Firefox lasted longer, and ping outlived the browsers.

Why ping can outlive browser access

ping only needs an IP address that is still cached somewhere and a route that still answers ICMP. A browser needs successful name resolution for a new navigation plus workable HTTP(S) behavior on top. That extra stack can fail sooner than a stale CLI reachability check.

This is again a mechanism-level inference. The thread does not expose the exact cache entry or connection state that kept ping working.

Why residual traffic does not prove takeover

Later steady or regular-looking traffic is better read through Residual Traffic Interpretation After DNS Failure than through a takeover claim.

  • Nonzero traffic after the main drop is compatible with clients or bots still using cached A/AAAA or NS data.
  • A regular cadence is plausibly explained by uptime monitors, search or archive crawlers, feed readers, retry loops, or a scraper that had already cached the IP.
  • Those explanations are ordinary enough that the traffic pattern alone is weak evidence for re-pointing, takeover, or hijack.

/etc/hosts as emergency continuity

Ward's workaround fits Emergency Host Overrides for Federated Sites: if an operator already knows the right origin IP for a trusted site, a local host override can preserve continuity while public DNS is unstable.

  • It is appropriate for a small known-site set with high confidence in the IP mapping.
  • It is not evidence that DNS recovered; it is a local bypass around current resolver state.
  • It must be removed again once the public path is trustworthy, or the operator risks stale manual routing.

Lessons for federated infrastructure

  • Shared namespace failure has fan-out risk: one lapsed domain can damage hundreds of distinct federated sites at once.
  • Operational diagnosis should separate naming failure, cache decay, application behavior, and continuity workarounds.
  • Residual traffic and partial reachability are not enough to prove hostile control.
  • Small, documented emergency continuity tactics such as host overrides are worth keeping ready for known high-value sites.
  • Recovery tracking should stay explicit about uncertainty until live fetches are stable again.
