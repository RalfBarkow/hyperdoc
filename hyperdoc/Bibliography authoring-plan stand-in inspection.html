What the stand-in layer covers

The stand-in report is the pre-browser protocol surface for bibliography authoring-plan inspection. It records six boundaries that can be inspected without needing the final browser pane to appear:

  1. Entry-page selection: whether HyperDoc selected the tracked entry page and found the expected live-plan link text.
  2. Runtime-surface inventory classification: whether the runtime page and workspace source align closely enough to act as the planned entry point.
  3. Workspace-vs-flake mismatch classification: whether the page is tracked or at risk of existing only in the workspace and therefore not in the flake-built browser runtime.
  4. Plan readiness: whether the authoring plan object already exists, with counts and any plan-construction error preserved.
  5. Artifact-bundle readiness: whether the review bundle can be materialized before any repo write.
  6. Failure classification before browser: whether the seam is already ready before pane opening or still blocked earlier.

Mapping to Universal Thing and browser isolation

This stand-in layer is a direct local application of the same Universal Thing and Browser Isolation in FedWiki pattern.

  • Universal Thing: the stand-in report plays the same role as a controlled collaborator that proves the upstream protocol without requiring the browser itself to be the only runtime host.
  • Browser stand-in: the report is the inspectable browser stand-in for bibliography authoring-plan readiness. It proves that page selection, plan construction, and artifact production have already reached a stable boundary.
  • Browser isolation layer: Playwright stays on the final pane-open and rendering side of the seam, while the stand-in report stays on the pre-browser side and classifies what is ready before rendering begins.

In other words, the stand-in report answers whether a bibliography plan is already ready before the pane-open and rendering boundary. The real browser tests still answer the later question of whether pane creation, rendering, and UI detection succeed.

Why keep this separate from the browser test

The separation matters because a failing browser pane-open case can now be classified more precisely:

  • if the stand-in report is not ready, the defect is earlier than browser rendering
  • if the stand-in report is ready-before-pane-open, the remaining defect is later, in pane-open wiring, rendering, UI polling, or browser environment

That preserves the browser as the final integration boundary without forcing every diagnosis to begin there.

Script and test relation

The existing stand-in script and Playwright stand-in tests remain in place. They now exercise the same stand-in report object that HyperDoc can inspect directly. That keeps the protocol surface unified instead of growing a second hand-maintained report path.
