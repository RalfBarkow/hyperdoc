Semantic-first anchor resolution

Connect now distinguishes between the thing the user clicks and the anchor the system stores. A visible click is a presentation-layer gesture. The active provider resolves that gesture to the strongest semantic anchor it can produce, and persistence stores that semantic anchor. DOM path or selector data remains fallback metadata only.

Inspectable objects

  • Semantic-first anchor resolution

Selection, resolution, and persistence

  • Selection is a presentation-layer gesture such as clicking visible rendered content.
  • Resolution maps that gesture to a semantic anchor kind such as a heading, list item, paragraph, source range, or story item.
  • Persistence stores the resolved semantic anchor envelope, not the raw presentation detail that happened to surface the click.

Semantic anchor envelope

A resolved anchor is semantic-first when its primary fields answer “what subject was selected?” rather than “what DOM node was clicked?” The envelope therefore keeps semantic identity and presentation fallback separate.

  • Provider kind identifies which resolver produced the anchor.
  • Semantic kind names the resolved anchor strategy, for example heading-anchor, list-item-anchor, or paragraph-anchor.
  • Durable identity fields carry the semantic identity appropriate to that strategy.
  • Human label helps recognition in the UI but is not the primary identity.
  • Presentation fallback metadata such as selector or DOM-path value is kept separately for diagnostics and repair heuristics.

Durability tiers

  • Strong: identity depends on authored or external identifiers that are expected to survive routine presentation changes.
  • Medium: identity depends on stable local structure such as heading scope, list position, paragraph order, or source line range.
  • Weak: identity depends mainly on presentation structure such as a DOM path or selector and can drift when rendering changes.

Current HyperDoc content example

The current HyperDoc content provider starts from visible clicks in rendered HTML but resolves them to semantic anchors where possible: heading-anchor, list-item-anchor, and paragraph-anchor. DOM-path information is retained only as fallback metadata.

Why DOM path is fallback only

A DOM path is a useful presentation breadcrumb, but it is usually a poor long-term identity mechanism. Rendered structure can shift without the underlying subject changing. Keeping DOM data as fallback metadata preserves repair and diagnostic value without pretending that presentation structure is the same thing as semantic identity.
