Why authoring guidance matters

HyperDoc documentation uses multiple surfaces with different strengths. Explicit guidance keeps new slices structurally consistent and reduces drift between durable architecture notes and fast-moving collaborative artifacts.

When to create a durable HyperDoc page

  • Create or update a durable page when a distinction should guide future work.
  • Prefer durable pages for architecture, boundary rules, and stable workflow guidance.
  • A durable page should avoid transient branch status, release churn, or commit narration.

When to add topic object code

  • Add a topic object when a concept needs reusable inspectable identity.
  • Use topics for concept reuse across multiple pages, not only one local narrative.
  • Topic objects are reusable semantic handles, not mere page metadata.
  • Topic object code currently lives under hyperdoc/topics/.
  • Production topic persistence belongs to the Dreyeck/DMX SQLite database; Markdown and HyperDoc notes are transitional seeds, exports, handover artifacts, or human-readable projections unless a slice explicitly says otherwise.
  • Keep stable topic key and topic title separate: the key preserves Lisp identity, while the title is the canonical page id in HyperBook topics.

When to embed inspectable objects in a page

  • Embed inspectable objects when page claims should be tied to runtime-inspectable handles.
  • Substantial topic pages should expose a dedicated Inspectable objects section rather than hiding object entry points inside prose.
  • Listed items must be useful next inspection steps: the main conceptual object, the main system boundary object, important helper/runtime objects, or relevant operations/functions.
  • Inspectable-object placement is flexible by page shape: on short pages it can appear near the top; on longer pages it can follow the main explanatory section.
  • Use <a hyperbook="topics" page="Exact Topic Title"> for topic pages.
  • Use expr references for non-topic workflow/runtime objects.
  • Inspectable objects are explanatory affordances, not decorative links.

When to create a FedWiki twin

  • Create a FedWiki twin when collaborative journaling or rapid iteration is expected.
  • Use topic-level correspondence between HyperDoc and FedWiki artifacts.
  • Not every HTML page detail needs a FedWiki twin equivalent.
  • A FedWiki twin is a parallel artifact, not a literal serialization target.

How to keep surfaces aligned without forcing symmetry

  • Align by concept intent, references, and navigable links.
  • Avoid requiring identical structure across page, topic, and twin surfaces.
  • Prefer additive changes to existing twins; avoid overwriting unrelated content.

Cross-linking guidance

  • Cross-link durable pages to related durable pages and external references where needed.
  • Expose corresponding topic objects in an Inspectable objects section.
  • Use first-mention topic linking only where the glossary is explicitly scoped and the term is unambiguous in that page cluster.
  • Avoid automatic global linking for ambiguous terms such as generic uses of system, component, or operation unless the glossary is explicitly scoped.
  • <source-of-function> only works for functions already present in the running image, so example-only functions require their owning ASDF subsystem to be loaded.
  • For topic-page links, keep page= equal to the exact canonical topic title string.
  • For FedWiki links in HyperBook contexts, prefer stable slug-based page= values.

Validation gates before commit

  1. Load gate: run asdf:load-system :hyperdoc.
  2. Topic gate: verify fboundp for new topic constructors.
  3. Coverage gate: run tools/check-topic-coverage.lisp on the new page.
  4. FedWiki syntax gate: run python3 -m json.tool on changed FedWiki page files.
  5. FedWiki semantic gate (where applicable): ensure journal checks are clear of creation, chronology, revision, and malformed findings.

When a page documents a runtime importer, deployment action, or other external write path, it should distinguish design and implementation status, dry-run evidence, and live-proof status. Reserve live-proven for a real create-then-update replay against a configured target.

Commit slicing guidance

  • Split durable HyperDoc edits and FedWiki twin edits into separate commits.
  • Use a docs(hyperdoc) commit for page/topic/cross-link changes.
  • Use a docs(fedwiki) commit for twin-page changes.
  • If no twins are changed, keep the slice as a single HyperDoc docs commit.

Workflow note: mandatory vs optional gates

  • Mandatory for HyperDoc page slices: load gate, topic gate for newly added topic functions, and page coverage gate.
  • Mandatory when FedWiki files are touched: json.tool syntax checks on changed page files.
  • Optional but recommended where relevant: FedWiki journal semantic checks for creation, chronology, revision, and malformed findings.
  • When to add topic objects: when a concept should be reused as an inspectable semantic handle across pages.
  • When to add twins: when collaborative journaling or parallel working traces are useful for the slice.
  • Helper command: tools/validate-documentation-slice.sh --page ... --topic ... --fedwiki ...

Article allegation slices

Use tools/article-allegation-slice.lisp when a documentation slice is driven primarily by article text, news reporting, or another source whose concrete claims should remain allegation-qualified unless stronger source metadata is supplied. The helper scaffolds one incident hub, a reusable set of concept pages, topic constructors, FedWiki twins, and an optional daily anchor without silently upgrading reported claims into settled repository fact.

  • Keep repo boundaries explicit: HyperDoc pages and topic object code under hyperdoc/topics/ stay in the hyperdoc repo on hauptsache; FedWiki twins and daily anchors stay in the pages repo on localhost; production project topic persistence belongs to the Dreyeck/DMX SQLite database.
  • Prefer the compact spec shape: slice id, mode, incident title, source label, epistemic status, summary, incident section list, concept list with topic handles, anchor date, and safeguard flags.
  • Use --print-plan to inspect the derived page titles, topic handles, FedWiki slugs, and daily-anchor target before any dry-run or live write.
  • Use tools/fedwiki-materialization.lisp for narrow live-page repair when HyperBook reports missing FedWiki slugs from a generated or topic-backed article slice; start with --print-plan, then materialize only the selected page or slice into the pages repo on localhost. That operation repairs the pages worktree; if fedwiki:wiki.ralfbarkow.ch still reports the slug missing afterwards, the remaining fault is site publication or sitemap refresh, not article-slice authoring.
  • Use the helper for incident pages that need sections such as claimed sequence, reported attribution, investigative or forensic claims, accountability questions, open uncertainties, and related concepts.
  • Generate topic constructors only for reusable concepts, not for every transient incident phrase.
  • Preserve distinctions such as precise weapon versus correct target, public attribution versus forensic attribution, and AI-assisted review versus human accountability.
  • Keep the emitted slice-metadata.lisp file with dry-run bundles so slices remain reconstructible as units rather than only as loose output files; it records the slice id, derived page titles, topic handles, FedWiki slugs, and anchor target.
  • When validating the generated slice, run load/topic/coverage gates in the HyperDoc repo and json.tool plus journal checks only on the actual changed FedWiki page files.

Lookup failures and counterpart scope

Treat a HyperBook lookup failure as a classified boundary problem, not as a generic missing-page message. A failed link can mean a missing HyperDoc page, a missing topic page, a missing FedWiki twin, a remote publication/resolution problem, or a misleading target label.

  • When a FedWiki page exists in the local pages repo but fedwiki:wiki.ralfbarkow.ch still cannot resolve it, classify that as a publication/resolution boundary problem and inspect a publication probe before recreating content.
  • When the missing target is a real HyperDoc page or topic gap, route the issue into a scaffold plan instead of flattening it into the same repair path as a FedWiki publication miss.
  • FedWiki counterpart sections must describe their site scope truthfully. Do not label a section Localhost FedWiki twin(s) when the rendered targets are mixed or point at a named remote site; use a neutral heading such as FedWiki counterparts and label entries with their actual site.

Failure modes and drift risks

  • False symmetry: treating page, topic object, and twin as equivalent artifacts.
  • Metadata drift: adding topics that duplicate page titles but provide no reusable concept handle.
  • Traceability gaps: adding narrative claims without inspectable object anchors.
  • Commit blur: mixing durable and twin updates in one commit, making history harder to review.
