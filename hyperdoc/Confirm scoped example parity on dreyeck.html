Confirm scoped example parity on dreyeck

This task confirms that dreyeck exposes the same intended Portable examples and ops-specific example scopes as localhost after deployment or restart.

Inspectable objects

  • Confirm scoped example parity on dreyeck
  • Scoped example parity
  • Live parity evidence
  • Probe dreyeck runtime load set
  • Portable example scope
  • Lazy example discovery

Purpose

Verify that the service does not only answer HTTP requests, but also serves the intended scoped example layers.

Prerequisites

  • Verify HyperDoc on dreyeck.ch passed.
  • You can either inspect the UI or run a live runtime probe.

UI-level confirmation

  1. Open the relevant system object in HyperDoc.
  2. Open its Examples surface.
  3. Confirm that the portable example layer for hyperdoc/examples is present.
  4. Confirm that the ops layer for hyperdoc/examples/ops is present.

Runtime-probe confirmation

Run the canonical probes in the live image: 

(mapcar (lambda (spec)
          (getf (hyperdoc::check-locator-of spec) :function))
        (hyperdoc::discover-example-checks :system "hyperdoc/examples"))

(mapcar (lambda (spec)
          (getf (hyperdoc::check-locator-of spec) :function))
        (hyperdoc::discover-example-checks :system "hyperdoc/examples/ops"))

Operationally, “nonempty” means that both calls return at least one discoverable check spec. The important invariant is presence of the intended scopes, not an overfitted count.

Expected results

  • Both scoped discovery calls are nonempty.
  • UI evidence and runtime evidence agree.

Failure interpretation

  • If the UI is missing the scopes and the runtime probes are empty, the service is under-loaded.
  • If manual `(asdf:load-system ...)` calls make the scopes appear immediately, startup/load-scope drift is confirmed.

Next step

If parity fails, continue with Probe dreyeck runtime load set and be prepared to roll back.
