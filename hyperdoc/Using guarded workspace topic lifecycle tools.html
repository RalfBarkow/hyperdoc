Using guarded workspace topic lifecycle tools

hyperdoc

Using guarded workspace topic lifecycle tools is the concise runbook for creating, updating, placing, unlinking, and deleting workspace artifacts in the guarded DMX shared-workspace boundary. It keeps topicmap 919822 usable for real work without widening HyperDoc into a generic DMX mutation surface.

For the short operator-facing front door across this shared-workspace cluster, start with How to work safely in topicmap context-window (919822).

Supported create, update, and upsert paths

  • continue_workspace_annotation: continue a saved workspace annotation from the preserved topic id through guarded workspace assignment, topicmap placement, guarded journal transitions, and reopen.
  • repair_workspace_topic_assignment: backfill or confirm workspace assignment only; it does not place the topic into the topicmap.
  • append_workspace_note: create or update a typed workspace note on the parent-note boundary.
  • update_workspace_note: update an existing workspace note by concrete topicId.
  • upsert_workspace_topic_factory_snippet: create or update a HyperDoc-owned topic-factory snippet twin and place it into topicmap 919822.
  • upsert_workspace_topicmap_context: add an existing topic to the workspace topicmap or refresh its validated long-form view props.

Use continue_workspace_annotation when annotation topic upsert has already succeeded and you need the remaining guarded continuation path. Use repair_workspace_topic_assignment when only workspace ownership is missing. Use upsert_workspace_topicmap_context when the topic already exists and you only need typed placement or validated repositioning.

Use upsert_workspace_topic_factory_snippet when you need a HyperDoc-owned topic to exist in the workspace.

Unlink versus hard delete

  • remove_workspace_topic_from_topicmap is unlink only. It removes topicmap membership and should leave the topic itself intact.
  • delete_workspace_note and delete_workspace_topic are hard delete only. They target /core/topic/<id>, not the topicmap membership route.
  • On the current HTTP client, live unlink is still intentionally unsupported because DELETE on /topicmaps/<topicmap>/topic/<topic> is not yet proven.

Ownership limits

  • Hard delete is allowed only for HyperDoc-owned workspace notes, handovers, and topic-factory snippet twins.
  • Foreign topics are never generic hard-delete targets through this MCP boundary.
  • Topic placement itself is not ownership-limited, but it still stays typed and validated.

Dry-run-first practice

  1. Inspect the current topicmap through read_dmx_topicmap.
  2. If needed, inspect the concrete topic through read_dmx_topic.
  3. Run validated_dmx_write_dry_run for topicmap_context_upsert or topicmap_context_remove before a live topicmap-context mutation.
  4. Run the live tool only after the dry-run summary shows the intended action and normalized payload.

The checked-in call sheet with exact MCP payloads lives at tools/guarded-workspace-topic-lifecycle-mcp-rehearsal.md. Keep the operational workflow explicitly dry-run-first whenever a live write would change workspace state.

If a topic is already present

  • If upsert_workspace_topic_factory_snippet returns topic-action update and topicmap-action already-present, treat that as the expected idempotent update path, not as a collision defect.
  • If upsert_workspace_topicmap_context returns topicmap-action set-view-props, the topic was already present; the tool is now updating validated view props instead of adding a second membership.
  • If a note already exists, use resolve_workspace_note or read_dmx_topic to confirm the concrete target before revising or deleting it.

Inspect before and after

  • read_dmx_topicmap with topicmapId = 919822 shows current topic ids and note ids in the workspace.
  • read_dmx_topic with the concrete topicId confirms title, note body, and selected child metadata.
  • The HyperDoc-side read-only counterpart is Diagnosing DMX workspace assignment and topicmap placement, which opens a dmx-topic-proxy and keeps workspace assignment separate from topicmap placement.
  • For the current maintenance defect set, use Diagnosing DMX workspace repair triage to list HyperDoc-owned objects in topicmap 919822 that still need workspace-assignment backfill.
  • For user-driven authenticated backfill inside HyperDoc itself, use Using authenticated workspace assignment repair console. That console keeps credentials ephemeral and still reuses the same guarded workspace-assignment repair executor.
  • After a live upsert, reread both the topicmap and the topic.
  • After a delete, reread the topic to confirm absence. After an unlink, reread the topicmap to confirm membership removal without assuming topic deletion.

ChatGPT and Codex use

Codex can already use these tools when attached to the same MCP server. ChatGPT can use the same tool surface only after the remote HTTPS MCP endpoint is registered as a custom app/connector in a ChatGPT workspace that supports developer mode and full MCP actions, and only after the server-side live-write gate and DMX credentials are enabled for write actions.
