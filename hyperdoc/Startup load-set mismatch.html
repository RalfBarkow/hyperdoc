Startup load-set mismatch

A Startup load-set mismatch occurs when startup reaches a working server implementation but not the full HyperDoc-specific system set expected for the intended surfaces.

Inspectable objects

  • Startup load-set mismatch
  • HyperBook server vs HyperDoc server load set
  • Load before serve for scoped examples
  • Probe dreyeck runtime load set
  • Running image coherence gate
  • ASDF source-registry contaminant

Diagnosis from this slice

The old dreyeck-style startup path reached the generic server and exposed base examples, but left portable and ops scopes empty. Explicit loads of :hyperdoc/examples and :hyperdoc/examples/ops restored the missing scopes immediately, while :hyperdoc/server produced parity directly.

What this diagnosis is not

This is not evidence of a separate discovery algorithm bug. It is evidence of runtime load-scope drift.

Operational consequence

Fix startup wiring first. Only if the intended systems are already loaded and parity still fails should the discovery path itself become the main suspect.

Source-registry mismatch

A newer mismatch appears when a long-running SLY image was not born from the HyperDoc direnv/nix develop environment. The image may have enough ASDF visibility to load parts of HyperDoc, but still report :s-graphviz -> NIL while resolving :clog-ace from /Users/rgb/common-lisp/clog-ace/clog-ace.asd. That is not a healthy partial success; it is a contaminated basis.

The canonical inspector startup path is therefore guarded: 

(asdf:load-system :hyperdoc)

(hyperdoc:repair-running-image-coherence
 :profile :clog-moldable-inspector)

(hyperdoc:load-coherent-system :clog-moldable-inspector
                               :profile :clog-moldable-inspector)

The repair step first returns values repaired-p, report, and repair-plan. If the current image cannot see required inspector systems from the repo/Nix source universe, or if ASDF resolves one from a foreign ~/common-lisp, the plan records the stale chunks and concrete repair actions. The guarded load then refuses with a structured gate chunk if coherence is still incomplete, and no asdf:load-system call is made for the inspector. Quicklisp, Downloads helper scripts, and silent foreign checkouts are outside this startup contract.

For :s-graphviz, the repair plan distinguishes two missing-system cases. :asdf-subsystem-not-visible means the current image cannot see the system but the dev-shell probe has found a candidate ASD path that may be loaded explicitly. :dev-shell-asdf-system-not-visible means the dev-shell probe did not find s-graphviz.asd, so the blocker is no longer just an attached-image cache problem. Use the focused diagnostic when the repair plan needs to show every registry row and direct ASD load attempt: 

(hyperdoc:explain-asdf-visibility
 :s-graphviz
 :profile :clog-moldable-inspector)
