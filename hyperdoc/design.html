HyperDoc design

The goal of HyperDoc is to support the creation of explainable and explorable software systems from composable units.

One source of inspiration is Bret Victor's "Explorable Explanations" (read in particular the "Postscript from 2024" at the end). HyperDoc wants to enable explorable explanations, but emphasizes the context of peer-to-peer communication, as in scientific research, over the context of expert-to-non-expert communication. Every reader is thus also a potential author, and readers should be able to explore not only the subject of the author's exposition, but also the implementation techniques, in order to learn from them. This leads to a somewhat brutalist approach that values transparency of implementation over the aesthetics of presentation. As you read this page, the title bar of its pane in the viewer shows you the name of the Common Lisp class that implements the page in memory. That's intentional!

Another source of inspiration is literate programming. Its goal is to make software source code more readable for humans, by embedding it into a narrative. In my opinion, experience has shown that this doesn't work out for non-trivial software. One reason is that understanding complex software system requires exploration rather than passive reading. The explorer must be able to execute code and inspect its results. Another reason is the linear structure of a narrative, which is insufficient for complex software, and often in conflict with the requirements of a programming language. This is why literate programming tools usually have to re-structure the code before compilation..

HyperDoc presents explorable software systems as hypertext, i.e. sets of interlinked pages. There are code pages, which are valid source code files according to the rules of the underlying programming language, and text pages, which are narratives. Moreover, both code and text pages can contain links to arbitrary objects in memory, and thus in particular results of example code. Code and results can also be transcluded into text pages (see here).

Code pages are subject to a few conventions (see here), but they do not require any preprocessing, unlike with literate programming. HyperDoc embraces its implementation language and adds to it, rather than making a slightly different one. The code you see is the code the compiler sees as well. To add explanations to the source code, you use comments, not fancy additional mechanisms. You can also add links to text pages, where you can explain whatever is too long or too differently structured to fit into source code comments.

Composability is realized by implementing HyperDocs a value-added ASDF systems. The software units you write using HyperDoc are plain ASDF systems. They can depend on any other ASDF system, and they can become dependencies of any other ASDF system. Using HyperDoc does not force anyone else to use HyperDoc, just to deploy your code.

Another aspect of composability is that link targets are in-memory Common Lisp data objects. HyperDoc provides some syntactic shorthands to make it easier to link to HyperDoc pages or entire HyperDocs, but ultimately these become links to data objects as well. This means that you can easily implement your own HyperDoc page types, if you like neither HTML nor Markdown. It also means that you can implement your own HyperDoc-like documentation system, and cross-link seamlessly.

An additional advantage resulting from an architecture based on plain data objects is the possibility to use different tools for exploring HyperDocs. Right now, you are using an in-browser object inspector that presents objects in lineups of panes. But other object inspectors using HTML-based views are imaginable. For example an inspector presenting objects in boxes placed on an infinite canvas, which users can arrange as they see fit.

Examples are another key ingredient of HyperDoc, although their implementation remains basic for now. Examples produce inspectable results, which permit explorers to better understand the software system. But examples can also contain assertions, taking the role of traditional unit tests. A testing framework that automatically runs all examples in a HyperDoc remains to be implemented. See this paper on example-driven development to learn more about this approach.
