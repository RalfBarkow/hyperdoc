Design

The main goal of HyperDoc is to support the creation of explainable and explorable convivial software systems from composable units. See here for a more detailed discussion of goals and values.

HyperDoc is aimed at knowledge workers: people who consult and contribute to networks of collective knowledge, with scientific research as one important case. That audience needs a hypermedia substrate that can combine diverse media, support both manual and automated processing, and tolerate a steeper learning curve than consumer-oriented personal knowledge tools.

One source of inspiration is Bret Victor's "Explorable Explanations" (read in particular the "Postscript from 2024" at the end). HyperDoc wants to enable explorable explanations, but emphasizes the context of peer-to-peer communication, as in scientific research or among collaborators, over the context of expert-to-non-expert communication. This leads to a focus on conviviality that is absent from Bret Victor's work.

Another source of inspiration is literate programming. Its goal is to make software source code more readable for humans, by embedding it into a narrative. In my opinion, experience has shown that this doesn't work very well except for small software. One reason is that understanding complex software system requires exploration rather than passive reading. Another reason is the linear structure of a narrative, which is not adapted to complex software, and often in conflict with the formal requirements of a programming language. This is why literate programming tools usually have to re-structure the code before compilation. HyperDoc shows you the code exactly as the compiler sees it.

The major innovation attempted in HyperDoc is integrating code as knowledge representation into hypermedia systems that would otherwise remain limited to passive media. Code has a double role here: it represents knowledge, and it also provides small situated tools for processing that knowledge. HyperDoc therefore favors links to code, functions, classes, and inspectable runtime objects as part of the documentation surface rather than as implementation details that should be hidden from view.

A third source of inspiration are notebook interfaces, which are similar to literate programming but embed a computation rather than a program into the narrative. This makes it possible to include computed results as well. Notebook interfaces are an evolution of the read–eval–print loop, and thus primarily a tool for performing explorative computations. They have recently been advocated as a medium for publishing explorable computations as well, but fail in this role by their restriction to a single linear narrative and computation. Notebooks are not composable. HyperDocs are.

HyperDoc's current architectural emphasis is consulting rather than authoring. Existing tools already cover many authoring workflows for code and text, even if they usually keep them separate. What is still weak in today's tooling is the ability to consult and explore code as collective knowledge. That is why HyperDoc puts more energy into explanation, inspection, code links, and runnable examples than into replacing every existing editing environment.

Tectonopedia illustrates another path in the same broad space. It is neither a notebook-style runtime environment nor a traditional literate-programming pipeline aimed at print-like output. It is a TeX-authored technical documentation system compiled into a web application and reference encyclopedia. HyperDoc can use it as a reference system for source-authored documentation and publication architecture without equating that pipeline with HyperDoc's own page/object/runtime-linked model.

HyperDoc uses hypertext, i.e. sets of interlinked pages, to represent explorable software systems. There are code pages, which are valid source code files according to the rules of the underlying programming language, and text pages, which are narratives. Moreover, both code and text pages can contain links to arbitrary data objects, and thus in particular results of example code. Code and results can also be transcluded into text pages. More generally, all links in HyperDoc refer to plain data objects. This means that you can implement your own HyperDoc page types, or even your own HyperDoc-like documentation system, and cross-link seamlessly.

The currently documented techniques remain deliberately experimental. The concrete set already present in the repository is expressed in existing HyperDoc vocabulary: source-code pages, links in code, special-hyperbook links to functions and classes by package-qualified name, and defexample forms with their play-button execution surface. One important use case remains weaker than the current examples model: computational story, where a narrative, the steps of a computation, and its intermediate results should stay together without collapsing into one linear notebook cell stream.

HyperDoc pages also act as communication objects in ongoing collaboration. They can start as focused discussion artifacts and later be consolidated into broader reference documentation. In that workflow, robot assistants are part of the interaction system around the pages: they help interpret, apply, and operationalize what collaborators have written, rather than replacing human-to-human communication.

This also means building bridges to other knowledge ecosystems instead of asking users to abandon them. The HyperBook interface is the clearest concrete outcome of that bridge-building so far: the existing documentation already uses Wikipedia as the example of a HyperBook that is not a HyperDoc, and the same interface pattern is what makes other wiki-like systems, such as Federated Wiki, relevant neighbors rather than foreign islands.

In practice, collaboration spans two connected communication surfaces: HyperDoc pages and localhost FedWiki pages. HyperDoc emphasizes durable, inspectable reference; FedWiki emphasizes rapid journaling and iterative editing. The goal is not to keep both representations identical, but to keep them navigably connected per topic so that people and assistants can move between stable context and active working history. The operational rules are documented in Communication Surfaces Policy.

An additional advantage resulting from an architecture based on plain data objects is the possibility to use different tools for exploring HyperDocs. Right now, you are using an in-browser object inspector that presents objects in lineups of panes. But other object inspectors using HTML-based views are imaginable. For example an inspector presenting objects in boxes placed on an infinite canvas, which users can arrange as they see fit.

The current implementation substrate for this work is Common Lisp as implementation substrate. It offers the interactivity and introspection needed for practical experimentation while remaining stable enough for the long life cycle of collective knowledge. In the current repository form, a HyperDoc unit is realized as an ASDF system in a version-controlled source tree. The longer-term vision is HyperDoc as protocol: a more encapsulated network of units that could support multiple browsers, including special-purpose browsers, without collapsing everything into one implementation technology or one browser surface.

Examples are another key ingredient of HyperDoc, although their implementation remains intentionally lightweight. Examples produce inspectable results, which permit explorers to better understand the software system. Examples can also contain assertions, taking the role of traditional unit tests, and HyperDoc now has a checks runner for batch discovery and execution. The current architectural question is not whether runnable support exists, but how defexample execution and validation should be scoped and placed in the object model. In this repository, that question is answered against ASDF-system-scoped examples and tests, where the runnable surface belongs to systems and the runner stays separate from root identity. See this paper on example-driven development to learn more about this approach.

For the longer horizon beyond individual runs and sessions, see The Life Cycle of Collective Knowledge. That page anchors why HyperDoc cares not only about reproducibility in one environment, but also about software knowledge remaining intelligible and reusable across time.
