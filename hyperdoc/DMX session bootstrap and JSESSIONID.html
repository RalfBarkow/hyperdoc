DMX session bootstrap and JSESSIONID

hyperdoc

DMX session bootstrap and JSESSIONID explains the specific aftermath that follows HyperDoc's username/password input mode. The concrete learning object is a dmx-auth-path-example. Username and password are the primary operator inputs. JSESSIONID is the later session-backed request shape after a successful bootstrap request. It is not a fourth input mode and this page does not add cookie-entry login.

Bootstrap path

For the learning example, HyperDoc turns username alice plus password example-password into the equivalent header Authorization: Basic YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==. 

POST /access-control/login HTTP/1.1
Authorization: Basic YWxpY2U6ZXhhbXBsZS1wYXNzd29yZA==
Content-Length: 0

A successful backend reply is expected to return a Set-Cookie header containing JSESSIONID. HyperDoc evidence records only the redacted cookie shape, not the raw cookie value.

Later guarded request shape

After bootstrap, HyperDoc's later request shape becomes session-backed. For the current learning example this means a cookie shape like: 

Cookie: <session cookie redacted>; dmx_workspace_id=919815

The workspace cookie remains optional transport context for the selected workspace. On guarded workspace-scoped mutation boundaries, HyperDoc resolves that workspace at request time and emits dmx_workspace_id=<workspace-id> for the concrete request. It does not replace authenticated session state.

External reference variant: Py4dmx

The external Py4dmx source cluster shows a different client-side session bootstrap. Its get_session_id() helper sends GET /core/topic/0 with Basic auth, captures JSESSIONID from a cookie jar, and later mutating requests add dmx_workspace_id.

That is useful source evidence that a generic REST client can harvest DMX session cookies, but it does not change HyperDoc's current in-repo contract. HyperDoc's guarded auth teaching surfaces still model POST /access-control/login as the current bootstrap path.

Boundary notes

  • Cookie aftermath is specific to username/password bootstrap.
  • authorization header and bearer token remain direct-header modes in HyperDoc's current learning model.
  • This page does not claim that hyperdoc-mcp.service already has live auth configured.
