Why reference systems matter

HyperDoc documentation compares ideas across multiple systems. Explicit reference systems reduce ambiguity: they make clear what is being borrowed, what is being adapted, and what remains intentionally different.

HyperDoc as a reference system

HyperDoc is itself a reference system for page-centered, object-linkable, inspectable documentation. It emphasizes explicit links between narratives, source code, and runtime objects.

FedWiki as a reference system

FedWiki serves as a reference system for journaling, neighborhood workflows, and collaborative page evolution. In HyperDoc work, FedWiki is often a fast working surface that complements durable HyperDoc pages.

Glamorous Toolkit as a reference system

GT serves as a reference system for moldable development and inspector-driven exploration. HyperDoc uses GT conceptually as a platform reference, without assuming that HyperDoc and GT share the same product scope or runtime form.

Correspondences and boundaries

  • Correspondence: inspectable objects and exploratory understanding are central in all three systems.
  • Boundary: HyperDoc is a hypertext documentation component, not an integrated IDE environment.
  • Boundary: FedWiki journaling workflows are complementary to HyperDoc pages, not replacements for topic/object modeling.

Risks of false equivalence

Treating GT, FedWiki, and HyperDoc as interchangeable can hide real design constraints and lead to misplaced implementation choices. Reference-system comparisons should preserve distinctions in medium, scope, and ownership.

Practical use in HyperDoc documentation

  • Name the reference system when introducing borrowed concepts.
  • Record the adaptation rule that makes the concept fit HyperDoc.
  • Document non-adopted parts explicitly to prevent implicit equivalence drift.
