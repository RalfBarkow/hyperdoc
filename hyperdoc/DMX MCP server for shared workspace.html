DMX MCP server for shared workspace

hyperdoc

DMX MCP server for shared workspace records the current HyperDoc-side Streamable HTTP MCP server boundary for the context-window workspace. The accepted foundation is local and Codex-first: it exposes the shared workspace and selected DMX topics or topicmaps as resources, keeps the write surface narrow and validated, and stays honest about what is still unproven for remote deployment.

Purpose

The MCP server is the shared machine-facing seam between HyperDoc and DMX. It lets Codex now, and ChatGPT later when attached to the same remote MCP boundary, read the same curated workspace state and use the same narrow note/handover tools instead of improvising directly against the raw DMX HTTP surface.

Current resource surface

  • workspace/context-window
  • topic/<id>
  • topicmap/<id>

These resources resolve through the same machine-readable DMX read paths that HyperDoc already treats as canonical.

Current tool surface

  • validated_dmx_write_dry_run
  • append_workspace_note
  • update_workspace_note
  • create_handover

The server deliberately does not expose a generic raw DMX JSON write tool or arbitrary topicmap mutation surface.

Guardrails

  • Topic reads use the canonical machine-readable read boundary.
  • Workspace note writes use the parent-note write boundary.
  • Topicmap-context-like payloads are normalized and validated before dry-run or live execution.
  • Dry-run stays the preferred planning mode before live mutation.

Deployment boundary

The current implementation is accepted as a local, Codex-first foundation. The next deployable shape for dreyeck.ch is a separate HyperDoc-side service and reverse-proxy route that reuses the same Lisp code and keeps the same guarded tool surface. The remote endpoint should not claim more than the currently proven boundaries: the original malformed DMX writer remains unproven, so the MCP server must continue to mediate writes through narrow typed adapters only.

Current pre-activation state

  • The repo-side service definition is present at services.hyperdocMcp.
  • The reverse proxy target is https://mcp.dreyeck.ch/mcp -> http://127.0.0.1:8787/mcp.
  • HYPERDOC_MCP_ENABLE_LIVE_WRITES stays 0 by default on dreyeck-ch.
  • The last public probe before activation returned 400 Requested Wiki Does Not Exist, and hyperdoc-mcp.service was not yet present on the host.

Operator activation checklist

  1. Verify repo-side deployment state on the local controller: 
    nix build .#hyperdoc-release
nix eval .#nixosConfigurations.dreyeck-ch.config.systemd.services.hyperdoc-mcp.serviceConfig.ExecStart --raw
nix eval '.#nixosConfigurations.dreyeck-ch.config.services.nginx.virtualHosts."mcp.dreyeck.ch".locations."/mcp".proxyPass' --raw
nix eval .#nixosConfigurations.dreyeck-ch.config.systemd.services.hyperdoc-mcp.environment.HYPERDOC_MCP_ENABLE_LIVE_WRITES --raw
  2. Confirm the host is reachable before activation: 
    ssh rgb@dreyeck.ch 'hostname; command -v nixos-rebuild; systemctl status hyperdoc-mcp --no-pager --lines=0 || true'
curl -i https://mcp.dreyeck.ch/mcp
  3. Run cautious remote activation: 
    nixos-rebuild dry-activate --flake .#dreyeck-ch --build-host rgb@dreyeck.ch --target-host rgb@dreyeck.ch
nixos-rebuild test --flake .#dreyeck-ch --build-host rgb@dreyeck.ch --target-host rgb@dreyeck.ch
  4. Probe the remote MCP surface after dry-activate and again after test: 
    ssh rgb@dreyeck.ch 'systemctl status hyperdoc-mcp --no-pager --lines=20'
curl -i https://mcp.dreyeck.ch/mcp
DMX_MCP_URL=https://mcp.dreyeck.ch/mcp python3 tools/probe-dmx-mcp-server.py
DMX_MCP_URL=https://mcp.dreyeck.ch/mcp DMX_MCP_TOPIC_URI=dmx://topic/907120 python3 tools/probe-dmx-mcp-server.py
  5. If all checks stay green, make activation persistent: 
    nixos-rebuild switch --flake .#dreyeck-ch --build-host rgb@dreyeck.ch --target-host rgb@dreyeck.ch

Good outputs

  • systemctl status hyperdoc-mcp shows active (running) and hyperdoc-mcp-release-start.
  • curl -i https://mcp.dreyeck.ch/mcp returns HTTP 405 with the JSON error method_not_allowed.
  • The MCP probe reports INIT_STATUS 200, WORKSPACE_READ_STATUS 200, WORKSPACE_TOPICMAP_ID 919822, and TOPIC_TITLE DMX incident remediation for HyperDoc.
  • The probe still reports DRY_RUN_STATUS 200 and DRY_RUN_VALIDATION_STATUS canonical.

Failure checks

  • Unit hyperdoc-mcp.service could not be found. means the new generation is not active.
  • Requested Wiki Does Not Exist on https://mcp.dreyeck.ch/mcp means the nginx host is still missing or not serving the MCP route.
  • INIT_STATUS, WORKSPACE_READ_STATUS, or TOPIC_READ_STATUS other than 200 means stop before switch.
  • If the probe output loses workspace/context-window or the guarded tools, stop and inspect the activated service before proceeding.

Rollback

  1. Rollback the host generation: 
    ssh rgb@dreyeck.ch 'sudo nixos-rebuild switch --rollback'
  2. If a specific generation must be restored: 
    ssh rgb@dreyeck.ch 'sudo /nix/var/nix/profiles/system-<generation>-link/bin/switch-to-configuration switch'
  3. Re-run the remote MCP probes and confirm the host is back in its last known-good state before attempting another activation.
