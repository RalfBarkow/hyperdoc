DMX MCP server for shared workspace

hyperdoc

DMX MCP server for shared workspace is the narrow Streamable HTTP boundary that turns the DMX context-window workspace into a shared blackboard for me, ChatGPT, and Codex, without bypassing HyperDoc's guarded DMX write contract. The accepted foundation is local and Codex-first: it exposes the shared workspace and selected DMX topics or topicmaps as resources, keeps the write surface narrow and validated, and stays honest about what is still unproven for remote deployment.

Purpose

The MCP server is the shared machine-facing seam between HyperDoc and DMX. It lets Codex now, and ChatGPT later when attached to the same remote MCP boundary, read the same curated workspace state and use the same narrow note/handover tools instead of improvising directly against the raw DMX HTTP surface.

Current resource surface

  • workspace/context-window
  • topic/<id>
  • topicmap/<id>

These resources resolve through the same machine-readable DMX read paths that HyperDoc already treats as canonical.

Current tool surface

  • read_dmx_topicmap
  • read_dmx_topic
  • resolve_workspace_note
  • validated_dmx_write_dry_run
  • append_workspace_note
  • update_workspace_note
  • create_handover

The resource surface remains canonical, but these read tools mirror the same projections for clients that only surface MCP tools. The server still deliberately does not expose a generic raw DMX JSON write tool or arbitrary topicmap mutation surface.

Guardrails

  • Topic reads use the canonical machine-readable read boundary.
  • Tool-only clients can list topicmap 919822, inspect note/topic ids, and fetch note bodies without broadening into generic DMX admin APIs.
  • Workspace note writes use the parent-note write boundary.
  • Topicmap-context-like payloads are normalized and validated before dry-run or live execution.
  • Forbidden short keys x, y, visibility, and pinned are rejected at the HyperDoc boundary.
  • Dry-run output shows normalized payload and validation status before any live mutation.
  • Dry-run stays the preferred planning mode before live mutation.
  • Live writes stay disabled unless explicit DMX credentials and the live-write flag are configured.
  • Bearer-token and allowed-origin checks keep the remote boundary narrow.

Why this server exists

The incident arc around topicmap 919822 proved two things at once: a shared DMX workspace is operationally useful, and raw generic DMX write endpoints are not safe enough to expose directly to collaboration tools.

The durable boundary is therefore: client -> DMX MCP server -> HyperDoc-side validated DMX adapter -> DMX backend.

Codex connection

The current project-local Codex entry is .codex/config.toml with the local Streamable HTTP endpoint http://127.0.0.1:8787/mcp.

  • codex mcp list --json shows the configured dmx-context-window server.
  • codex mcp get dmx-context-window --json confirms the Streamable HTTP transport and URL.
  • The MCP server itself was proven live against https://dmx.ralfbarkow.ch by reading workspace/context-window, topic 907120, and topic 921464, then running validated_dmx_write_dry_run.
  • Future ChatGPT connector/app attachment should use the same HTTPS-exposed server rather than a separate raw DMX bridge.

Deployment boundary (corrected)

The repo-owned nixosConfigurations.dreyeck-ch proved the MCP service shape, but it was the wrong production activation boundary because switching that full host profile replaced host-owned definitions on dreyeck. The live host remains authoritative in /etc/nixos.

The corrected split is additive: the HyperDoc repo owns the MCP runtime, reusable module, and sidecar import, while dreyeck's /etc/nixos owns activation beside the existing workspace-based hyperdoc.service.

Current deployment contract

  • hyperdoc-mcp binds to 127.0.0.1:8787.
  • nginx proxies https://mcp.dreyeck.ch/mcp to http://127.0.0.1:8787/mcp.
  • HYPERDOC_MCP_ENABLE_LIVE_WRITES stays 0 by default.
  • The existing workspace-based hyperdoc.service deployment remains untouched.

Host-side runbook

Use Add HyperDoc MCP beside the authoritative host config on dreyeck.ch for the additive sidecar config, exact operator steps, and the wildcard certificate reuse model. The workspace import remains a temporary bridge only; the hardened steady-state path installs a host-owned sidecar under /etc/nixos and reuses useACMEHost = "dreyeck.ch" rather than introducing a dedicated MCP certificate flow. Do not activate .#dreyeck-ch on the live host for this slice.

Good outputs

  • systemctl status hyperdoc-mcp shows active (running) and hyperdoc-mcp-release-start.
  • curl -i http://127.0.0.1:8787/mcp and curl -i https://mcp.dreyeck.ch/mcp both return HTTP 405 with the JSON error method_not_allowed, and the HTTPS 405 proves the live nginx route is terminating TLS and reaching MCP.
  • The MCP probe reports INIT_STATUS 200, WORKSPACE_READ_STATUS 200, WORKSPACE_TOPICMAP_ID 919822, and TOPIC_TITLE DMX incident remediation for HyperDoc.
  • The probe still reports DRY_RUN_STATUS 200 and DRY_RUN_VALIDATION_STATUS canonical.
  • read_dmx_topicmap for topicmap 919822 returns current topic ids and note ids.
  • read_dmx_topic returns the readable note body and selected metadata for a concrete topicId.
  • resolve_workspace_note returns existingTopicId when a reused noteKey resolves through the read client.

noteKey resolution semantics

append_workspace_note is intended to be idempotent by noteKey, not by title text. HyperDoc derives the note URI from the note key, asks the read client for /core/topic/uri/<uri>, and then plans either topic-action update or topic-action create before any live write happens.

That lookup happens during dry run and during live execution planning. If the read client resolves an existing note, the dry-run summary shows a non-empty existing-topic-id, topic-action update, and either topicmap-action already-present or topicmap-action add. If existing-topic-id stays empty, the note is absent or the current read surface cannot prove the lookup.

update_workspace_note still requires an explicit topicId. Use read_dmx_topicmap, read_dmx_topic, or resolve_workspace_note first when the caller does not already know the target id.

Failure checks

  • If the host-owned activation proposes unrelated core host changes, stop; the MCP slice is meant to be additive.
  • Unit hyperdoc-mcp.service could not be found. means the new generation is not active.
  • INIT_STATUS, WORKSPACE_READ_STATUS, or TOPIC_READ_STATUS other than 200 means stop before switch.
  • If https://mcp.dreyeck.ch/mcp is already returning HTTP 405, treat the route and certificate boundary as live; do not open a dedicated ACME workflow for MCP on dreyeck.
  • If topicmap_context_add is planned without both topicmapId and topicId, stop; the guarded dry-run boundary intentionally refuses underspecified topicmap writes.
  • If dry-run append_workspace_note keeps returning an empty existing-topic-id for a reused noteKey, inspect the read surface first instead of assuming idempotent update semantics.
  • If the probe output loses workspace/context-window or the guarded tools, stop and inspect the activated service before proceeding.

Out of scope

  • No generic DMX admin surface.
  • No arbitrary topicmap mutation tools.
  • No full DMX synchronization framework.
  • No claim that ChatGPT connector attachment was exercised in this slice.
