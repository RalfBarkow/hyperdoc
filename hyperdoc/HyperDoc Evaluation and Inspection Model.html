Why an evaluation and inspection model matters

HyperDoc pages can embed runtime object handles. A clear model is required to distinguish expression evaluation, object inspection, and page navigation so failures are interpreted in the correct layer.

What expr= does

expr links embed an expression reference that is evaluated in the HyperDoc runtime context to produce a value. That value is then available for inspection and view rendering.

The expression mechanism is about value production from explicit references; it is not by itself page routing.

Evaluation vs inspection

  • Evaluation: executes/reads an expression and produces a value object.
  • Inspection: renders available views for that value object.
  • Navigation: opens another page target; may accompany inspection but is a separate action.

From object to view

After evaluation produces an object, the inspector layer selects from available views based on object/class support. Mapping is extensible and context-sensitive; not every object has the same view set.

Inspectable objects and explanatory affordances

Inspectable object links are explanatory affordances: they let readers move from narrative claims to runtime objects and inspect views in place.

They are not decorative links and not equivalent to normal page navigation links.

The same evaluation-to-inspection path applies to scoped example execution: a run action produces a result object that is then inspected, while test surfaces batch those results separately from the HyperDoc root identity. The ASDF system boundary behind that scope is explained in Understanding ASDF Systems in HyperDoc.

Raw console traces as pre-object execution evidence

The recent INSPECTOR-PERF lines are already an instance of same-protocol evidence. They are emitted at the execution seam itself while pane creation, view selection, rendering, and inspect-click navigation are happening. In that sense they are not retrospective explanation and not merely debugging noise.

Their current weakness is form. A raw console trace is truthful and sequence-preserving, but it is also transient, linear, console-bound, and hard to query as an object. The architectural problem is not that the inspector lacks evidence. It is that the evidence has not yet been promoted into an execution evidence object.

HyperDoc should therefore treat those lines as the first draft of objectified execution evidence. A durable inspector session, pane run, or view render event would preserve the same information in a form that can be inspected, linked, and reused from narrative pages.

View selection and extension points

  • View selection occurs in moldable inspector behavior over runtime objects.
  • Extension points come from defining/adapting object views for relevant classes.
  • HyperDoc pages reference these objects and views; they do not require one uniform view schema.

Evaluation boundaries and responsibilities

  • Expression layer: resolves and evaluates embedded expressions.
  • Inspector layer: chooses and renders views for resulting objects.
  • Routing layer: resolves page targets when navigation is requested.
  • Boundary rule: keep value production, view rendering, and page routing conceptually separate.

Common failure modes and debugging paths

  • Expression resolves to missing/undefined symbol: check topic/function availability and load context.
  • Evaluation succeeds but expected view missing: check inspector view definitions and object class support.
  • Link opens unexpected page/context: check whether link is routing-based or expr-based and verify target context.
  • Remote/local confusion during exploration: verify source context before diagnosing evaluation or view behavior.
