The Roots of Lisp

hyperdoc

Paul Graham's article The Roots of Lisp (draft dated 18 January 2002) retraces a construction from John McCarthy's 1960 paper. McCarthy showed how a small number of rules for evaluating expressions, together with a notation for functions, can define a programming language.

Graham's central question is how Lisp can be described in Lisp itself. His answer culminates in EVAL.: a function written in the reconstructed Lisp that takes a Lisp expression and an environment and returns the value of that expression.

This page follows the steps needed for that result. At the relevant points, it includes examples. The play button ► belongs to the example. Clicking it runs that example and opens its result for inspection.

The two evaluators used on this page

Two functions must be distinguished from the outset. ROOTS-EVAL is Common Lisp code in this project. It implements the evaluation rules of the reconstructed Lisp. EVAL. is a function defined within that reconstructed Lisp. A run of EVAL. therefore takes place inside ROOTS-EVAL.

The first function lets us test each step of the reconstruction. The second is the result that Graham is working toward.

1. Why begin with seven operators?

Graham first defines a Lisp expression as either an atom or a list of expressions. If an expression is a non-empty list, its first element is its operator and the remaining elements are its arguments. The next task is to say how such expressions obtain values.

The seven primitive operators provide the first evaluation rules. They are not seven examples chosen at random. Together they let a program preserve an expression as data, distinguish atoms from lists, compare atoms, take lists apart, construct lists, and choose between alternatives. Those are the operations later used to define the evaluator.

Operator What it does Why it is needed
QUOTE Returns its argument without evaluating it. Lets a list be treated as data rather than as a function call.
ATOM Tests whether a value is an atom or the empty list. Distinguishes the two kinds of expression.
EQ Compares two atomic values. Recognizes names and other atoms.
CAR Returns the first element of a non-empty list. Obtains an operator or the first part of data.
CDR Returns the list after its first element. Obtains the arguments or the remaining data.
CONS Adds a value to the front of a list. Constructs expressions and result lists.
COND Tests clauses in order and evaluates the result of the first true clause. Expresses case distinctions and recursive stopping conditions.

QUOTE and COND do not evaluate all of their arguments. The other five primitive operators do. This difference will reappear in the definition of EVAL..

2. How are new functions expressed?

The primitive operators give values to a small set of forms. To define further operations, Graham next introduces LAMBDA. In a call whose operator is a LAMBDA expression, the arguments are evaluated, their values are associated with the parameters, and the body is evaluated with those associations available. 

((lambda (x y)
   (cons x (cdr y)))
 'z
 '(a b c))

This expression returns (Z B C). A parameter may also occur in the operator position. A function expression can therefore be passed as an argument and then called: 

((lambda (f)
   (f '(b c)))
 '(lambda (x)
    (cons 'a x)))

This expression returns (A B C).

LABEL adds what ordinary LAMBDA lacks here: a name by which the function can call itself. Graham uses it to define SUBST, which replaces every occurrence of an atom inside a nested expression. 

((label subst
   (lambda (x y z)
     (cond
       ((atom z)
        (cond ((eq z y) x)
              ('t z)))
       ('t
        (cons (subst x y (car z))
              (subst x y (cdr z)))))))
 'm
 'b
 '(a b (a b c) d))

The expected value is (A M (A M C) D). The recursive calls use only the evaluation rules introduced so far. We will run this expression below, first directly and then through EVAL..

3. Why does EVAL. need more functions?

Before defining EVAL., Graham defines several functions from the primitives and from LAMBDA and LABEL. NULL., AND., and NOT. express recurring tests. APPEND. combines lists. Two further functions prepare the representation of an environment: 

(pair. '(x y) '(a b))
=> ((X A) (Y B))

(assoc. 'x '((x a) (y b)))
=> A

PAIR. associates parameters with argument values. ASSOC. finds the value associated with a name. An environment is such a list of associations. These functions are introduced here because EVAL. must construct and search environments when it evaluates function calls; they are not an unrelated library inventory.

4. How does EVAL. assign a value to every expression?

EVAL. takes two arguments: e, the expression to be evaluated, and a, its environment. Its outer COND distinguishes four kinds of expression.

Form of e Action of EVAL.
An atom Use ASSOC. to look up its value in the environment.
A list whose operator is an atom Apply the rule for a primitive operator, COND, or a named function.
A call whose operator is a LABEL expression Add the function's name and definition to the environment, then evaluate the call.
A call whose operator is a LAMBDA expression Evaluate the arguments, associate their values with the parameters, and evaluate the body in the extended environment.

This is the definition to which those four cases refer: 

(defun eval. (e a)
  (cond
    ((atom e)
     (assoc. e a))
    ((atom (car e))
     (cond
       ((eq (car e) 'quote)
        (cadr e))
       ((eq (car e) 'atom)
        (atom (eval. (cadr e) a)))
       ((eq (car e) 'eq)
        (eq (eval. (cadr e) a)
            (eval. (caddr e) a)))
       ((eq (car e) 'car)
        (car (eval. (cadr e) a)))
       ((eq (car e) 'cdr)
        (cdr (eval. (cadr e) a)))
       ((eq (car e) 'cons)
        (cons (eval. (cadr e) a)
              (eval. (caddr e) a)))
       ((eq (car e) 'cond)
        (evcon. (cdr e) a))
       ('t
        (eval. (cons (assoc. (car e) a)
                     (cdr e))
               a))))
    ((eq (caar e) 'label)
     (eval. (cons (caddar e) (cdr e))
            (cons (list (cadar e) (car e)) a)))
    ((eq (caar e) 'lambda)
     (eval. (caddar e)
            (append. (pair. (cadar e)
                            (evlis. (cdr e) a))
                     a)))))

EVCON. examines the clauses of a COND expression. EVLIS. evaluates the arguments of a function call. Both are recursive functions defined by the same means as the earlier functions. No new evaluation principle is introduced at this point.

The two following runs answer different questions and must not be collapsed into one.

First run: evaluate SUBST directly

Second run: let EVAL. evaluate the same SUBST application

In the second run, the definition of EVAL. and its supporting functions have been loaded into the reconstructed Lisp. The LABEL/SUBST application is quoted and passed to EVAL. as data, together with an empty environment. EVAL. must interpret that data as an expression and return its value.

6. What has been shown?

The definition of EVAL. uses the language elements introduced in the preceding steps. It is itself a Lisp expression, and it can compute the value of another Lisp expression. This is the result Graham describes when he says that Lisp can be written in itself.

The experiment does not remove the need for an implementation. ROOTS-EVAL, written in Common Lisp, still executes the reconstructed language and therefore executes EVAL.. The point is that the rules of the reconstructed language can be expressed as a function in that same language.

The reconstructed evaluator also retains historical limitations discussed by Graham. In particular, its environment gives it dynamic rather than lexical scope. It is not a model of all of modern Common Lisp.
