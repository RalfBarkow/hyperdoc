Goal

Retrace one correction that differs in executable evaluator code, then keep it separate from the dynamic-binding problem that Graham diagnoses without converting the evaluator to lexical scope.

Starting situation

Lynn says that Graham “corrects bugs,” but that phrase is not an enumerated errata list. The identification here is a source-backed inference from Graham's notes and the corresponding evaluator rules. Deliberate omissions, such as dotted-pair syntax in a teaching parser or an omitted apply, are simplifications rather than automatically bugs.

Step 1 — compare the named-call rules

Click: run the named-call retrace example. Observe: :GRAHAM-CORRECTED evaluates the quoted argument once and returns (A B C). :MCCARTHY-PAPER evaluates the argument, inserts the value (B C) into the lambda application, and then tries to evaluate that value again as an application whose operator is B. The resulting language error is captured in the comparison. Why this matters: Graham's change is an executable correction to the named-call rule, not merely editorial commentary.

Step 2 — inspect the surviving binding problem

Click: run the minimal dynamic-capture example. Observe: the result is INNER, while a lexical closure reading would preserve OUTER. Why this matters: the named-call correction does not make the evaluator lexical. Graham diagnoses the MAPLIST/DIFF name collision, but his evaluator retains the historical dynamic environment.

Expected result

  • Named-call comparison replay status: :CONFIRMED.
  • Corrected value: (A B C).
  • Historical path: captured ROOTS-LANGUAGE-ERROR involving operator B.
  • Dynamic-capture value: INNER.

Boundary

The historical rule is opt-in for one evaluation. The corrected rule remains the default and is dynamically scoped to the call, so a historical replay cannot leak into later evaluations. This page does not claim that Lynn's phrase is a formal errata catalogue, and it does not label intentional teaching simplifications as accidental defects.
